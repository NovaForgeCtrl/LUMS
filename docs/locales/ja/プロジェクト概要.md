# LUMS

**ノイズのない Linux アップデート管理。**

## はじめに

LUMS は Linux のアップデートを一元管理します。サーバーはクライアント、インストール済みソフトウェア、利用可能なアップデートを表示します。管理対象の各 Linux システム上のエージェントは、そのシステムのパッケージマネージャーを使用して、承認されたパッケージ操作を実行します。LUMS は Debian/Ubuntu の APT や Arch Linux の pacman を置き換えるものではありません。

**既存の LUMS インストールを利用するだけの場合:** 管理者から案内されたアドレスを開き、ご自身のアカウントでサインインしてください。機能が表示されない場合は、アカウントにその機能を使用する権限がない可能性があります。管理者に問い合わせてください。アカウントを共有したり、クライアントトークンを Web パスワードとして使用したりしないでください。

**LUMS をインストールまたは運用する場合:** まず[インストールガイド](インストールとアップグレード.md)から始め、続いて[管理ガイド](管理とバックアップ.md)を読んでください。問題が発生した場合は、[トラブルシューティングガイド](トラブルシューティング.md)を参照してください。各言語のユーザー向け・管理者向けガイドの一覧は [`docs/README.md`](../../README.md) にあります。英語のルートガイドが引き続き技術的な原本です。翻訳された手順が不完全に見える場合や英語版と異なる場合は、英語の原本に従ってください。

テスト実行の成功や Docker イメージのビルド成功は、本番環境へのインストールでは**ありません**。本番デプロイには、HTTPS、保護されたアプリケーションシークレット、永続データ、検証済みのバックアップ、強化されたコンテナーも必要です。ご自身の環境のプレースホルダーとストレージパスを確認するまで、本番用コマンドをコピーしないでください。

### Web インターフェースの言語

Web インターフェースは、ドイツ語、英語（米国・英国）、フランス語、スペイン語、簡体字中国語、日本語、ポーランド語、スウェーデン語、ノルウェー語（ブークモール）、フィンランド語に対応しています。言語は、ログインページの右上から選択します。選択しない場合、LUMS はブラウザーの言語を使用しようとします。サインイン後は、アカウントに保存された言語が優先されます。翻訳が提供されていない場合、一部の技術的なテキストや動的なテキストは元の言語のまま表示されることがあります。Markdown ガイドは Web インターフェースとは別のものであり、自動的には翻訳されません。翻訳された Markdown ガイドは別途保守されています。言語ごとの提供範囲は、ドキュメント索引で確認してください。

---

LUMS は、Linux クライアント向けに、制御され、監査可能で、安全なソフトウェアおよびアップデート管理を提供するために設計された Linux アップデート管理サーバーです。

LUMS は、クライアント側で制御されないアップデート作業に頼る代わりに、ソフトウェアインベントリ、アップデートの検出、パッケージ操作、アップデートジョブ、実行の監視、結果の報告のための中央管理レイヤーを提供します。

LUMS は、アップデートを**可視化され、制御され、追跡可能で、復旧可能**にしたい環境のために設計されています。

---

## LUMS とは

LUMS（**Linux Update Management Server**）は、中央サーバーと軽量な Linux クライアントで構成されます。

サーバーは、管理インターフェース、API、認証、認可、ジョブ管理、監査ログ、永続的な状態を提供します。

クライアント側のエージェントは、ローカルのパッケージマネージャー操作を実行し、その結果をサーバーに報告します。

基本的なアーキテクチャは次のとおりです。

```text
                    ┌──────────────────────┐
                    │      Web Browser      │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │     LUMS Server      │
                    │                      │
                    │ Web UI / API         │
                    │ Authentication       │
                    │ RBAC                 │
                    │ Job Management       │
                    │ Audit Logging        │
                    │ SQLite               │
                    └──────────┬───────────┘
                               │
                         HTTPS / API
                               │
              ┌────────────────┴────────────────┐
              │                                 │
              ▼                                 ▼
      ┌─────────────────┐             ┌─────────────────┐
      │   Linux Client  │             │   Linux Client  │
      │                 │             │                 │
      │ LUMS Agent      │             │ LUMS Agent      │
      │ Package Manager │             │ Package Manager │
      │ Watcher         │             │ Watcher         │
      └─────────────────┘             └─────────────────┘
```

## なぜ LUMS なのか

Linux システムには、すでに優れたパッケージ管理ツールが備わっています。

LUMS はそれらを置き換えようとするものではありません。

代わりに LUMS は、これらのツールを包む管理レイヤーを提供し、管理者が次のような疑問に中央から答えられるようにします。

* どのクライアントが存在するか
* どのソフトウェアがインストールされているか
* どのアップデートが利用可能か
* どのパッケージをインストールまたは削除すべきか
* どのアップデートジョブが実行中か
* アップデート中に何が起きたか
* クライアントは結果を正常に報告したか
* 再起動が必要だったか
* 中断されたジョブは安全に復旧できるか
* 誰が管理操作を開始したか

目的は、基盤となる Linux のパッケージマネージャーを隠すことではありません。

目的は、その操作を**管理可能で監査可能**にすることです。

## 主な機能

### クライアント管理

LUMS は、登録済みの Linux クライアントとその認証状態を保持します。

各クライアントには、個別の認証トークンが発行されます。

クライアントトークンは、平文の認証情報としては保存されません。サーバーは SHA-256 ダイジェストを保存し、受信したクライアント認証をそのダイジェストに対して検証します。

管理者は次の操作を行えます。

* クライアントの登録
* クライアントの無効化
* クライアントトークンのローテーション
* クライアントの状態の確認
* クライアントの報告状況の監視

---

### ソフトウェアインベントリ

クライアントは、インストール済みのソフトウェアを LUMS サーバーに報告します。

サーバーはインベントリを保存し、管理インターフェースを通じて公開します。

インストール済みソフトウェアの表示は、パッケージ管理の検索とは意図的に分離されています。

これにより、管理者や読み取り専用ユーザーは、パッケージ管理操作が自動的に公開されることなく、インストール済みソフトウェアを確認できます。

---

### アップデートインベントリ

クライアントは、パッケージのアップデートが利用可能かどうかを定期的に判定します。

サーバーは、報告されたアップデート情報を保存し、権限のあるユーザーが利用できるようにします。

アップデート情報は、制御されたアップデートジョブの基礎として使用できます。

---

### パッケージ管理

LUMS は、クライアントエージェントを通じてパッケージ管理操作を提供します。

サポートされるパッケージ操作は次のとおりです。

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

パッケージ管理レイヤーは、基盤となるパッケージマネージャーを抽象化します。

現在サポートされているパッケージマネージャーのファミリーは次のとおりです。

* **Debian / Ubuntu:** APT / dpkg
* **Arch Linux:** pacman

LUMS ではパッケージ検索も利用できます。

検索リクエストは対象クライアントに送信され、ローカルのパッケージマネージャーで実行され、結果がサーバーに返されて表示されます。

---

### アップデートジョブ

アップデート操作は、永続的なジョブとして表現されます。

1 つのジョブには 1 つ以上のパッケージ操作を含めることができ、サーバー側で実行状態が維持されます。

一般的なライフサイクルは次のとおりです。

```text
PENDING
   │
   ▼
RUNNING
   │
   ├──────────────► SUCCESS
   │
   └──────────────► FAILED
```

パッケージ単位の結果は個別に追跡されるため、すでに正常に完了した操作を不必要に繰り返すことなく、中断されたジョブを復旧できます。

---

### 制御された実行

LUMS は、Web インターフェースから渡された任意のシェルコマンドを実行しません。

サーバーは、検証済みのアクションとパッケージ名を使用して、構造化されたジョブを作成します。

クライアントエージェントは、それらのアクションを適切なローカルのパッケージマネージャー操作にマッピングします。

これにより、次の間に意図的な境界が設けられます。

```text
Web UI
   ↓
API
   ↓
Validated Job
   ↓
Agent
   ↓
Package Manager
```

---

### アイドル状態を考慮した実行

LUMS は、クライアントがアクティブとみなされている間、アップデートの実行を延期できます。

現在のアイドルしきい値は **300 秒**です。

サポートされている場合、エージェントは `loginctl` を通じてローカルシステムのセッション／アイドル情報を使用します。

アイドル検出が利用できない場合、LUMS はクライアントがアイドルであるかのように扱うことはしません。

**アイドル状態が不明であることは、アイドル状態が確認されたことと同じではない**ため、この区別は重要です。

---

### ジョブの復旧

アップデートジョブは、中断に耐えられるように設計されています。

サーバーは、永続的なジョブ状態とパッケージ項目の状態を保持します。

復旧時には、すでに成功したパッケージ項目は不必要に再実行されません。

これにより、複数パッケージの操作に対してチェックポイントに似た実行モデルが実現します。

目標は次のとおりです。

> **ジョブ全体を無差別に再開するのではなく、ジョブを復旧する。**

---

### 再起動の検出

一部のパッケージ操作では、システムの再起動が必要になる場合があります。

そのため LUMS は、パッケージマネージャーが正常終了したからといってシステムが完全に稼働可能な状態であると想定するのではなく、再起動の検出をアップデート結果の処理の一部として扱います。

クライアントは、検出した再起動の要否をサーバーに報告します。

---

### クライアント認証

クライアントとの通信は、クライアントごとのトークンで認証されます。

トークンには次の特性があります。

* 個別に割り当てられる
* ローテーション可能
* サーバー側には SHA-256 ダイジェストとしてのみ保存される
* クライアントの報告を受け付ける前に検証される

トークンのローテーションにより、管理者はクライアントを再作成することなく、以前に発行したクライアント認証情報を無効化できます。

---

### ヘルスダッシュボード

`/health` の認証済みヘルスダッシュボードは、データベースの状態、クライアントの報告状況、バックアップストレージの可視性、およびテレメトリが設定されている場合の CPU／メモリのテレメトリをまとめて表示します。これは運用状況をすばやく確認するためのビューであり、コンテナー、リバースプロキシ、ホスト、バックアップのログの確認や、復元テストの実施の代わりにはなりません。[LUMS_Health_Dashboard.md](LUMS_システム健全性ダッシュボード.md) を参照してください。

---

### アラート

LUMS には、アラート管理 API と、保存されたアラート記録のための基本的なダッシュボードが含まれています。管理者は、ルールの作成と管理、アラートの手動トリガー、およびアクティブなアラートの確認応答、解決、手動でのエスカレーションを行えます。ルールの条件としきい値は設定として保存されます。現在のサーバーは、それらをテレメトリに対して自動的には評価しません。通知連携（メール、Slack、PagerDuty、汎用 Webhook）は API からは利用できず、アラート履歴を保持するため一括クリアは無効になっています。実装されている範囲については、[`docs/LUMS_REALTIME_ALERTING_IMPLEMENTATION.md`](../../LUMS_REALTIME_ALERTING_IMPLEMENTATION.md) を参照してください。

---

### 監査性

管理操作およびセキュリティ上重要な操作は、LUMS の監査ログシステムに記録されます。

監査証跡は、次の問いに答えることを目的としています。

```text
Who?
What?
When?
Against which object?
With which result?
```

これには、認証関連の操作、クライアント管理、ユーザー管理、アップデートジョブの作成など、セキュリティ上重要な操作が含まれます。

---

## 設計原則

LUMS は次のシンプルな原則に従います。

> **Linux のアップデート管理を、可視化され、制御され、復旧可能で、監査可能なものにする。ただし、基盤となる Linux ツールは隠さない。**

## アーキテクチャ

LUMS は、管理、実行、永続化を明確に定義されたコンポーネントに分離します。

サーバーは、オーケストレーションとポリシーを担当します。

クライアントは、ローカルシステムとのやり取りを担当します。

パッケージマネージャーは、ソフトウェアの実際のインストール、削除、更新を引き続き担当します。

この分離は意図的なものです。

## サーバーコンポーネント

LUMS サーバーは、中央の管理レイヤーを提供します。

### Web アプリケーション

Web アプリケーションは、次の項目のための管理インターフェースを提供します。

* クライアント管理
* ソフトウェアインベントリ
* アップデート情報
* アップデートジョブ
* パッケージ管理
* アップデート履歴
* ユーザー管理
* システムメンテナンス

このインターフェースは、現在のユーザーの RBAC ロールを尊重します。

そのため、フロントエンドの表示はユーザーの権限に合わせて調整されますが、認可は常にサーバー側でも強制されます。

---

### API

API は、Web インターフェースと Linux クライアントを、サーバー側のアプリケーションロジックに接続します。

API は次のような操作を処理します。

* クライアントの登録と管理
* クライアントのレポート
* パッケージ検索
* パッケージ検索の結果
* アップデートジョブ
* ジョブの結果
* ユーザー管理
* 監査イベント

API エンドポイントは、状態を変更する操作を実行する前に入力を検証します。

---

### 認証とセッション

管理ユーザーは、LUMS の Web アプリケーションを通じて認証します。

セッションはサーバーによって制御され、明示的なセッションの失効に対応します。

認証のセキュリティには次が含まれます。

* Argon2 を使用したパスワードのハッシュ化
* セッション管理
* セッションの失効
* ログインのレート制限
* CSRF 保護
* ロールベースの認可

クライアント認証は、管理者認証とは別のものです。

---

### RBAC

LUMS は、ロールテンプレートとユーザーごとの権限を組み合わせます。Administrator、Operator、Viewer の各テンプレートは、アカウントごとにカスタマイズできる出発点となる権限セットを提供します。

認可は、アカウントに保存された権限を使用してサーバー上で強制されます。

さらにフロントエンドは、ユーザーの権限で許可されていない機能を非表示にします。

つまり、ボタンを非表示にすることは、セキュリティ境界としては決して扱われません。

---

### SQLite の永続化

LUMS は、アプリケーションの永続的な状態に SQLite を使用します。

データベースには、次のような情報が保存されます。

* ユーザー
* セッション
* クライアント
* クライアント認証の状態
* ソフトウェアインベントリ
* 利用可能なアップデート
* アップデートジョブ
* パッケージ単位のジョブ結果
* パッケージ検索のリクエストと結果
* 監査情報

アプリケーションは、データベース接続で SQLite の外部キー制約の強制を明示的に有効にします。

現在の本番環境における SQLite のベースラインは次のとおりです。

```text
journal_mode = wal
busy_timeout = 5000
synchronous = 2
foreign_keys = ON
```

LUMS は、現在の本番構成で SQLite の WAL モードを使用します。

## コンテナーアーキテクチャ

LUMS サーバーは、強化された Docker コンテナーとしてデプロイされます。

アプリケーションコンテナーは、意図的に使い捨てのものとして扱われます。

アプリケーションの永続的な状態は、専用の Docker ボリュームに保存されます。

```text
lums-data
```

本番コンテナーは、読み取り専用のルートファイルシステムを使用します。

書き込み可能な場所は、必要なランタイムおよび永続ストレージのパスに意図的に制限されています。

本番のセキュリティベースラインには次が含まれます。

```text
read-only root filesystem
all Linux capabilities dropped
no-new-privileges
restricted /tmp
restricted /run
read-only secret mount
dedicated persistent data volume
non-root application user
```

アプリケーションは、内部的に次のアドレスで公開されます。

```text
127.0.0.1:5050
```

外部からの HTTPS アクセスは、リバースプロキシを通じて提供されます。

---

## 永続コンポーネントと使い捨てコンポーネント

LUMS は、永続的な状態を、置き換え可能なランタイムコンポーネントから分離します。

```text
Persistent
├── SQLite database
├── client state
├── user state
├── job state
└── audit state

Disposable
├── Docker container
├── application process
└── generated runtime state
```

そのため、アプリケーションコンテナーを置き換えても、LUMS のデータベースが本質的に削除されることはありません。

この分離は、アップグレードと復旧にとって重要です。

## クライアントアーキテクチャ

Linux クライアントは、連携する複数のコンポーネントで構成されます。

### LUMS エージェント

エージェントは、LUMS サーバーおよびローカルの Linux システムとのやり取りを担当します。

現在のエージェントのバージョン:

```text
1.7.0
```

エージェントは次を処理します。

* 認証
* インベントリの収集
* アップデートの検出
* パッケージ検索
* パッケージ操作
* アップデートジョブの実行
* 結果の報告
* 再起動の検出
* アイドル状態の処理

---

### パッケージマネージャーレイヤー

パッケージマネージャーレイヤーは、ネイティブの Linux パッケージマネージャーを包む、制御された抽象化を提供します。

エージェントは、LUMS がパッケージマネージャーを置き換えることを必要としません。

代わりに、次のようになります。

```text
LUMS Action
     │
     ▼
Package Manager Abstraction
     │
     ├── Debian / Ubuntu → APT / dpkg
     │
     └── Arch Linux      → pacman
```

これにより、ディストリビューション固有のパッケージ処理はクライアント内に保たれます。

---

### 実行ウォッチャー

ウォッチャーは、クライアント上でのアップデートジョブの実行を監視します。

現在のウォッチャーのバージョン:

```text
1.2.1
```

ウォッチャーは、エージェントおよびサーバー側のジョブ状態と連携して動作します。

その目的は、実行されるはずのジョブが無期限に未処理のまま残らないようにすることです。

---

## レポートの経路

通常のクライアントのレポートは、次の方向に流れます。

```text
Linux Client
    │
    │ inventory / update information
    ▼
LUMS API
    │
    ▼
SQLite
    │
    ▼
Web UI
```

たとえば、クライアントが実行したアップデート確認によって生成された情報は、サーバーに報告され、そのクライアントの現在のアップデート状態として保存されます。

ブラウザーが、クライアントのパッケージマネージャーに直接問い合わせることはありません。

---

## パッケージ検索の経路

パッケージ検索は、異なるリクエスト／レスポンスのフローに従います。

```text
Browser
   │
   │ search request
   ▼
LUMS Server
   │
   │ package-search request
   ▼
Linux Client
   │
   │ APT / pacman search
   ▼
Linux Client
   │
   │ search result
   ▼
LUMS Server
   │
   ▼
Browser
```

そのため、サーバーは、すべてのクライアントについてリモートのパッケージリポジトリの完全なインデックスを保持する必要はありません。

検索は、クライアント自身のパッケージ管理環境を使用して実行されます。

---

## アップデート実行の経路

アップデートジョブは、次の一般的なアーキテクチャに従います。

```text
Browser
   │
   │ create job
   ▼
LUMS API
   │
   │ validate request
   ▼
SQLite
   │
   │ persistent job
   ▼
Linux Client
   │
   │ execute action
   ▼
APT / dpkg / pacman
   │
   │ result
   ▼
Linux Client
   │
   │ validated result
   ▼
LUMS API
   │
   ▼
SQLite
   │
   ▼
Browser
```

これにより、LUMS の中心となる実行チェーンが形成されます。

> **Browser → API → SQLite → Agent → Package Manager → Result → SQLite → UI**

---

## アトミックなジョブ取得

アップデートジョブは、サーバー側の永続的なオブジェクトです。

実行の前に、エージェントは実行可能なジョブを取得する必要があります。

ジョブの取得はアトミックに実行されるため、同じ保留中のジョブが複数の実行経路によって意図せず取得されることはありません。

これは、タイマー、リトライ、復旧、または複数のクライアント側プロセスが関わる場合に特に重要です。

---

## ジョブの実行

サーバーは、構造化されたジョブを作成します。

クライアントエージェントは、サポートされるジョブアクションを解釈し、対応するローカル操作を実行します。

サポートされるパッケージアクションは次のとおりです。

```text
INSTALL_PACKAGE
REMOVE_PACKAGE
UPDATE_PACKAGE
UPDATE_SYSTEM
```

パッケージ名は、パッケージジョブが作成される前に検証されます。

エージェントは、パッケージ名を任意のシェルの断片として扱うことはありません。

---

## パッケージ管理の抽象化

パッケージ操作は、パッケージマネージャーの抽象化の背後に意図的に実装されています。

これにより、上位レベルの LUMS のジョブモデルは、ディストリビューション固有のコマンドから独立した状態に保たれます。

例:

```text
INSTALL_PACKAGE
       │
       ├── Debian / Ubuntu → APT
       │
       └── Arch Linux      → pacman
```

同じ原則は、削除やパッケージのアップデートにも当てはまります。

---

## Debian / Ubuntu

Debian 系のシステムでは、LUMS はネイティブの APT/dpkg ツールを使用します。

典型的な役割には次が含まれます。

* パッケージ検索
* パッケージメタデータの参照
* パッケージのインストール
* パッケージの削除
* パッケージのアップデート
* システムのアップデート
* アップデートの検出

LUMS エージェントは APT を置き換えるものではありません。

APT を包む、制御されたオーケストレーションを提供します。

---

## Arch Linux

Arch Linux のシステムでは、LUMS はネイティブの pacman パッケージマネージャーを使用します。

典型的な役割には次が含まれます。

* パッケージ検索
* パッケージメタデータの参照
* パッケージのインストール
* パッケージの削除
* パッケージのアップデート
* システムのアップデート
* アップデートの検出

ディストリビューション固有の動作は、パッケージマネージャーレイヤー内に留まります。

---

## パッケージ検索

パッケージ検索は、インストール済みソフトウェアのインベントリとは別のものです。

この区別は重要です。

```text
Installed Software
        │
        └── What is already installed?

Package Management Search
        │
        └── What package can the client currently find?
```

検索結果には、次のようなパッケージ情報が含まれる場合があります。

* パッケージ名
* バージョン
* 説明
* 利用可能な場合はリポジトリ情報

検索結果は LUMS サーバーに返され、パッケージ管理インターフェースに表示されます。

---

## パッケージ管理の権限

パッケージ管理は特権操作です。

現在の権限モデルは次のとおりです。

```text
Administrator → allowed
Operator      → allowed
Viewer        → not allowed
```

Viewer は、引き続きインストール済みソフトウェアを確認できます。

パッケージ管理インターフェース自体は Viewer には表示されず、対応するサーバー側の変更系エンドポイントは、それぞれ独立して認可を強制します。

---

## アップデート結果の処理

LUMS は、アップデート操作の結果を、生のコマンド出力を単に表示するのではなく、構造化された状態として扱います。

関連する情報には次が含まれます。

* 成功または失敗
* パッケージ単位の結果
* 実行状態
* エラー情報
* 再起動の要否
* 完了のタイムスタンプ

これにより、サーバーは意味のあるアップデート履歴を維持できます。

---

## 再起動の検出

パッケージ操作の後、クライアントは、その操作によって再起動が必要になったかどうかを確認します。

その結果は、ジョブ結果の一部としてサーバーに報告されます。

そのため、再起動の要否は、クライアント側のターミナルセッションの中で失われることなく、アップデート操作に関連付けられたまま残ります。

---

## クライアント認証の境界

クライアント API は、管理者の Web セッションとは別の認証メカニズムを使用します。

```text
Administrative User
        │
        ▼
 Web Authentication
        │
        ▼
    LUMS Server

Linux Client
        │
        ▼
 Client Token
        │
        ▼
    LUMS Server
```

この分離により、管理者のブラウザーセッションとクライアントの認証情報が、互いに置き換え可能な認証メカニズムになることを防ぎます。

---

## 監査証跡

セキュリティ上重要な操作および管理操作は、サーバー側の監査システムによって記録されます。

監査証跡は、通常のアプリケーションログを補完します。

ログは、アプリケーションの動作に関する疑問に答えます。

監査ログは、それに加えて、重要な管理操作とそのコンテキストを記録します。

この区別は、クライアント、ユーザー、認証状態、またはアップデートジョブへの変更を調査する際に役立ちます。

---

## 運用原則

LUMS は、次の要素を意図的に分離します。

```text
Management
     │
     ▼
Policy / Authorization
     │
     ▼
Job
     │
     ▼
Client Execution
     │
     ▼
Native Package Manager
```

各レイヤーには、定義された責任があります。

サーバーは管理します。

エージェントは実行します。

パッケージマネージャーは、実際のシステム変更を行います。

結果は、同じ制御されたチェーンを通って戻ります。

## ロールベースのアクセス制御

LUMS は、3 つの管理ロールを使用します。

```text
Administrator
Operator
Viewer
```

認可は、サーバー側で強制されます。

フロントエンドは、さらにユーザーの権限に合わせて表示されるインターフェースを調整しますが、フロントエンドでの表示・非表示がセキュリティ境界とみなされることはありません。

### Administrator

Administrator は、次にアクセスできます。

* クライアントの表示
* インストール済みソフトウェアの表示
* 利用可能なアップデートの表示
* アップデートジョブの作成と実行
* アップデート履歴の表示
* パッケージ管理の使用
* システムメンテナンスの実施
* クライアントの作成と無効化
* クライアントトークンのローテーション
* ユーザーの作成と管理
* ロールとユーザーアクセスの管理

### Operator

Operator は、次にアクセスできます。

* クライアントの表示
* インストール済みソフトウェアの表示
* 利用可能なアップデートの表示
* アップデートジョブの作成と実行
* アップデート履歴の表示
* パッケージ管理の使用
* システムメンテナンスの実施

Operator は、次にはアクセスできません。

* ユーザー管理
* ロールの管理
* クライアントの作成または無効化
* クライアントトークンのローテーション

### Viewer

Viewer は、次に対する読み取り専用のアクセス権を持ちます。

* クライアント
* インストール済みソフトウェア

Viewer は、次の機能を利用できません。

* 利用可能なアップデートの管理
* アップデートジョブ
* アップデート履歴
* パッケージ管理
* システムメンテナンス
* その他の状態を変更する管理操作

サーバーは、これらの制限を独立して強制します。

---

## ユーザー管理

LUMS は、`users.manage` 権限を持つアカウントにユーザー管理を提供します。

この権限を持つユーザーは、ロールテンプレートを使用してアカウントを作成し、その後、権限を個別に割り当てるか、そのテンプレートを明示的に適用できます。新しいアカウントは権限なしで始まり、作成後に権限エディターが開きます。ユーザー管理者は、アカウントの所有者には表示されない非公開の管理用メモを保存することもできます。

`backups.manage` を持つ管理者は、サーバーで設定されたディレクトリ内に、検証済みの `.db` または `.db.gz` のデータベースバックアップを作成でき、そのマウントされた場所の中の安全なサブフォルダーを選択できます。Docker ストレージの設定と復旧については、[`administration.md`](../../../administration.md) とアプリ内の Markdown 復元ガイドを参照してください。

ユーザーのパスワードは、平文や可逆暗号化ではなく、Argon2 パスワードハッシュを使用して保存されます。

ユーザー管理の操作は、次によって保護されます。

* 認証
* 権限ベースの認可
* CSRF 保護
* 入力の検証
* 重複ユーザーのチェック
* 監査ログ

ユーザー管理インターフェースは、`users.manage` がない場合は公開されません。

---

## セッションセキュリティ

管理者の認証は、サーバー側のセッション処理を使用します。

セッションセキュリティには次が含まれます。

* 認証済みセッションの状態
* セッションの失効
* 状態を変更するリクエストに対する CSRF 保護
* ログインのレート制限
* 無効化されたアカウントの強制
* ロールのチェック

セッションを失効させると、ユーザーインターフェースを単に非表示にするのではなく、対応する認証済み状態が無効になります。

---

## ログインのレート制限

ログインの失敗が繰り返されると、段階的なレート制限の対象になります。

現在のしきい値は次のとおりです。

```text
5 attempts  → 30 seconds
6 attempts  → 60 seconds
7 attempts  → 120 seconds
8+ attempts → 300 seconds
```

関連する状態は SQLite に永続化されます。

認証に成功すると、該当する失敗状態はクリアされます。

これにより、単純なアプリケーションの再起動でログイン保護を回避されることを防ぎます。

---

## クライアントトークンのセキュリティ

登録された各クライアントは、独自の認証トークンを持ちます。

サーバーは、トークンを SHA-256 ダイジェストとして保存します。

通常のサーバー側の検証には、元のトークンは必要ありません。

トークンのローテーションにより、管理者は既存の認証情報を無効化し、代わりのものを発行できます。

これにより、次の明確なライフサイクルが形成されます。

```text
Create
  │
  ▼
Use
  │
  ▼
Rotate
  │
  ▼
Old token invalid
```

---

## API セキュリティ

LUMS は、状態を変更する操作を実行する前に API の入力を検証します。

セキュリティ制御には次が含まれます。

* 認証
* ユーザーごとの権限による認可
* 該当する場合の CSRF 保護
* 入力の検証
* パッケージ名の検証
* 構造化されたジョブアクション
* パラメーター化されたデータベースクエリ
* 制御されたエラー処理

アプリケーションは、ユーザーが指定したパッケージ名を、制限のないシェルコマンドとして使用することはありません。

---

## SQL インジェクション対策

データベース操作では、パラメーター化された SQL ステートメントを使用します。

ユーザーが制御する値が、SQL クエリに直接連結されることはありません。

これは、次のような領域に適用されます。

* 認証
* クライアント管理
* ユーザー管理
* パッケージ検索
* アップデートジョブ
* 監査データ
* 結果の報告

目標は、データ値を SQL 命令から分離しておくことです。

---

## SQLite のセキュリティベースライン

現在の本番環境における SQLite の設定は次のとおりです。

```text
journal_mode = wal
busy_timeout = 5000
synchronous = 2
foreign_keys = ON
```

外部キー制約の強制は、アプリケーションがデータベース接続に対して明示的に有効にします。

現在の構成では、WAL モードを使用します。

データベースは、使い捨てのアプリケーションコンテナーのファイルシステム内ではなく、永続的な Docker ボリュームに保存されます。

---

## ジョブの復旧とチェックポイント

LUMS は、アップデートジョブを永続的なステートマシンとして扱います。

複数パッケージのジョブには、個別のパッケージ操作が複数含まれる場合があります。

各パッケージ項目は、それぞれ独自の結果状態に到達できます。

実行が中断された場合、復旧処理は次を区別できます。

```text
already successful
        │
        └── do not unnecessarily repeat

not completed
        │
        └── eligible for recovery
```

これにより、中断後に、完了済みのパッケージ操作を無差別に繰り返してしまうリスクが減ります。

---

## 制御されたアップデートの実行

LUMS は、アップデートジョブ API を通じて要求できるアクションを意図的に制限しています。

サポートされるアクションは次のとおりです。

```text
INSTALL_PACKAGE
REMOVE_PACKAGE
UPDATE_PACKAGE
UPDATE_SYSTEM
```

サーバーは、ジョブを作成する前に、アクションと関連するパッケージ情報を検証します。

その後、エージェントは、構造化されたアクションを適切なパッケージマネージャー操作にマッピングします。

これにより、アップデートシステムが汎用のリモートコマンド実行メカニズムになることを避けます。

---

## パッケージ操作

パッケージ操作は、クライアントのネイティブなパッケージマネージャーを通じて実行されます。

### インストール

検証済みのパッケージ名が、インストールのためにパッケージマネージャーの抽象化に渡されます。

### 削除

検証済みのパッケージ名が、削除のためにパッケージマネージャーの抽象化に渡されます。

### パッケージのアップデート

クライアントが利用可能なアップデートとして報告している場合、特定のパッケージをアップデートできます。

### クライアントのシステムアップデート

システムアップデート操作は、アップデート処理をネイティブなパッケージマネージャーに委ねます。

すべての操作は、構造化された結果を LUMS サーバーに返します。

---

## パッケージマネージャーの安全性

LUMS は、パッケージマネージャーを特権を持つローカルコンポーネントとして扱います。

そのため、エージェントはパッケージマネージャーの動作を自ら模倣しようとはしません。

代わりに、エージェントは次を行います。

1. 要求された操作を検証する
2. 適切なパッケージマネージャーの実装を選択する
3. 制御された操作を実行する
4. 結果を取得する
5. 結果をサーバーに報告する

ディストリビューション固有の動作は、パッケージマネージャーレイヤー内に分離されたままです。

---

## 再起動の扱い

一部のパッケージ操作では、再起動が必要になる場合があります。

LUMS は、再起動の要否をアップデートジョブの結果の一部として記録します。

これにより、管理者は次を区別できます。

```text
Update completed
```

と、次です。

```text
Update completed
Reboot required
```

したがって、再起動の要否は、無関係な通知として扱われるのではなく、運用状態の一部となります。

---

## 監査ログ

LUMS は、重要な管理操作およびセキュリティ上重要な操作について、アプリケーションの監査証跡を保持します。

例には次が含まれます。

* 認証関連のイベント
* クライアント管理
* トークン操作
* ユーザー管理
* アップデートジョブの作成
* セキュリティ上重要な状態の変更

監査ログは、通常の診断ログとは別のものです。

診断ログは、アプリケーションのトラブルシューティングに役立ちます。

監査記録は、関連する操作の管理上の履歴を提供します。

---

## セキュリティの強化

現在のデプロイには、複数の層の強化が含まれています。

### コンテナーの強化

本番コンテナーは次を使用します。

* 非 root でのアプリケーション実行
* 読み取り専用のルートファイルシステム
* 削除された Linux ケーパビリティ
* `no-new-privileges`
* 制限された一時ファイルシステム
* 読み取り専用のシークレットマウント
* 専用の永続データボリューム

### ネットワークの強化

アプリケーションコンテナーは、ホスト上のループバックにバインドされます。

```text
127.0.0.1:5050
```

そのため、アプリケーションのポートが LAN サービスとして直接公開されることはありません。

外部からのアクセスは、HTTPS のリバースプロキシで処理されます。

ファイアウォールは、内部のアプリケーションポートを公開しません。

### トランスポートセキュリティ

管理者のアクセスは、HTTPS を通じて提供されます。

リバースプロキシが、外部の TLS 終端を処理します。

HTTP リクエストは HTTPS にリダイレクトされます。

### シークレットと設定

機密性の高いランタイムの認証情報は、アプリケーションのソースツリーの外に保管されます。

本番のシークレットは、読み取り専用のシークレットファイルとしてコンテナーにマウントされます。

リポジトリおよび Docker のビルドコンテキストのルールにより、一般的なバックアップ、シークレット、データベース、証明書のアーティファクトが、イメージのビルドコンテキストに意図せず入り込むことを防ぎます。

### 依存関係とビルドのセキュリティ

本番環境の Python の依存関係は固定されています。

本番環境の Python ベースイメージは、ダイジェストで固定されています。

Docker のビルドコンテキストは、`.dockerignore` によって制限されます。

これらの制御により、ビルドの再現性が向上し、機密ファイルが誤って含まれることが減ります。

## パッケージ単位のジョブ状態

複数のパッケージを含むジョブでは、パッケージ単位の進捗を追跡できます。

例:

```text id="v9w1sh"
Job #42

package-a → SUCCESS
package-b → SUCCESS
package-c → FAILED
package-d → PENDING
```

したがって、復旧は、成功したパッケージ操作を無差別に繰り返すのではなく、ジョブの未完了の部分に対して実行できます。

## ジョブの復旧

復旧は、永続的なチェックポイントを中心に設計されています。

サーバーは、ジョブの状態を保持します。

クライアントは、パッケージ単位の結果を報告します。

実行が中断された場合、サーバーは、どの作業がすでに完了していて、どの作業が復旧の対象として残っているかを判断できます。

意図された復旧の原則は次のとおりです。

> **何も起きなかったと仮定するのではなく、既知の状態から続行する。**

## 結果の検証

クライアントのジョブ結果は、サーバーの永続的な状態に受け入れられる前に検証されます。

これにより、不正な形式の結果や不完全な結果の送信から、ジョブの状態が保護されます。

検証は、次のような関連フィールドに適用されます。

* ジョブの識別情報
* 実行状態
* パッケージの結果データ
* エラー情報
* 再起動の情報

したがって、結果処理レイヤーは、認証済みクライアントとサーバーの永続的な状態との間の、もう 1 つの境界として機能します。

現在のロールは次のとおりです。

```text id="2xqv79"

Operator
Viewer
```

## ドキュメントの原則

ドキュメントは、システムの一部として扱われます。

コードが動作していても、ドキュメントが古いアーキテクチャを記述したままであれば、機能は完全に完成したとはみなされません。

意図された関係は次のとおりです。

```text id="0m1m5u"
Implementation
      │
      ├── Tests
      ├── Security Review
      └── Documentation
               │
               ▼
          Release Ready
```

これは、セキュリティ上重要なデプロイや管理の手順にとって、特に重要です。

## 変更の哲学

変更は、慎重に行うべきです。

一般的な変更では、次に答えられる必要があります。

1. これはどのような問題を解決するのか
2. どのコンポーネントがその変更を担うべきか
3. その変更はセキュリティに影響するか
4. 永続的な状態に影響するか
5. クライアントに影響するか
6. ドキュメントの変更が必要か
7. 既存の機能が引き続き動作することを、どのテストが証明するのか

これにより、システムの一部を修正しながら、別の部分を気付かないうちに壊してしまうリスクが減ります。

## 最終的なアーキテクチャ

最上位のレベルでは、LUMS は 5 つのレイヤーとして理解できます。

```text id="7b4p6n"
┌───────────────────────────────────────────────┐
│                    UI                         │
│       Human interaction and visibility        │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                    API                        │
│    Authentication, authorization, validation  │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                  Persistence                   │
│       Jobs, clients, users, results, audit   │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                    Agent                      │
│      Local execution and system reporting     │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│              Native Linux Tools               │
│              APT / dpkg / pacman             │
└───────────────────────────────────────────────┘
```

各レイヤーには、特定の責務があります。

UI は、操作を提供します。

API は、ポリシーを強制します。

SQLite は、永続的な状態を提供します。

エージェントは、制御されたクライアント側の実行を行います。

ネイティブのパッケージマネージャーは、実際のシステム変更を行います。
