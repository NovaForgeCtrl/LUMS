# LUMS — 管理ガイド

> **ノイズのない Linux アップデート管理。**

このガイドでは、サーバーとクライアントのインストール後に行う LUMS の日常管理と運用を説明します。Web インターフェースでの管理作業と、LUMS サーバーおよび管理対象クライアント上での制御された運用作業を扱います。

インストール手順は[インストールガイド](インストールとアップグレード.md)、診断は[トラブルシューティングガイド](トラブルシューティング.md)、セキュリティ構成と監査情報は[セキュリティモデル](セキュリティモデル.md)を参照してください。英語原本は[administration.md](../../../administration.md)です。

## 日常管理を始める前に

* **ユーザーアカウント:** LUMS Web UI で実行できる操作を決めます。共有せず、利用者ごとにアカウントを作成してください。
* **クライアント:** 管理対象の Linux コンピューターです。クライアントトークンは秘密情報であり、Web アカウントのパスワードとは別です。
* **更新ジョブ:** エージェントが取得し、対象ホスト上で APT または pacman を使って実行する要求です。実行前に対象とパッケージを確認します。
* **バックアップ:** データベースの別個の検証済みコピーです。同じ Docker ボリューム内のコピーは、そのボリュームの喪失に対する保護になりません。
* **アップグレード:** データベースではなくコンテナーバージョンを置き換えます。通常のアップグレードで `lums-data` を削除または再作成してはいけません。

### 変更前の安全チェック

1. 更新ジョブが実行中か確認し、必要ならメンテナンス時間を確保します。
2. 最近作成された利用可能なデータベースバックアップを確認します。
3. 実行中のイメージ、コンテナー設定、データパスを記録します。
4. 稼働中コンテナーを止める前に、新しいイメージをビルドしてテストします。
5. 同じデータ、シークレット、バックアップマウント、セキュリティオプションを引き継いでコンテナーを置き換えます。
6. 起動後にコンテナー状態、ログ、HTTPS サインイン、データを確認します。
7. 新バージョンを検証するまで、旧コンテナーをロールバック用に保持します。

通常のアップグレードで `docker volume rm lums-data`、`docker system prune --volumes`、その他の削除コマンドを実行しないでください。データを永久に失う可能性があります。どのコンテナーやパスが有効か不明な場合は、まず現在の構成を確認してください。例示コマンドを確認せずにコピーしないでください。

## 管理責任とロール

LUMS では、Linux ソフトウェアインベントリ、利用可能な更新、パッケージ操作、更新ジョブ、管理対象クライアント、ユーザー、運用履歴を一元管理します。標準のロールテンプレートは Administrator、Operator、Viewer です。アカウント作成時にテンプレートが推奨権限を設定します。管理者はユーザーごとに権限を調整できます。アクセス可否を決めるのはロール名ではなく、保存済み権限です。

| ロール | 主な用途 |
| --- | --- |
| Administrator | ユーザー、ロール、クライアント、トークン、更新、パッケージ、システム運用の管理 |
| Operator | クライアントとソフトウェアの閲覧、更新ジョブの作成／実行、履歴確認、パッケージ／システム保守 |
| Viewer | クライアントとインストール済みソフトウェアの読み取り専用確認 |

Administrator テンプレートは `users.manage` など全管理権限を既定で持ちます。Operator はユーザー管理、ロール割り当て、クライアント作成／無効化、トークンローテーションを既定では行えません。Viewer は更新情報、ジョブ実行、パッケージ管理、システム保守、ユーザー管理、クライアント管理を既定では行えません。最小権限のロールを割り当て、必要な権限だけを付与してください。管理者アカウントを日常的な読み取り専用監視に使わないでください。

主な権限には `users.manage`、`clients.manage`、`clients.view`、`software.view`、`updates.view`、`packages.search`、`jobs.manage`、`backups.manage` があります。クライアント関連権限には `clients.view` が必要です。`jobs.manage` には `updates.view` も必要です。最後に残る `users.manage` 権限ユーザーを削除できないため、管理者が誤って全員をロックアウトすることは防止されます。権限の詳細は[英語原本のユーザー管理セクション](../../../administration.md)を確認してください。

## ユーザーと認証

`users.manage` 権限を持つユーザーは、ユーザー管理画面からアカウントを作成できます。ユーザー名、パスワード、ロールラベルを指定し、作成後に権限を個別設定するか、`administrator`、`operator`、`viewer` テンプレートを適用します。新しいアカウントは権限なしで作成されます。パスワードは平文で保存されず、Argon2 によるハッシュ化が使用されます。

作成後はユーザー一覧、ロールと権限、アカウント有効状態、サインインを確認してください。パスワードをドキュメント、チケット、スクリーンショット、非保護チャネルで送信しないでください。不要になったアカウントは共有または転用せず無効化し、認証が拒否されることを確認します。アカウント無効化後の既存セッションもセキュリティ調査時に考慮してください。ユーザーテーブルを直接編集しないでください。

LUMS はログイン失敗をレート制限します。

| 失敗回数 | ロックアウト時間 |
| ---: | ---: |
| 5 | 30 秒 |
| 6 | 60 秒 |
| 7 | 120 秒 |
| 8 以上 | 300 秒 |

状態は SQLite に保存され、正常なログインで該当する失敗状態が解除されます。認証失敗が続く場合は、認証情報の誤り、保存済み認証情報の古さ、自動クライアントの設定ミス、繰り返しの手動試行、認証情報攻撃の可能性を調べ、レート制限を迂回しないでください。

## データベースバックアップ

`backups.manage` 権限を持つユーザーは **Datenbank-Backups** 画面から SQLite バックアップを作成できます。Administrator には `005-backup-permission` マイグレーションでこの権限が付与されます。新規アカウントには Administrator テンプレートを適用するか、権限を明示的に付与します。

画面は `.db` と `.db.gz` に対応し、SQLite オンラインバックアップ API を使い、完了したデータベースを検証して、所有者のみがアクセスできる権限でファイルを保存します。最新 10 件を一覧表示します。LUMS はバックアップを暗号化、自動削除、スケジュール、ダウンロード、復元しません。`backups.manage` 権限のある管理者は確認後に個別バックアップを削除できます。バックアップ先を適切に保護してください。

サーバー側の `LUMS_BACKUP_DIR` で基準ディレクトリが固定されます。画面からその配下の相対サブディレクトリを選択でき、必要なら作成されます。絶対パス、親ディレクトリへの移動、シンボリックリンクのサブディレクトリは拒否されます。ホストパスはサーバー管理者が Docker にマウントする必要があります。Docker 環境ではコンテナー UID/GID `10001` が書き込み可能な別のホストディレクトリを作成します。

```bash
sudo install -d -o 10001 -g 10001 -m 0700 /var/backups/lums
```

LUMS コンテナー設定に次のオプションを追加します。

```bash
-v /var/backups/lums:/var/backups/lums \
-e LUMS_BACKUP_DIR=/var/backups/lums \
```

ホスト故障への耐性を高めるには、別ディスクまたはリモートストレージを使用してください。NAS を Debian ホストにマウントしてから、そのマウント先を Docker bind mount の左側に指定できます。バックアップ UI はコンテナー側の基準ディレクトリを表示し、選択した相対パスはその配下になります。コンテナー内で保存先が利用でき、書き込み可能でなければ、画面にストレージ利用不可と表示されます。

復元では、稼働中データベースが置き換わります。専用の復元手順に従い、復元テストを管理された別環境で定期的に実施してください。[データベースバックアップの復元](データベースバックアップの復元.md)を参照してください。バックアップ一覧や監査ログ上の成功記録は、復元できることの証明ではありません。

## クライアント管理

クライアント管理には `clients.manage` 権限が必要です。クライアント認証は、どのシステムが LUMS に報告できるかを決定します。各クライアントに固有のトークンを使用し、パスワードと同様に保護してください。複数マシンで同じトークンを再利用しないでください。トークンを漏えいまたはローテーションした場合は、以前の認証情報を無効化し、新しいトークンを安全なチャネルで対象クライアントに配布します。

クライアントの有効／無効状態、最後の報告時刻、エージェントと Watcher の動作を確認します。無効化によって報告を停止できても、インベントリやジョブの履歴が自動的に消えるとは限りません。廃止前に必要な記録を確認してください。

## インベントリ、更新、パッケージ操作

インストール済みソフトウェアと利用可能な更新を、それぞれの表示で確認します。パッケージ検索は対象クライアントのローカルパッケージマネージャーで実行され、結果がサーバーに返されます。読み取り権限のみのユーザーが検索や変更操作をできるとは限りません。

パッケージ操作にはインストール、削除、単一パッケージの更新、システム更新があります。変更前にクライアント、パッケージ名、操作内容、依存関係やメンテナンス影響を確認します。APT／dpkg または pacman が実際の操作を担当します。LUMS はパッケージマネージャーを置き換えず、任意のシェルコマンドを実行する機能も提供しません。

更新ジョブは対象と操作を指定して作成し、状態、パッケージごとの結果、失敗内容、再起動要否を監視します。API 要求の成功だけでは、パッケージ操作の完了を意味しません。クライアントから返された最終状態とジョブ履歴を確認してください。APT や pacman がロックされている場合、同じホストで別のパッケージ操作が進行していないか調べ、ロックファイルをむやみに削除しないでください。

Watcher は更新ジョブの実行を監視し、アイドル状態を確認した上でジョブを取得します。アイドル検出は可能な場合 `loginctl` を使用します。実行中にサーバーやクライアントが再起動した場合でも、サーバーに保存されたジョブ状態とパッケージ単位のチェックポイントに従って復旧します。すでに成功したパッケージ処理を不必要に再実行しないでください。`RUNNING` 状態を手動で `SUCCESS` や `FAILED` に変更してはいけません。

更新後に再起動が必要と報告された場合は、適切なメンテナンス時間に再起動し、クライアントの報告、ジョブ状態、更新後のシステム状態を再確認します。

## 監視、ログ、監査

運用担当者は実行中／失敗／完了ジョブ、クライアント報告、再起動要否、パッケージマネージャーエラー、監査イベントを確認します。Watcher、Agent、systemd timer、アプリケーション、監査ログの時刻と対象を照合してください。秘密情報やトークンをログ、スクリーンショット、報告に含めないでください。

管理操作やセキュリティ関連イベントは LUMS 監査ログに記録されます。監査ログは通常のアプリケーションログとは区別して取り扱います。状態を変更する前に観察と記録を行い、変更後に結果を検証してください。

## データベース、コンテナー、HTTPS

SQLite データベースは永続 Docker ボリューム `lums-data` の `/var/lib/lums/lums.db` に保存されます。コンテナーは置き換え可能ですが、データボリュームは永続です。マイグレーションは正しいアプリケーション版で実行されることを確認し、失敗時にはログとデータベース状態を調査します。直接 SQL で本番データを変更しないでください。

本番コンテナーでは root ファイルシステムを読み取り専用とし、root 以外の `lums` ユーザー（UID `10001`）、全 Linux capability の削除、`no-new-privileges`、必要な一時ファイル領域のみへの書き込み、読み取り専用のシークレットマウントを維持します。コンテナーを privileged モードで起動しないでください。アプリケーションポートは `127.0.0.1:5050` のみで公開し、外部 HTTPS は Nginx リバースプロキシ経由にします。ポート `5000` を直接公開しないでください。

Nginx の TLS 証明書、HTTPS リダイレクト、ホスト名、セキュリティヘッダー、プロキシ先を定期確認します。シークレット、秘密鍵、データベース、トークンを Git、Docker イメージ、公開ログに入れないでください。シークレットや TLS 素材をバックアップする場合もアクセス権を厳しく制限します。

## バックアップと復旧の原則

バックアップ対象には、少なくとも LUMS データベース、アプリケーションシークレット、TLS 素材、デプロイ構成を含めます。アクティブなコンテナーの外部に保管し、同じ Docker ボリュームだけをバックアップとみなさないでください。ライブ SQLite データベースを一貫性保証のない方法でコピーしないでください。バックアップファイルが存在し、適切な権限で保護されていることを確認します。

復元では既存の本番データベースを置き換える前に現状を別途保存し、復元ファイルの整合性を検査し、ユーザー、クライアント、ジョブ、パッケージ、監査データを確認します。SQLite の integrity check が成功しても、アプリケーション状態全体の正しさが保証されるわけではありません。復元は本番障害が起きる前に別環境で試験してください。

## 保守、アップグレード、ロールバック

変更前に実行中ジョブを確認し、必要なら保守時間を設定します。最近の検証済みバックアップを作成し、実行中のイメージ、設定、データパスを記録してください。新しいリポジトリ変更を確認し、テストスイートを実行し、イメージをビルドして検査してから、コンテナーを制御された方法で置き換えます。

通常の更新手順は次のとおりです。

```text
確認 → バックアップ → テスト → ビルド → デプロイ → 検証
```

コンテナー置き換え後、起動状態、ログ、HTTPS 接続、マイグレーション、ユーザーとクライアント、永続データ、Agent 通信、更新ジョブ、監査記録、セキュリティ設定を確認します。新しいコンテナーが動作しない場合は、旧イメージと構成を使ってロールバックします。ロールバック後もデータベーススキーマ互換性を確認し、状態を検証するまではクライアント更新を再開しないでください。

`lums-data` ボリュームを削除したり再作成したりすることは、通常のアップグレードやロールバックの手順ではありません。重大なデータベース変更時は、変更内容、バックアップ、ロールバック計画を先に確認します。

## アンインストール

アンインストールの前に、保持する必要のあるデータ、バックアップ、証明書、シークレット、構成を確認します。コンテナーを削除してもボリュームが残る場合があります。永続データを削除するのは、必要性とバックアップを確認した後に限ってください。クライアント側では Agent、Watcher、systemd サービスと timer を個別に停止／削除し、必要に応じてクライアント設定やトークンを失効させます。

## 日常の管理チェックリスト

* 必要な利用者にだけ最小限のロールと権限を付与する。
* クライアントごとに個別のトークンを使い、安全にローテーションする。
* ジョブ対象、パッケージ、進捗、結果、再起動要否を確認する。
* エラーと監査記録を調査し、秘密情報を露出しない。
* データベースと構成のバックアップを別の保護された場所に保管し、復元テストを実施する。
* アップグレード前後のコンテナー、HTTPS、永続データ、権限、クライアント通信を検証する。
* **まず観察し、次に変更し、最後に検証する。**
