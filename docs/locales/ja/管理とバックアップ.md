# LUMS — 管理ガイド

> **ノイズのない Linux アップデート管理。**

このガイドでは、サーバーとクライアントをインストールした後の LUMS の日常的な管理と運用について説明します。

LUMS の Web インターフェースで行う管理作業と、LUMS サーバーおよび管理対象クライアント上で行う制御された運用作業を中心に扱います。

インストール手順は別ドキュメントの [`install.md`](インストールとアップグレード.md) に記載されています。

トラブルシューティング手順は別ドキュメントの [`troubleshooting.md`](トラブルシューティング.md) に記載されています。

セキュリティアーキテクチャと監査情報は別ドキュメントの [`security.md`](セキュリティモデル.md) に記載されています。

---

## はじめに: 日常的な管理

このガイドは、既存の LUMS インストールを担当する方向けです。
詳細な技術セクションは英語で管理されています。まず次の用語を押さえてください。

* **ユーザーアカウント:** LUMS Web インターフェースで個人が実行できる操作を決定します。
  アカウントは共有せず、一人ひとりに専用のアカウントを発行してください。
* **クライアント:** 管理対象の Linux コンピューターです。クライアントトークンは秘密情報であり、
  Web アカウントのパスワードとは別のものです。
* **更新ジョブ:** エージェントが取得し、対象コンピューター上で APT または pacman を使って
  実行する、要求された操作です。開始する前に対象とパッケージを確認してください。
* **バックアップ:** データベースの、別に保管された検証済みのコピーです。同じ Docker ボリューム内の
  コピーは、そのボリュームの喪失に対する保護にはなりません。
* **アップグレード:** コンテナーのバージョンを置き換えるものであり、データベースは置き換えません。
  通常のアップグレードで `lums-data` を削除したり再作成したりしてはいけません。

### 変更前の安全チェックリスト

1. 更新ジョブが実行中かどうか、またメンテナンスウィンドウが必要かどうかを確認します。
2. 最近の、利用可能なデータベースバックアップが存在することを確認します。
3. 実行中のイメージ、コンテナー設定、データパスを記録します。
4. 稼働中のコンテナーを停止する前に、新しいイメージをビルドしてテストします。
5. 同じデータ、シークレット、バックアップのマウントと同じセキュリティオプションを使って、
   コンテナーを置き換えます。
6. 起動後に、コンテナーの状態、ログ、HTTPS サインイン、データを確認します。
7. 新しいバージョンが検証されるまで、古いコンテナーをロールバック用に保持します。

**実行しないでください:** 通常のアップグレードの一環として `docker volume rm lums-data`、
`docker system prune --volumes`、その他の削除コマンドを実行してはいけません。
データが完全に失われる可能性があります。どのコンテナーやパスが有効か不明な場合は、
作業を止めてまず現在の構成を確認してください。確認せずに例のコマンドをコピーしないでください。

## 1. 管理の概要

LUMS は、Linux のソフトウェアインベントリ、利用可能な更新、パッケージ操作、更新ジョブ、管理対象クライアント、ユーザー、運用履歴を一元的に管理します。

管理インターフェースには 3 つのロールテンプレートがあります。

* **Administrator**
* **Operator**
* **Viewer**

アカウントを作成すると、選択したロールによって推奨される権限のセットが設定されます。
管理者はユーザーごとにその権限を調整できます。アクセスを決定するのは、ロール名ではなく保存された権限です。

LUMS はまた、サーバー側の管理操作とクライアント側のパッケージ実行を分離しています。

通常の運用の流れは次のとおりです。

```text
Administrator / Operator
        │
        ▼
   LUMS Web UI
        │
        ▼
     LUMS API
        │
        ▼
      SQLite
        │
        ▼
   Managed Client
        │
        ▼
 APT / pacman / system
        │
        ▼
      Result
        │
        ▼
     LUMS API
        │
        ▼
      SQLite
        │
        ▼
    Web Interface
```

LUMS サーバーは、管理対象クライアント上でパッケージ管理コマンドを直接実行しません。

パッケージ操作は、管理対象システムにインストールされた LUMS Agent によって実行されます。

---

## 2. 管理上の責任

LUMS の管理は、いくつかの領域に分けられます。

### ユーザー管理

管理者は次を管理します。

* LUMS ユーザー
* ユーザーロール
* アカウントの状態
* 管理アクセス

ユーザー管理には `users.manage` 権限が必要です。

Administrator テンプレートには、この権限が既定で含まれています。

Operator と Viewer には、既定ではこの権限は付与されません。

---

### クライアント管理

管理者は次を管理します。

* 登録済みクライアント
* クライアントの状態
* クライアント認証
* クライアントトークン
* トークンのローテーション
* クライアントの有効化と無効化

クライアントの認証によって LUMS へのレポートを許可するシステムが決まるため、クライアント管理には `clients.manage` 権限が必要です。

---

### 更新管理

Administrator および Operator テンプレートには、次の操作を行う権限が付与されます。

* 利用可能な更新の表示
* 更新ジョブの作成
* パッケージ操作の実行
* 更新履歴の確認
* 個別パッケージの管理
* システム更新の実行

Viewer テンプレートは読み取り専用であり、更新操作を実行できません。

---

### パッケージ管理

LUMS は、クライアントのネイティブなパッケージマネージャーを通じてパッケージ管理操作をサポートします。

現在サポートされているパッケージ管理バックエンドは次のとおりです。

* Debian 系システム向けの **APT/dpkg**
* Arch Linux 向けの **pacman**

LUMS は、オペレーティングシステムのパッケージマネージャーを置き換えるものではありません。

代わりに、パッケージ操作を要求して追跡するための一元的なインターフェースを提供します。

---

### 運用管理

管理者および Operator は、次の項目を監視する必要があります。

* 実行中の更新ジョブ
* 失敗したジョブ
* 完了したジョブ
* クライアントのレポート
* 再起動の要否
* パッケージマネージャーのエラー
* 監査アクティビティ

これらの状況に対する詳細なトラブルシューティング手順は、[`troubleshooting.md`](トラブルシューティング.md) に記載されています。

---

## 3. 管理ロール

LUMS には現在 3 つのロールがあります。

| ロール        | 目的                                     |
| ------------- | ---------------------------------------- |
| Administrator | 完全な管理権限                           |
| Operator      | 日常的な運用管理                         |
| Viewer        | クライアントとソフトウェアの読み取り専用の閲覧 |

各ロールは権限テンプレートです。アカウントごとに個別に保存された権限が、サーバー側で適用されます。

したがって、インターフェース要素を非表示にすること自体は、セキュリティ制御とは見なされません。

権限のない API 操作も、サーバーが拒否する必要があります。

---

## 4. Administrator

Administrator テンプレートは、LUMS アプリケーションの全権限を既定で提供します。

Administrator は次の操作を行えます。

* 管理対象クライアントの表示
* インストール済みソフトウェアの表示
* 利用可能な更新の表示
* 更新ジョブの作成と実行
* 更新履歴の確認
* パッケージ管理操作の実行
* システムメンテナンスの実行
* クライアントの作成
* クライアントの無効化
* クライアントトークンのローテーション
* LUMS ユーザーの作成と管理
* ロールテンプレートと個別権限の割り当て

Administrator テンプレートの完全な権限は、必要とするユーザーにのみ付与してください。

Operator または Viewer のアカウントで足りる場合は、日常的な読み取り専用の監視に管理者アカウントを使用しないでください。

---

## 5. Operator

Operator テンプレートは、日常的な更新およびシステム管理を想定しています。

Operator は次の操作を行えます。

* 管理対象クライアントの表示
* インストール済みソフトウェアの表示
* 利用可能な更新の表示
* 更新ジョブの作成と実行
* 更新履歴の確認
* パッケージ管理操作の実行
* システムメンテナンスの実行

Operator テンプレートは、次の権限を付与しません。

* LUMS ユーザーの作成または管理
* ユーザーロールの割り当て
* クライアントの作成または無効化
* クライアントトークンのローテーション

この既定の分離により、アカウントおよびクライアント管理の権限を付与せずに、日常的な更新作業を実行できます。
個別の付与は、`users.manage` を持つユーザーが変更できます。

---

## 6. Viewer

Viewer テンプレートは、読み取り専用の閲覧権限を提供します。

Viewer は次の操作を行えます。

* 管理対象クライアントの表示
* インストール済みソフトウェアの表示

Viewer テンプレートは、次の管理機能を付与しません。

* 利用可能な更新の管理
* 更新ジョブの作成
* 更新ジョブの実行
* 更新履歴
* パッケージ管理
* システムメンテナンス
* ユーザー管理
* クライアント管理
* トークンのローテーション

これらに対応する変更系 API 操作も、サーバー側で保護されています。

したがって Viewer アクセスは、運用を制御せずに状況を確認する必要があるユーザー向けです。

---

## 7. ロール選択のガイドライン

必要な機能を提供する最小のロールを使用してください。

### Administrator

ユーザーが次を管理する必要がある場合に使用します。

* ユーザー
* ロール
* クライアント
* クライアント認証
* トークン
* 更新
* パッケージ
* システム操作

### Operator

ユーザーが次のような日常的な運用作業を行う必要がある場合に使用します。

* 更新の確認
* パッケージのインストール
* パッケージの削除
* パッケージの更新
* 更新ジョブの実行
* ジョブ履歴の確認

### Viewer

ユーザーが次の可視性のみを必要とする場合に使用します。

* クライアント
* インストール済みソフトウェア

## 8. 管理上のセキュリティ原則

LUMS の管理は、最小権限の原則に従います。

管理アクセスは、ユーザーの作業に必要な機能に限定する必要があります。

特に次の点に注意してください。

* 日常的な閲覧に Administrator アカウントを使用しない
* 管理者間でアカウントを共有しない
* クライアントトークンを共有しない
* ドキュメントに認証情報を記載しない
* スクリーンショットやログにクライアントトークンを露出させない
* 文書化された復旧手順が明示的に求める場合を除き、データベースを直接変更して LUMS Web インターフェースを迂回しない

管理操作が失敗した場合は、永続的な状態を変更する前に原因を調査してください。

次の原則を使用してください。

> **まず観察し、次に変更し、最後に検証する。**

## 9. 管理ワークフロー

通常の管理ワークフローは、次の順序に従います。

```text
1. Authenticate
      │
      ▼
2. Verify role
      │
      ▼
3. Select client / operation
      │
      ▼
4. Review current state
      │
      ▼
5. Perform required operation
      │
      ▼
6. Monitor job
      │
      ▼
7. Verify result
      │
      ▼
8. Review history / audit information
```

管理操作は、実行後に必ず検証してください。

API リクエストが成功しても、要求したパッケージ操作やシステム操作が正常に完了したことの証明にはなりません。

管理対象クライアントが報告する最終状態が、運用上の関連する結果です。

## 11. ユーザー管理

ユーザー管理は、`users.manage` 権限を持つユーザーが利用できます。

管理者は、専用のユーザー管理インターフェースで LUMS アプリケーションアカウントを作成および管理できます。

ユーザーアカウントは、管理対象クライアントの認証とは別のものです。

LUMS ユーザーは、アプリケーションアカウントで Web アプリケーションに認証します。

管理対象クライアントは、クライアントトークンで LUMS API に認証します。

これらの認証メカニズムを混同してはいけません。

```text
LUMS User
    │
    │ username + password
    ▼
Web Interface
    │
    ▼
LUMS Application

Managed Client
    │
    │ client token
    ▼
LUMS API
```

## 12. ユーザーの作成

`users.manage` を持つユーザーは、新しい LUMS ユーザーを作成できます。

ユーザーを作成する際、管理者は次を指定します。

* ユーザー名
* パスワード
* ロールラベル（後から権限を割り当てるためのロールテンプレートが利用可能）

利用可能なロールテンプレートは次のとおりです。

* `administrator`
* `operator`
* `viewer`

サーバーは、アカウントを作成する前に、指定された値を検証します。

新しいアカウントは権限なしで開始されます。作成後、管理者は個別のチェックボックスを割り当てるか、
いずれかのロールテンプレートを適用できます。テンプレートを適用すると既定の権限が事前に選択され、
その後カスタマイズできます。利用可能な権限は次のとおりです。

| 権限              | 付与されるアクセス                                  |
| ----------------- | --------------------------------------------------- |
| `clients.view`    | クライアント一覧とシステム情報の表示                |
| `software.view`   | インストール済みソフトウェアの表示                  |
| `updates.view`    | 更新、ジョブ、更新履歴の表示                        |
| `packages.search` | パッケージリポジトリの検索                          |
| `jobs.manage`     | パッケージ操作と更新ジョブの作成                    |
| `clients.manage`  | クライアントの登録／削除とクライアントトークンのローテーション |
| `users.manage`    | ユーザーの作成、ロール、権限、内部メモの管理        |
| `backups.manage`  | データベースバックアップの作成と確認                |

クライアント関連の権限には `clients.view` が必要です。`jobs.manage` には `updates.view` も必要です。
LUMS は、`users.manage` を持つ最後の有効なアカウントの削除を防止するため、
管理者が誤って自分自身をロックアウトすることはありません。

パスワードは平文では保存されません。

LUMS は、アプリケーション認証情報に Argon2 ベースのパスワードハッシュを使用します。

作成後、次を確認してください。

* ユーザー名がユーザー一覧に表示されている
* ロールテンプレートと個別権限が正しい
* アカウントが有効になっている
* ユーザーが正常に認証できる

パスワードを、ドキュメント、チケット、スクリーンショット、その他の安全でないチャネルで送信しないでください。

## データベースバックアップインターフェース

`backups.manage` 権限を持つユーザーは、**Datenbank-Backups** から SQLite バックアップを作成できます。
Administrator アカウントは、マイグレーション `005-backup-permission` を通じてこの権限を受け取ります。
新しいアカウントは、Administrator テンプレートを適用するか、明示的に付与することでこの権限を得られます。

このインターフェースは、ネイティブの `.db` ファイルと圧縮された `.db.gz` ファイルをサポートします。
SQLite のオンラインバックアップ API を使用し、完成したデータベースを検証し、所有者のみの権限でファイルを保存します。
UI には最新の 10 ファイルが一覧表示されます。バックアップは LUMS によって暗号化、自動削除、
スケジュール、ダウンロード、復元されることはありません。`backups.manage` を持つ管理者は、
確認後に一覧から個別のバックアップを削除できます。保存先は、それに応じて保護してください。

ベースとなる対象ディレクトリは、サーバー側の `LUMS_BACKUP_DIR` 設定で固定されています。
インターフェースでは、このベースの下の相対サブディレクトリを選択でき、必要に応じて作成されます。
絶対パス、親ディレクトリへの移動、シンボリックリンクのサブディレクトリは拒否されます。
ホストのパスは、サーバー管理者が Docker にマウントする必要があります。Docker デプロイメントでは、
コンテナーの UID/GID `10001` が書き込める、別のホストディレクトリを作成してください。

```bash
sudo install -d -o 10001 -g 10001 -m 0700 /var/backups/lums
```

LUMS コンテナーの設定に、次のオプションを追加します。

```bash
-v /var/backups/lums:/var/backups/lums \
-e LUMS_BACKUP_DIR=/var/backups/lums \
```

ホスト障害への耐性を高めるには、別のディスクまたはリモートストレージを使用してください。
たとえば、まず Debian ホストに NAS をマウントし、そのマウント済みのパスを Docker バインドマウントの左側として使用します。
バックアップ UI にはコンテナー側のベースディレクトリが表示され、選択した相対パスはその下になります。
バックアップ先は、コンテナー内で利用可能かつ書き込み可能である必要があります。
そうでない場合、インターフェースはバックアップストレージが利用できないと報告します。

復元手順については、[`server/static/backup-restore.md`](../../../server/static/backup-restore.md) を参照してください。日本語のガイドは[データベースバックアップの復元](データベースバックアップの復元.md)です。

## 13. ユーザーロール

必要最小限の権限に応じてロールテンプレートを選択し、その後アカウントごとに個別の権限を確認してください。

| ロールテンプレート | ユーザー管理 | クライアント管理 | 更新 | パッケージ管理 | 読み取り専用アクセス |
| ------------- | --------------: | ----------------: | ------: | -----------------: | ---------------: |
| Administrator |             Yes |               Yes |     Yes |                Yes |              Yes |
| Operator      |              No |                No |     Yes |                Yes |              Yes |
| Viewer        |              No |                No |      No |                 No |              Yes |

これらは既定値であり、固定された境界ではありません。管理者は各ユーザーの権限セットをカスタマイズできます。
ロールの強制は、結果として得られるユーザーごとの権限を通じて、サーバー上で行われます。

Web インターフェースは割り当てられたロールを反映しますが、サーバーが引き続き権威あるセキュリティ境界です。

## 14. ユーザーアカウントの無効化

アカウントが LUMS にアクセスできなくなるべき場合は、認証情報を共有したり転用したりせず、アカウントを無効化してください。

例:

* 管理者がプロジェクトを離れる場合
* Operator がアクセスを必要としなくなった場合
* 管理アクセスを一時的に削除する場合
* 侵害されたアカウントへのセキュリティ対応

アカウントを無効化した後は、認証が拒否されることを確認してください。

アカウントのセキュリティ調査では、既存の認証済みセッションも考慮する必要があります。

文書化された復旧手順がデータベースレベルの介入を明示的に求める場合を除き、`users` テーブルを手動で変更しないでください。

---

## 15. パスワード管理

パスワードはアプリケーション認証情報であり、機密情報として扱う必要があります。

管理者は次を徹底してください。

* パスワードを共有しない
* パスワードを Git に保存しない
* パスワードをドキュメントに記載しない
* パスワードをスクリーンショットに含めない
* パスワードを不必要にシェル履歴へ書き込まない
* ユーザーが適切で安全なチャネルを通じて認証情報を受け取る

LUMS は、平文のパスワードではなくパスワードハッシュを保存します。

パスワードが侵害された疑いがある場合は、元のパスワードを復元しようとするのではなく、適切なアカウント管理手順を通じてパスワードを置き換えてください。

---

## 16. セッション

LUMS は、Web アクセスに認証済みのアプリケーションセッションを使用します。

セッション処理は、アプリケーションのセキュリティ境界の一部です。

関連するアカウントがもうアクセスできないはずの場合、予期しない認証済みセッションはセキュリティイベントとして扱ってください。

関連する状況は次のとおりです。

* 無効化されたアカウントがまだ有効に見える
* 予期しない管理アクセス
* 認証情報の侵害の疑い
* 予期しないブラウザーセッション
* セキュリティ調査

セッションと認証の詳細なトラブルシューティングについては、[`troubleshooting.md`](トラブルシューティング.md) を参照してください。

---

## 17. ログインのレート制限

LUMS は、繰り返されるログイン失敗にレート制限を適用します。

現在の段階は次のとおりです。

| 失敗回数 |     ロックアウト |
| --------------: | ----------: |
|               5 |  30 秒 |
|               6 |  60 秒 |
|               7 | 120 秒 |
|              8+ | 300 秒 |

レート制限の状態は SQLite に永続化されます。

ログインに成功すると、該当する失敗回数の状態がクリアされます。

認証の失敗が繰り返される場合は、レートリミッターを迂回するのではなく、原因を調査してください。

考えられる原因は次のとおりです。

* 誤った認証情報
* 古くなった保存済みの認証情報
* 誤った認証情報を使用している自動化されたクライアント
* 手動でのログイン試行の繰り返し
* 認証情報攻撃の可能性

---

## 18. クライアント管理

管理対象クライアントは、LUMS Agent を実行している Linux システムです。

クライアントは、LUMS に次のような情報を提供します。

* クライアント ID
* インストール済みソフトウェア
* 利用可能な更新
* パッケージ管理の結果
* 更新ジョブの結果
* 再起動の状態
* 運用ステータス

LUMS サーバーはクライアントの状態を保存し、Web インターフェースを通じて公開します。

実際のパッケージ管理操作は、クライアントがローカルで実行します。

---

## 19. クライアント認証

各管理対象クライアントは、クライアントトークンを使用して LUMS に認証します。

トークンは、管理対象クライアントの認証情報として機能します。

クライアントトークンは、パスワードと同じ注意を払って扱ってください。

次のことは絶対にしないでください。

* トークンを Git にコミットする
* トークンを公開ドキュメントに記載する
* トークンをスクリーンショットに含める
* トークンを課題トラッカーに貼り付ける
* トークンを診断出力に露出させる
* あるクライアントのトークンを別のクライアントと共有する

トークンは、発行された対象のクライアントにのみインストールしてください。

---

## 20. クライアント登録

新しいクライアントは、まず LUMS に登録する必要があります。

登録プロセスにより、サーバー側のクライアント ID と認証情報が確立されます。

登録後:

1. LUMS Agent をインストールする
2. クライアントトークンを設定する
3. LUMS サーバーのエンドポイントを設定する
4. TLS の信頼を確立する
5. 初回のエージェント実行を行う
6. クライアントが正常にレポートすることを確認する
7. クライアントが LUMS インターフェースに表示されることを確認する

Agent サービスが正常に起動しただけでは、クライアントが運用可能であるとは見なすべきではありません。

サーバーは、有効なクライアントレポートを受信して受け入れる必要があります。

---

## 21. クライアントステータス

クライアントビューは、さまざまな運用状態を区別するために使用してください。

例:

* クライアントは登録済みだがレポートしていない
* クライアントが正常にレポートしている
* クライアントが古い情報をレポートしている
* クライアントが無効化されている
* クライアント認証の失敗
* クライアント側のパッケージマネージャーの失敗

クライアントがレポートを停止した場合は、まず問題が次のどれであるかを判断してください。

1. ネットワーク接続
2. TLS の信頼
3. クライアント認証
4. Agent の実行
5. サーバーの可用性
6. サーバー側の処理

実際にどの層が失敗しているかを特定する前に、クライアントの認証情報を変更することは避けてください。

---

## 22. クライアントトークンのローテーション

必要に応じて、クライアントトークンをローテーションできます。

典型的な理由は次のとおりです。

* トークン露出の疑い
* 認証情報のローテーションポリシー
* 管理上のメンテナンス
* クライアント構成の置き換え
* セキュリティインシデント対応

トークンのローテーションにより、そのクライアントに対して受け入れられる認証情報が変わります。

ローテーション後:

1. 新しいクライアントトークンを取得する
2. クライアント構成を更新する
3. Agent を実行する
4. 認証が成功することを確認する
5. 結果として得られるクライアントレポートを確認する
6. 通常のレポートが再開されたことを確認する

新しい認証経路が検証されるまで、古いクライアント構成を削除しないでください。

---

## 23. クライアントの無効化

クライアントが LUMS の運用に参加すべきでなくなった場合、そのクライアントを無効化できます。

例:

* システムの廃止
* 一時的なメンテナンス
* クライアントの置き換え
* 認証情報の侵害の疑い

クライアントを無効化する前に、そのクライアントに関連付けられたアクティブな更新ジョブがないか確認してください。

無効化後:

* クライアントが運用可能なものとして扱われなくなったことを確認する
* 関連する更新ジョブの履歴を確認する
* 調査に必要な監査情報を保持する

クライアントが一時的にオフラインになったというだけの理由で、永続的なクライアントデータを削除しないでください。

---

## 24. クライアント管理チェックリスト

クライアントを追加または変更する際は、チェーン全体を確認してください。

```text
[ ] Client exists in LUMS
[ ] Client is enabled
[ ] Client token is valid
[ ] TLS trust is valid
[ ] LUMS Agent is installed
[ ] Agent configuration is valid
[ ] Initial report succeeds
[ ] Client appears in the Web UI
[ ] Installed software is reported
[ ] Available updates are reported
[ ] Update jobs can be tracked
[ ] Results are returned correctly
```

クライアントが運用可能となるのは、レポートと認証のチェーン全体が機能している場合のみです。

---

## 25. 管理原則

ユーザー管理とクライアント管理は、分離を保つ必要があります。

LUMS アプリケーションアカウントは、**個人が何を行ってよいか**を決定します。

クライアントトークンは、**どの管理対象システムが LUMS と通信してよいか**を決定します。

```text
Application User
      │
      └── Role / Permissions

Managed Client
      │
      └── Client Token / Identity
```

一方のメカニズムを他方の代わりに使用しないでください。

## 26. ソフトウェアインベントリ

LUMS は、管理対象クライアントが報告したソフトウェア情報を保持します。

ソフトウェアインベントリにより、管理者と Operator は、クライアントにどのパッケージがインストールされているかを確認できます。

インベントリは LUMS Agent によって収集され、サーバーに報告されます。

サーバーは、報告された情報をクライアントインターフェースを通じて利用可能にします。

インベントリは、クライアントが報告した状態のスナップショットとして扱う必要があります。

ネイティブのパッケージマネージャーを置き換えるものではありません。

---

## 27. インストール済みソフトウェア

**Installed Software** セクションには、選択したクライアントが報告したパッケージが表示されます。

Administrator と Operator は、ローカルのパッケージフィルターを使って、表示されるインベントリを絞り込めます。

インストール済みソフトウェアのフィルターは、ローカルのインターフェース機能です。

パッケージ管理の検索とは別のものです。

この区別は重要です。

```text
Installed Software
    │
    └── Filter already reported package inventory

Package Management
    │
    └── Search the client's package repositories
```

そのため、インストール済みのパッケージが、設定済みのリポジトリでもう利用できなくなっている場合、パッケージ管理の検索には表示されないことがあります。

---

## 28. 利用可能な更新

LUMS は、更新が利用可能なパッケージに関する情報も収集します。

利用可能な更新の情報は、管理対象クライアント上で、そのネイティブなパッケージ管理システムを使って生成されます。

報告された情報は、対応が必要なパッケージを特定するために使用できます。

更新ジョブを作成する前に、次を確認してください。

* クライアント ID
* パッケージ名
* 現在インストールされているバージョン
* 利用可能なバージョン
* パッケージのステータス
* クライアントが現在到達可能かどうか

利用可能なすべての更新をすぐにインストールすべきだと考えないでください。

実行前に、運用要件、メンテナンスウィンドウ、アプリケーションの依存関係、クライアントの状態を考慮する必要があります。

---

## 29. パッケージ管理

LUMS は、サポートされている Linux クライアント向けに、一元的なパッケージ管理操作を提供します。

現在のパッケージ管理アクションは次のとおりです。

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

操作は LUMS を通じて要求されますが、LUMS Agent によってローカルで実行されます。

Agent は、実際のパッケージ操作をネイティブのパッケージマネージャーに委任します。

```text
LUMS Web UI
      │
      ▼
LUMS API
      │
      ▼
Update Job
      │
      ▼
LUMS Agent
      │
      ├── APT / dpkg
      │
      └── pacman
```

そのため LUMS は、オペレーティングシステムのパッケージデータベースやパッケージ管理の実装から独立したままです。

---

## 30. パッケージ検索

**Package Management** インターフェースは、インストール済みソフトウェアのフィルターとは別のパッケージ検索を提供します。

この検索は、管理対象クライアントにパッケージ情報を要求します。

Debian 系システムでは、Agent は APT のパッケージ管理ツールを使用します。

Arch Linux では、Agent は `pacman` を使用します。

検索結果には次が含まれることがあります。

* パッケージ名
* パッケージのバージョン
* パッケージの説明
* 利用可能な場合はリポジトリ情報

パッケージ検索では何もインストールされません。

したがって、検索は読み取り専用の操作です。

---

## 31. パッケージのインストール

Administrator と Operator は、パッケージインストールジョブを作成できます。

通常のワークフローは次のとおりです。

1. 管理対象クライアントを選択する
2. **Package Management** を開く
3. 必要なパッケージを検索する
4. 結果を確認する
5. インストールアクションを選択する
6. ジョブを作成する
7. 実行を監視する
8. 結果を確認する
9. インストール済みソフトウェアを更新または再確認する

パッケージは、Agent がネイティブのパッケージマネージャーを使ってインストールします。

ジョブが正常に作成されても、インストールがすでに完了したことを意味しません。

最終的なジョブの結果を確認する必要があります。

---

## 32. パッケージの削除

パッケージの削除も、同じ制御されたジョブワークフローに従います。

パッケージを削除する前に、次を確認してください。

* 正しいクライアント
* 正しいパッケージ
* 意図した操作
* 他のソフトウェアがそのパッケージに依存していないか

実行後、結果のジョブステータスとクライアントが報告するソフトウェアの状態を確認してください。

LUMS は、パッケージマネージャーの依存関係の処理を迂回しません。

操作の解決は、引き続きネイティブのパッケージマネージャーが担当します。

---

## 33. パッケージの更新

更新が利用可能な場合、特定のパッケージを更新できます。

ワークフローは次のとおりです。

```text
Available Update
      │
      ▼
Review Package
      │
      ▼
Create UPDATE_PACKAGE Job
      │
      ▼
Agent Execution
      │
      ▼
Result Validation
```

LUMS は、対応する更新ジョブを作成する前に、パッケージ情報を検証します。

パッケージが更新可能として一覧にもう表示されていない場合、そのジョブ要求を有効な更新操作として扱うべきではありません。

これにより、古い更新情報が無条件に実行されることを防ぎます。

---

## 34. システムの更新

`UPDATE_SYSTEM` は、クライアントのネイティブなパッケージ管理メカニズムを使って、より広範なシステム更新を実行します。

この操作は複数のパッケージに影響するため、メンテナンス操作として扱う必要があります。

システム更新を開始する前に、次を確認してください。

* クライアントの可用性
* メンテナンスウィンドウ
* 現在実行中のジョブ
* パッケージマネージャーの状態
* 関連する場合は利用可能なディスク容量
* 再起動が必要になる可能性があるかどうか

更新後、次を確認してください。

* ジョブの結果
* クライアントレポート
* インストール済みソフトウェア
* 利用可能な更新
* 再起動の状態

---

## 35. 更新ジョブ

パッケージと更新に関するすべての変更操作は、LUMS の更新ジョブとして表現されます。

これにより、共通の実行および追跡モデルが提供されます。

典型的なジョブのライフサイクル:

```text
PENDING
   │
   ▼
RUNNING
   │
   ├──────────────► FAILED
   │
   ▼
SUCCESS
```

クライアントが利用できなくなった場合や実行が中断された場合、ジョブには追加の対応が必要になることもあります。

現在のクライアントビューのみに頼るのではなく、ジョブ履歴を権威ある運用記録として使用してください。

---

## 36. ジョブの作成

更新ジョブを作成する前に、意図した操作を慎重に確認してください。

確認項目:

* クライアント
* アクション
* パッケージ
* 該当する場合は対象バージョン
* 現在のパッケージ状態
* メンテナンス要件

サポートされているアクションは次のとおりです。

| アクション        | 目的                         |
| ----------------- | ---------------------------- |
| `INSTALL_PACKAGE` | パッケージをインストールする |
| `REMOVE_PACKAGE`  | パッケージを削除する         |
| `UPDATE_PACKAGE`  | 特定のパッケージを更新する   |
| `UPDATE_SYSTEM`   | システム全体の更新を実行する |

更新ジョブの作成は、**Administrator** と **Operator** のロールに制限されています。

Viewer は更新ジョブを作成できません。

---

## 37. ジョブの実行

作成後、ジョブは LUMS Agent によって処理されます。

Agent はジョブを受信し、要求された操作をローカルで実行します。

サーバーは、結果の状態を追跡します。

Agent は、HTTP リクエストの成功をパッケージ操作の成功の証明とは見なしません。

代わりに、実際のパッケージマネージャーの結果が LUMS に返されます。

この区別は重要です。

```text
API request accepted
        ≠
Package operation successful
```

したがって、最終的な実行結果は常に確認する必要があります。

---

## 38. ジョブの結果

完了したジョブには、明示的な結果が含まれている必要があります。

関連する結果は次のとおりです。

* 実行の成功
* 実行の失敗
* パッケージマネージャーのエラー
* 実行の中断
* 復旧に関連する状態
* 該当する場合は再起動に関連する状態

ジョブが失敗した場合、Administrator と Operator は、すぐに同じ操作を繰り返すのではなく、結果を確認する必要があります。

元の失敗を理解しないまま実行を繰り返すと、診断が難しくなることがあります。

---

## 39. ジョブ履歴

更新履歴は、過去の更新アクティビティの運用記録を提供します。

次のような疑問に答えるために使用します。

* このパッケージはすでに更新されたか？
* どのクライアントが操作を実行したか？
* ジョブはいつ作成されたか？
* 実行はいつ始まったか？
* 実行はいつ終了したか？
* 操作は成功したか？
* パッケージマネージャーはエラーを報告したか？

過去のジョブ情報は、繰り返される失敗や中断されたメンテナンス操作を調査する際に特に重要です。

---

## 40. 失敗したジョブ

ジョブが失敗した場合:

1. クライアントとジョブ ID を記録する
2. ジョブの結果を確認する
3. 失敗がサーバーで発生したのかクライアントで発生したのかを判断する
4. 関連する Agent ログを確認する
5. ネイティブのパッケージマネージャーの状態を確認する
6. 根本的な問題を修正する
7. 原因を理解した後にのみ再試行する

一般的な原因は次のとおりです。

* 利用できないリポジトリ
* パッケージマネージャーのロック
* ネットワークの問題
* 無効なパッケージ要求
* 依存関係の競合
* ディスク容量の不足
* 中断されたパッケージ操作
* クライアント認証または通信の問題

詳細な診断手順は、[`troubleshooting.md`](トラブルシューティング.md) に記載されています。

---

## 41. パッケージマネージャーのロック

APT と pacman は、パッケージ操作の同時実行を防ぐことがあります。

パッケージマネージャーがすでに使用中であるためにパッケージ管理操作が失敗した場合:

* アクティブなパッケージ管理プロセスを特定する
* どの操作が実行中かを判断する
* 必要に応じて、正当な操作が終了するまで待つ
* その後、LUMS の操作を再試行する

パッケージマネージャーの実行中に、パッケージマネージャーのロックファイルを**無闇に削除しないでください**。

ロックファイルを削除しても、根本的な同時操作の問題は解決せず、パッケージ管理の状態が損なわれる可能性があります。

---

## 42. アイドルを考慮した実行

LUMS は、更新ジョブを実行するかどうかを判断する際に、クライアントのアイドル情報を使用できます。

このメカニズムは、管理対象システムの対話的な利用を中断しないようにすることを目的としています。

アイドル検出は、クライアント上の Agent が行います。

アイドル情報が利用できない場合、Agent はアイドル状態を作り出すのではなく、その状況を報告する必要があります。

管理者は、次を区別する必要があります。

* クライアントがアイドル状態である
* クライアントがアクティブである
* アイドル検出が利用できない
* クライアントに到達できない

これらの状態は、運用上の意味がそれぞれ異なります。

---

## 43. 更新実行の監視

メンテナンス中は、次を監視してください。

* ジョブの状態
* クライアントの接続性
* Agent のアクティビティ
* パッケージマネージャーの結果
* 再起動の要否

ジョブが `RUNNING` のままであっても、パッケージマネージャーがまだ動作しているとは限りません。

実行が停止しているように見える場合は、別のジョブを作成する前に、クライアントと Agent の状態を調査してください。

---

## 44. 再起動の要件

一部のパッケージおよびシステムの更新では、再起動が必要になることがあります。

LUMS は、管理対象クライアントが報告する再起動関連の状態を追跡します。

システム更新後:

1. 報告された再起動の状態を確認する
2. 再起動が必要かどうかを判断する
3. 適切なメンテナンスウィンドウで再起動を実行する
4. Agent が再びレポートするのを待つ
5. クライアントが通常の動作に戻ったことを確認する

再起動の要件を、自動的に更新の失敗と解釈してはいけません。

---

## 45. 運用更新チェックリスト

日常的なパッケージメンテナンスの場合:

```text
[ ] Correct client selected
[ ] Client is reachable
[ ] Current software state reviewed
[ ] Available updates reviewed
[ ] Correct package/action selected
[ ] Maintenance requirements checked
[ ] Update job created
[ ] Job execution monitored
[ ] Job result verified
[ ] Installed software verified
[ ] Available updates rechecked
[ ] Reboot state checked
[ ] Job history reviewed if required
```

操作は、結果として得られたクライアントの状態が検証された後にのみ完了となります。

---

## 46. パッケージ管理の原則

LUMS は、一元的なオーケストレーションと可視性を提供します。

実際のパッケージ管理は、引き続き管理対象のオペレーティングシステムが担当します。

したがって:

> **LUMS は操作を要求して追跡し、ネイティブのパッケージマネージャーがそれを実行する。**

この分離により、LUMS は各オペレーティングシステムのパッケージ管理のセマンティクスを維持したまま、さまざまな Linux システムを管理できます。

## 47. ジョブの復旧

LUMS は、すでに正常に完了した操作を無闇に繰り返すことなく、中断された更新ジョブを処理するよう設計されています。

更新の実行では、進行状況を追跡するためにチェックポイント情報を使用します。

これは特に次の場合に重要です。

* Agent が中断された
* クライアントが再起動した
* サーバーが再起動された
* ネットワーク通信が一時的に利用できない
* 結果が報告される前にパッケージ操作が完了した

復旧メカニズムは、記録されたジョブの状態を使用して、まだ実行する必要がある作業を判断します。

---

## 48. パッケージ単位のチェックポイント

複数のパッケージ操作を含むジョブは、個別に処理されます。

パッケージ操作が成功すると、Agent が次の操作に進む前にそれが記録されます。

概念的には次のとおりです。

```text
Job
 │
 ├── Package A → SUCCESS
 │
 ├── Package B → SUCCESS
 │
 ├── Package C → interrupted
 │
 └── Package D → PENDING
```

復旧後、すでに完了したパッケージ操作を不必要に再実行すべきではありません。

その後、残りの作業は記録された状態から続行できます。

これにより、中断後にパッケージ操作が繰り返されるリスクが減ります。

---

## 49. 中断されたジョブ

更新ジョブが中断された場合は、すぐに代替のジョブを作成しないでください。

まず、次を判断してください。

1. どのジョブが中断されたか
2. どのパッケージ操作がアクティブだったか
3. どのパッケージ操作がすでに成功したか
4. パッケージマネージャーが操作を完了したか
5. Agent がジョブを自動的に復旧したか
6. クライアントが再起動を必要としているか

手動で介入する前に、既存のジョブ履歴と Agent ログを確認する必要があります。

---

## 50. Agent の復旧

Agent は、中断後に復旧可能な作業を継続する責任を負います。

復旧では、可能な限り成功したパッケージの結果を保持する必要があります。

パッケージ操作がすでに成功として記録されている場合、復旧でその同じ操作を無闇に再実行してはいけません。

復旧が操作の状態を安全に判断できない場合、その状況は運用上の問題として扱い、調査する必要があります。

ジョブを完了したように見せるためだけに、データベース内のジョブの状態を手動で変更しないでください。

---

## 51. ジョブ中のサーバー再起動

LUMS サーバーの再起動は、必ずしもクライアント側のパッケージ操作が中断されたことを意味しません。

サーバーとクライアントは、別々の実行状態を持ちます。

サーバーの再起動後:

1. LUMS コンテナーが実行中であることを確認する
2. データベースが利用可能であることを確認する
3. クライアントが LUMS と通信できることを確認する
4. 影響を受けた更新ジョブを確認する
5. Agent のレポートを確認する
6. 最終的なパッケージの状態を確認する

クライアント側の実行結果が、パッケージ操作に関する重要な真実の情報源であり続けます。

---

## 52. ジョブ中のクライアント再起動

クライアントの再起動は、Agent の実行を中断することも、更新自体が再起動を必要とするために発生することもあります。

これらの状況は区別する必要があります。

### 想定された再起動

更新が完了し、システムの再起動が必要です。

### 想定外の中断

操作が完了する前、または結果を報告できる前にシステムが再起動しました。

クライアントが復帰した後:

1. Agent が通常どおり起動するのを待つ
2. LUMS との通信を確認する
3. 影響を受けたジョブを確認する
4. パッケージの状態を確認する
5. 再起動のステータスを確認する
6. 該当する場合は、復旧が続行されるのを待つ

---

## 53. 再起動の検出

LUMS は、管理対象クライアントが報告する再起動の要件を追跡できます。

再起動の検出は、マシンが現在到達可能かどうかの検出とは別のものです。

これらは別々の状態です。

```text
Client reachable
        │
        ├── reboot not required
        │
        └── reboot required

Client unreachable
        │
        └── current state cannot be confirmed
```

したがって管理者は、到達できないクライアントを、再起動が必要であることの証拠として扱わないようにする必要があります。

---

## 54. 再起動後の検証

必要な再起動の後:

1. オペレーティングシステムが利用可能になるまで待つ
2. Agent のサービスまたはタイマーを確認する
3. クライアント認証を確認する
4. クライアントレポートを確認する
5. 影響を受けた更新ジョブを確認する
6. インストール済みのパッケージバージョンを確認する
7. 利用可能な更新を確認する
8. 別の再起動が必要かどうかを確認する

再起動は、クライアントが再び正常にレポートした後にのみ、運用上完了したと見なすべきです。

---

## 55. 更新ジョブの監視

Administrator と Operator は、計画されたメンテナンス中にジョブを監視する必要があります。

重要な状態は次のとおりです。

| 状態      | 意味                                     |
| --------- | ---------------------------------------- |
| `PENDING` | ジョブは存在するが、実行は開始されていない |
| `RUNNING` | ジョブの実行が進行中                     |
| `SUCCESS` | 実行が正常に完了した                     |
| `FAILED`  | 実行がエラーで完了した                   |

ジョブの状態は、常にその結果情報とあわせて解釈する必要があります。

たとえば `FAILED` のジョブは、単に再試行するのではなく、記録された結果を使って調査する必要があります。

---

## 56. 実行ウォッチャー

LUMS Agent には、専用の実行ウォッチャーが含まれています。

ウォッチャーは、クライアント上での更新ジョブの実行を監視する役割を担います。

その目的は、レポートのワークフローとは独立して、信頼性の高い実行処理をサポートすることです。

現在のウォッチャーのバージョンは次のとおりです。

**Watcher 1.2.1**

Agent のバージョンは次のとおりです。

**Agent 1.7.0**

これらのバージョンは、クライアントのアップグレード後に確認する必要があります。

---

## 57. ウォッチャーの監視

管理者は、管理対象クライアント上の systemd を通じてウォッチャーを確認できます。

有用な確認方法は次のとおりです。

```bash
systemctl status lums-agent-watcher.service --no-pager
```

および:

```bash
journalctl -u lums-agent-watcher.service --no-pager -n 100
```

タイマーは次のコマンドで確認できます。

```bash
systemctl status lums-agent-watcher.timer --no-pager
```

oneshot サービスの正確な active/inactive 状態は、そのタイマーおよびジャーナルとあわせて解釈する必要があります。

oneshot サービスでは、`inactive (dead)` 状態は自動的にエラーであるとは限りません。

---

## 58. レポートと実行のタイマー

LUMS は、定期的なクライアントのレポートと実行の監視を分離しています。

レポートタイマーは、Agent の定期実行を担当します。

ウォッチャータイマーは、ウォッチャーの定期実行を担当します。

クライアント側のスケジューリングの問題を診断する際は、両方を確認してください。

```bash
systemctl list-timers --all | grep lums-agent
```

想定されるユニットは次のとおりです。

```text
lums-agent.timer
lums-agent-watcher.timer
```

タイマーが実行されていない場合は、次を確認します。

```bash
systemctl status lums-agent.timer --no-pager
systemctl status lums-agent-watcher.timer --no-pager
```

その後、対応するジャーナルのエントリを確認します。

---

## 59. 監査ログ

LUMS は、重要な管理操作およびセキュリティ関連のアプリケーションアクションを監査ログに記録します。

監査情報は、次を確認するのに役立ちます。

* どの操作が行われたか
* どのユーザーが開始したか
* どのクライアントが影響を受けたか
* 操作がいつ行われたか
* 操作が受け入れられたかどうか
* どの管理アクションが実行されたか

監査情報は、運用上の証拠として扱う必要があります。

不用意に削除または変更してはいけません。

---

## 60. 管理監査イベント

関連する管理アクティビティには、次のような操作が含まれます。

* ユーザーの作成
* ロールの割り当て
* クライアント管理
* トークンのローテーション
* 更新ジョブの作成
* パッケージ管理操作
* 認証関連のセキュリティイベント

正確なイベントデータは、操作によって異なります。

予期しないアクティビティを調査する際は、管理者は監査情報をジョブ履歴とあわせて使用する必要があります。

---

## 61. 監査ログの取り扱い

監査ログは、慎重に取り扱う必要があります。

次のことをしてはいけません。

* 操作を隠すために過去の監査エントリを変更する
* エクスポートしたログで機密性の高い認証情報を露出させる
* クライアントトークンを含むログを公開する
* パスワードや認証素材を公開する
* 機密性の高いログ出力を公開の課題トラッカーにコピーする

トラブルシューティングのためにログを共有する必要がある場合は、先に認証情報とその他の機密情報を伏せてください。

---

## 62. アプリケーションログ

アプリケーションログは、LUMS サーバーの内部動作を記述します。

有用な情報源は次のとおりです。

```bash
sudo docker logs --tail 100 lums
```

ライブ監視する場合:

```bash
sudo docker logs -f lums
```

問題を調査する際は、可能な限り時間範囲を絞り込んでください。

より小さな関連部分で足りる場合に、本番ログ全体を自動的にダンプしないでください。

---

## 63. Agent ログ

クライアント側の Agent のアクティビティは、systemd を通じて確認できます。

```bash
journalctl -u lums-agent.service --no-pager -n 100
```

ウォッチャーのアクティビティの場合:

```bash
journalctl -u lums-agent-watcher.service --no-pager -n 100
```

特定の時間範囲では、systemd ジャーナルのフィルタリングを使用できます。

例:

```bash
journalctl -u lums-agent.service \
    --since "30 minutes ago" \
    --no-pager
```

可能な限り、ログは影響を受けたジョブ ID と関連付けてください。

---

## 64. ログの相関

更新の問題を調査する際は、システム全体で情報を相関させてください。

```text id="jv3j7c"
Web UI
  │
  ├── Job ID
  │
  ▼
LUMS API / Application Log
  │
  ▼
Update Job
  │
  ▼
Agent
  │
  ▼
Native Package Manager
```

これにより、ある層で観察された問題が、その同じ層で発生したと思い込むという、よくある間違いを防げます。

---

## 65. 管理監視チェックリスト

通常の運用中は、定期的に次を確認してください。

```text
[ ] LUMS container is running
[ ] HTTPS endpoint is available
[ ] Database is accessible
[ ] Clients are reporting
[ ] No unexpected failed jobs
[ ] No unexplained authentication failures
[ ] Agent timers are active
[ ] Watcher timers are active
[ ] Package-manager operations complete normally
[ ] Audit activity is available
[ ] Logs contain no unexplained recurring errors
```

これらの確認の頻度は、LUMS デプロイメントの運用上の重要度に合わせる必要があります。

---

## 66. 復旧の原則

更新の問題が発生した場合、最も安全な管理上の対処法は次のとおりです。

```text
Observe
   │
   ▼
Identify affected job/client
   │
   ▼
Inspect state and logs
   │
   ▼
Determine actual failure point
   │
   ▼
Correct underlying problem
   │
   ▼
Allow recovery or retry
   │
   ▼
Verify final state
   │
   ▼
Document significant incidents
```

実際の失敗の状態を理解するまでは、破壊的な復旧アクションを避けてください。

特に、見た目を整えるためだけに、ジョブ、データベースレコード、パッケージマネージャーのロック、永続的なクライアントデータを手動で削除しないでください。

> **まず証拠を保全する。次に状態を修復する。最後に結果を検証する。**

## 67. データベース管理

LUMS は、アプリケーションデータベースとして SQLite を使用します。

本番データベースは、永続的な Docker ボリューム内に保存されます。

```text
/var/lib/lums/lums.db
```

Docker ボリュームが保持されている限り、データベースはコンテナーの置き換え後も永続します。

データベースには、次のようなアプリケーションの状態が含まれます。

* ユーザー
* 管理対象クライアント
* 更新ジョブ
* パッケージ情報
* 監査情報
* 認証関連の状態
* マイグレーションの状態

管理者は、データベースを重要なアプリケーションデータとして扱う必要があります。

---

## 68. SQLite のランタイム構成

現在の本番 SQLite のベースラインは次のとおりです。

| 設定           | 値                         |
| -------------- | -------------------------- |
| `journal_mode` | `wal`                      |
| `busy_timeout` | `5000`                     |
| `synchronous`  | `2`                        |
| `foreign_keys` | アプリケーションによって有効化 |

アプリケーションは、データベース接続に対して SQLite の外部キー制約の強制を明示的に有効にします。

管理者は、これらの設定を不用意に変更してはいけません。

データベースのランタイム構成への変更は、本番に導入する前にテストする必要があります。

---

## 69. データベースの整合性

データベース破損の兆候や、予期しないアプリケーション動作がある場合は、データベースの整合性を確認する必要があります。

典型的な SQLite の整合性チェックは次のとおりです。

```bash id="f0g8sl"
sudo docker exec lums \
    sqlite3 /var/lib/lums/lums.db \
    "PRAGMA integrity_check;"
```

正常なデータベースでは、次が返されます。

```text
ok
```

整合性チェックでエラーが報告された場合は、アプリケーションの状態を無闇に変更し続けないでください。

影響を受けたデータベースを保全し、原因を調査してください。

---

## 70. データベースマイグレーション

LUMS は、アプリケーションのマイグレーションを使用してデータベースの変更を導入します。

マイグレーションは、アプリケーションの通常の起動およびマイグレーションの仕組みを通じて実行させる必要があります。

管理者は、エラーを回避するためだけにマイグレーションの状態を手動で変更してはいけません。

アプリケーションの更新後、次を確認してください。

1. コンテナーが正常に起動する
2. マイグレーションが完了する
3. アプリケーションに到達できる
4. 既存のユーザーが引き続き利用できる
5. 既存のクライアントが引き続き利用できる
6. 既存のジョブ履歴が引き続き利用できる

---

## 71. 永続的な Docker ボリューム

LUMS のアプリケーションデータを含む Docker ボリュームは、重要な永続リソースです。

本番ボリュームは次のとおりです。

```text
lums-data
```

次のコマンドで確認します。

```bash id="f3z2kd"
sudo docker volume inspect lums-data
```

LUMS コンテナーを置き換える際は、ボリュームをアタッチしたままにする必要があります。

コンテナーを削除しても、ボリュームは自動的には削除**されません**。

ただし、ボリュームを削除すると、別途バックアップが存在しない限り、永続的なアプリケーションデータが完全に削除されます。

---

## 72. コンテナー管理

LUMS アプリケーションは、堅牢化された Docker コンテナー内で実行されます。

本番のセキュリティベースラインには、次が含まれます。

* 非 root のアプリケーションユーザー
* 読み取り専用のルートファイルシステム
* 削除された Linux ケーパビリティ
* `no-new-privileges`
* 制限された一時ファイルシステム
* 読み取り専用のシークレットマウント
* 専用の永続データボリューム
* localhost のみのアプリケーションポート

トラブルシューティングが便利になるというだけの理由で、より弱いセキュリティ設定でコンテナーを起動してはいけません。

---

## 73. コンテナーのステータス

現在のコンテナーの状態は、次で確認します。

```bash id="4n6p2v"
sudo docker ps --filter name=lums
```

完全なランタイム構成は、次で確認します。

```bash id="k1q4z8"
sudo docker inspect lums
```

重要なプロパティは次のとおりです。

* 実行状態
* 再起動ポリシー
* ユーザー
* 読み取り専用のルートファイルシステム
* ケーパビリティ
* セキュリティオプション
* ポートバインディング
* ボリュームマウント

---

## 74. コンテナーのセキュリティ検証

堅牢化されたランタイムは、想定されるプロパティを引き続き提供している必要があります。

例:

```bash id="0u7x3n"
sudo docker inspect lums \
    --format '{{.Config.User}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.Privileged}}'
```

想定されるベースラインは、次と同等です。

```text
lums true false
```

ケーパビリティは削除されたままである必要があります。

```bash id="k5n8ae"
sudo docker inspect lums \
    --format '{{json .HostConfig.CapDrop}}'
```

想定される出力:

```text
["ALL"]
```

セキュリティオプションには、次が含まれている必要があります。

```text
no-new-privileges:true
```

## 75. アプリケーションポート

LUMS アプリケーションは、ホスト上でループバックインターフェースを通じてリッスンします。

想定されるマッピングは次のとおりです。

```text
127.0.0.1:5050 → container:5000
```

次のコマンドで確認します。

```bash id="b6v2w0"
sudo docker port lums
```

アプリケーションポートを LAN に直接公開してはいけません。

外部アクセスは、HTTPS 経由の Nginx を通じて提供されます。

---

## 76. Nginx と HTTPS

Nginx は、LUMS の外部 HTTPS エントリポイントを提供します。

通常のリクエストの経路は次のとおりです。

```text
Client Browser
      │
      ▼
HTTPS :443
      │
      ▼
Nginx
      │
      ▼
127.0.0.1:5050
      │
      ▼
LUMS Container
```

Docker のアプリケーションポートは、localhost にバインドされたままにする必要があります。

したがって管理者は、ファイアウォールや Docker の構成を通じてポート `5050` を直接公開しないようにしてください。

---

## 77. HTTPS の検証

Nginx を変更した後は、リロードする前に必ず構成を検証してください。

```bash id="7f1h9m"
sudo nginx -t
```

構成が有効な場合:

```bash id="4g5s2w"
sudo systemctl reload nginx
```

次に、HTTPS を確認します。

```bash id="2w8v6c"
curl -I https://LUMS-SERVER/
```

`LUMS-SERVER` は、サーバーの TLS 証明書でカバーされているホスト名に置き換えてください。
日常的な検証には `-k` を使用しないでください。証明書の検証がスキップされます。

HTTPS のレスポンスが成功すれば、Nginx が LUMS アプリケーションに到達できることが確認できます。

証明書の検証は、管理者が通常使用するホスト名またはアドレスでもテストする必要があります。

`-k` で証明書の検証を恒久的に無効にしてはいけません。

---

## 78. HTTP リダイレクト

HTTP エンドポイントは、クライアントを HTTPS にリダイレクトする必要があります。

確認:

```bash id="w5q0rx"
curl -I http://127.0.0.1/
```

想定される動作は、HTTPS エンドポイントへの HTTP リダイレクトです。

管理アクセスには HTTPS を使用してください。

---

## 79. TLS 証明書のメンテナンス

TLS 証明書と秘密鍵は、Docker イメージの外部にあります。

典型的な場所は次のとおりです。

```text
/etc/lums/tls/lums.crt
/etc/lums/tls/lums.key
```

秘密鍵は、保護されたままにする必要があります。

証明書を置き換える前に:

1. 新しい証明書を検証する
2. 対応する秘密鍵を検証する
3. ファイル権限を確認する
4. Nginx の構成を検証する
5. Nginx をリロードする
6. HTTPS を確認する
7. アプリケーションへのログインを確認する

TLS の秘密鍵を、Git リポジトリや Docker イメージに配置してはいけません。

---

## 80. シークレット管理

アプリケーションのシークレットは、コンテナーイメージの外部に保存されます。

本番のシークレットは、読み取り専用でコンテナーにマウントされます。

```text
/etc/lums/secrets/lums_secret
        │
        ▼
/run/secrets/lums_secret
```

アプリケーションは、次を通じてシークレットを受け取ります。

```text
LUMS_SECRET_KEY_FILE
```

管理者は、次のことを絶対にしてはいけません。

* シークレットをコミットする
* シークレットを出力する
* シークレットをドキュメントに含める
* スクリーンショットで露出させる
* イメージレイヤーに配置する

シークレットが露出した疑いがある場合は、侵害されたものとして扱い、適切なシークレットのローテーション手順に従ってください。

---

## 81. バックアップ戦略

LUMS のデータは、重要な管理上の変更の前にバックアップする必要があります。

最低限、次の保護を検討してください。

* SQLite のアプリケーションデータ
* アプリケーション構成
* TLS 素材
* アプリケーションのシークレット
* クライアント構成情報
* 関連する運用ドキュメント

バックアップは、本番コンテナーおよびその永続 Docker ボリュームとは別に保管する必要があります。

同じホストまたは Docker ボリューム内にしか存在しないバックアップでは、そのホストやボリュームの喪失に対する十分な保護になりません。

---

## 82. データベースバックアップ

SQLite データベースは、変更が行われているデータベースファイルをその状態を考慮せずに単にコピーするのではなく、SQLite を考慮した方法でバックアップする必要があります。

バックアップを実行する前に:

1. 本番データベースを特定する
2. バックアップ先が利用可能であることを確認する
3. 適切な SQLite 安全な方法でバックアップを作成する
4. バックアップが存在することを確認する
5. 作成日時を記録する

ファイルのコピーが成功したからといって、有効で復元可能なデータベースバックアップが存在するとは限りません。

---

## 83. バックアップの検証

バックアップは、テストされるまで信頼できるとは見なされません。

バックアップについて、次を定期的に確認してください。

* 読み取れる
* SQLite データとして開ける
* 整合性をチェックできる
* 分離されたテスト環境に復元できる

たとえば、展開したテスト用コピーは次のコマンドで確認できます。

```bash id="p3v7cx"
sqlite3 /path/to/test-copy.db \
    "PRAGMA integrity_check;"
```

想定される結果:

```text
ok
```

本番バックアップのテストを、稼働中の本番データベースを上書きして行ってはいけません。

---

## 84. 復元の原則

復元は、制御された管理操作です。

復元する前に:

1. 正しいバックアップを特定する
2. その整合性を検証する
3. 必要な復旧ポイントを決定する
4. 必要に応じてアプリケーションのアクティビティを停止または分離する
5. 現在の本番状態を保全する
6. バックアップを復元する
7. データベースの整合性を検証する
8. アプリケーションを起動する
9. マイグレーションを検証する
10. ユーザーとクライアントを検証する
11. ジョブ履歴を検証する
12. 通常のクライアントレポートを検証する

復旧中に、本番データベースの唯一のコピーを上書きしてはいけません。

---

## 85. 復元の検証

復元後は、最低限、次を確認してください。

```text id="q6r2yh"
[ ] Container starts
[ ] Database opens
[ ] SQLite integrity check passes
[ ] Users are present
[ ] Roles are correct
[ ] Clients are present
[ ] Client authentication works
[ ] Job history is present
[ ] Audit information is available
[ ] HTTPS works
[ ] Clients can report
[ ] New operations can be created
```

復元は、アプリケーションとその管理対象クライアントが検証された後にのみ完了となります。

---

## 86. サーバーバックアップの原則

永続的な LUMS データに関する最も重要な管理上のルールは次のとおりです。

> **検証済みの復旧経路なしに、破壊的なデータベース操作やボリューム操作を決して行わない。**

特に、コンテナーを再構築または置き換えるというだけの理由で `lums-data` を削除してはいけません。

コンテナーの置き換えと永続データの削除は、別々の操作です。

---

## 87. サーバー管理チェックリスト

重要なサーバー側の変更を行う前に:

```text id="7h3m0p"
[ ] Current container state recorded
[ ] Current image recorded
[ ] Database backup available
[ ] Backup integrity verified
[ ] Active jobs reviewed
[ ] Client reporting state reviewed
[ ] Configuration changes documented
[ ] TLS material available
[ ] Secret handling verified
[ ] Rollback path known
```

これらの条件を検討した後にのみ、重要な本番変更を進めるべきです。

---

## 88. サーバー管理の原則

LUMS は、アプリケーションの状態を、使い捨てのアプリケーションコンテナーから分離しています。

```text
Disposable
└── LUMS Container

Persistent
├── SQLite Database
└── lums-data Volume

External
├── TLS Material
└── Application Secret
```

この分離により、永続的なアプリケーションデータを意図せず破壊することなく、アプリケーションコンテナーを置き換えられます。

> **必要な場合はアプリケーションを置き換える。データの削除が明示的に意図されていない限り、データは保持する。**

## 89. 定期メンテナンス

定期メンテナンスは、LUMS のインストールの信頼性を保ち、予期しない運用上の問題のリスクを減らします。

典型的なメンテナンス活動には、次が含まれます。

* 失敗した更新ジョブの確認
* クライアントのレポートの確認
* アプリケーションログの確認
* 監査アクティビティの確認
* バックアップの検証
* 利用可能なディスク容量の確認
* Docker コンテナーの状態の確認
* TLS 証明書の有効性の確認
* セキュリティ更新の確認
* 現在の LUMS のバージョンとイメージの確認

変更が本番クライアントに影響し得る場合、メンテナンスは適切なメンテナンスウィンドウに実施する必要があります。

---

## 90. 変更前のメンテナンス

LUMS サーバーに影響し得るメンテナンスを行う前に:

1. アクティブな更新ジョブを確認する
2. クライアントが予期しないメンテナンス中でないことを確認する
3. 現在のバックアップを作成または検証する
4. 現在のコンテナーとイメージの状態を記録する
5. 計画した変更を文書化する
6. ロールバックの経路が存在することを確認する

本番コンポーネントをすぐに停止または削除することから、メンテナンスを始めてはいけません。

まず、現在の状態を確認してください。

---

## 91. Docker イメージのメンテナンス

LUMS アプリケーションのイメージは、レビュー済みのソースツリーから再ビルドする必要があります。
ホストのアップデーターは現在、リポジトリとデプロイメントのチェックのみを提供します。
本番コンテナーの置き換えは、データベースのバックアップ、マイグレーションの安全性、復元／ロールバックが
実装され、実際のデプロイメント構成に対してテストされるまで、意図的に無効化されています。

通常のアカウントで、チェックアウトからリポジトリの最新性チェックを実行します。

```bash
bash scripts/update-lums.sh --check-repository
```

これは `origin/main` をフェッチし、そのコミットをローカルの `HEAD` と比較します。
チェックアウトの更新、イメージのビルド、稼働中のサービスの変更は行いません。

デプロイメントチェックは、次で実行できます。

```bash
bash scripts/update-lums.sh --check
```

これはクリーンなチェックアウトを必要とし、現在のコンテナー構成を検証します。
ボリューム、マウント、セキュリティ設定が文書化されたフィクスチャと異なるデプロイメントは、拒否されることがあります。
チェックが成功しても、データベースの復元やロールバックが機能することの証明にはなりません。

`--check` または `--check-repository` を指定しない場合でも、アップデーターは本番コンテナーの置き換えを拒否します。
本番環境固有のバックアップ、マイグレーション、ロールバックの手順が実装され、分離された環境で検証されるまで、
このアップデーターを使って稼働中のコンテナーを停止または置き換えてはいけません。

アップデーターは、完全なテストスイートを実行しません。プロジェクトの仮想環境を持つチェックアウトで、
関連するテストを次のコマンドで実行します。

```bash
.venv/bin/python -m pytest -q tests/test_database_backup.py tests/test_update_lums.py
```

テスト結果を理解した場合にのみ、先に進んでください。テストスイートが成功しても、実際の本番データベースに対する
検証済みのバックアップと復元のテストの代わりにはなりません。

---

```bash id="h6s2we"
sudo docker image inspect lums:new
```

デプロイする前に、イメージの構成を確認してください。

適切な場合は、次を確認します。

* イメージのダイジェスト
* ベースイメージ
* アプリケーションファイル
* インストールされた依存関係
* イメージのサイズ
* 公開されているポート
* 設定されたユーザー

イメージは、ビルドとテストの結果をレビューした後にのみデプロイする必要があります。

## 93. 制御されたコンテナーの置き換え

コンテナーの置き換えは、慎重に行う必要があります。

本番コンテナーを置き換える前に:

```text id="m3z8qk"
[ ] Tests passed
[ ] New image exists
[ ] Database backup available
[ ] Active jobs reviewed
[ ] Current image recorded
[ ] Persistent volume confirmed
[ ] Secret available
[ ] TLS configuration available
[ ] Rollback image identified
```

例を実行する前に、実際に稼働中のコンテナーと比較してください。以下の値は例であり、
すべてのインストールで安全なコマンドではありません。特に、`:` の左側にある Docker バインドマウントの
ソースパスはホストと一致する必要があり、古いコンテナーの名前が異なる場合があります。

環境変数の値を出力せずに、イメージ、マウント、公開ポート、再起動ポリシー、堅牢化設定を表示します。

```bash
sudo docker inspect lums --format 'Image={{.Config.Image}}
Mounts={{json .Mounts}}
Ports={{json .HostConfig.PortBindings}}
Restart={{json .HostConfig.RestartPolicy}}
Readonly={{.HostConfig.ReadonlyRootfs}}
CapDrop={{json .HostConfig.CapDrop}}
SecurityOpt={{json .HostConfig.SecurityOpt}}
Tmpfs={{json .HostConfig.Tmpfs}}'
```

出力は非公開の場所に保存し、新しいコンテナーが、同じデータベースボリューム、シークレットファイル、
バックアップディレクトリ、ローカルのみのポートバインディング、セキュリティオプションを維持していることの
確認に使用してください。シークレットの内容や環境変数の値を、メモやメッセージに貼り付けないでください。

これらの条件を検討した後にのみ、既存のコンテナーを停止してください。

本番コンテナーは、堅牢化されたランタイム構成を維持する必要があります。

例:

```bash id="n8q2kf"
sudo docker stop lums
sudo docker rename lums lums-before-upgrade
```

次に、確立された堅牢化構成で新しいイメージを起動します。

```bash id="c7w4md"
sudo docker run -d \
    --name lums \
    --restart unless-stopped \
    --read-only \
    --cap-drop=ALL \
    --security-opt=no-new-privileges:true \
    --tmpfs /tmp:rw,noexec,nosuid,size=64m \
    --tmpfs /run:rw,noexec,nosuid,size=16m \
    -p 127.0.0.1:5050:5000 \
    -v /etc/lums/secrets/lums_secret:/run/secrets/lums_secret:ro \
    -v lums-data:/var/lib/lums \
    -v /var/backups/lums:/var/backups/lums \
    -e LUMS_SECRET_KEY_FILE=/run/secrets/lums_secret \
    -e LUMS_BACKUP_DIR=/var/backups/lums \
    lums:new
```

新しいデプロイメントが検証されるまで、`lums-before-upgrade` を削除しないでください。

## 94. アップグレード後の検証

コンテナーを置き換えた直後に、次を確認します。

```bash id="b4m7tz"
sudo docker ps --filter name=lums
```

次に、ログを確認します。

```bash id="v5n2ra"
sudo docker logs --tail 100 lums
```

HTTPS を確認します。

```bash id="w9x1kf"
curl -I https://LUMS-SERVER/
```

`LUMS-SERVER` は、サーバーの TLS 証明書でカバーされているホスト名に置き換えてください。
日常的な検証には `-k` を使用しないでください。証明書の検証がスキップされます。

次に、通常の管理インターフェースでアプリケーションを確認します。

既存のユーザー、クライアント、最近の履歴がまだ存在することを確認してください。
起動やマイグレーションのエラーがないか、ログを確認してください。コンテナーが実行中であるというだけでは、
アプリケーションやそのデータベースが正常であることの証明にはなりません。

### 新しいコンテナーが動作しない場合はロールバックする

新しいバージョンが検証に合格するまで、古いコンテナーを保持してください。新しいコンテナーが使用できず、
古いコンテナーの名前が `lums-before-upgrade` であることを確認済みの場合は、**新しいコンテナーのみ**を停止して削除し、
その後、古いコンテナーの名前を戻して再起動します。

```bash
sudo docker stop lums
sudo docker rm lums
sudo docker rename lums-before-upgrade lums
sudo docker start lums
```

`-v` なしの `docker rm lums` は、コンテナーを削除するだけで、`lums-data` ボリュームは削除しません。
このロールバックのコマンドに `-v` を絶対に追加しないでください。コンテナー名が異なる場合や、
どちらが古いコンテナーでどちらが新しいコンテナーか確実でない場合は、これらのコマンドを実行せず、
現在の状態を確認するか、管理者に助けを求めてください。ロールバック後は、ログを確認し、
Web インターフェースとデータが利用可能であることを確認してください。

## 95. アップグレード後の永続データ

コンテナーの置き換えで、永続的な Docker ボリュームが削除されてはいけません。

確認:


次が、

```text id="m7z3kc"
/var/lib/lums
```

* ユーザーがまだ存在する
* ロールが正しいままである
* クライアントが登録されたままである
* ジョブ履歴が引き続き利用できる
* 監査情報が引き続き利用できる
* マイグレーションが正常に完了した

## 96. アップグレード後のセキュリティベースライン

新しいイメージをデプロイした後、堅牢化されたランタイムを再度確認します。

確認:

```bash id="q6c3xv"
sudo docker inspect lums \
    --format '{{.Config.User}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.Privileged}}'
```

想定されるベースライン:

```text id="s0r8jm"
lums true false
```

次も確認します。

```text id="g4m2vx"
CapDrop = ALL
SecurityOpt = no-new-privileges:true
```

また、次が、

```text id="c3p9rw"
127.0.0.1:5050 → container:5000
```

アプリケーションの公開状態のままであることも確認します。

アプリケーションのアップグレードが成功しても、セキュリティベースラインが気づかないうちに弱められてはいけません。

---

## 97. アップグレード後のクライアント通信

サーバーのアップグレード後、管理対象クライアントが引き続き通信できることを確認します。

まず、少なくとも 1 台の代表的なクライアントを確認してください。

確認:

```text id="x8h5qk"
[ ] Client authentication succeeds
[ ] Client report is accepted
[ ] Installed software is available
[ ] Available updates are available
[ ] Update jobs can be created
[ ] Agent results are accepted
```

複数のクライアントプラットフォームをデプロイしている場合は、サポートされている各プラットフォームの代表的なシステムを確認してください。

---

## 98. アップグレード後の更新実行

LUMS サーバーを置き換えた直後に、大規模な本番更新を実行しないでください。

まず、制御された機能テストを行ってください。

適切なテストでは、経路全体を検証する必要があります。

```text id="y7k2fd"
Web UI
  ↓
API
  ↓
Update Job
  ↓
Agent
  ↓
Package Manager
  ↓
Result
  ↓
Database
  ↓
Web UI
```

制御されたテストが成功した後にのみ、通常のメンテナンス操作を再開してください。

---

## 99. ロールバック

新しいイメージが予期しない本番の問題を引き起こした場合、ロールバックできる必要があります。

次を保全してください。

* 以前の正常に動作していたイメージ
* 永続データ
* データベースバックアップ
* 以前の構成
* 以前の TLS 素材
* 関連するログ

新しいコンテナーが使用できない場合:

1. 新しいコンテナーを停止する
2. 可能であれば、調査用にそれを保全する
3. それ以上の管理上の変更を止める
4. 以前に正常と確認されていたイメージを復元する
5. 既存の永続ボリュームを再利用する
6. 堅牢化されたランタイムを起動する
7. アプリケーションを検証する
8. クライアントを検証する
9. ジョブの状態を検証する
10. 失敗したイメージを別途調査する

通常のロールバックの一環として、永続ボリュームを削除してはいけません。

---

## 100. ロールバックの検証

ロールバック後、次を確認します。

```text id="z1j8md"
[ ] LUMS starts
[ ] HTTPS works
[ ] Users can authenticate
[ ] Roles are correct
[ ] Clients are present
[ ] Client authentication works
[ ] Job history is available
[ ] Audit information is available
[ ] Package inventory is available
[ ] Update jobs can be tracked
[ ] Security baseline is intact
```

ロールバックは、アプリケーションとクライアント通信の経路が検証された後にのみ完了となります。

---

## 101. 緊急時の管理

緊急時の管理では、可能な限り、証拠と永続的な状態を保全する必要があります。

例:

* アプリケーションのクラッシュの繰り返し
* データベースの整合性エラー
* 広範囲に及ぶクライアント認証の失敗
* 予期しないパッケージジョブの動作
* 認証情報の露出の疑い
* 壊れたアップグレード
* 全ユーザーに影響する TLS の障害

推奨される順序は次のとおりです。

```text id="f8k3wz"
Preserve
   ↓
Observe
   ↓
Isolate
   ↓
Recover
   ↓
Verify
   ↓
Document
```

ログ、データベース、コンテナー、クライアントレコードを、問題の一部のように見えるというだけの理由で削除することは避けてください。

---

## 102. 管理変更の原則

重要な本番変更には、それぞれ明確に定義された 3 つの状態が必要です。

### 変更前

現在の本番状態が把握されており、復旧可能である。

### 変更中

文書化された手順を使って変更が行われる。

### 変更後

結果として得られた状態が、想定されるベースラインに照らして検証される。

これにより、管理作業が再現可能になり、意図しない構成のドリフトが減ります。

---

## 103. 制御されたアンインストール

アンインストールは、破壊的な管理操作です。

LUMS のデプロイメントを意図的に削除する場合にのみ、実行してください。

LUMS を削除する前に:

```text id="u5r2nc"
[ ] All managed clients identified
[ ] Active update jobs reviewed
[ ] Required job history exported or preserved
[ ] Required audit information preserved
[ ] Database backup created
[ ] Backup verified
[ ] TLS material preserved if required
[ ] Application secret preserved if required
[ ] Documentation preserved
[ ] Reinstallation requirements documented
```

永続データが不要であると確認する前に、それを削除してはいけません。

---

## 104. コンテナーの削除

デプロイメントを廃止した後にアプリケーションコンテナーを削除するには:

```bash id="n2x7kc"
sudo docker stop lums
sudo docker rm lums
```

これらのコマンドでは、Docker ボリュームは意図的に削除**されません**。

これにより、後の調査や復旧のために、アプリケーションデータを利用可能なまま残せます。

---

## 105. 永続データの削除

LUMS の Docker ボリュームの削除は、別の破壊的な操作です。

データベースとすべての保存済みアプリケーション状態がもう不要であると確認した後にのみ、実行してください。

例:

```bash id="r8w3mz"
sudo docker volume rm lums-data
```

これにより、そのボリュームに保存されている永続的なアプリケーションデータが完全に削除されます。

通常のアップグレードやロールバックの際に、このコマンドを実行しないでください。

---

## 106. クライアントコンポーネントの削除

管理対象クライアントを LUMS から恒久的に削除する場合は、クライアントのオペレーティングシステムの手順に従って、その Agent コンポーネントをアンインストールまたは無効化してください。

廃止後、クライアントは LUMS サーバーにレポートしなくなる必要があります。

過去の記録が必要な場合は、クライアントを削除する前に、関連するジョブと監査情報を保全してください。

## 109. 管理の完了

LUMS の管理では、常に、制御され、観察可能で、元に戻せる変更を優先する必要があります。

管理のライフサイクルは次のとおりです。

```text id="w6f1pa"
Plan
  ↓
Observe
  ↓
Change
  ↓
Verify
  ↓
Document
  ↓
Maintain
```

最も重要な運用原則は次のとおりです。

> **必要最小限の権限を使用する。**

> **永続データを保全する。**

> **現在の状態を理解せずに状態を変更しない。**

> **重要な操作の結果は、必ず検証する。**

> **テスト済みの復旧経路を維持する。**

インストール手順については、[`install.md`](インストールとアップグレード.md) を参照してください。

セキュリティアーキテクチャと監査結果については、[`security.md`](セキュリティモデル.md) を参照してください。

診断と復旧の手順については、[`troubleshooting.md`](トラブルシューティング.md) を参照してください。

## 110. 最終的な管理原則

LUMS は、Linux のアップデート管理を予測可能で観察可能にすることを目的としています。

したがって、管理作業は、思い込みや無闇な繰り返しに基づいてはいけません。

何かが変化したとき:

**まず観察し、次に変更し、最後に検証する。**

何かが壊れたとき:

**証拠を保全する。失敗した層を特定する。慎重に復旧する。**

何かがうまく動いているとき:

**結果を記録し、正常に動作する既知のベースラインを維持する。**
