# LUMS — オプションのテーマシステム

> **1 つの LUMS · 複数のインターフェース · 同じバックエンド**

LUMS には、ユーザーインターフェースの外観を変えながら、基盤となる LUMS の機能を変えない、オプションのクライアント側テーマシステムがあります。

テーマは表示レイヤーに限られます。LUMS のバックエンド、認証、認可、更新実行、パッケージ管理、クライアント管理、ジョブ処理、セキュリティ制御を置き換えたり、変更したり、迂回したりするものではありません。

このテーマシステムは、アプリケーション自体の一貫性を保ちながら、さまざまな視覚的な好みに LUMS を適応させるために用意されています。

## 実装状況と正とする情報源

現在のブラウザー実装は `server/static/theme.js` にあります。`standard`、`LUMSStadium`、`golf`、`nerd`、`geek`、`admin` をサポートし、選択をブラウザーの `localStorage` に `lums-theme` というキーで保存します。保存された識別子がない、または無効な場合は `standard` にフォールバックします。`nerd` テーマはマトリックス効果を開始し、`geek` テーマはネットワーク効果を開始します。テーマ選択はブラウザーの設定であり、アカウント設定でもサーバー側の認可状態でもありません。

このリファレンスには設計要件や概念例も含まれます。「すべき」「必須」「将来」などの表現はアーキテクチャ上の指針であり、特定の視覚機能やアクセシビリティ動作が実装済みである証拠ではありません。概念を提供済みの機能として扱う前に、ソースコードで現在の動作を確認してください。

## 1. 概要

オプションのテーマシステムにより、LUMS の Web インターフェースは同じアプリケーションバックエンドを使いながら、複数の視覚的な環境を提供できます。

テーマによって変更できるもの:

* 色
* タイポグラフィ
* 背景
* 装飾要素
* 視覚的な強調
* ナビゲーションの外観
* アニメーション
* オプションの視覚効果
* ページ固有の表示

テーマによって変更してはならないもの:

* ユーザー権限
* 利用可能な API エンドポイント
* 認証動作
* 認可判断
* CSRF 保護
* クライアント認証
* 更新実行
* パッケージ管理の権限
* ジョブ状態の処理
* 監査ログ
* データベース動作
* セキュリティ境界

原則は単純です。

> **テーマは LUMS の外観を変えますが、LUMS が実行できる操作は変えません。**

---

## 2. 設計原則

テーマシステムはいくつかの原則に従います。

### 2.1 オプションであること

テーマは任意のフロントエンド機能です。

追加テーマを選ばなくても、LUMS は完全に機能します。

標準の LUMS 外観がデフォルトの表示になります。

---

### 2.2 クライアント側であること

テーマ選択はフロントエンドに属します。

テーマを変更するために、サーバー側のアプリケーション状態を変更する必要はありません。

したがって、選択したテーマは表示設定であり、アカウント権限でもバックエンド設定でもありません。

---

### 2.3 バックエンドから独立していること

すべてのテーマが同じ LUMS バックエンドを使用します。

次の要素は選択テーマから独立したままです。

```text
Authentication
Authorization
RBAC
Client Management
Software Inventory
Update Detection
Package Management
Update Jobs
Job Recovery
Audit Logging
Database Operations
```

セキュリティや運用に関わるすべての判断は、引き続きバックエンドを正とします。

---

### 2.4 テーマをセキュリティに利用しないこと

テーマをセキュリティ機構として使用してはなりません。

たとえば、インターフェース上で操作を隠しても、権限を付与したり取り消したりすることにはなりません。

ユーザーに操作権限がない場合、どのテーマが有効であってもサーバーは要求を拒否する必要があります。

これにより、フロントエンドの表示が認可境界になることを防ぎます。

---

### 2.5 適切なフォールバック

テーマシステムは常に有効なフォールバックを用意する必要があります。

次の場合:

* テーマが選択されていない
* 保存済みテーマが利用できなくなった
* テーマ識別子が無効である
* テーマ素材を読み込めない

インターフェースを使用不能にするのではなく、LUMS は標準表示にフォールバックする必要があります。

---

## 3. 概念アーキテクチャ

テーマシステムは、既存の LUMS アプリケーションを囲む独立した表示レイヤーとして考えることができます。

```text
┌──────────────────────────────────────┐
│              LUMS UI                 │
│                                      │
│  ┌────────────────────────────────┐  │
│  │        Theme Presentation      │  │
│  │                                │  │
│  │ Standard / Stadium / Golf /    │  │
│  │ Nerd / Geek / Admin / ...      │  │
│  └────────────────────────────────┘  │
│                  │                   │
│                  ▼                   │
│        Common Frontend Logic        │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│             LUMS API                 │
│                                      │
│ Authentication / RBAC / Jobs /       │
│ Clients / Packages / Updates / Logs  │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│          LUMS Backend                │
│                                      │
│ Flask / SQLite / Job Processing /   │
│ Client Communication                 │
└──────────────────────────────────────┘
```

重要な境界は、**表示**と**アプリケーションロジック**の間にあります。

テーマはその境界より上に位置します。

## 4. テーマのライフサイクル

概念上、テーマの選択は次の順序で行われます。

```text
User selects theme
        │
        ▼
Frontend stores selection
        │
        ▼
Theme initialization
        │
        ▼
Theme applied to UI
        │
        ▼
LUMS continues using
the same backend and permissions
```

選択そのものによって、新しい LUMS 環境が作られるわけではありません。

引き続き存在するのは、1 つの LUMS アプリケーション、1 つのバックエンド、1 つのセキュリティモデルです。

---

## 5. テーマ識別子

テーマでは、表示名に依存するのではなく、安定した内部識別子を使う必要があります。

例:

```text
standard
LUMSStadium
golf
nerd
geek
admin
```

識別子は実装上の詳細です。

表示されるテーマ名は、バックエンドやアプリケーションアーキテクチャを変更せずに独立して変更できます。

テーマ識別子が削除または改名された場合、古い識別子がローカルに保存されたままのユーザーに対して、テーマシステムはフォールバックを提供する必要があります。

## 6. 責任の分離

テーマシステムの責任範囲は、意図的に限定されています。

### テーマレイヤー

担当するもの:

* 視覚的な表示
* テーマ選択
* テーマ固有のスタイル
* オプションの視覚効果
* テーマ固有のフロントエンド装飾
* アクセシビリティに関わる表示動作

### 共通フロントエンド

担当するもの:

* アプリケーションデータの表示
* LUMS API の呼び出し
* ジョブとソフトウェア情報の描画
* ユーザー操作の処理
* 表示レベルでの可視性制御

### バックエンド

担当するもの:

* 認証
* 認可
* RBAC
* CSRF 保護
* クライアント認証
* ジョブ作成
* ジョブ実行
* パッケージ管理
* データベース操作
* 監査ログ
* セキュリティ判断

この分離は設計の基本です。

## 7. セキュリティ境界

認可の目的において、テーマシステムのコードは**信頼できません**。

テーマがインターフェース要素を変更したり隠したりしても、要求された操作を検証する責任はバックエンドにあります。

概念上:

```text
Frontend visibility
        ≠
Backend permission
```

例:

```text
Viewer
  │
  ├── Theme may display no package-management controls
  │
  └── Backend still rejects unauthorized package operations
```

同じ原則は管理者機能、更新ジョブ、クライアント管理、その他すべての特権操作に適用されます。

---

## 8. 運用原則

LUMS の運用アーキテクチャから見て、テーマシステムは意識する必要のない存在であるべきです。

テーマ変更のために、次の操作を必要としてはなりません:

* データベースの再構築
* クライアント設定の変更
* クライアントトークンの変更
* 更新エージェントの再起動
* 更新ジョブの変更
* RBAC の変更
* ネットワーク設定の変更
* パッケージ管理動作の変更

テーマは表示設定であり、運用設定ではありません。

## 11. テーマの構造

オプションのテーマシステムは、テーマの選択と実際の視覚表示を分離します。

概念上、テーマは次の 3 層で構成されます。

```text
Theme Identifier
       │
       ▼
Theme Selection
       │
       ▼
Theme Presentation
```

識別子は、どのテーマが選択されているかを示します。

選択機構は、現在どのテーマを有効にするかを決定します。

表示レイヤーは、対応する視覚設定を LUMS インターフェースに適用します。

この分離により、LUMS アプリケーションの基本アーキテクチャを変更せずにテーマを追加または削除できます。

---

## 12. テーマ選択

テーマ選択はフロントエンドが処理します。

選択テーマは、サーバー側のアカウント属性ではなく、ローカルな表示設定として扱います。

概念上:

```text
User
 │
 ▼
Theme Selector
 │
 ▼
Selected Theme Identifier
 │
 ▼
Frontend Theme Initialization
 │
 ▼
Active Theme
```

バックエンドが、現在選択されている視覚テーマを知る必要はありません。

つまり、テーマ変更が他のユーザーに影響することもありません。

2 人のユーザーが同じ LUMS インスタンスにアクセスしながら、まったく異なる視覚テーマを使うことができます。

---

## 13. ローカルのテーマ設定

選択したテーマはブラウザー内にローカル保存できます。

ローカルに保存する目的は利便性です。

```text
Browser
   │
   ├── Theme preference
   │
   └── LUMS application
```

したがって、保存されたテーマ選択は信頼できないクライアント側状態として扱う必要があります。

サーバーは、これを次のものとして解釈してはなりません:

* ロール
* 権限
* 認証状態
* セキュリティ設定
* 管理者設定

ブラウザーは外観を選択できますが、認可を制御するものではありません。

---

## 14. テーマの初期化

LUMS インターフェースの読み込み時に、フロントエンドは有効にするテーマを決定します。

概念上の順序:

```text
Page Load
   │
   ▼
Read Stored Theme
   │
   ▼
Is Theme Valid?
   │
   ├── Yes ──────► Apply Theme
   │
   └── No ───────► Use Standard Theme
```

設定が保存されていない場合は、標準の LUMS 表示を使用します。

保存済みの識別子がサポート対象外になった場合も、同じフォールバック動作を適用します。

これにより、古いローカル設定がインターフェースを壊すのを防ぎます。

---

## 15. デフォルトテーマ

標準 LUMS テーマは基準となる表示です。

これはオプションテーマを定義する際の参照となる外観を提供します。

そのため、標準テーマは次の条件を満たす必要があります:

* 機能する
* 読みやすい
* アクセシブルである
* 視覚的に完成している
* オプションの装飾素材に依存しない

通常の LUMS 運用にオプションテーマを必須としてはなりません。

---

## 16. テーマの適用

フロントエンドは、共有アプリケーション状態またはルートレベルのテーマ属性で有効テーマを表現できます。

概念上:

```html
<html data-theme="theme-id">
```

フロントエンドの進化に伴い、具体的な実装は異なる可能性があります。

重要なアーキテクチャ要件は、フロントエンドのスタイル機構が有効テーマを一貫して識別できることです。

これにより、テーマ固有のスタイルを共通のアプリケーション構造から分離できます。

---

## 17. テーマ固有のスタイル

テーマスタイルは、アプリケーションのマークアップを複製するのではなく、主に CSS で実装する必要があります。

概念上:

```text
Common HTML
     │
     ├── Standard styling
     ├── Stadium styling
     ├── Golf styling
     ├── Nerd styling
     ├── Geek styling
     └── Admin styling
```

こうすることで、同じアプリケーションコンポーネントをすべてのテーマで利用できます。

たとえば、クライアントのテーブルは、有効なテーマにかかわらずクライアントのテーブルです。

変わるのは表示だけです。

---

## 18. 共通アプリケーションコンポーネント

テーマごとに LUMS の独立したページを作ってはなりません。

次の原則を維持する必要があります。

```text
One component
       │
       ├── Theme A
       ├── Theme B
       ├── Theme C
       └── Theme D
```

次のようにするのではありません。

```text
Theme A → separate page
Theme B → separate page
Theme C → separate page
```

ページを重複させると保守が大幅に難しくなり、テーマ間で動作に違いが生じる可能性があります。

そのため、テーマはアプリケーション自体を置き換えるのではなく、共通インターフェースを装飾する必要があります。

---

## 19. テーマ素材

必要に応じて、テーマは追加のフロントエンド素材を使用できます。

素材の例:

* 背景画像
* 装飾グラフィック
* アイコン
* アニメーション
* 視覚的なオーバーレイ
* テーマ固有のイラスト

素材は引き続きフロントエンド表示レイヤーの一部です。

次のものを含めてはなりません:

* 認証情報
* クライアントトークン
* シークレットキー
* データベースファイル
* 認証用情報
* 非公開の運用データ

テーマ素材は公開フロントエンドリソースとして扱う必要があります。

---

## 20. オプションの視覚効果

テーマによっては追加の視覚効果を提供できます。

例:

* アニメーション背景
* 装飾用ネットワーク効果
* 環境的な動き
* テーマに合わせたインターフェース要素
* 動的な視覚装飾

このような効果はオプションでなければなりません。

LUMS の機能動作に必須であってはなりません。

---

## 21. 動きを減らす設定

視覚効果は、動きを減らす設定を好むユーザーに配慮する必要があります。

アニメーションや継続的に変化する要素を使う場合、テーマシステムは適切な動きを減らす動作を提供する必要があります。

概念上:

```text
Normal motion
     │
     ├── animations enabled
     └── visual effects enabled

Reduced motion
     │
     ├── animations reduced or disabled
     └── essential interface remains functional
```

アクセシビリティは装飾アニメーションより優先されます。

視覚効果を無効にした状態でも、テーマは利用可能でなければなりません。

---

## 22. テーマの独立性

テーマ変更によって運用上の副作用が発生してはなりません。

例:

```text
Theme change
     │
     ├── No client restart
     ├── No agent restart
     ├── No job cancellation
     ├── No database migration
     ├── No token rotation
     └── No permission change
```

したがって、テーマシステムは LUMS の運用ライフサイクルから意図的に分離されています。

---

## 23. テーマの障害処理

テーマは安全に失敗する必要があります。

テーマ固有の素材や表示コンポーネントを読み込めなくても、共通 LUMS インターフェースは引き続き使用可能でなければなりません。

望ましい復旧経路:

```text
Theme error
    │
    ▼
Fallback to standard presentation
    │
    ▼
LUMS remains usable
```

視覚上の問題をアプリケーションの可用性問題にしてはなりません。

---

## 24. 新しいテーマの追加

新しいテーマは、アプリケーション動作と表示の既存の分離に従う必要があります。

概念上:

```text
1. Define theme identifier
2. Define visual design
3. Add theme styling
4. Add optional assets
5. Add theme to selection mechanism
6. Test normal pages
7. Test different RBAC roles
8. Test reduced-motion behavior
9. Test fallback behavior
10. Verify no backend behavior changed
```

既存の LUMS 機能が変更されずに保たれた場合にのみ、新しいテーマを完成とみなせます。

---

## 25. テーマの削除

テーマの削除も適切に処理する必要があります。

ユーザーのローカルに削除済みテーマが保存されている場合、フロントエンドはその識別子が利用できなくなったことを検出し、標準テーマにフォールバックする必要があります。

視覚テーマの削除によって、ユーザーの LUMS インターフェースが使えなくなってはなりません。

---

## 26. テーマの命名

テーマ名では次のものを明確に区別する必要があります:

* 内部識別子
* 表示名
* 視覚コンセプト

例:

```text
Internal identifier:  standard
Display name:         Standard LUMS
```

この分離により、内部実装を不必要に変更することなく、表示文言を変更できます。

---

オプションの LUMS テーマシステムは、共通のアプリケーションを維持しながら、複数の視覚的なアイデンティティを提供するよう設計されています。

現在文書化されているテーマ案:

すべて同じアプリケーションの一部です。

## 29. Standard LUMS

Standard LUMS テーマは、アプリケーションの基準となる表示です。

特定の視覚コンセプトを必要とせず、明快で機能的なインターフェースを提供することが目的です。

標準テーマでは、次の点を優先する必要があります。

* 読みやすさ
* 明確な情報階層
* 予測可能なナビゲーション
* アクセシビリティ
* 視覚的な気を散らす要素の少なさ
* 一貫したコンポーネント表示

標準テーマはテーマシステムのフォールバック表示です。

したがって、オプションの視覚テーマがすべて利用できない場合でも、Standard LUMS テーマを使用できる必要があります。

---

## 30. LUMS Stadium

**LUMS Stadium** は、LUMS インターフェースをより表現豊かに解釈したテーマです。

このコンセプトは、システム管理とスタジアムをイメージした視覚的アイデンティティを組み合わせます。

デザイン要素の例:

* スコアボードをイメージした情報パネル
* より目立つ視覚的な状態表示
* イベントを意識した表示
* テーマに合わせた背景
* 運用状態の視覚的な強調
* スタジアムを想起させる装飾

このテーマの機能は Standard LUMS と同一です。

更新の成功は、引き続き更新の成功です。

ジョブの失敗は、引き続きジョブの失敗です。

変わるのは表示だけです。

---

## 31. Golf Club

**Golf Club** テーマは、意図的に対照的な視覚的アイデンティティを提供します。

従来のサーバーやインフラストラクチャを思わせるデザインの代わりに、落ち着いたレクリエーションのコンセプトを使用します。

視覚デザインでは、次の要素を強調できます。

* すっきりした表面
* 控えめな装飾
* ゴルフをイメージした要素
* コースを思わせる視覚的な比喩
* 落ち着いた状態表示
* さりげないテーマアクセント

このコンセプトは、機能を維持するために LUMS が従来の管理コンソールのような外観である必要はないことを示しています。

バックエンドとアプリケーションの動作は変わりません。

---

## 32. Nerd Mode

**Nerd Mode** は、より技術的で遊び心のある表示を目指します。

次のような要素を使って、LUMS の技術的な性質を強調できます。

* ターミナルをイメージしたスタイル
* 技術用語
* システムを中心とする視覚要素
* 開発者向けの表示
* 診断ツールを思わせるデザイン
* 意図的に技術的な装飾

それでも、テーマは明確な情報階層を維持する必要があります。

遊び心のあるインターフェースによって、運用情報を理解しにくくしてはなりません。

---

## 33. Geek Lab

**Geek Lab** は、より実験的な技術環境を表現します。

視覚コンセプトには、次の要素を組み合わせることができます。

* 研究室の美的要素
* 技術的な実験
* インフラストラクチャの可視化
* システム図
* 科学や工学をイメージした要素
* 実験的な視覚効果

このテーマは、基盤となる LUMS の機能を維持しながら、インフラストラクチャ研究室のような雰囲気をインターフェースに与えることを目指します。

視覚的な実験は、アプリケーションの運用から分離しておく必要があります。

---

## 34. Enterprise Admin

**Enterprise Admin** テーマは、より保守的な管理インターフェースを表します。

視覚デザインでは、次の点を強調できます。

* 構造化された情報
* コンパクトなレイアウト
* 管理ダッシュボード
* 明確な状態表示
* 高い情報密度
* 装飾要素の削減

従来型の管理コンソールの外観を好むユーザーに特に適したテーマです。

追加の管理者権限を付与するものではありません。

この名称は視覚コンセプトを表すものであり、認可レベルを示すものではありません。

---

## 35. テーマの比較

テーマは、同じアプリケーションを異なる視点から視覚的に表現したものです。

| テーマ | 視覚的な方向性 | 主な特徴 |
| ---------------- | --------------------------- | ------------------- |
| Standard LUMS | すっきり／機能的 | 基準インターフェース |
| LUMS Stadium | スタジアム／イベント | 表現豊か |
| Golf Club | レクリエーション／落ち着き | リラックス |
| Nerd Mode | 技術的／遊び心 | 開発者向け |
| Geek Lab | 実験的／技術的 | 研究室 |
| Enterprise Admin | 構造的／管理向け | 保守的 |

この表は表示コンセプトだけを説明します。

次のような違いを表すものでは**ありません**。

* 権限
* 機能
* API アクセス
* クライアントアクセス
* ジョブ実行
* パッケージ管理
* セキュリティ

## 36. 同じインターフェース、異なる表示

中心的な設計目標は、同じアプリケーションコンポーネントがテーマをまたいでも認識できることです。

例:

```text id="5dhlf7"
Client List
   │
   ├── Standard presentation
   ├── Stadium presentation
   ├── Golf presentation
   ├── Nerd presentation
   ├── Geek presentation
   └── Enterprise presentation
```

基盤となるクライアントデータは同一です。

変わるのは表示だけです。

同じことが次の要素にも当てはまります。

* ソフトウェアインベントリ
* 利用可能な更新
* 更新ジョブ
* ジョブ履歴
* ユーザー情報
* システム状態
* パッケージ管理インターフェース

---

## 37. 運用状態

テーマによって、異なる運用状態を視覚的に強調できます。

例:

```text id="5wyy17"
PENDING
RUNNING
SUCCESS
FAILED
```

テーマはこれらの状態を異なる方法で表示できますが、意味は一貫させなければなりません。

テーマによってアプリケーションの状態を再定義してはなりません。

たとえば:

```text id="j4i9qd"
SUCCESS ≠ "looks green"

SUCCESS = actual LUMS job state
```

視覚表現は、バックエンド状態の描画にすぎません。

---

## 38. エラーの表示

テーマによってエラーの視覚的な表示方法を変えることもできます。

ただし、エラー情報は理解できる状態に保たなければなりません。

テーマによって次のことをしてはなりません。

* 重要なエラー情報を隠す
* 技術情報を装飾的な文言に置き換える
* 警告を通常の状態と区別できなくする
* 運用上の失敗を抑制する

視覚スタイルで表示を改善することはできますが、問題の理解に必要な診断情報を取り除いてはなりません。

---

## 39. 状態の一貫性

同じ状態は、すべてのテーマで一貫した意味を持つ必要があります。

例:

| 状態 | 意味 |
| ------- | ------------------------- |
| Pending | 実行待ち |
| Running | 現在処理中 |
| Success | 正常に完了 |
| Failed | 実行に失敗 |

テーマによって、色、アイコン、タイポグラフィ、レイアウトを変えてこれらの状態を表現できます。

基盤となる意味は変えてはなりません。

---

## 40. テーマ固有の装飾

装飾要素は運用情報より目立たないようにする必要があります。

例:

* 背景
* パターン
* イラスト
* 環境的な効果
* テーマに合わせたアイコン
* 視覚的な飾り

次の優先順位を維持してください。

```text id="3m08d7"
Operational Information
        │
        ▼
Application Usability
        │
        ▼
Accessibility
        │
        ▼
Visual Decoration
```

装飾を、LUMS の運用に必要な情報より優先してはなりません。

---

## 41. 視覚的な情報密度

テーマによって視覚的な情報密度を変えることができます。

例:

* Enterprise Admin は情報密度を優先できます。
* Standard LUMS はバランスの取れた読みやすさを優先できます。
* Golf Club は余白を多めにできます。
* Nerd Mode は技術的な要素をコンパクトにできます。
* Stadium は大きな状態表示を強調できます。
* Geek Lab は視覚的な文脈を増やせます。

これらは表示上の選択です。

基盤となるデータの量や権威性は変わりません。

---

## 42. テーマをまたいだアクセシビリティ

すべてのテーマで基本的な使いやすさを維持する必要があります。

これには次のものが含まれます。

* 読みやすいテキスト
* 十分に識別できる視覚表示
* 使用可能なコントロール
* 理解しやすい状態表示
* キーボード操作への対応
* 使用可能なフォーカス状態
* 動きを減らす設定との互換性

重要な状態を伝える手段として、色だけに頼ってはなりません。

たとえば、失敗したジョブを特定の色だけで識別できる状態にしてはいけません。

---

## 43. テーマ固有のアニメーション

視覚コンセプトの改善に役立つ場合、テーマにアニメーションを含めることができます。

例:

* 控えめなトランジション
* アニメーション背景
* ネットワーク効果
* 状態遷移
* 環境的な装飾

アニメーションはアプリケーションより優先度を低くする必要があります。

次のような影響があってはなりません。

* 操作を妨げる
* コントロールを覆い隠す
* 運用データから継続的に注意をそらす
* アクセシビリティを損なう
* バックエンド操作に影響する

---

## 44. 生きたネットワーク

一部の LUMS テーマでは、ネットワークをイメージした動的な視覚レイヤーを使用できます。

このコンセプトは、LUMS を稼働するインフラストラクチャ環境として表現します。

```text id="7w1v8b"
Client ─────┐
            │
Client ─────┼──── LUMS
            │
Client ─────┘
```

このような可視化は、実際のアプリケーションデータに明示的に接続されていない限り、装飾です。

したがって、アプリケーションが明示的に情報を提供しない限り、ネットワークの視覚表示を正式なネットワークトポロジーとして解釈してはなりません。

この区別は重要です。

> **視覚表現が自動的に運用テレメトリになるわけではありません。**

---

## 45. 装飾データと実データ

テーマ固有の視覚効果は、実際の LUMS データと明確に区別する必要があります。

例:

```text id="z6i5j0"
Decorative node
    ≠
Real client

Animated connection
    ≠
Real network connection

Visual status effect
    ≠
Backend job state
```

これにより、ユーザーが美的な可視化を実際のシステム情報と取り違えることを防ぎます。

---

## 46. テーマのアイデンティティ

各テーマは、別製品になることなく、認識できるアイデンティティを持つ必要があります。

目標:

```text id="qv1fbe"
Different visual identity
          +
Same LUMS functionality
          =
Optional LUMS Theme
```

これにより、アプリケーションの技術的完全性を保ちながら、テーマシステムに遊び心と柔軟性を持たせます。

---

## 47. テーマの設計規則

すべてのテーマに適用される最も重要な設計規則:

> **テーマは表現豊かでも、変わっていても、技術的でも、遊び心があっても、保守的でも構いません。ただし、常に LUMS でなければなりません。**

選択された視覚表示にかかわらず、アプリケーションは同じシステムとして認識されなければなりません。

# LUMS — オプションのテーマシステム

## パート 4 — フロントエンド実装とアクセシビリティ

## 48. フロントエンドのテーマレイヤー

オプションのテーマシステムは、LUMS フロントエンドに完全に属します。

その責任は表示とユーザー設定の処理に限定されます。

概念上:

```text
┌─────────────────────────────────┐
│          LUMS Frontend          │
│                                 │
│  Common Application Logic       │
│              │                  │
│              ▼                  │
│       Theme Presentation        │
│              │                  │
│              ▼                  │
│       Browser Rendering         │
└─────────────────────────────────┘
```

テーマレイヤーは共通フロントエンドロジックを置き換えません。

その周囲に表示レイヤーを追加します。

---

## 49. テーマの初期化

テーマの初期化は通常のフロントエンド起動処理の一部として行う必要があります。

概念上の順序:

```text
Frontend starts
      │
      ▼
Theme system initializes
      │
      ▼
Stored preference is evaluated
      │
      ▼
Theme availability is checked
      │
      ├── Valid → selected theme
      │
      └── Invalid → standard theme
      │
      ▼
LUMS interface rendered
```

初期化は軽量で、バックエンドの可用性に依存してはなりません。

後続の API 要求が失敗する場合でも、ユーザーは視覚表示を読み込める必要があります。

---

## 50. テーマ状態

有効なテーマはフロントエンド状態です。

そのため、アプリケーション状態とは異なるものとして扱う必要があります。

### テーマ状態

例:

```text
Active visual theme
Reduced-motion preference
Visual presentation preferences
```

### アプリケーション状態

例:

```text
Logged-in user
User role
Client state
Package state
Update state
Job state
Audit state
```

テーマ状態がアプリケーション状態を上書きしたり、偽装したりしてはなりません。

---

## 51. ルートのテーマ属性

ルートレベルの属性は、有効なテーマを表す概念的な方法として適しています。

例:

```html
<html data-theme="standard">
```

または:

```html
<html data-theme="nerd">
```

CSS は有効なテーマをセレクターとして使用できます。

具体的な実装は変化しても、アーキテクチャ上の目標は同じです。

> **1 つのアプリケーション構造、複数の表示定義。**

---

## 52. CSS の構成

テーマ固有のスタイルは、共通の LUMS スタイルと区別できるようにする必要があります。

概念上:

```text
Common styles
│
├── Layout
├── Forms
├── Tables
├── Navigation
├── Status elements
└── Shared components

Theme styles
│
├── Standard
├── Stadium
├── Golf
├── Nerd
├── Geek
└── Admin
```

共通スタイルは機能的な構造を定義します。

テーマスタイルは視覚的なアイデンティティを定義します。

これにより重複が減り、今後のテーマ保守が容易になります。

---

## 53. CSS 変数

テーマシステムでは CSS カスタムプロパティを使って、意味上の値と視覚的な表現を分離できます。

例:

```css
:root {
    --lums-background: ...;
    --lums-surface: ...;
    --lums-text: ...;
    --lums-accent: ...;
}
```

テーマは独自の値を定義できます。

```css
[data-theme="example"] {
    --lums-background: ...;
    --lums-surface: ...;
    --lums-text: ...;
    --lums-accent: ...;
}
```

重要なのは、可能な限りコンポーネントがテーマ固有の値を直接ハードコードせず、意味を表す変数を使用することです。

---

## 54. 共通コンポーネント

テーマシステムはコンポーネントを複製するのではなく、共有コンポーネントのスタイルを変更する必要があります。

一般的なコンポーネント:

* ナビゲーション
* ボタン
* フォーム
* テーブル
* 状態表示
* カード
* ダイアログ
* パッケージ管理要素
* 更新ジョブ要素
* クライアント情報
* システム情報

有効なテーマにかかわらず、同じコンポーネントの機能は同一でなければなりません。

---

## 55. テーマ素材

オプションテーマは専用の素材を使用できます。

素材のカテゴリ例:

```text
Images
Icons
Backgrounds
Decorative graphics
Fonts
Animation assets
Visual effects
```

テーマ素材はフロントエンドリソースのままです。

機密性のあるアプリケーション情報を含めてはなりません。

特に、テーマ素材には次の情報を絶対に含めないでください。

* パスワード
* シークレットキー
* クライアントトークン
* データベースの内容
* 非公開証明書
* 認証用情報

---

## 56. 素材の読み込み

テーマ素材は必要な場合にのみ読み込む必要があります。

テーマが存在するというだけで、すべての LUMS ページの負荷を不必要に増加させてはなりません。

可能であれば:

```text
Selected theme
      │
      ▼
Required assets
      │
      ▼
Browser
```

すべてのテーマの素材を同時に読み込むのではなく、選択したテーマの素材だけを読み込みます。

テーマや視覚効果を追加するほど、この点は重要になります。

---

## 57. テーマのパフォーマンス

視覚的なカスタマイズによって LUMS の使いやすさを大きく損なってはなりません。

特に、次の点に注意してください。

* 大きな背景画像
* 継続的にアニメーションする要素
* canvas 効果
* DOM の反復更新
* 負荷の高い視覚フィルター
* 不必要なネットワーク要求

クライアント一覧、ソフトウェアインベントリ、更新ジョブ表示などの運用ページは、引き続き応答性を保つ必要があります。

---

## 58. 装飾用 JavaScript

テーマは視覚効果のために JavaScript を使用できます。

例:

* アニメーション背景
* ネットワーク可視化
* 動的な装飾
* テーマ固有の操作

このような JavaScript は、アプリケーションの運用ロジックから分離する必要があります。

装飾用スクリプトが次を担当してはなりません。

* 認可
* ジョブ作成
* パッケージのインストール
* パッケージの削除
* 更新実行
* クライアント認証
* 監査ログ

次の区別を明確に保ってください。

```text
Theme JavaScript
      ≠
LUMS operational JavaScript
```

---

## 59. ネットワークの可視化

テーマがネットワーク形式の可視化を使用する場合、それは表示コンポーネントとして扱う必要があります。

例:

```text
Canvas / Visual Layer
        │
        ▼
Decorative Network
        │
        ▼
Theme Presentation
```

権威ある LUMS データに明示的に接続されていない限り、実際のネットワーク状態を表すかのように示してはなりません。

これにより、装飾グラフィックが監視情報やテレメトリと誤認されるのを防ぎます。

---

## 60. 動きを減らす設定

アニメーションを使用するテーマは、動きを減らす設定に対応する必要があります。

望ましい動作の概念:

```text
prefers-reduced-motion: reduce
            │
            ▼
Reduce or disable decorative motion
```

必須機能は変更しないでください。

動きを減らす設定が影響するのは表示だけです。

---

## 61. フォーカスとキーボード操作

テーマスタイルはキーボード操作の使いやすさを維持する必要があります。

重要な対話型要素には、視認できるフォーカス状態が必要です。

同等に明確な代替表示を提供せずに、フォーカス枠を削除してはなりません。

例:

```text
Keyboard focus
      │
      ▼
Clearly visible control state
```

これは次の要素に適用されます。

* ナビゲーション
* ボタン
* リンク
* フォームフィールド
* セレクター
* ダイアログ
* パッケージ管理コントロール

---

## 62. 色への非依存

重要な情報を色だけに頼って伝えてはなりません。

例:

```text
FAILED
```

テーマの色が利用できなくても、テキスト、アイコン、構造、その他のアクセシブルな表示で意味が理解できる必要があります。

テーマによって色パレットが大きく異なるため、これは特に重要です。

---

## 63. コントラスト

すべてのテーマで、次の間に十分なコントラストを保つ必要があります。

* テキストと背景
* コントロールと背景
* 状態表示と周囲の要素
* フォーカス中の要素とその周囲

見た目に魅力的な色使いは、読みやすさの代わりにはなりません。

テーマの色とアクセシビリティ要件が相反する場合、読みやすさを優先します。

---

## 64. テーマ選択 UI

テーマセレクター自体は共通の LUMS インターフェースの一部です。

有効テーマにかかわらず、理解できる状態でなければなりません。

概念上:

```text
Theme selector
      │
      ├── Standard LUMS
      ├── LUMS Stadium
      ├── Golf Club
      ├── Nerd Mode
      ├── Geek Lab
      └── Enterprise Admin
```

別のテーマを選択すると表示が更新されますが、現在の LUMS セッションや運用状態は変更されません。

---

## 65. セッションからの独立

テーマ変更によってユーザーをログアウトさせてはなりません。

次のことをしてはなりません。

* セッションを無効化する
* ロールを変更する
* クライアントトークンをローテーションする
* サーバー側の認証状態を変更する

テーマ設定は認証とは別のものです。

```text
Theme change
     │
     └── Session remains unchanged
```

---

## 66. RBAC からの独立

テーマは RBAC から独立したままでなければなりません。

例:

```text
Administrator
     │
     └── sees functionality permitted to administrators

Operator
     │
     └── sees functionality permitted to operators

Viewer
     │
     └── sees functionality permitted to viewers
```

選択したテーマはこれらの権限を変更しません。

Enterprise Admin を使う Viewer が管理者になることはありません。

Nerd Mode を使う Administrator が管理者権限を失うこともありません。

すべての場合において、バックエンドが権威ある情報源です。

---

## 67. エラーの分離

オプションの視覚機能の障害によって、LUMS の中核的な運用が壊れてはなりません。

たとえば、装飾アニメーションが失敗した場合:

```text
Animation failure
      │
      ▼
Theme remains usable
      │
      ▼
LUMS remains operational
```

可能な限り、視覚機能はアプリケーション機能とは独立して失敗するようにします。

これはアニメーション背景やネットワーク可視化などのオプション効果で特に重要です。

---

## 68. ブラウザー互換性

テーマシステムは、LUMS のデプロイ環境で対象となるブラウザーがサポートする機能を使う必要があります。

視覚機能を利用できない場合も、インターフェースが使えなくなるのではなく、適切に簡易化して動作する必要があります。

標準表示を基本のフォールバックとして維持してください。

---

## 69. 実装原則

実装は次のように要約できます。

```text
Common HTML
     +
Common LUMS JavaScript
     +
Theme selection
     +
Theme-specific CSS/assets
     =
Optional visual layer
```

次の要素はテーマレイヤーの外に置かなければなりません。

```text
Authentication
Authorization
Database
Jobs
Package management
Client authentication
Audit logging
Security decisions
```

この分離により、テーマシステムは表現力を保ちながら、LUMS の中核動作と結合することを避けられます。

## パート 5 — セキュリティ、テスト、開発

## 70. セキュリティ境界

テーマシステムはフロントエンドの一部であるため、信頼できないクライアント環境で動作します。

ブラウザーが制御するのは表示レイヤーです。

ブラウザーは LUMS の認可を制御**しません**。

セキュリティ境界は次のとおりです。

```text id="h8e2ks"
Browser
   │
   │ untrusted presentation
   ▼
LUMS API
   │
   │ authoritative validation
   ▼
LUMS Backend
```

したがって、セキュリティ上重要な判断はすべてサーバー側に置く必要があります。

---

## 71. テーマ選択は認可ではない

選択されたテーマを認可シグナルとして解釈してはなりません。

たとえば:

```text id="8u3r8v"
data-theme="admin"
```

と指定されていても、現在のユーザーが管理者という意味ではありません。

テーマ識別子の `admin` という語は、単なる説明です。

ユーザーの実際のロールは、常に認証済みアプリケーションセッションとサーバー側認可ロジックから決定しなければなりません。

---

## 72. フロントエンドの可視性はセキュリティではない

テーマやフロントエンドスクリプトは、インターフェース要素を隠せます。

これは表示上は役立ちます。

しかし、アクセス制御としては十分ではありません。

例:

```text id="7m8c6w"
Hidden button
      ≠
Unauthorized operation prevented
```

対応する API エンドポイントは、ユーザー権限を独立して検証する必要があります。

これは、特権を必要とする LUMS のすべての機能に適用されます。

---

## 73. テーマ素材は公開情報

フロントエンド素材は、LUMS Web インターフェースにアクセスできるすべての人が閲覧可能と考える必要があります。

そのため、テーマファイルにシークレットを含めてはなりません。

次の情報をテーマ素材に含めないでください。

```text id="1zjz7n"
Passwords
API secrets
Client tokens
Private keys
Database files
Session secrets
Authentication credentials
```

機密に保つ必要がある情報は、テーマ素材に含めてはいけません。

---

## 74. テーマにバックエンドのシークレットを含めない

テーマ JavaScript にサーバー認証情報や特権 API 情報を含めてはなりません。

必要なデータがある場合、テーマは既存のフロントエンドアプリケーションレイヤーを通じてやり取りする必要があります。

代替の認証機構を導入してはなりません。

次の原則を適用します。

> **テーマは表示データを利用します。セキュリティ認証情報を作成するものではありません。**

---

## 75. クロスサイトリクエストフォージェリ

テーマ機能は既存の CSRF 保護を迂回してはなりません。

保護された要求を必要とする操作をテーマのインターフェース要素が開始する場合、その要求は共通 LUMS インターフェースと同じセキュリティ要件に従う必要があります。

視覚用コードであることを理由に例外を認めてはなりません。

---

## 76. API の利用

テーマが独自の運用 API ロジックを直接実装するのは避ける必要があります。

アプリケーションデータが必要な場合、LUMS フロントエンド／アプリケーションの既存メカニズムを利用してください。

これにより、次の個別実装が複数作られるのを防ぎます。

* 認証
* API 要求
* エラー処理
* 認可に関する前提
* ジョブ処理

共通のアプリケーションロジックが、権威あるフロントエンド統合レイヤーです。

---

## 77. テーマの分離

コア LUMS 機能を削除せずにテーマだけを削除できる必要があります。

概念上:

```text id="3m1o8q"
Remove optional theme
        │
        ▼
Standard LUMS remains
        │
        ▼
Application remains operational
```

これにより、オプションテーマは真に任意のものになります。

---

## 78. セキュリティテスト

テーマ変更によって LUMS のセキュリティモデルが変わらないことを確認するテストが必要です。

関連する確認項目:

* Viewer は引き続き Viewer である
* Operator は引き続き Operator である
* Administrator は引き続き Administrator である
* 保護された API エンドポイントが引き続き保護される
* CSRF 保護が引き続き有効である
* クライアント認証が変更されない
* 更新ジョブの権限が変更されない
* パッケージ管理権限が変更されない
* 監査ログが変更されない

操作が安全であることの証拠として、テーマ自体を使ってはなりません。

---

## 79. テーマの機能テスト

各テーマを共通アプリケーションに対してテストする必要があります。

最低限、次を確認します。

```text id="9w6h1m"
Login
Client list
Client details
Installed software
Available updates
Update jobs
Job history
Package management
User management
System maintenance
Logout
```

利用可能な機能は、認証済みユーザーのロールによって異なります。

テストの目的は、テーマの描画によって通常のアプリケーション機能が壊れないことを確認することです。

---

## 80. RBAC とテーマのテスト

テーマテストでは、関連するすべてのロールを対象にする必要があります。

基本的なマトリックス:

| ロール | テーマテスト |
| ------------- | ------------- |
| Administrator | 必須 |
| Operator | 必須 |
| Viewer | 必須 |

各ロールについて、テーマを変更しても許可される機能が変わらないことを確認します。

例:

```text id="3n5p2m"
Viewer + Nerd Mode
        =
Viewer permissions

Viewer + Enterprise Admin
        =
Viewer permissions
```

視覚テーマによって結果が変わってはなりません。

---

## 81. テーマ切替テスト

テーマ切替は繰り返しテストする必要があります。

切替シーケンスの例:

```text id="gk2j7m"
Standard
   ↓
Stadium
   ↓
Golf
   ↓
Nerd
   ↓
Geek
   ↓
Admin
   ↓
Standard
```

このシーケンスの間、アプリケーションは使用可能な状態を維持する必要があります。

特に次の点を確認してください。

* レイアウトの変更
* テーブル
* ナビゲーション
* ダイアログ
* フォーム
* 状態表示
* 長いテキスト
* レスポンシブ動作

---

## 82. 保存動作のテスト

テーマ設定がローカルに保存される場合、次をテストします。

1. テーマを選択する。
2. ページを再読み込みする。
3. テーマが選択されたままであることを確認する。
4. ブラウザーを閉じる。
5. 再度 LUMS を開く。
6. 設定が引き続き正しく処理されることを確認する。
7. 保存されたテーマを削除または無効化する。
8. 標準テーマにフォールバックすることを確認する。

保存値をアプリケーションのセキュリティ状態として信頼してはなりません。

---

## 83. 無効なテーマのテスト

無効なテーマ識別子によってインターフェースが壊れてはなりません。

例:

```text id="4j5cqn"
unknown-theme
```

の場合、ページを使用不能にするのではなく、安全にフォールバックする必要があります。

望ましい動作:

```text id="5x9h2f"
Invalid theme
     │
     ▼
Standard theme
     │
     ▼
LUMS remains usable
```

---

## 84. 素材障害のテスト

オプション素材の障害もテストする必要があります。

例:

* 画像が見つからない
* アニメーションが利用できない
* 素材パスが無効
* 視覚機能が未サポート
* オプション装飾の JavaScript エラー

可能な限り、共通アプリケーションは引き続き使用可能でなければなりません。

---

## 85. 動きを減らす設定のテスト

アニメーションを含むテーマは、通常環境と動きを減らす環境の両方でテストします。

```text id="l1h4nb"
Normal motion
     │
     └── Theme effects available

Reduced motion
     │
     └── Effects reduced or disabled
```

どちらの場合も、重要なアプリケーションコントロールは完全に機能する必要があります。

---

## 86. レスポンシブテスト

テーマはさまざまなビューポートサイズでテストする必要があります。

最低限:

* デスクトップ
* タブレット相当のビューポート
* 狭いモバイル相当のビューポート

視覚的なアイデンティティを優先して、操作可能なコントロールや読みやすいアプリケーションデータを犠牲にしてはなりません。

特に次の点に注意してください。

* ナビゲーション
* テーブル
* 操作ボタン
* パッケージ管理コントロール
* ジョブ状態情報
* ダイアログ
* テーマセレクター

---

## 87. パフォーマンステスト

視覚効果がブラウザー性能に与える影響を評価する必要があります。

確認項目:

* ページ読み込み時間
* 描画の応答性
* CPU 使用率
* メモリ使用量
* アニメーションの滑らかさ
* DOM の反復更新
* ネットワーク要求

テーマは表示を改善するものであり、性能上のボトルネックになってはなりません。

---

## 88. 開発ワークフロー

可能な限り、新しいテーマはバックエンド変更から独立して開発します。

推奨ワークフロー:

```text id="1i8qz6"
Design
   ↓
Frontend implementation
   ↓
Theme selector integration
   ↓
Accessibility review
   ↓
Functional testing
   ↓
RBAC testing
   ↓
Fallback testing
   ↓
Performance review
   ↓

```

実際のアプリケーション要件がある場合にのみ、バックエンドを変更します。

通常、視覚テーマにバックエンド変更は必要ありません。

---

## 89. 開発ルール

テーマを開発するとき:

1. 既存の LUMS コンポーネントを再利用する。
2. ページの重複を避ける。
3. テーマ固有のスタイルを分離する。
4. 装飾用 JavaScript を運用ロジックから分離する。
5. 認証ロジックを導入しない。
6. 認可ロジックを導入しない。
7. シークレットを公開しない。
8. アクセシビリティを維持する。
9. 動きを減らす設定への対応を維持する。
10. 関連するすべてのロールをテストする。
11. 標準テーマへのフォールバックをテストする。
12. 新しい素材と動作を文書化する。

---

## 90. 変更の検証

テーマ変更を完了とする前に、表示と機能の両方を検証してください。

有用な検証手順:

```text id="i1v9yb"
Theme changed
      │
      ▼
Visual inspection
      │
      ▼
Page functionality
      │
      ▼
Role behavior
      │
      ▼
API behavior
      │
      ▼
Browser console
      │
      ▼
Regression tests
```

正しく見えるだけでは、テーマは完成していません。

LUMS の動作も変更されていない必要があります。

---

## 91. 回帰防止の原則

テーマ開発は、他の LUMS 変更と同じ一般原則に従う必要があります。

> **変更 → テスト → 検証 → 文書化**

視覚変更も機能上の回帰を引き起こす可能性があります。

例:

* ボタンが隠れる
* テキストが読めなくなる
* レイアウトが壊れる
* コントロールが使えなくなる
* JavaScript の競合
* 素材の欠落
* セレクターの誤り
* モバイルレイアウトの失敗

したがって、テストはテーマ開発の一部であり、任意の最終工程ではありません。

---

## 92. トラブルシューティング: テーマが読み込まれない

選択したテーマが表示されない場合:

1. ページを再読み込みする。
2. 標準テーマが読み込まれるか確認する。
3. ブラウザーコンソールを確認する。
4. 選択されたテーマ識別子が有効か確認する。
5. 必要なテーマ素材が利用可能か確認する。
6. JavaScript エラーを確認する。
7. 必要に応じてローカルのテーマ設定を消去する。
8. 再読み込みし、標準テーマへのフォールバックを確認する。

フロントエンドのテーマ問題を解決するために、バックエンドのセキュリティ設定を変更してはなりません。

---

## 93. トラブルシューティング: テーマでレイアウトが壊れる

テーマによってレイアウトに問題が生じた場合:

1. Standard LUMS テーマに切り替える。
2. 共通インターフェースが機能することを確認する。
3. 影響を受けているコンポーネントを特定する。
4. テーマ固有の CSS を調べる。
5. レスポンシブ動作を確認する。
6. ブラウザーコンソールのエラーを確認する。
7. テーマ固有のスタイルを修正する。
8. 他のテーマも再テストする。

標準テーマは重要な診断上の比較対象になります。

---

## 94. トラブルシューティング: テーマで JavaScript エラーが発生する

テーマ固有の JavaScript でエラーが発生した場合:

1. 標準テーマに切り替える。
2. LUMS の通常機能を確認する。
3. エラーが発生しているテーマスクリプトを特定する。
4. エラーが装飾によるものか、アプリケーションに関わるものか判断する。
5. テーマ固有の障害を取り除く。
6. 共通 LUMS JavaScript に影響がないことを確認する。
7. テーマ切替を再テストする。

装飾テーマのエラーを補うためだけに、運用 JavaScript を変更してはなりません。

---

## 95. トラブルシューティング: テーマ設定が無効

古いテーマや無効なテーマがローカルに保存されている場合:

```text id="b9n8wq"
Invalid stored preference
        │
        ▼
Fallback to Standard
        │
        ▼
Select a valid theme
```

バックエンドへ手動介入するのではなく、安全にフォールバックする方法が望ましい解決策です。

---

## 96. テーマの文書化

新しいテーマごとに次を文書化します。

* 内部識別子
* 表示名
* 視覚コンセプト
* 必要な素材
* オプションの視覚効果
* アクセシビリティ上の考慮事項
* 動きを減らす設定での動作
* 既知の制限

実装に関する文書では、テーマの動作に関する推測ではなく、現在の実際のコードを記述する必要があります。

---

## 98. 開発原則

オプションのテーマシステムは、制御されたフロントエンド拡張であり続ける必要があります。

運用上の複雑さを増やさずに LUMS の表現力と適応性を高めることが目的です。

したがって、望ましいアーキテクチャは次のとおりです。

```text id="l2e8o9"
Common LUMS
     │
     ├── Common functionality
     ├── Common security
     ├── Common backend
     └── Common application state
              │
              ▼
       Optional Theme Layer
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
    Theme A Theme B Theme C
```

共通アプリケーションが基盤です。

テーマはオプションの拡張です。

## 99. テーマの保守

可能な限り、テーマの保守は LUMS コアの保守と分離する必要があります。

視覚テーマの更新では、通常フロントエンド素材だけを変更します。

一般的な変更:

* CSS の調整
* 視覚素材
* テーマ固有の JavaScript
* アクセシビリティの改善
* レスポンシブレイアウトの修正
* アニメーションの調整
* テーマ名や表示の変更

テーマ更新のために、次の変更を必要としてはなりません。

* クライアント設定
* クライアントトークン
* データベーススキーマ
* 更新ジョブ
* パッケージ管理ロジック
* 認証
* RBAC
* サーバー側セキュリティ制御

テーマ変更でこのような修正が予期せず必要になった場合は、作業を進める前に依存関係をレビューしてください。

---

## 100. テーマの更新

テーマ更新は通常の LUMS 開発プロセスに従う必要があります。

```text id="2p7z9r"
Modify
   ↓
Test
   ↓
Verify
   ↓
Document
```

大きな変更の場合:

```text id="p7l5me"

   ↓

   ↓

   ↓

   ↓

   ↓
Performance review
   ↓
Documentation
```

見た目が正しいだけで、テーマを完成とみなしてはなりません。

## 101. 新しいテーマの追加

LUMS バックエンドを変更せずに新しいテーマを導入できます。

推奨プロセス:

### ステップ 1 — コンセプトを定義する

次の点を説明します。

* 視覚的アイデンティティ
* 対象とするスタイル
* タイポグラフィ
* 色
* 装飾要素
* オプションのアニメーション

### ステップ 2 — 識別子を定義する

安定した内部識別子を選択します。

### ステップ 3 — 表示を実装する

必要なスタイルと素材を追加します。

### ステップ 4 — 選択に統合する

共通テーマセレクターからテーマを選択できるようにします。

### ステップ 5 — テストする

次を検証します。

* 通常のページ
* 対話型コントロール
* レスポンシブレイアウト
* アクセシビリティ
* 動きを減らす設定
* 関連するすべての RBAC ロール
* フォールバック動作

### ステップ 6 — 文書化する

テーマと関連する実装詳細を記録します。

## 102. テーマの削除

テーマをローカルで選択したままのユーザーとの互換性を考慮して、テーマの削除を扱う必要があります。

そのため、フロントエンドは古い識別子を安全に処理する必要があります。

望ましい動作:

```text id="x4e7p1"
Old theme identifier
       │
       ▼
Theme no longer available
       │
       ▼
Standard LUMS
```

ブラウザー側の設定を削除するだけのために、テーマ削除でデータベース移行が必要になってはなりません。

---

## 103. テーマ名の変更

通常、表示名は内部識別子とは別に変更できます。

例:

```text id="8q4n1k"
Internal identifier
        │
        └── remains stable

Display name
        │
        └── may change
```

内部識別子自体を変更する場合、既存のローカル設定に対して移行または互換性マッピングが必要になる場合があります。

可能な限り、識別子は安定させてください。

---

## 104. テーマの互換性

テーマは共通の LUMS UI の変更と互換性を保つ必要があります。

新しい共通コンポーネントを導入したときは、既存テーマについて次を確認します。

* スタイルの欠落
* 間隔の崩れ
* 読みにくいテキスト
* 色の誤り
* レスポンシブ動作の欠落
* フォーカス状態の誤り
* アクセシブルでないコントロール

新しいバックエンド機能が導入されても、自動的に新しいテーマ機能が必要になるわけではありません。

共通アプリケーションを正とします。

---

## 105. 新しい LUMS 機能

LUMS に新機能が加わった場合、通常は共通機能が動作した後にテーマ対応を評価します。

推奨順序:

```text id="z4b7jx"
New LUMS feature
       │
       ▼
Common implementation
       │
       ▼
Functional tests
       │
       ▼
Theme compatibility
       │
       ▼
Theme-specific refinement
```

これにより、視覚的なカスタマイズがコア機能開発の依存要件になることを防ぎます。

---

## 106. テーマ API の安定性

本当に必要な場合を除き、テーマシステムに独立した API レイヤーを作らないようにします。

テーマは、LUMS が既に使用している同じフロントエンドアプリケーション状態と API の仕組みを利用する必要があります。

これにより次の項目が減ります。

* 要求ロジックの重複
* エラー処理の重複
* 認可前提の不一致
* 追加の保守負担
* 不必要な攻撃対象領域

そのため、テーマシステムは意図的に軽量です。

---

## 107. テーマのセキュリティレビュー

テーマを追加または大幅に変更する際は、次を確認してください。

```text id="3eq4w6"

[ ] No authentication bypass
[ ] No authorization logic
[ ] No CSRF bypass
```

変更が純粋に視覚的に見える場合でも、このレビューを行う必要があります。

フロントエンドコードも実行可能なコードです。

## 111. デプロイからの独立

テーマ素材は LUMS アプリケーションのフロントエンドに含まれます。

一般的なデプロイ手順は、メインのインストール／管理文書に記載されています。

この文書では、意図的に次の内容を重複して説明しません。

* Docker のデプロイ手順
* コンテナー強化コマンド
* Nginx 設定
* データベースのバックアップ手順
* サーバー復旧手順
* クライアントのインストール手順

これらの内容は、適切な運用文書に属します。

この分離により、デプロイアーキテクチャの変更に伴ってテーマ文書が古くなることを防ぎます。

## 112. ソースと実行時の分離

テーマシステムはアプリケーションソースの一部として理解する必要があります。

次の間には区別があります。

```text id="b6q7jv"
Source
   │
   ├── Theme definitions
   ├── CSS
   ├── JavaScript
   └── Assets

Runtime
   │
   ├── Built LUMS image
   └── Running LUMS application
```

ソースコード内のテーマ変更が、すでに稼働しているデプロイ環境に自動的に反映されるわけではありません。

更新済みフロントエンド素材を提供する責任は、通常の LUMS ビルド／デプロイ手順にあります。

## 113. バージョン管理

テーマに独自の LUMS バックエンドバージョンを導入する必要はありません。

テーマはフロントエンド／アプリケーションのバージョンの一部として進化できます。

テーマ変更で互換性に関する懸念が生じた場合、その内容を明示的に文書化してください。

例:

```text id="5y1p8f"

     │
     ├── visual-only
     │
     └── compatibility-affecting
```

後者のカテゴリでは追加の回帰テストが必要です。

## 119. 最終原則

オプションのテーマシステムは、技術アーキテクチャを損なうことなく、LUMS をより個人的で表現豊かにし、適応しやすくするためにあります。

基本原則は変わりません。

> **1 つの LUMS · 複数のインターフェース · 同じバックエンド**

テーマは LUMS の雰囲気を変えることができます。

しかし、LUMS が実際に実行できる操作を変えてはなりません。
