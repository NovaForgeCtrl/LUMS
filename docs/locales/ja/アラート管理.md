# LUMS アラート管理: 現在の実装

この文書は、LUMS のコードに現在存在するアラート管理機能を説明します。機能ロードマップでも、画面上のすべての操作が利用可能であるという保証でもなく、コードの参照資料です。実装の中心は `server/alerts.py` と `server/alerts_routes.py` です。

## 実装済みの機能

LUMS はアラートルール、アラート記録、状態履歴を SQLite に保存します。Flask blueprint はアプリケーションのデータベース接続ファクトリーを使って、リクエストごとの `AlertManager` を作成します。マネージャーは各リクエストでルールと未解決アラートをデータベースから読み込みます。

現在の API は次をサポートします。

- アラートルールの一覧表示、作成、更新、削除
- 既存の有効なルールに対する手動アラート発火
- アクティブなアラートとページ分割された履歴の表示
- アクティブなアラートの確認、解決、手動エスカレーション

重大度は `critical`、`warning`、`info` です。保存されるアラート状態は `triggered`、`acknowledged`、`resolved`、`escalated` です。確認、解決、エスカレーションの変更は `alert_history` に記録されます。解決済みアラートはマネージャーのアクティブ一覧から除かれますが、データベースには残ります。

## 重要な制限

ルールモデルには条件、しきい値、重大度、エスカレーション経路、グループ化フラグ、重複排除フラグが保存されます。現在のサーバーは、テレメトリやその他の測定値に対する条件の評価を**行いません**。ルールは自動発火しません。認証済みの呼び出し元が `POST /alerts/trigger` を呼び出す必要があります。グループ化と重複排除の値は保存されますが、適用されません。手動で発火すると、マネージャーはルールのエスカレーション経路に指定されたプロバイダーへ送信を試みます。しかし Web アプリケーションはプロバイダーマップが空の状態で各マネージャーを作成し、連携エンドポイントからプロバイダーを設定できません。そのため、アプリケーション経由で発火したアラートは現在配信されません。

`AlertManager` はメール、Slack、PagerDuty、汎用 Webhook のプロバイダークラスを定義しますが、アプリケーションからは設定できません。連携 API は意図的に連携を利用不可として報告し、設定、テスト、削除の要求に `501 Not Implemented` を返します。アラート履歴をこのエンドポイントから削除できないように、`POST /alerts/clear-all` も `501` を返します。

`/alerts/` ページは基本的なサーバー描画の概要です。ルール、履歴、連携のタブ操作とアラートのアクションボタンは、完全な対話型管理画面ではありません。表示されたボタンが動作すると想定せず、文書化された API の動作を正としてください。現在の実装にはリアルタイムの push 通知や WebSocket 更新はありません。

## ルートとアクセス制御

すべてのルートで認証済み Web セッションが必要です。

| メソッド | ルート | 権限 | 現在の動作 |
| --- | --- | --- | --- |
| `GET` | `/alerts/` | `alerts.view` | 基本的なアラート概要を表示 |
| `GET` | `/alerts/rules` | `alerts.view` | 保存済みルールを一覧表示 |
| `POST` | `/alerts/rules` | `alerts.manage` | 検証済みルールを作成 |
| `PUT` | `/alerts/rules/<rule_id>` | `alerts.manage` | 保存済みルールを更新 |
| `DELETE` | `/alerts/rules/<rule_id>` | `alerts.manage` | データベース制約が許す場合にルールを削除 |
| `GET` | `/alerts/current` | `alerts.view` | アクティブなアラートを返す |
| `GET` | `/alerts/history` | `alerts.view` | アラート履歴を返す |
| `POST` | `/alerts/trigger` | `alerts.manage` | 有効なルールのアラートを手動作成 |
| `POST` | `/alerts/<alert_id>/acknowledge` | `alerts.manage` | 確認を記録 |
| `POST` | `/alerts/<alert_id>/resolve` | `alerts.manage` | アクティブなアラートを解決 |
| `POST` | `/alerts/<alert_id>/escalate` | `alerts.manage` | エスカレーション数を手動で増加 |
| `POST` | `/alerts/clear-all` | `alerts.manage` | 無効。`501` を返す |
| `GET` | `/alerts/integrations` | `alerts.view` | 空の一覧と `available: false` を返す |
| `POST` / `DELETE` | `/alerts/integrations/...` | `alerts.manage` | 無効。`501` を返す |

状態を変更するルートには、該当する権限に加えて CSRF 保護が必要です。権限チェックはサーバーで強制されます。`alerts.manage` は `alerts.view` に依存します。ロールへの権限付与は、セキュリティ移行処理と権限設定で管理されます。

## 永続テーブル

`AlertManager` は作成時に次のテーブルを初期化します。

- `alert_rules`: ルール定義と設定値
- `alerts`: アラート記録と現在のライフサイクル状態
- `alert_history`: 確認、解決、エスカレーションの履歴
- `notification_integrations`: 将来用の連携設定スキーマ
- `alert_notifications_log`: 将来用の配信ログスキーマ

最後の 2 テーブルが存在しても、連携が利用可能という意味ではありません。安全な永続設定と配信動作が実装されるまで、連携用 HTTP エンドポイントは無効です。

## 検証

アラートルート、権限の強制、リクエストデータの検証、永続化、ライフサイクル動作は `tests/test_alerts.py` でテストされています。デプロイするリビジョンに対して該当テストを再実行してください。テストに合格しても、無効な連携ルートや未評価のルールが利用可能な機能になるわけではありません。
