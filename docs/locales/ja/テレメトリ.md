# LUMS CPU・メモリ・ネットワークのテレメトリ

## 概要

オプションの LUMS テレメトリエージェントは、管理対象の Linux システムから CPU 使用率、メモリ使用率、ネットワークカウンター、および範囲を制限したホストスナップショットを収集し、LUMS サーバーに送信します。

サーバーはテレメトリサンプルを保存し、クライアントのテレメトリダッシュボードで使用する認証済み履歴 API を提供します。

テレメトリは既存の LUMS reporting Agent および Watcher とは別の機能です。どちらのコンポーネントも置き換えず、パッケージの更新も実行しません。

## コンポーネント

| コンポーネント | 役割 |
| --- | --- |
| `agent/telemetry.py` | CPU、メモリ、ホスト、ネットワーク、センサー、サービス、コンテナーのメトリクスを収集 |
| `agent/lums-telemetry.service` | 制限付き systemd サービスとしてテレメトリエージェントを実行 |
| `agent/lums-telemetry.timer` | テレメトリ収集を定期的にスケジュール |
| `server/app.py` | 送信を認証し、メトリクスを検証してサンプルを保存 |
| `server/static/telemetry.js` | フリート概要、履歴チャート、ドーナツゲージを表示 |

## 測定値

各サンプルには、次の必須フィールドが含まれます。

- `cpu_percent`: 0～100 の CPU 使用率。
- `memory_percent`: 0～100 のメモリ使用率。
- `memory_total_bytes`: 検出されたメモリ合計（バイト）。
- `memory_available_bytes`: 使用可能なメモリ（バイト）。

エージェントバージョン 1.1.0 以降では、次のオプションの累積カウンターも送信されます。

- `network_rx_bytes`: 起動後に受信したバイト数。ループバック以外の全インターフェースの合計です。
- `network_tx_bytes`: 起動後に送信したバイト数。ループバック以外の全インターフェースの合計です。

2 つのカウンターは、負でない整数として必ず同時に送信してください。これらを省略する古いエージェントも引き続き動作しますが、そのクライアントのネットワークデータはダッシュボードに表示されません。サーバーは生のカウンターを保存し、データ要求時に連続するサンプルからバイト毎秒を計算します。最初のサンプル、カウンターのリセット（再起動など）の後、またはサンプル間隔が 5 分を超える場合は、速度を表示しません。

エージェントバージョン 1.2.0 以降では、範囲を制限したシステムスナップショットも報告されます。

- ロードアベレージ、稼働時間、オペレーティングシステム、カーネル、ルートファイルシステムの使用状況。
- 各ネットワークインターフェースのリンク状態、バイトカウンター、エラー、ドロップ数。
- 設定済み DNS サーバーと、ベストエフォートで確認したゲートウェイ、DNS、インターネットへの到達性。
- カーネルから取得できる場合の温度およびファンの読み取り値。
- 選択された systemd サービスの状態、稼働時間、再起動回数。ローカルのツールと権限で読み取り専用の確認が可能な場合は、Docker および Podman コンテナーの名前と正規化された状態。
- 履歴チャートおよびしきい値イベント評価用の、各テレメトリサンプル時点のディスク使用率。

エージェントバージョン 1.3.0 以降では、範囲を制限した運用イベントの概要も報告されます。SSH ログイン失敗の件数とタイムスタンプ、最近の journal 警告およびエラー件数、ログイン／ログアウトのタイムスタンプ、最近の起動に関する journal の最初と最後のタイムスタンプが含まれます。生の journal メッセージ、ユーザー名、送信元アドレスは送信されません。各 journal クエリは一致するレコード 500 件に制限され、ダッシュボードでは件数 500 を `500+` と表示します。起動履歴は最大 10 件、ログイン／ログアウト履歴は最大 20 件です。

サーバーは連続するサンプルからインターフェースごとのスループットを計算します。サービス、コンテナー、温度、ファン、イベントの詳細は最新のスナップショットのみ保存し、履歴サンプルごとには重複して保存しません。オペレーティングシステムで公開されていない、または許可されていないオプションのメトリクスは利用不可として表示されます。エージェントはサービスやコンテナーを起動、停止、変更しません。エージェントサービスには Docker ソケットへのアクセス権が付与されていません。実行環境ですでにサービスアカウントによる読み取りが許可されていない限り、コンテナーの詳細は利用できません。

テレメトリの systemd ユニットは読み取り専用の journal アクセスのために `systemd-journal` グループに属します。これによりシステムログへのアクセス権が付与されますが、エージェントが送信するのは上記の範囲を制限した概要のみです。既定のサービス許可リストには LUMS、Docker、SSH のユニットが含まれます。エージェントの環境ファイルにカンマ区切りの `LUMS_MONITORED_SERVICES` 値を設定すると上書きできます。有効な `.service` ユニット名のみ受け付けます。

ゲートウェイへの到達性確認には、利用可能な場合は 1 パケットの ping を使用します。DNS への到達性確認には短時間の `getent` 検索を使用し、インターネットへの到達性確認には `1.1.1.1:443` への短時間の TCP 接続を試みます。これらはあくまで指標であり、障害ではなくファイアウォールポリシーを反映している場合があります。

サンプルのタイムスタンプはサーバーが割り当て、無効なペイロードは拒否します。

サーバーの更新後、データベースマイグレーションを一度実行してください（`python3 server/security_migration.py`）。これにより、ネットワーク列、最新システム状態テーブル、ダッシュボード設定、イベント履歴が作成されます。新しいメトリクスの報告を開始するには、各クライアントのエージェントも更新してください。LUMS サーバー自体を監視するには、サーバーをクライアントとして登録し、そのホストにもテレメトリエージェントをインストールして設定します。

## セキュリティとプライバシー

テレメトリエンドポイントでは、設定済みの LUMS クライアントトークンによるクライアント認証が必要です。

エージェントはリモートサーバーへの接続に HTTPS を使用します。平文 HTTP が許可されるのは `localhost`、`127.0.0.1`、`::1` のみです。リモートサーバーへの接続には HTTPS が必要です。証明書検証用の CA ファイルを任意で設定できます。

エージェントはクライアントトークンを JSON ペイロードに含めず、ログにも記録しません。systemd サービスは制限付き実行環境を使用し、記載されたメトリクスの収集に root 権限を必要としません。

テレメトリに含まれるのはシステムリソースと運用メタデータであり、パッケージ更新や任意のコマンド出力ではありません。インターフェースアドレス、DNS サーバー、サービス名、コンテナー名は機密性のあるインフラ情報となる場合があります。ダッシュボードと API へのアクセスは `clients.view` 権限で保護されます。

## データ保持

サーバーは新しいテレメトリ送信を処理する際、7 日より古いテレメトリサンプルを削除します。

認証済み履歴エンドポイントでは、1～168 時間の期間を指定できます。アクセスには適切なクライアント閲覧権限が必要です。大きな結果セットは最大 1,000 サンプルにダウンサンプリングされる場合があります。

`/health` ダッシュボードでは 1 時間、24 時間、7 日の履歴期間を選択でき、表示データは 5 秒ごとに更新されます。選択したクライアントについて、CPU、メモリ、ディスク使用率、ネットワーク合計の履歴に加え、ディスク、ロード、稼働時間、カーネル、オペレーティングシステム、インターフェース、接続状況、センサー、サービス、コンテナーの最新情報を表示します。また、状態、古いテレメトリ、高負荷でフィルターでき、検索と並べ替えに対応したフリート概要と、クライアントごとの詳細を表示します。CPU とメモリは折れ線グラフ、面グラフ、現在値のドーナツゲージで表示できます。選択した表示形式はブラウザーに記憶されます。ネットワーク通信量はダウンロード速度とアップロード速度で表示されます。2 分より古いテレメトリは古いデータとして表示されます。フリート概要はクライアント閲覧権限が必要な `/api/telemetry/overview` エンドポイントを使用します。履歴要求は 1～168 時間に制限され、最大 1,000 サンプルにダウンサンプリングされる場合があります。systemd timer はワンショットエージェントを 5 秒ごとに実行する設定ですが、実際のサンプル頻度はサービスの完了時間とネットワークの可用性によって異なります。ダッシュボードには最近の SSH 失敗、journal 警告／エラー件数、ログイン／ログアウト履歴、起動履歴も表示されます。しきい値警告には、ログイン中のユーザーが設定した CPU、RAM、ディスクの上限を使用します。journal 件数はクエリごとに一致するレコード 500 件までです。最後に成功したバックアップ作成時刻はサーバーの監査ログから読み取られます。これは復元テストではありません。

ヘルスダッシュボードのレイアウトは固定です。ユーザーごとに独立して保存される CPU、RAM、ディスクのしきい値（50%～99%、既定値 90%）を設定できます。しきい値超過と 2 分を超えるテレメトリの途絶はイベント履歴に表示されます。しきい値アラートは保持中のサンプルから導出され、ログイン中のユーザーのしきい値を使用します。サービス状態の遷移と新しい SSH 失敗タイムスタンプは、データ取り込み時に記録されます。イベントは最大 7 日間保持され、イベントエンドポイントは最大 500 件を返します。

選択したクライアントと期間について CSV および JSON エクスポートを利用できます。履歴のダウンロードにはその期間内の保持されている全サンプルが含まれます。チャートは最大 1,000 ポイントにダウンサンプリングされます。エクスポートには `clients.view` 権限が必要で、ブラウザーにはキャッシュされません。

Wazuh と Suricata は、オプションのユーザー別ステータス行として表示できます。これらの行が示すのは設定済みの systemd サービス状態のみです。LUMS はそれらの API に接続せず、アラートも収集しません。サービスを報告するには、インストール済みユニット（例: `wazuh-agent.service`、`wazuh-manager.service`、`suricata.service`）をエージェントの `LUMS_MONITORED_SERVICES` 許可リストに含めます。LUMS で統合用の認証情報が必要になったり保存されたりすることはありません。

## 設定

テレメトリエージェントは `LUMS_BASE`、`LUMS_TOKEN`、任意の `LUMS_CA_FILE` 環境変数を使用します。リモートサーバーへの接続には HTTPS が必要です。インストールと設定方法については[インストールガイド](インストールとアップグレード.md)を参照してください。

## インストールと運用

テレメトリサービスは通常の LUMS クライアントとは別です。Debian では、まずクライアント上の LUMS リポジトリのチェックアウトを更新し、ルートディレクトリから `sudo bash scripts/install-telemetry-agent.sh` を実行します。インストーラーは `/etc/default/lums-agent` に `LUMS_BASE` と `LUMS_TOKEN` が定義されていることを確認し、現在のコレクターと systemd ユニットをインストールして timer を有効化し、テストサンプルを送信します。トークンは表示しません。

timer とサービスの状態は `systemctl status lums-telemetry.timer` および `systemctl status lums-telemetry.service` で確認します。最近のサービスログは `journalctl -u lums-telemetry.service -n 30 --no-pager` で確認できます。スケジュールされた実行の合間にワンショットサービスが非アクティブでも、必ずしもエラーではありません。timer と最近のログも確認してください。

`/monitoring` ページでは、サンプルがない状態、詳細スナップショットを含まない基本テレメトリ、古くなったスナップショットを区別し、これらのクライアント側チェックを表示します。トラブルシューティング時にトークンを貼り付けたり共有したりしないでください。

## トラブルシューティング

- **サンプルが表示されない:** サーバー URL、クライアントトークン、認証を確認します。
- **TLS エラー:** サーバー証明書と設定済み CA ファイルを確認します。
- **サービス障害:** サービスの journal を確認します。
- **履歴が表示されない:** クライアント閲覧権限と要求期間（1～168 時間）を確認します。

ダッシュボードの状態しきい値とバックアップストレージ表示の制約については、[LUMS ヘルスダッシュボード](LUMS_システム健全性ダッシュボード.md)を参照してください。一般的な手順は、[インストールガイド](インストールとアップグレード.md)と[トラブルシューティングガイド](トラブルシューティング.md)を参照してください。原文は[英語のテレメトリガイド](../../../telemetry.md)です。
