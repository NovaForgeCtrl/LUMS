# LUMS インストールガイド

## Linux アップデート管理サーバー

**プロジェクト：** LUMS
**スローガン：** ノイズのない Linux アップデート管理。
**リポジトリ：** `NovaForgeCtrl/LUMS`

---

## はじめに：開始前にインストールを理解する

本ガイドは、高度なメンテナンスと検証手順を含む完全なサーバーインストールを扱います。これは**レビューなしに実行できる単一スクリプトではありません**：サーバー名、TLS 証明書、シークレットファイル、バックアップ先、ネットワーク、データベースはインストールごとに異なります。

### 何がインストールされるのか？

* **LUMS サーバー：** Docker コンテナ内で動作する Web インターフェースと API。
* **Nginx：** 外部からの HTTPS 接続を受け入れ、ローカルでコンテナに転送します。
* **データボリューム：** SQLite データベースを格納します。このボリュームはアップグレードを経ても存続し、通常のコンテナ置換時に決して削除してはなりません。
* **シークレットファイル：** とりわけアプリケーションセッションを保護します。Git リポジトリ、Docker イメージ、チャットメッセージに決して入れないでください。
* **LUMS エージェントとウォッチャー：** 管理対象 Linux クライアントに個別にインストールします。サーバーが動作しているだけでは、どのクライアントも更新されません。

| 用語 | 意味 |
| --- | --- |
| ターミナル / シェル | Linux コマンドを入力するテキストウィンドウ。 |
| `sudo` | 後続のコマンドを管理者権限で実行します。Linux がパスワードを求めることがあります。 |
| ホスト | Docker と LUMS サーバーを実行する Linux コンピューター。 |
| コンテナ | LUMS Web アプリケーションを実行する分離されたプロセス。 |
| イメージ | Docker がコンテナを起動するために使用する準備済みテンプレート。 |
| ボリューム | コンテナが置換されても残る永続的な Docker ストレージ。 |
| プレースホルダー | `LUMS-SERVER` のような、実際の値に置き換える必要があるテキスト。 |

### テストのみ実行する（これはサーバーをインストールしません）

これらの手順は Debian 13 向けで、ソースをチェックアウトし、ローカルでテストを実行するのに適しています。ネットワーク経由で到達可能な本番サーバーを作成するものでは**なく**、他のコンピューターにエージェントをインストールするものでもありません。`sudo` は Debian パッケージをインストールする場合にのみ必要です。

```bash
sudo apt update
sudo apt install -y git python3 python3-venv
git clone https://github.com/NovaForgeCtrl/LUMS.git ~/LUMS
cd ~/LUMS
python3 -m venv .venv-test
./.venv-test/bin/python -m pip install -r server/requirements.txt -r requirements-dev.txt
./.venv-test/bin/pytest -q
```

`apt update` はパッケージリストを更新するだけで、インストール済みのすべてのソフトウェアをアップグレードするものではありません。`.venv-test` Python 仮想環境は、テスト依存関係をシステムの他の部分と分離します。テスト実行が成功すると、終了コード `0` で終了します。テストの数はプロジェクトの成長に伴って変化することがあります。環境の作成に失敗した場合は、`python3-venv` がインストールされていることを確認してください。テストが失敗した場合は、完全なエラーを保存し、[トラブルシューティングガイド](トラブルシューティング.md) を読んでください。本番データを削除しないでください。

実際のインストールに進む場合は、番号付きのセクションに進み、最初にセキュリティとバックアップの手順を読んでください。LUMS が既に稼働している場合は、初回インストール手順ではなく [`administration.md`](管理とバックアップ.md) のアップグレード手順を使用してください。

# 1. 概要

LUMS は、管理された更新配布、クライアントレポート、パッケージ管理、更新ジョブ実行、結果検証、および監査可能な管理のための集中型 Linux アップデート管理プラットフォームです。

現在のアーキテクチャは、管理サーバーと管理対象 Linux クライアントを分離しています。

サーバーは以下を提供します：

* Web ベースの管理
* クライアント管理
* クライアント認証
* パッケージインベントリ
* 利用可能な更新のレポート
* パッケージ検索
* パッケージのインストールと削除
* 更新ジョブ管理
* ジョブ結果の検証
* 更新履歴
* ロールベースのアクセス制御
* 監査ログ
* SQLite ベースの永続状態

Linux クライアントは以下を提供します：

* システム情報
* インストール済みパッケージのインベントリ
* 利用可能な更新の検出
* パッケージ操作
* 更新ジョブ実行
* アイドル状態の検出
* ジョブのチェックポイントと復元
* 再起動の検出
* 結果のレポート

現在の実装は以下をサポートしています：

```text
Debian / Ubuntu
    └── APT / dpkg

Arch Linux
    └── pacman
```

# 2. アーキテクチャ

本番アーキテクチャは以下のとおりです：

```text
                         LUMS Server
                              │
                              │ HTTPS :443
                              ▼
                       ┌──────────────┐
                       │    Nginx     │
                       │  TLS / Proxy │
                       └──────┬───────┘
                              │
                              │ HTTP
                              ▼
                       127.0.0.1:5050
                              │
                              ▼
                    ┌───────────────────┐
                    │   Docker: lums    │
                    │                   │
                    │   Gunicorn        │
                    │   Flask :5000     │
                    │   SQLite          │
                    └─────────┬─────────┘
                              │
                              ▼
                         lums-data
                              │
                              ▼
                   /var/lib/lums/lums.db


        Linux Client
              │
              │ HTTPS + Bearer Token
              ▼
         LUMS API
              │
              ├── Report
              ├── Package Search
              ├── Job Retrieval
              └── Job Result
```

LUMS アプリケーションは**ネットワークに直接公開されることを意図していません**。

アプリケーションコンテナは以下のようにバインドされています：

```text
127.0.0.1:5050 → container:5000
```

Nginx が外部 HTTPS エントリポイントです。

ポート `5000` は直接公開されません。

ポート `5050` は localhost 専用に保たなければなりません。

LUMS は現在、3 つの Web ロールを提供しています：

```text

viewer
```

## Administrator

管理者は以下を含む管理操作を実行できます：

```text
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
Create and disable clients
Rotate client tokens
Manage users
Manage roles
```

---

## Operator

オペレーターは運用管理を実行できます：

```text
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
```

オペレーターは以下にアクセスできません：

```text
User management
Role management
Client creation/disabling
Client-token rotation
```

---

## Viewer

Viewer は意図的に制限されたアクセス権を持ちます。

Viewer は以下にアクセスできます：

```text

Installed software
```

以下の管理領域は Viewer インターフェースから隠され、サーバー側で保護されます：

```text

Update Jobs
Update History
Package Management
System Maintenance
```

したがって、UI の非表示はセキュリティ境界ではありません。

サーバー側の認可が引き続き必須です。

# 10. ホスト設定ディレクトリの準備

必要なホスト側ディレクトリを作成します：

```bash
sudo install -d -m 700 /etc/lums
sudo install -d -m 700 /etc/lums/secrets
sudo install -d -m 700 /etc/lums/tls
```

シークレットディレクトリにはアプリケーションシークレットが含まれます。

TLS ディレクトリには TLS 証明書と秘密鍵が含まれます。

これらのディレクトリを保護することで、偶発的な開示のリスクが減少します。

確認します：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums \
    /etc/lums/secrets \
    /etc/lums/tls
```

# 11. アプリケーションシークレットの作成

LUMS アプリケーションシークレットは、Docker イメージに直接埋め込むのではなく、ホスト上に保存されます。

本番シークレットのパスは：

```text
/etc/lums/secrets/lums_secret
```

ランダムなシークレットを生成します：

```bash
sudo sh -c 'umask 077 && openssl rand -hex 32 > /etc/lums/secrets/lums_secret'
```

生成されたファイルを保護します：

```bash
sudo chmod 600 \
    /etc/lums/secrets/lums_secret
```

シークレットを表示せずに権限を確認します：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums/secrets/lums_secret
```

期待値：

```text
600
```

シークレットは決して以下にしてはなりません：

```text
Committed to Git
Printed into logs
Included in the Docker image
Placed into screenshots
Published in issues
Included in documentation
```

コンテナは読み取り専用バインドマウントを通じてシークレットを受け取ります。

---

# 12. TLS 素材の準備

LUMS は外部アクセスに HTTPS を使用します。

推奨されるホスト側の場所は：

```text
/etc/lums/tls/lums.crt
/etc/lums/tls/lums.key
```

Nginx を設定する前に、適切な証明書と秘密鍵をインストールしてください。

秘密鍵を保護します：

```bash
sudo chmod 600 \
    /etc/lums/tls/lums.key
```

証明書は Nginx サービスから読み取り可能でも問題ありません：

```bash
sudo chmod 644 \
    /etc/lums/tls/lums.crt
```

確認します：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums/tls/lums.crt \
    /etc/lums/tls/lums.key
```

秘密鍵は決して Git にコミットしたり、Docker イメージに含めたりしてはなりません。

# 13. インストール原則

インストールは管理された段階で進めるべきです：

```text
Repository
    ↓
Host configuration
    ↓
Application secret
    ↓
TLS material
    ↓
Docker image
    ↓
Persistent volume
    ↓
Hardened container
    ↓
Nginx / HTTPS
    ↓
Administrator
    ↓
Server validation
    ↓
Linux clients
```

サーバーが独自の検証チェックに合格する前に、本番クライアントを接続しないでください。

以下のセクションでは、Docker イメージの構築と強化された本番展開について続けます。

# 14. LUMS Docker イメージのビルド

本番イメージをビルドする前に、リポジトリが意図する状態にあることを確認してください。

リポジトリに入ります：

```bash
cd /opt/lums-public
```

本番イメージを作成する前にテストスイートを実行します：

```bash
./.venv-test/bin/pytest -q
```

テスト数はプロジェクトの進化に伴い増加することが見込まれます。

重要な要件は、展開前に該当するテストスイートが正常に完了することです。

Docker イメージをビルドします：

```bash
sudo docker build \
    -t lums:latest \
    .
```

イメージが存在することを確認します：

```bash
sudo docker image ls lums
```

イメージを検査します：

```bash
sudo docker image inspect lums:latest
```

本番イメージはピン留めされた Python 3.13 slim ベースイメージに基づいています。

Dockerfile は必要に応じてピン留めされた本番依存関係も使用します。

# 16. 永続 Docker ボリュームの作成

永続 LUMS データボリュームを作成します：

```bash
sudo docker volume create lums-data
```

確認します：

```bash
sudo docker volume inspect lums-data
```

ボリュームは永続アプリケーションデータを保存します：

```text
lums-data
    ↓
/var/lib/lums
    ↓
/var/lib/lums/lums.db
```

コンテナファイルシステム自体を永続アプリケーションストレージとして扱ってはなりません。

したがって、`lums-data` ボリュームが保持されている限り、データベースはコンテナ置換後も存続します。

> [!IMPORTANT]
> 通常のアプリケーションアップグレード中に `lums-data` を削除しないでください。

ボリュームを削除すると、内部に保存されている SQLite データベースが削除されます。

# 25. 読み取り専用ルートファイルシステムの確認

# 35. Nginx の設定

Nginx は LUMS の外部 HTTPS エントリポイントを提供します。

アプリケーション自体は以下にバインドされたままです：

```text
127.0.0.1:5050
```

意図されるリクエストパスは：

```text
Client
   │
   │ HTTPS
   ▼
Nginx :443
   │
   │ HTTP localhost
   ▼
127.0.0.1:5050
   │
   ▼
LUMS container :5000
```

Nginx サイト設定を作成します：

```bash
sudo tee /etc/nginx/sites-available/lums > /dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;

    server_name LUMS-SERVER;

    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;

    server_name LUMS-SERVER;

    ssl_certificate     /etc/lums/tls/lums.crt;
    ssl_certificate_key /etc/lums/tls/lums.key;

    location / {
        proxy_pass http://127.0.0.1:5050;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
```

以下を置き換えます：

```text
LUMS-SERVER
```

インストールで使用するホスト名またはアドレスに。

本番設定でリテラルプレースホルダーを使用しないでください。

---

```bash
for row in rows:
    print(row)

PY
```

```text
session data
client tokens
application secrets
```

# 52. Viewer の分離の確認

Viewer アカウントでログインし、表示されるインターフェースを確認します。

Viewer は管理コントロールを受け取るべきではありません。

Viewer は UI をバイパスして保護されたエンドポイントを直接呼び出せてはなりません。

保護された操作には認可失敗が返されるはずです。

期待される原則は：

```text
UI restriction
     +
server-side authorization
     =
RBAC boundary
```

JavaScript や隠し HTML 要素のみを認可メカニズムとして依存しないでください。

# 54. ログイン速度制限の確認

# 65. クライアントトークン

これは、クライアント資格情報がパスワードのように扱われるべきことを意味します。

実際のトークンを以下に置かないでください：

```text

documentation
screenshots
issue reports
shell history
public configuration
```

# 66. クライアントトークンのプロビジョニング

クライアント上で。

```text
    ↓

    ↓

    ↓
```

# 68. TLS 信頼

LUMS エージェントは HTTPS でサーバーと通信します。

証明書検証は有効のままにしなければなりません。

公開的に信頼された証明書の場合、通常のオペレーティングシステムのトラストストアで十分です。

プライベートラボ CA の場合、クライアントに CA 証明書をインストールします。

検証を無効にすることで証明書の問題を解決しないでください。

正しい解決策は、クライアントが意図する認証局を信頼するようにすることです。

---

# 69. Debian / Ubuntu の TLS 信頼

Debian 系システムでは、プライベート CA をシステムトラストストアにインストールできます。

CA 証明書をコピーします：

```bash
sudo cp \
    lums-ca.crt \
    /usr/local/share/ca-certificates/lums-ca.crt
```

トラストストアを更新します：

```bash
sudo update-ca-certificates
```

証明書が受け入れられることを確認します：

```bash
curl -I \
    https://LUMS-SERVER/
```

コマンドが `-k` なしで成功した場合、システム信頼設定は機能しています。

---

# 70. Arch Linux の TLS 信頼

Arch Linux では、システムの設定されたトラストストアメカニズムを使用してプライベート CA をインストールします。

CA をインストールした後、アクティブなトラストストア設定に従ってトラストデータベースを更新します。

確認します：

```bash
curl -I \
    https://LUMS-SERVER/
```

接続は以下なしで成功するはずです：

```text
-k
```

エージェントを証明書検証を無視するように永続的に設定しないでください。

# 80. 実行ウォッチャーのインストール

LUMS 実行ウォッチャーは、クライアント上の保留中の更新ジョブを検出して実行する責任があります。

アーキテクチャはレポートと実行を分離します：

```text
Reporting
    │
    ▼
lums-agent.service
    │
    └── system inventory / update detection

Execution
    │
    ▼
lums-agent-watcher.service
    │
    └── pending update jobs
```

この分離により、通常のクライアントレポートが更新実行とは独立して継続できます。

# 84. アイドル対応実行の理解

ウォッチャーは、更新ジョブを実行する前にクライアントのアイドル情報を使用できます。

意図されるフローは：

```text
Pending job
    │
    ▼
Watcher
    │
    ▼
Idle detection
    │
    ├── idle state available
    │       │
    │       ▼
    │   idle threshold
    │       │
    │       ▼
    │   execute when allowed
    │
    └── idle state unavailable
            │
            ▼
        use configured
        fallback behavior
```

アイドル検出は認証や認可として解釈してはなりません。

これは実行スケジューリングメカニズムにすぎません。

# 85. アイドル検出の確認

インストールされたエージェント/ウォッチャー実装を通じて、アイドル検出パスを手動で実行します。

結果のサービスジャーナルを検査します：

```bash
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 100 \
    --no-pager
```

プラットフォームが必要なアイドル情報を提供しない場合、クライアントはアイドル検出を利用不可としてレポートする場合があります。

これは自動的に失敗ではありません。

重要な区別は：

```text
idle_supported = available
```

対：

```text
idle_supported = unavailable
```

アイドル情報が返されなかったからといって、クライアントがアイドルであると仮定してはなりません。

# 97. ジョブチェックポイントの確認

LUMS はジョブとパッケージアイテムの状態を追跡します。

パッケージベースのジョブでは、個々のパッケージアイテムをチェックポイントできます。

意図される動作は：

```text
Package A → SUCCESS
Package B → SUCCESS
Package C → RUNNING
             │
             ▼
          interruption
             │
             ▼
          recovery
             │
             ▼
Package A → not repeated
Package B → not repeated
Package C → resumed / handled
```

これにより、中断後に完了したパッケージ操作が不必要に繰り返されるのを防ぎます。

# 132. バックアップ戦略

LUMS SQLite データベースは永続アプリケーション状態です。

```text

TLS material
LUMS application secret
Deployment configuration
```

またはコンテナファイルシステムに依存しないでください。

Docker ボリューム：

# 165. クライアントインストールの削除

LUMS クライアントは別々に廃止しなければなりません。

エージェントタイマーを無効化します：

```bash
sudo systemctl disable --now \
    lums-agent.timer
```

ウォッチャータイマーを無効化します：

```bash
sudo systemctl disable --now \
    lums-agent-watcher.timer
```

残りのサービスを停止します：

```bash
sudo systemctl stop \
    lums-agent.service \
    lums-agent-watcher.service
```

インストールされた systemd ユニットを削除します：

```bash
sudo rm -f \
    /etc/systemd/system/lums-agent.service \
    /etc/systemd/system/lums-agent-watcher.service \
    /etc/systemd/system/lums-agent.timer \
    /etc/systemd/system/lums-agent-watcher.timer
```

systemd を再読み込みします：

```bash
sudo systemctl daemon-reload
```

エージェントインストールを削除します：

```bash
sudo rm -rf \
    /opt/lums-agent
```

クライアント設定を削除します：

```bash
sudo rm -f \
    /etc/default/lums-agent
```

これらのステップは、クライアントが LUMS 管理から真に削除される場合にのみ実行してください。
