# LUMS トラブルシューティング

本ガイドは、LUMS サーバー、Linux エージェント、実行ウォッチャー、更新ジョブ、認証、パッケージ管理、データベース、および Docker 展開に関するトラブルシューティング手順を提供します。

トラブルシューティングのプロセスは常に**変更前の観察**から始めるべきです。

目的は、設定、データベース状態、認証情報、またはセキュリティ制御を不必要に変更することなく、期待される動作が停止する最初のコンポーネントを特定することです。

---

## はじめに：安全にトラブルシューティングする

Linux が初めての場合、エラーは自動的にデータが失われたことを意味するものではありません。一度に複数のことを変更しないでください。以下のチェックから始め、**問題が発生したとき**とその直前に**何が起こったか**をメモしてください。

### LUMS サーバーでの最初のチェック

```bash
sudo docker ps -a --filter name=lums
sudo docker logs --tail 100 lums
sudo systemctl status nginx --no-pager
sudo nginx -t
```

`docker ps -a` は停止したコンテナも表示します。`docker logs` は最近のアプリケーションメッセージを読み取ります。`systemctl status` は Nginx が実行中かどうかを示し、`nginx -t` は設定を変更せずにチェックします。`nginx -t` が失敗した場合、原因が修正されるまで Nginx を再読み込みしないでください。

### 管理対象クライアントでの最初のチェック

```bash
sudo systemctl status lums-agent.service --no-pager
sudo journalctl -u lums-agent.service -n 100 --no-pager
sudo systemctl status lums-agent-watcher.service --no-pager
sudo journalctl -u lums-agent-watcher.service -n 100 --no-pager
```

エージェントとウォッチャーは別々のサービスです。エージェントのレポート成功は、ウォッチャーが更新ジョブを実行できることを証明するものではありません。`oneshot` サービスの場合、成功後に `inactive` であっても正常なことがあります。結果とログメッセージも確認してください。

### コマンド出力を共有する前に

ログと設定にパスワード、クライアントトークン、セッションまたは API キー、秘密鍵、個人情報が含まれていないか確認してください。シークレットファイルの内容や環境変数の完全な値を絶対に共有しないでください。助けが必要な場合は、機密情報を削除した上で関連するエラーメッセージのみを共有してください。

**最初に以下を行わないでください**：データベースや Docker ボリュームの削除、コンテナを特権モードで実行、セキュリティオプションの無効化、パッケージマネージャーのロックファイルの削除、またはトークンのローテーション。これらの操作はデータを破壊し、証拠を消去し、問題を悪化させる可能性があります。チェックが失敗した場合は、その出力を保存し、以下の関連セクションに進んでください。

# 1. トラブルシューティング哲学

LUMS は複数の独立したコンポーネントから構成されています。

クライアントレポートの成功は、更新実行が機能していることを自動的に意味するものではありません。

主要な運用パスは次のとおりです：

```text
Linux Client
    │
    ├── LUMS Agent
    │
    └── Execution Watcher
            │
            ▼
          HTTPS
            │
            ▼
        Nginx
            │
            ▼
        LUMS API
            │
            ▼
         SQLite
```

更新実行はパッケージ管理レイヤーを追加します：

```text
Browser
   │
   ▼
LUMS API
   │
   ▼
SQLite
   │
   ▼
Update Job
   │
   ▼
Execution Watcher
   │
   ▼
LUMS Agent
   │
   ▼
APT / pacman
   │
   ▼
Result
   │
   ▼
LUMS API
   │
   ▼
SQLite
```

トラブルシューティングの際は、**最初に失敗したコンポーネント**を特定してください。

例えば：

```text
Agent report fails
    ↓
Check agent service
    ↓
Check network
    ↓
Check TLS
    ↓
Check client token
    ↓
Check LUMS API
```

すぐに以下を行わないでください：

* データベースを変更する
* Docker ボリュームを削除する
* エージェントを再インストールする
* 認証情報をローテーションする
* パッケージマネージャーのロックファイルを削除する
* セキュリティ制御を無効にする
* コンテナを特権モードにする

これらの操作は有用な診断情報を破壊したり、追加の問題を引き起こす可能性があります。

# 2. 診断ベースライン

特定の問題を調査する前に、主要コンポーネントの現在の状態を確認してください。

LUMS 本番展開では以下を使用します：

```text
Application port: 127.0.0.1:5050
External access: HTTPS through Nginx
Database: /var/lib/lums/lums.db
Docker volume: lums-data
Agent: 1.7.0
Watcher: 1.2.1
```

本番コンテナは以下で強化されています：

```text
Read-only root filesystem
No Linux capabilities
no-new-privileges
Non-root application user
Protected secret mount
Dedicated persistent data volume
```

アプリケーションポートは意図的にローカルホストのみにバインドされています。

期待されるネットワークパスは：

```text
Client / Browser
       │
       ▼
     HTTPS
       │
       ▼
    Nginx :443
       │
       ▼
127.0.0.1:5050
       │
       ▼
 Docker container
       │
       ▼
    LUMS :5000
```

# 3. 最初の診断チェック

## 3.1 LUMS コンテナの確認

LUMS サーバー上で：

```bash
sudo docker ps
```

`lums` コンテナが実行中である必要があります。

完全なコンテナ概要：

```bash
sudo docker ps -a \
    --filter name=lums
```

調査する前に停止したコンテナを削除しないでください。

古いフォールバックコンテナには、展開問題を調査する際に有用な情報が含まれている場合があります。

---

## 3.2 最近のアプリケーションログの確認

最近の LUMS ログを検査します：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

ライブ出力の場合：

```bash
sudo docker logs \
    -f \
    lums
```

特定のリクエストまたはジョブを調査する際は、可能な限り問題を再現する前にログ検査を開始してください。

これにより、クライアントアクションと対応するサーバー側イベントを関連付けやすくなります。

---

## 3.3 Nginx の確認

リバースプロキシを確認します：

```bash
sudo systemctl status nginx \
    --no-pager
```

設定を検証します：

```bash
sudo nginx -t
```

設定テストが成功すると、以下が報告されるはずです：

```text
syntax is ok
test is successful
```

Nginx が実行されていない場合、Docker コンテナ自体が健全であっても、LUMS への HTTPS アクセスは通常失敗します。

---

## 3.4 エージェントの確認

管理対象 Linux クライアント上で：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

最近のエージェント出力を検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

`Type=oneshot` サービスの場合、実行成功後の非アクティブ状態は正常なことがあります。

重要な情報は実行結果です。

成功した実行は以下で終わるはずです：

```text
status=0/SUCCESS
```

---

## 3.5 実行ウォッチャーの確認

ウォッチャーはレポートエージェントとは別のコンポーネントです。

独立して確認します：

```bash
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

最近の出力を検査します：

```bash
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 100 \
    --no-pager
```

したがって、エージェントレポートの成功は、実行ウォッチャーが正しく機能していることを**証明するものではありません**。

---

## 3.6 LUMS タイマーの確認

関連するすべてのタイマーを確認します：

```bash
sudo systemctl list-timers \
    --all | grep lums
```

期待されるタイマーには、エージェントとウォッチャーのスケジューリングメカニズムが含まれます。

タイマーが欠けているか非アクティブな場合、何も変更する前にそのユニットを検査してください。

---

# 4. LUMS コンテナが実行されていない

`lums` コンテナが実行されていない場合、すぐに再作成しないでください。

まずその状態を検査します：

```bash
sudo docker ps -a \
    --filter name=lums
```

次にコンテナを検査します：

```bash
sudo docker inspect lums
```

最近のログを確認します：

```bash
sudo docker logs \
    --tail 200 \
    lums
```

終了状態を確認します：

```bash
sudo docker inspect \
    --format '{{.State.Status}} {{.State.ExitCode}}' \
    lums
```

結果は以下の区別に役立つ場合があります：

```text
Normal shutdown
Application failure
Configuration failure
Container runtime failure
Health/startup problem
```

コンテナが予期せず終了した場合、置き換える前にログとコンテナ状態を保存してください。

---

# 5. コンテナは起動するが LUMS に到達できない

LUMS アプリケーションは、ネットワークから Docker アプリケーションポートを通じて直接アクセスされることを意図していません。

本番アプリケーションは以下にバインドされています：

```text
127.0.0.1:5050
```

ポートバインディングを確認します：

```bash
sudo docker port lums
```

ホストリスナーも確認します：

```bash
sudo ss -lntp | grep -E ':443|:5050'
```

期待されるアーキテクチャは：

```text
HTTPS :443
    │
    ▼
  Nginx
    │
    ▼
127.0.0.1:5050
    │
    ▼
Docker
    │
    ▼
LUMS :5000
```

コンテナは実行中だが HTTPS が失敗する場合、各レイヤーを個別に調査してください：

1. Docker コンテナ
2. ローカルアプリケーションポート
3. Nginx 設定
4. TLS
5. ファイアウォール/ネットワークパス

トラブルシューティングの近道としてポート `5050` を公開しないでください。

---

# 6. Nginx がエラーを返す

サービスを確認します：

```bash
sudo systemctl status nginx \
    --no-pager
```

設定を検証します：

```bash
sudo nginx -t
```

最近の Nginx メッセージを検査します：

```bash
sudo journalctl \
    -u nginx \
    -n 100 \
    --no-pager
```

次に LUMS コンテナが実際に実行中であることを確認します：

```bash
sudo docker ps
```

リバースプロキシエラーは、LUMS アプリケーション自体が壊れていることを自動的に意味するものではありません。

失敗の可能性がある場所は：

```text
Browser
   ↓
TLS
   ↓
Nginx
   ↓
127.0.0.1:5050
   ↓
Docker
   ↓
LUMS
```

一度に複数のコンポーネントを変更するのではなく、レイヤーを別々にテストしてください。

---

# 7. HTTPS / TLS の問題

まず HTTPS エンドポイントをテストします：

```bash
curl -I https://LUMS-SERVER/
```

証明書検証が失敗した場合、問題が以下かを判断します：

```text
Certificate
Certificate chain
Hostname
Trust store
Nginx configuration
Client CA configuration
```

Nginx を検証します：

```bash
sudo nginx -t
```

証明書または TLS 設定を意図的に変更した場合、Nginx を再読み込みします：

```bash
sudo systemctl reload nginx
```

その後、再度テストします：

```bash
curl -I https://LUMS-SERVER/
```

プライベート認証局を使用するクライアントは、適切な CA 証明書を信頼する必要があります。

TLS 証明書検証を永続的な回避策として無効にしないでください。

証明書検証をバイパスする成功した接続テストは、本番 TLS 設定が正しいことを証明しません。

# 8. エージェントサービスが失敗する

サービスを確認します：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

最近のジャーナルを読み取ります：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

以前の結果を検査した後でのみ、サービスを再度開始します：

```bash
sudo systemctl start \
    lums-agent.service
```

次に確認します：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

および：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

以下を探します：

```text
Configuration errors
Missing environment values
TLS errors
Authentication failures
API errors
Python exceptions
Package-manager errors
```

1 回の実行が失敗したからといって、エージェントを再インストールしないでください。

# 9. エージェントが `LUMS_TOKEN` の欠落を報告する

エージェントは通常、systemd サービス環境を通じて本番設定を受け取ります。

エージェントをシェルから手動で起動した場合、systemd の `EnvironmentFile` はそのシェルに自動的にロードされません。

したがって：

```bash
sudo /opt/lums-agent/agent.py --version
```

は、以下の動作と異なる場合があります：

```bash
sudo systemctl start \
    lums-agent.service
```

トークンが排他的に systemd 設定を通じて提供されている場合。

認証問題を調査する際は、まず実際のサービスをテストします：

```bash
sudo systemctl start \
    lums-agent.service
```

次に検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

本番トークンを不必要にシェルコマンドにコピーしないでください。

本番トークンを診断ログに出力しないでください。

# 10. エージェントがサーバーに到達できない

ネットワーク接続性から始めます：

```bash
ping LUMS-SERVER
```

次に HTTPS をテストします：

```bash
curl -I https://LUMS-SERVER/
```

HTTPS が機能するがエージェントが依然として失敗する場合、以下を調査します：

```text
Client configuration
Client token
TLS trust
API response
Client identity
Agent version
```

エージェントを検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

同時にサーバーを検査します：

```bash
sudo docker logs \
    --tail 200 \
    lums
```

これにより、リクエストが LUMS に到達しているかどうかを判断するのに役立ちます。

クライアントに接続失敗が表示され、サーバーに対応するリクエストが表示されない場合、アプリケーション設定を変更する前にネットワークまたは TLS パスを調査してください。

# 11. トラブルシューティングを続ける

基本的なサーバー、Docker、Nginx、TLS、エージェント層が機能している場合、以下に進みます：

```text
Client Authentication
Token Rotation
Update Detection
Execution Watcher
Idle Detection
Pending Jobs
```

次のセクションでは、クライアント認証とトークン関連の問題について続けます。

# 12. クライアント認証

LUMS はエージェント通信にクライアント固有の認証を使用します。

クライアントが登録されると、クライアントは LUMS サーバーとの認証済み通信に使用される認証情報を受け取ります。

認証失敗はクライアントトークンを露出せずに調査すべきです。

---

## 12.1 クライアントが LUMS によって受け入れられない

エージェントが認証失敗を報告した場合、まずエージェントログを検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

次に LUMS コンテナログを検査します：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

以下を探します：

```text
401 Unauthorized
403 Forbidden
Invalid client token
Unknown client
Authentication failure
```

`401` レスポンスは通常、認証問題を示します。

`403` レスポンスは、認証は成功したが要求された操作が許可されていないことを示す場合があります。

すぐにトークンをローテーションしないでください。

まず問題が以下かを判断します：

```text
Wrong token
Wrong client ID
Disabled client
Incorrect server URL
TLS problem
Malformed request
Server-side authentication failure
```

---

## 12.2 クライアントは存在するが認証が失敗する

クライアントが LUMS 管理インターフェースに依然として存在することを確認します。

エージェントリクエストが失敗したからといって、クライアントレコードを変更しないでください。

クライアントが存在する場合、設定されたクライアントIDとエージェントが使用するIDを比較します。

本番トークン自体は診断出力に出力してはなりません。

認証情報を露出するのではなく、設定メタデータとサービス状態を使用してトラブルシューティングしてください。

---

# 13. クライアントトークンのローテーション

クライアントトークンのローテーションは、前のトークンを無効にし、新しい認証情報で置き換えます。

トークンが意図的にローテーションされた場合、影響を受けたエージェントは再度認証する前に新しいトークンを受け取る必要があります。

期待されるシーケンスは：

```text
Administrator
    │
    ▼
Rotate client token
    │
    ▼
Old token becomes invalid
    │
    ▼
New token assigned to client
    │
    ▼
Agent configuration updated
    │
    ▼
Agent reports again
```

エージェントが古いトークンを使い続ける場合、認証は失敗します。

---

## 13.1 トークンローテーション後

エージェントサービスを確認します：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

次に systemd を通じてエージェントを実行します：

```bash
sudo systemctl start \
    lums-agent.service
```

結果を検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

認証が依然として失敗する場合、サーバーログを検査します：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

トークンを繰り返しローテーションしないでください。

繰り返しローテーションは、クライアントに現在展開されている認証情報を特定することをより困難にする可能性があります。

---

# 14. クライアントが無効化されている

無効化されたクライアントはアクティブな管理対象クライアントとして扱ってはなりません。

無効化されたクライアントに属するエージェントが通信を試みる場合、サーバー側の認証結果を検査します。

確認します：

```text
Client identity
Client enabled state
Authentication result
Agent configuration
```

単にエラーを消すためにクライアントを再度有効化しないでください。

まずクライアントが無効化された理由を判断してください。

---

# 15. 更新検出

更新検出は複数の独立したステップから構成されます。

エージェントは以下を行う必要があります：

1. パッケージマネージャーのクエリを実行する
2. 結果を解析する
3. 結果を LUMS に送信する
4. LUMS が結果を検証する
5. LUMS が結果を永続化する
6. UI が現在の状態を表示する

いずれかのステップで失敗すると、更新情報が正しくないように見える可能性があります。

基本的なフローは：

```text
APT / pacman
     │
     ▼
Agent
     │
     ▼
HTTPS
     │
     ▼
LUMS API
     │
     ▼
SQLite
     │
     ▼
Web UI
```

---

## 15.1 更新が表示されない

まずクライアントが実際に正常にレポートしたかを判断します。

確認します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

次にサーバーを検査します：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

エージェントが正常に完了したが更新が表示されない場合、パッケージマネージャーを変更する前に API とデータベースの状態を調査してください。

---

## 15.2 Debian / Ubuntu の更新検出

Debian パッケージマネージャーは APT を使用します。

APT 関連の問題を調査する際は、まず APT 自体が機能していることを確認します：

```bash
sudo apt update
```

トラブルシューティング中にパッケージのアップグレードを自動的に実行しないでください。

このテストの目的は、リポジトリメタデータを正常に更新できるかどうかを判断することです。

APT がリポジトリ、DNS、TLS、署名、またはロックエラーを報告した場合、LUMS を調査する前に基盤となる APT 問題を解決してください。

---

## 15.3 Arch Linux の更新検出

Arch Linux は `pacman` を使用します。

リポジトリメタデータを確認します：

```bash
sudo pacman -Sy
```

診断にリポジトリメタデータの更新が実際に必要な場合にのみ使用してください。

不要なシステムアップグレードと診断テストを組み合わせないでください。

パッケージ関連のエラーについては、設定を変更する前に `pacman` の正確な出力を検査してください。

---

# 16. LUMS とクライアント間の利用可能な更新の差異

更新情報は 2 つの観察の間で変化する可能性があります。

例えば：

```text
Client reports updates
        ↓
Repository metadata changes
        ↓
Package is upgraded manually
        ↓
LUMS displays older information
```

したがって、常に最後の成功したクライアントレポートのタイムスタンプを考慮してください。

差異は自動的にデータベースの問題を示すわけではありません。

確認します：

```text
Last Agent execution
Last successful report
Package-manager state
Repository metadata
Displayed update state
```

# 17. パッケージ管理

LUMS のパッケージ管理は、クライアントページに表示されるインストール済みパッケージフィルターとは別です。

パッケージ管理のワークフローは：

```text
User
 │
 ▼
Package Search
 │
 ▼
LUMS API
 │
 ▼
Agent
 │
 ▼
APT / pacman
 │
 ▼
Search Result
 │
 ▼
LUMS API
 │
 ▼
Web UI
```

パッケージのインストール、削除、または更新は、通常の LUMS ジョブメカニズムを使用します。

期待される実行パスは：

```text
Package Action
     │
     ▼
Update Job
     │
     ▼
Execution Watcher
     │
     ▼
Agent
     │
     ▼
APT / pacman
```

## 17.1 パッケージ検索が結果を返さない

まずエージェントが稼働していることを確認します：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

次にエージェントジャーナルを検査します：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

Debian ベースのクライアントでは APT メタデータを確認します。

Arch ベースのクライアントでは pacman リポジトリメタデータを確認します。

空の検索結果が LUMS データベースが空であることを意味すると仮定しないでください。

検索はクライアントパッケージマネージャーを通じて実行されます。

---

## 17.2 パッケージ検索は機能するがインストールが失敗する

成功した検索は、パッケージマネージャーがパッケージを見つけられたことのみを証明します。

インストールが成功することを証明するものではありません。

考えられる原因には以下が含まれます：

```text
Dependency conflicts
Repository changes
Package no longer available
Insufficient privileges
Package-manager lock
Disk-space problems
Network problems
Package-manager errors
```

対応する更新ジョブを検査します。

エージェントジャーナルにはパッケージマネージャーの結果が含まれているはずです。

---

# 18. パッケージインストールジョブ

パッケージインストールは通常の更新ジョブインフラストラクチャを使用します。

関連するアクションは：

```text
INSTALL_PACKAGE
```

インストールをトラブルシューティングする際：

1. LUMS のジョブ状態を確認します。
2. エージェントの実行を確認します。
3. パッケージマネージャーの出力を確認します。
4. LUMS に報告された最終結果を確認します。

SQLite のジョブステータスを手動で変更しないでください。

期待されるライフサイクルは：

```text
PENDING
   ↓
RUNNING
   ↓
SUCCESS
```

または：

```text
PENDING
   ↓
RUNNING
   ↓
FAILED
```

失敗したパッケージインストールは、通常のジョブと監査メカニズムを通じて追跡可能であるべきです。

---

# 19. パッケージ削除ジョブ

パッケージ削除は同じジョブライフサイクルに従います。

アクションは：

```text
REMOVE_PACKAGE
```

削除が失敗した場合、以下を検査します：

```text
Update job
Agent journal
Package-manager output
Final job result
```

失敗したパッケージ操作を隠すためにデータベースレコードを手動で削除しないでください。

失敗したジョブは有用な診断情報です。

---

# 20. パッケージ更新ジョブ

パッケージ固有の更新は以下を使用します：

```text
UPDATE_PACKAGE
```

ジョブが作成される前に、パッケージが利用可能な更新を持つものとして LUMS に認識されている必要があります。

UI が期待されるパッケージ更新を提供しない場合：

1. 更新情報を更新する
2. パッケージマネージャーの状態を確認する
3. 利用可能な更新の結果を確認する
4. 状態が矛盾している場合はサーバーログを検査する

SQLite に更新レコードを手動で挿入しないでください。

---

# 21. システム更新ジョブ

完全なシステム更新は以下を使用します：

```text
UPDATE_SYSTEM
```

これは以下とは異なります：

```text
UPDATE_PACKAGE
```

システム更新は複数のパッケージに影響し、オペレーティングシステムと結果のパッケージ状態によっては再起動を必要とする場合があります。

システム更新をトラブルシューティングする際は、失敗が以下で発生したかを判断します：

```text
Update preparation
Package-manager execution
Result collection
Reboot detection
Post-reboot reporting
```

---

# 22. パッケージマネージャーのロック

別のパッケージ管理プロセスが既に実行されている場合、パッケージマネージャーは操作を拒否する場合があります。

典型的な例は：

```text
APT is already running
dpkg is locked
pacman is locked
```

まずロックを保持しているプロセスを特定します。

ロックファイルを盲目的に削除しないでください。

ロックファイルは、別のパッケージ管理プロセスが正当にアクティブであることを示す場合があります。

パッケージ操作の実行中に削除すると、パッケージ管理状態を損傷する可能性があります。

正しいトラブルシューティングのシーケンスは：

```text
Lock error
   ↓
Identify active process
   ↓
Determine whether it is legitimate
   ↓
Wait or resolve the process safely
   ↓
Retry operation
```

---

# 23. パッケージマネージャーの失敗と LUMS の失敗

常にパッケージマネージャーの失敗と LUMS の失敗を区別してください。

例えば：

```text
APT fails
    ↓
Agent reports APT failure
    ↓
LUMS stores FAILED result
```

この場合、ジョブが失敗しても LUMS は正しく機能している可能性があります。

逆に：

```text
APT succeeds
    ↓
Agent cannot report result
    ↓
LUMS never receives SUCCESS
```

ここではパッケージ操作は成功したが、LUMS レポートパスが失敗した可能性があります。

したがって、パッケージマネージャーの結果と LUMS ジョブの結果は別々に調査しなければなりません。

---

# 24. 有用な診断の分離

パッケージジョブが失敗した場合、まず失敗を分類します：

```text
A. Package-manager failure
B. Agent execution failure
C. Agent reporting failure
D. Server/API failure
E. Database persistence failure
F. UI display problem
```

この分類は無関係なコンポーネントが変更されるのを防ぎます。

パッケージマネージャーのエラーが自動的に Docker 再ビルドになるべきではありません。

UI 表示の問題が自動的にデータベースの削除になるべきではありません。

認証失敗が自動的にエージェントの再インストールになるべきではありません。

---

# 25. 次のトラブルシューティング領域

クライアント認証、更新検出、パッケージ管理が機能している場合、次の診断領域は実行ライフサイクル自体です：

```text
Update Job
    ↓
Watcher
    ↓
Agent
    ↓
Execution
    ↓
Result
    ↓
Checkpoint / Recovery
    ↓
Final Job State
```

次のセクションでは、**実行ウォッチャー、アイドル検出、ジョブ状態、復旧、再起動処理** について説明します。

# 26. 更新ジョブの実行

LUMS 更新ジョブは、エージェントと実行ウォッチャーを通じて非同期に実行されます。

通常の実行パスは：

```text
User
 │
 ▼

 │
 ▼
SQLite
 │
 ▼

 │
 ▼
Execution Watcher
 │
 ▼
Agent
 │
 ▼

 │
 ▼

 │
 ▼
```

常に現在のジョブ状態を最初に確認してください。

---

## 26.1 ジョブが `PENDING` でスタックしている

ジョブが `PENDING` のままの場合、エージェントを調査する前に実行ウォッチャーを確認します。

ウォッチャーを確認します：

```bash id="wq5h3v"
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

最近のウォッチャー出力を検査します：

```bash id="8y0v7e"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

次にエージェントを確認します：

```bash id="j8x4qm"
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

待機中のジョブは通常、実行段階がまだ開始されていないことを示します。

考えられる原因には以下が含まれます：

```text
Watcher is not running
Watcher timer is not running
Client is offline
Client is not idle
Client has not reported recently
Job is not eligible for execution yet
```

SQLite のジョブ状態を手動で変更しないでください。

---

# 27. ジョブが `RUNNING` でスタックしている

`RUNNING` ジョブは、実行が開始されたことを示します。

まずエージェントが実際にジョブを実行しているかを判断します。

確認します：

```bash id="s2z5ek"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

次にウォッチャーを検査します：

```bash id="x4f6cb"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

実行中のジョブは、以下に応じて時間がかかる場合があります：

```text
Package count
Repository speed
Network latency
Package-manager operations
System load
Reboot requirements
```

UI がまだ更新されていないという理由だけで、アクティブなパッケージ操作を終了しないでください。

まず、基盤となるプロセスがまだアクティブかを判断してください。

---

# 28. ジョブが `FAILED`

失敗したジョブは、必ずしも LUMS サーバーの失敗を示すわけではありません。

どのレイヤーが失敗を生み出したかを判断します。

検査します：

```text id="5t9b83"
Job state
Agent execution result
Package-manager result
Server logs
Agent logs
```

主なカテゴリは：

```text
Package-manager failure
Agent execution failure
Agent reporting failure
Server/API failure
Authentication failure
Recovery failure
```

元のエラーは可能な限り保存すべきです。

失敗したジョブを手動で作成した成功レコードで置き換えないでください。

---

# 29. ジョブが `SUCCESS` だがパッケージが変更されていない

成功した LUMS ジョブは、要求された操作がエージェントの結果に従って完了したことを意味します。

期待されるパッケージ状態がジョブ結果と一致しない場合、クライアントを直接確認します。

Debian ベースのシステムの場合：

```bash id="gqdbm7"
dpkg-query -W \
    -f='${Package} ${Version}\n' \
    PACKAGE_NAME
```

Arch Linux の場合：

```bash id="2x9f7v"
pacman -Q \
    PACKAGE_NAME
```

`PACKAGE_NAME` を調査中のパッケージに置き換えてください。

次にローカルのパッケージ状態と LUMS の結果を比較します。

考えられる説明には以下が含まれます：

```text
Package was changed after the job
Package name refers to a virtual/provided package
Package-manager output was interpreted differently than expected
The job result was generated before another local change
```

不一致が特定されるまで LUMS データベースを変更しないでください。

---

# 30. 実行ウォッチャー

実行ウォッチャーは、実行可能なジョブを発見する責任があります。

ウォッチャーは独立したコンポーネントとして扱わなければなりません。

そのサービスを確認します：

```bash id="w5m0c8"
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

そのタイマーを確認します：

```bash id="3v1x7r"
sudo systemctl list-timers \
    --all | grep lums
```

そのジャーナルを検査します：

```bash id="d5m0xk"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

エージェントは機能するがジョブが決して開始されない場合、ウォッチャーは最初に調査すべきコンポーネントの 1 つであるべきです。

---

# 31. ウォッチャーは実行されるがジョブを実行しない

ウォッチャーの実行は、ジョブが開始されることを自動的に意味するものではありません。

ジョブは実行条件を満たす必要があります。

確認します：

```text id="m7p2zq"
Client exists
Client is enabled
Client is reachable
Client has recent status
Client is eligible
Job is pending
Job is not already completed
Execution conditions are satisfied
```

クライアントが対象でない場合、ウォッチャーはジョブを正しく保留状態のままにすることがあります。

これは必ずしもエラーではありません。

---

# 32. アイドル検出

LUMS は、ジョブを実行すべきかどうかを決定する際に、クライアントのアイドル情報を使用できます。

目的は、クライアントがアクティブに使用されている間にメンテナンス操作を開始することを避けることです。

したがって、アイドル判断は実行失敗ではなく、スケジューリング条件として扱うべきです。

クライアントは、非アイドルと見なされながらも正常にレポートする場合があります。

トラブルシューティングのシーケンスは：

```text
Agent reports
     ↓
Idle information available?
     ↓
Idle state acceptable?
     ↓
Job eligible?
     ↓
Watcher executes
```

---

## 32.1 クライアントはレポートするがアイドルと見なされない

エージェントジャーナルを確認します：

```bash id="5r2q1k"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

報告されたアイドル情報を探します。

次にウォッチャーを検査します：

```bash id="2a6v8m"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

重要な区別は：

```text
Agent communication successful
```

対：

```text
Client eligible for maintenance execution
```

これらは別個の状態です。

---

# 33. アイドル検出が利用できない

一部のシステムはすべてのアイドル状態情報を提供しない場合があります。

利用できないアイドルメカニズムは、壊れたエージェントとして自動的に解釈されるべきではありません。

まず報告された機能を判断します。

関連する概念は：

```text
Idle supported
Idle source
Idle state
Idle duration
```

プラットフォームが期待されるアイドル情報を提供できない場合、サーバーデータベースを変更するのではなく、エージェントのプラットフォーム固有の実装を調査してください。

---

# 34. 更新ジョブの復旧

LUMS はチェックポイントと復旧を使用して、中断された更新ジョブが完了として扱われないようにします。

ジョブは以下の理由で中断される場合があります：

```text
Agent restart
Client reboot
Network interruption
Package-manager interruption
Server restart
Watcher restart
System failure
```

復旧は、既に完了した作業とまだ実行が必要な作業を区別しなければなりません。

原則は：

```text
Completed work remains completed.
Incomplete work remains recoverable.
```

---

# 35. 中断されたジョブ

ジョブが中断された場合、まずその状態を検査します。

次にエージェントを検査します：

```bash id="3u8d4k"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

ウォッチャーを検査します：

```bash id="w4x1b9"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

ジョブを手動で成功としてマークしないでください。

復旧メカニズムは、どのパッケージアイテムが既に完了したかを判断すべきです。

---

# 36. 復旧がパッケージ操作を繰り返す

復旧がトリガーされた場合、既に成功したパッケージアイテムを不必要に再度実行すべきではありません。

復旧モデルはアイテムレベルの状態に基づいています。

概念的に：

```text
Job
 ├── Package A → SUCCESS
 ├── Package B → SUCCESS
 ├── Package C → FAILED
 └── Package D → PENDING
```

復旧は成功したアイテムを保持し、残りの作業を続けるべきです。

この動作が正しくないと思われる場合、データベースを変更する前にジョブとパッケージアイテムの履歴を検査してください。

---

# 37. クライアントが更新中に再起動する

再起動はエージェントプロセスを中断する可能性があります。

期待される復旧パスは：

```text
Update starts
    ↓
Package operation
    ↓
Client reboot
    ↓
Agent starts again
    ↓
State is reported
    ↓
LUMS evaluates recovery
```

したがって、再起動は自動的にジョブが永久に失敗したことを意味するものではありません。

クライアントが戻った後、エージェントサービスを検査します：

```bash id="jjh3u8"
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

次に最近の実行を検査します：

```bash id="h7y5gk"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

---

# 38. 再起動検出

再起動検出は、更新操作の一部としてシステム再起動が発生したかどうかを判断するために使用されます。

これは、更新が再起動を必要とするパッケージを変更する場合に特に重要です。

Arch Linux の場合、再起動検出をパッケージマネージャーの終了ステータスと混同してはなりません。

パッケージ操作が成功しても、システムが依然として再起動を必要とする場合があります。

再起動処理をトラブルシューティングする際は、以下を比較します：

```text
Package operation result
Reboot requirement
Actual reboot state
Post-reboot Agent report
Final LUMS job state
```

---

# 39. ジョブ結果が報告されなかった

パッケージ操作が完了したように見えても LUMS が最終結果を表示しない場合、レポートパスを調査します。

エージェントを確認します：

```bash id="t0r8kf"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

次にサーバーを確認します：

```bash id="h5n1xv"
sudo docker logs \
    --tail 200 \
    lums
```

パッケージ操作自体は成功したがエージェントがエラーを報告する場合、その問題をパッケージ管理の失敗ではなくレポートの失敗として分類します。

---

# 40. ジョブ実行中のサーバー再起動

サーバー再起動は、更新操作が失敗した証拠として自動的に扱ってはなりません。

サーバーが再び利用可能になった後、ジョブ状態を評価する必要があります。

確認します：

```text id="j4t7yw"
Container state
Database availability
Job state
Client state
Agent report
Watcher state
```

復旧メカニズムは、中断された作業を安全に続行できるかどうかを判断する責任があります。

サーバー再起動後にジョブ状態を手動で書き換えないでください。

---

# 41. データベースは利用可能だがジョブ状態が正しくない

SQLite にアクセスできるがジョブ状態が一貫していないように見える場合、データベースを変更する前にアプリケーションと監査ログを検査します。

有用な情報には以下が含まれます：

```text
Job ID
Client ID
Job action
Job creation time
Current state
Package-item states
Agent result
Recovery events
Audit events
```

データベースはアプリケーションデータストアであり、手動修復インターフェースではありません。

直接的な変更は検証、認可、監査、復旧ロジックをバイパスする可能性があります。

---

# 42. 手動のジョブ状態変更

更新ジョブ状態への手動 SQL 変更は、通常のトラブルシューティングとして使用すべきではありません。

以下のような操作を避けます：

```sql id="8hbyqv"
UPDATE update_jobs ...
```

または：

```sql id="n1h7yr"
DELETE FROM update_jobs ...
```

管理されたデータベース復旧手順が明示的に要求しない限り。

データベースレベルの修復が本当に必要な場合、バックアップを保存し、適用する前に正確な変更を記録してください。

通常の運用問題はアプリケーションとエージェントメカニズムを通じて解決すべきです。

---

# 43. ウォッチャーとエージェントの診断マトリックス

次のマトリックスを使用して、最も可能性の高いレイヤーを特定します：

| 症状                                             | 最初に検査するコンポーネント |
| ------------------------------------------------ | ---------------------------- |
| クライアントが認証できない                       | エージェント + LUMS API      |
| クライアントは正常にレポートするがジョブが保留中 | 実行ウォッチャー             |
| ジョブは実行中になるが終了しない                 | エージェント + パッケージマネージャー |
| パッケージ操作が失敗する                         | パッケージマネージャー       |
| パッケージ操作は成功するが結果が欠けている       | エージェントレポート         |
| 更新中にクライアントが再起動した                 | エージェント + 復旧          |
| 再起動後もジョブ状態が一貫しない                 | 復旧 + データベース状態      |
| ジョブが決して検出されない                       | ウォッチャー + タイマー      |
| クライアントが対象外                             | アイドル / クライアント状態  |
| UI が古い状態を表示                              | API + 最新クライアントレポート |

このマトリックスは出発点であり、実際のログとジョブ状態を検査することの代替ではありません。

# 45. SQLite とデータベースのトラブルシューティング

LUMS はアプリケーションデータベースとして SQLite を使用します。

本番データベースは永続 Docker ボリューム内に保存されます：

```text id="9c6w3e"
/var/lib/lums/lums.db
```

データベースはアプリケーション管理下にあり、通常は手動で変更すべきではありません。

データベース関連の問題を調査する際は、まず問題が以下かを判断します：

```text id="4k4z1m"
Database availability
Database locking
Application configuration
Data consistency
Migration state
Application logic
```

---

# 46. データベースが利用できない

LUMS がデータベースエラーを報告した場合、まずコンテナが実行中かを確認します：

```bash id="0l5q6h"
sudo docker ps
```

次にアプリケーションログを検査します：

```bash id="6j5p8m"
sudo docker logs \
    --tail 200 \
    lums
```

すぐに Docker ボリュームを削除しないでください。

永続ボリュームには本番アプリケーションデータが含まれています。

削除すると以下が永久に削除される可能性があります：

```text id="4bq9rj"
Users
Clients
Client configuration
Update jobs
Audit data
Application state
```

---

# 47. SQLite データベースのロック

SQLite のロック問題はアプリケーションログを通じて調査すべきです。

検査します：

```bash id="l8f6vk"
sudo docker logs \
    --tail 200 \
    lums
```

本番アプリケーションは以下を使用します：

```text id="2d3m8x"
journal_mode = wal
busy_timeout = 5000
synchronous = 2
```

アプリケーションはまた、データベース接続で SQLite 外部キー強制を有効にします。

データベースロックは自動的にデータベースが破損していることを意味するものではありません。

考えられる原因には以下が含まれます：

```text id="9w4qcz"
Concurrent writes
Long-running transaction
Application process still using the database
Unexpected process termination
Filesystem problem
```

SQLite ジャーナルファイルを手動で削除しないでください。

---

# 48. SQLite 外部キー

LUMS はアプリケーションレベルで SQLite 外部キー強制を明示的に有効化します。

これは、アプリケーション接続の確立時に、データベースレコード間の関係が SQLite によって検証されることを意味します。

外部キー関連のエラーが発生した場合、まずアプリケーションログを検査します。

操作を成功させるために外部キー強制を無効にしないでください。

外部キーの失敗は、アプリケーションロジックまたはデータ整合性の問題を示す場合があります。

---

# 49. SQLite データベースの整合性

データベース破損が疑われる場合、まず不必要な変更を停止してください。

現在の状態を保存し、アプリケーションログを検査します。

データベースのコピーに対して管理された整合性チェックを実行できます。

文書化された復旧手順が要求しない限り、本番データベースに対して直接破壊的な修復操作を実行しないでください。

一般的な原則は：

```text id="t4d1km"
Preserve
   ↓
Inspect
   ↓
Verify
   ↓
Recover
   ↓
Validate
```

以下から始めないでください：

```text id="z1f6rw"
Delete database
Recreate database
Recreate Docker volume
```

---

# 50. データベースマイグレーション

LUMS はデータベーススキーマ変更を導入するためにアプリケーションマイグレーションを使用します。

マイグレーションの問題が発生した場合、コンテナログを検査します：

```bash id="x4h9vf"
sudo docker logs \
    --tail 200 \
    lums
```

以下を探します：

```text id="m2x7kc"
Migration failure
SQL error
Duplicate column
Missing table
Constraint error
Migration already applied
```

マイグレーションシステムが管理された復旧手順を具体的に要求しない限り、マイグレーションレコードを手動で編集しないでください。

既に適用されたマイグレーションは、通常、手動で再度実行すべきではありません。

---

# 51. データベースボリューム

LUMS データベースは永続 Docker ボリュームに保存されます：

```text id="p6m3jw"
lums-data
```

ボリュームを検査します：

```bash id="v4c7yq"
sudo docker volume inspect \
    lums-data
```

ボリュームは通常のコンテナ再作成を経ても永続的でなければなりません。

アプリケーションコンテナ自体は使い捨てです。

アプリケーションデータはそうではありません。

したがって：

```text id="z9f4ws"
Container
    ≠
Persistent database
```

コンテナの再作成をデータボリュームの再作成と混同しないでください。

---

# 52. データベースのディスク容量

SQLite は正常動作のために利用可能なファイルシステム容量を必要とします。

ホストファイルシステムを確認します：

```bash id="j6k1pt"
df -h
```

inode の可用性も確認します：

```bash id="q2c5ra"
df -i
```

ディスク容量不足は、最初はアプリケーションの問題のように見えるデータベースエラーを引き起こす可能性があります。

データベースが突然読み取り専用になるか、書き込みが失敗し始めた場合、SQLite 設定を変更する前にファイルシステム容量を確認してください。

# 53. RBAC のトラブルシューティング

LUMS はロールベースのアクセス制御を使用します。

現在のロールは：

```text id="k8w5j2"
Administrator
Operator
Viewer
```

権限は意図的に異なります。

---

## 53.1 Administrator

管理者は以下を実行できます：

```text id="n4x7pa"
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
Create and disable clients
Rotate client tokens
Manage users
Manage roles
```

管理者専用操作にはユーザー管理とロール管理が含まれます。

---

## 53.2 Operator

オペレーターは以下を実行できます：

```text id="b7c2mz"
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
```

オペレーターは以下を実行できません：

```text id="q8v3kd"
Manage users
Manage roles
Create or disable clients
Rotate client tokens
```

---

## 53.3 Viewer

Viewer は意図的に制限されたアクセスを持ちます。

Viewer は以下を実行できます：

```text id="y5m2rx"
View clients
View installed software
```

以下の機能は Viewer インターフェースから隠され、サーバー側でブロックされます：

```text id="e8c4nw"
Available Updates
Update Jobs
Update History
Package Management
System Maintenance
```

これは意図的なセキュリティ制御です。

Viewer がこれらの機能の 1 つにアクセスできる場合、単なる UI の問題ではなく RBAC 問題として扱ってください。

---

# 54. Viewer が見えすぎる

Viewer が利用可能であるべきでない機能を見る場合、両方のレイヤーを確認します：

```text id="x5j3mq"
Browser UI
    +
Server-side authorization
```

JavaScript または HTML で要素を隠すことは十分なセキュリティではありません。

API も未認可の操作を拒否しなければなりません。

調査する際：

1. 認証されたユーザーのロールを判断します。
2. 影響を受けるエンドポイントを特定します。
3. サーバーのレスポンスを確認します。
4. 必要に応じてアプリケーションログを検査します。
5. 関連する RBAC テストを検証します。

UI 要素を隠すだけで認可問題を解決しないでください。

---

# 55. Viewer が期待されるデータを見ることができない

Viewer は依然として現在の RBAC モデルによって明示的に許可された情報にアクセスできるはずです。

許可されたクライアント情報が欠けている場合：

```text id="3h6q8f"
Verify login
   ↓
Verify role
   ↓
Verify client visibility
   ↓
Inspect API response
   ↓
Inspect browser console if necessary
```

ページが現在不完全に見えるからといって、追加の権限を付与しないでください。

欠けている情報が意図的に制限されているかどうかを最初に判断してください。

---

# 56. オペレーターが操作を実行できない

オペレーターが `403 Forbidden` を受け取った場合、まず要求されたアクションが管理者専用かどうかを判断します。

オペレーターアクセスには以下は含まれません：

```text id="n5y7cu"
User management
Role administration
Client creation/deactivation
Client token rotation
```

操作がオペレーターに許可されるべき場合、エンドポイントの認可デコレーターと対応する RBAC テストを検査します。

診断の近道としてユーザーを一時的に Administrator に昇格させないでください。

---

# 57. Administrator が操作を実行できない

Administrator は現在サポートされているすべての管理操作にアクセスできるはずです。

Administrator が認可エラーを受け取った場合：

```text id="q7d2nv"
Verify authenticated session
        ↓
Verify current role
        ↓
Verify endpoint authorization
        ↓
Inspect CSRF requirements
        ↓
Inspect application logs
```

状態変更操作の場合、有効なセッションだけでは十分でない場合があります。

必要な場合は CSRF 保護も満たさなければなりません。

---

# 58. ユーザー管理

ユーザー管理は Administrators に制限されています。

ユーザー管理のワークフローは：

```text id="x4j6pw"
Administrator
    │
    ▼
User Management
    │
    ├── Create user
    ├── Assign role
    └── Enable / disable user
```

ユーザーを作成できない場合、確認します：

```text id="b3q9fz"
Current role
Username validation
Role validation
Duplicate username
Password validation
CSRF protection
Application logs
```

SQLite に直接ユーザーを作成しないでください。

直接的なデータベース挿入はパスワードハッシュ、検証、認可、監査ログをバイパスします。

---

# 59. ユーザー作成が失敗する

ユーザー作成が失敗した場合、ブラウザのレスポンスとサーバーログを検査します。

API は以下を検証すべきです：

```text id="7x3m5n"
Username
Role
Password requirements
Duplicate account
Authenticated administrator
CSRF token
```

リクエストが拒否された場合、どの検証ルールがトリガーされたかを判断します。

1 つのアカウント作成リクエストを成功させるためだけに検証を弱めないでください。

---

# 60. パスワードの問題

LUMS は平文パスワードではなくパスワードハッシュメカニズムを使用してユーザーパスワードを保存します。

ユーザーがログインできない場合：

```text id="9w3r5b"
Verify username
   ↓
Verify account enabled state
   ↓
Verify password
   ↓
Check login rate limiting
   ↓
Inspect authentication logs
```

平文パスワードを絶対に保存またはログに記録しないでください。

パスワードを診断コマンドやログファイルにコピーしないでください。

---

# 61. 無効化されたユーザーアカウント

無効化されたアカウントはアクティブなログインアカウントとして扱ってはなりません。

無効化されたユーザーが依然として認証できる場合、調査します：

```text id="z6t2hx"
Current account state
Authentication lookup
Session state
Session revocation
Browser session
Server-side authorization
```

単にアカウントを削除しないでください。

アカウントを保持することは監査履歴にとって重要です。

---

# 62. セッションの問題

LUMS はサーバー側のセッション処理を使用します。

ユーザーが古いまたは予期しないアクセスを持つように見える場合、まずログアウトし、新しいセッションを確立します。

問題が続く場合、調査します：

```text id="q1y7vm"
Account state
Role
Session state
Session revocation
Cookie configuration
CSRF protection
```

ログイン問題を回避するためにセッションセキュリティ制御を無効にしないでください。

---

# 63. セッションの無効化

セッションの無効化は以下の場合に関連します：

```text id="4n8z7p"
A password changes
A user is disabled
A role changes
A session must be invalidated
A security event requires forced logout
```

ユーザーがアカウント変更後もアクセスを保持しているように見える場合、既存のセッションが正しく無効化されたかを判断します。

アカウント状態を確認した後にのみ、新しいブラウザセッションでテストしてください。

ブラウザクッキーを削除するだけでは、サーバー側のセッション無効化が機能することを証明しないと仮定しないでください。

---

# 64. ログイン速度制限

LUMS は繰り返される認証失敗試行にログイン速度制限を適用します。

現在の動作は、増加するロックアウト間隔を使用します：

```text id="p7k4xz"
5 attempts  → 30 seconds
6 attempts  → 60 seconds
7 attempts  → 120 seconds
8+ attempts → 300 seconds
```

失敗状態は SQLite に永続化されます。

ログイン試行が予期せずブロックされた場合、データベースを変更する前に認証状態を検査します。

速度制限の応答は、自動的に認証失敗ではありません。

アカウントが設定された失敗試行しきい値に達したことを示す場合があります。

---

# 65. ログインは機能するが API が `403` を返す

成功したログインは認証を証明しますが、認可は証明しません。

`403 Forbidden` レスポンスは以下を示す場合があります：

```text id="m9c2vx"
Insufficient role
Missing CSRF protection
Disallowed operation
Disabled functionality
```

何かを変更する前に正確なエンドポイントを特定します。

正しいトラブルシューティングの質問は：

```text id="0q4g1k"
"Is this user authenticated?"
```

に続いて：

```text id="x8v5md"
"Is this authenticated user authorized for this operation?"
```

これらは別個のセキュリティチェックです。

---

# 66. CSRF エラー

状態変更ブラウザリクエストはクロスサイトリクエストフォージェリから保護されています。

状態変更リクエストが予期せず失敗した場合：

```text id="6z4qpn"
Verify authenticated session
        ↓
Verify CSRF token
        ↓
Verify request method
        ↓
Verify endpoint
        ↓
Inspect server response
```

トラブルシューティングの回避策として CSRF 保護を無効にしないでください。

CSRF チェックの失敗は、セキュリティ制御が意図通りに機能していることです。

---

# 67. ブラウザ UI と API が一致しない

UI がアクションが利用可能であることを示しているが API が拒否する場合：

```text id="v8n3ty"
Browser UI
   ↓
Displayed role/state
   ↓
API request
   ↓
Server-side authorization
```

サーバー側の結果が権威的です。

UI は以下が発生した後に古い状態を含む可能性があります：

```text id="4g7m2x"
Role changes
Session changes
Client changes
Page remains open for a long time
```

サーバー側の認可が正しくないと仮定する前に、ページを再読み込みして新しいセッションを確立してください。

---

# 68. RBAC 診断マトリックス

| 症状                             | 最初に検査するコンポーネント            |
| -------------------------------- | --------------------------------------- |
| Viewer が管理 UI を見る          | クライアントページのロール処理          |
| Viewer API リクエストが成功する  | サーバー側 RBAC                         |
| オペレーターが `403` を受け取る  | エンドポイント権限モデル                |
| Administrator が `403` を受け取る | セッション / CSRF / エンドポイント認可 |
| ユーザーを作成できない           | 管理者ロール + 検証                     |
| 無効化されたユーザーがログインできる | アカウント状態 + セッション処理      |
| ログインが一時的にブロックされる | 速度制限                                |
| 状態変更リクエストが拒否される   | CSRF / セッション                       |
| UI と API が一致しない           | ブラウザ状態 + サーバー認可             |

サーバー側の認可結果は、インターフェース要素が表示されているかどうかよりも常に重要です。

継続的な監視の場合：

```bash id="x3v8kp"

    lums
```

可能な場合は、ログを監視しながら問題を再現してください。

```text id="p8k4zw"
    ↓

    ↓

    ↓

    ↓

```

# 71. アプリケーションログにエラーが含まれている

まずメッセージを生成したコンポーネントを特定します。

典型的なソースには以下が含まれます：

```text id="w4c8rn"
Flask application
Gunicorn
Database layer
Authentication
Authorization
Package management
Job execution
Client reporting
```

最後のログメッセージが根本原因であると仮定しないでください。

イベントシーケンスの最初の関連するエラーを探します。

可能な場合は、以下を関連付けます：

```text id="n6q2vy"
Timestamp
Client
Request
Job ID
Error
Result
```

# 72. 監査ログ

LUMS は、セキュリティ関連のアプリケーションアクションを監査ログに記録します。

監査ログは以下を調査する際に有用です：

```text id="j8r4px"
User changes
Authentication events
Administrative actions
Client management
Token operations
Update-job creation
Security-relevant state changes
```

監査イベントはアプリケーションイベントの証拠として扱うべきであり、システムログの代替として扱うべきではありません。

技術的な実行の詳細にはアプリケーションログを、セキュリティ関連のアプリケーションアクションには監査ログを使用してください。

---

# 73. 監査イベントが欠けている

期待される監査イベントが欠けている場合：

1. 正確なアクションを特定します。
2. API エンドポイントを特定します。
3. アクションが実際にサーバーに到達したことを確認します。
4. アプリケーションログを検査します。
5. 監査イベントが作成されるべき前にアクションが拒否されたかを判断します。

単に監査証跡を完全に見せるために監査レコードを手動で挿入しないでください。

監査レコードは実際のアプリケーションイベントに対応すべきです。

---

# 74. 監査ログとアプリケーションログの違い

2 つのログシステムは異なる目的を持っています。

例えば：

```text id="7q2m5k"
Application log
→ technical execution information

Audit log
→ security-relevant application event
```

したがって、パッケージマネージャーのエラーが、別個の管理監査イベントを表さずにアプリケーションまたはエージェントログに表示される場合があります。

逆に、ユーザー管理アクションは、操作自体が技術的に単純であっても、監査可能なアプリケーションイベントを生成すべきです。

# 75. ログの機密情報

以下を診断出力に意図的に入れないでください：

```text id="3m7v9x"

Application secret keys
Passwords
Session secrets
Private keys
TLS private material
```

診断コマンドがこれらの値の 1 つを露出する場合、代わりに秘匿されたまたはメタデータのみのチェックを使用してください。

トラブルシューティングのためにログを共有する際は、チケット、ドキュメント、GitHub issue、またはチャットにコピーする前にシークレットを確認してください。

# 76. Docker コンテナセキュリティ

本番 LUMS コンテナは意図的に強化されています。

期待されるセキュリティプロパティには以下が含まれます：

```text id="z4w6pt"
Non-root application user
Read-only root filesystem
All Linux capabilities dropped
no-new-privileges enabled
No privileged mode
Dedicated writable data volume
Read-only secret mount
Restricted temporary filesystems
```

これらのプロパティの 1 つが予期せず変更された場合、設定ドリフトとして扱ってください。

セキュリティへの影響が明示的に評価されない限り、アプリケーション問題を解決するためにコンテナを弱めないでください。

# 77. コンテナランタイムセキュリティの確認

コンテナを検査します：

```bash id="b8x5jq"
sudo docker inspect lums
```

焦点を絞ったランタイムチェックの場合：

```bash id="r3n7cw"
sudo docker inspect \
    --format='ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} Privileged={{.HostConfig.Privileged}} CapDrop={{json .HostConfig.CapDrop}} SecurityOpt={{json .HostConfig.SecurityOpt}}' \
    lums
```

期待される値には以下が含まれます：

```text id="k5m2zr"
ReadonlyRootfs=true
Privileged=false
CapDrop=[ALL]
SecurityOpt=[no-new-privileges:true]
```

正確なフォーマットは Docker バージョンによって異なる場合があります。

重要なのはセキュリティプロパティ自体です。

---

# 78. コンテナが root として実行される

LUMS アプリケーションは、専用の非特権アプリケーションユーザーとして実行すべきです。

コンテナが予期せず root として実行される場合、まずイメージとランタイム設定を検査します：

```bash id="p6x4nz"
sudo docker inspect \
    --format='{{.Config.User}}' \
    lums
```

次に Dockerfile を検査します。

本番コンテナを root に切り替えることでアプリケーション権限問題を解決しないでください。

ディレクトリが書き込みアクセスを必要とする場合、正確なパスを特定し、それが永続アプリケーションデータか一時データかを判断します。

---

# 79. 読み取り専用ルートファイルシステム

本番コンテナは読み取り専用ルートファイルシステムを使用します。

これにより、アプリケーションイメージが不要なランタイム変更から保護されます。

アプリケーションが以下を報告する場合：

```text id="y5k8mc"
Read-only filesystem
Permission denied
Cannot create file
Cannot write temporary data
```

まずアプリケーションが**どこに**書き込もうとしているかを判断します。

期待される書き込み可能な場所は意図的に制限されています。

永続アプリケーションデータは以下に属します：

```text id="q9m3xr"
/var/lib/lums
```

一時ランタイムデータは設定された一時ファイルシステムを使用できます。

アプリケーションパスが予期せず書き込み可能だからという理由だけで `--read-only` を無効にしないでください。

---

# 80. `/tmp` が書き込み可能でない

アプリケーションが一時ストレージを必要とする場合、一時ファイルシステムを確認します：

```bash id="a7w4vn"
sudo docker inspect \
    --format='{{json .HostConfig.Tmpfs}}' \
    lums
```

本番コンテナは制限された `/tmp` を提供します。

一時ファイルシステムは一時データのみを目的としています。

永続データをそこに保存してはなりません。

---

# 81. シークレットマウントの問題

LUMS アプリケーションシークレットは、保護されたファイルマウントを通じて提供されます。

シークレットはイメージに直接埋め込むべきではありません。

LUMS がシークレットの欠落を報告した場合、まずランタイム設定を検査します：

```bash id="j4p7zx"
sudo docker inspect \
    lums
```

シークレットマウントが存在し、読み取り専用であることを確認します。

シークレットの内容を出力しないでください。

有用な診断は、内容を表示せずにファイルが存在し、期待される権限を持っていることを確認することです。

---

# 82. シークレットファイルが欠けている

ホスト上にシークレットファイルが存在しない場合、コンテナは正しく認証または初期化できません。

まず期待されるシークレットパスが存在するかを判断します。

シークレットをランダムに再作成しないでください。

置換シークレットは、アプリケーションがどのように使用するかによって、既存のセッションまたは他の暗号状態を無効にする可能性があります。

したがって、意図的なシークレット置換は管理されたセキュリティ操作として扱わなければなりません。

---

# 83. 永続ボリュームが書き込み可能でない

LUMS がアプリケーションデータを書き込めない場合、ボリュームを検査します：

```bash id="y6c2mt"
sudo docker volume inspect \
    lums-data
```

次にコンテナマウントを検査します：

```bash id="e5w8rq"
sudo docker inspect \
    --format='{{json .Mounts}}' \
    lums
```

アプリケーションデータベースは永続書き込み可能ボリューム上に存在しなければなりません。

回避策としてコンテナファイルシステム全体を書き込み可能にしないでください。

正しい解決策は、永続性を必要とする特定のパスを特定することです。

# 85. Docker イメージとコンテナ設定

```text id="s7q2mj"
    +
```

4. 意図的に設定を修正します。

# 103. 失敗の組み合わせマトリックス

いくつかの症状は、複数のコンポーネントを一緒に考慮すると診断が容易になります。

| 症状                                         | 最初に調査する可能性が最も高い領域 |
| -------------------------------------------- | ---------------------------------- |
| ブラウザが接続できない                       | Nginx / TLS / ネットワーク         |
| Nginx は機能するがアプリケーションが失敗する | Docker / LUMS                      |
| LUMS は機能するがクライアントがレポートできない | エージェント / TLS / トークン   |
| クライアントはレポートするがジョブが保留中のまま | ウォッチャー / 対象判定        |
| ジョブは実行されるがパッケージが失敗する     | APT / pacman                       |
| パッケージは成功するが結果が欠けている       | エージェントレポート               |
| 結果はサーバーに到達するが UI が古い         | API / データベース / ブラウザ状態  |
| Viewer がデータを変更できる                  | サーバー側 RBAC                    |
| ユーザーがログインできない                   | アカウント / パスワード / 速度制限 |
| ログインは機能するがアクションが拒否される   | RBAC / CSRF                        |
| データベース書き込みが失敗する               | SQLite / ディスク / 権限           |
| コンテナ再作成後にデータが失われる           | 永続ボリューム設定                 |
| アプリケーションがルートファイルシステムに書き込む | コンテナファイルシステム設定 |
| ポート 5050 が外部から到達可能               | Docker / ファイアウォール設定      |

この表は最初に調査する場所を特定するものであり、必ずしも最終的な根本原因ではありません。

# 104. 一般的なトラブルシューティングの誤り

以下の近道を避けてください：

## データベースを削除しないでください

```text id="h7k2px"
Deleting lums.db
Deleting lums-data
```

永続アプリケーション状態を破壊する可能性があります。

---

## セキュリティ制御を無効にしないでください

以下を永続的に無効にしないでください：

```text id="j5r9cw"
RBAC
CSRF protection
TLS validation
Container hardening
Read-only filesystem
no-new-privileges
Capability restrictions
```

セキュリティ制御を削除する回避策は、完了した修正ではありません。

---

## コンテナを特権モードで実行しないでください

トラブルシューティングソリューションとして以下を避けます：

```text id="b3x7mz"
--privileged
```

アプリケーションが追加のアクセスを必要とする場合、正確にどのアクセスが必要かを判断します。

---

## ポート 5050 を公開しないでください

以下を変更しないでください：

```text id="v8n4qr"
127.0.0.1:5050
```

を：

```text id="p2m6wy"
0.0.0.0:5050
```

に変更して Nginx をバイパスするだけの理由で。

アプリケーションは意図的にリバースプロキシの背後で保護されています。

---

## ジョブ状態を手動で変更しないでください

以下を直接変更することを避けます：

```text id="r7c5xn"
update_jobs
update_job_packages
```

運用問題を隠すため。

アプリケーション、エージェント、ウォッチャー、復旧メカニズムを使用してください。

---

## パッケージマネージャーのロックを盲目的に削除しないでください

ロックはアクティブなパッケージマネージャープロセスを示す場合があります。

まずプロセスを特定してください。

---

## 認証情報を繰り返しローテーションしないでください

繰り返しのトークンまたはシークレットローテーションは、追加の認証問題を引き起こす可能性があります。

まず、現在設定されている認証情報とサーバーが期待する認証情報を特定してください。

# 105. 復旧原則

以下の原則はすべての LUMS トラブルシューティングに適用されます：

### まず保存する

問題が理解されるまで以下を保持します：

```text id="q3m8vx"
Logs
Job state
Database
Container state
Configuration
Error messages
```

### 一度に 1 つのことを変更する

複数の変更が同時に行われると、元の原因が特定しにくくなります。

### 各変更後に検証する

制御された変更の後：

```text id="z6w2kp"
Re-test
Check logs
Verify state
Confirm security properties
```

### 可逆的な変更を優先する

可能な限り、アプリケーション状態を破壊せずに元に戻せる変更を使用してください。

### セキュリティ制御をアクティブに保つ

成功したトラブルシューティング結果は、不必要なセキュリティ回帰を導入してはなりません。

# 106. 本番トラブルシューティングのシーケンス

一般的な LUMS 本番問題については、この順序を使用してください：

```text id="f4n8rx"
1. Identify the symptom
        ↓
2. Identify the affected component
        ↓
3. Inspect current state
        ↓
4. Inspect relevant logs
        ↓
5. Reproduce safely
        ↓
6. Determine the first failing layer
        ↓
7. Apply the smallest required change
        ↓
8. Re-test
        ↓
9. Verify security controls
        ↓
10. Document the result
```

この順序は、無関係なコンポーネントが不必要に変更されるのを防ぎます。

# 110. トラブルシューティングを停止するタイミング

以下の場合に変更を停止します：

```text id="v9m4xr"
The root cause is identified
    AND
The corrective action is understood
    AND
The system is stable
    AND
Security controls remain intact
```

根本原因が理解されていない場合、環境を繰り返し変更するのではなく、現在の状態を保存してください。

きれいに保存された失敗は、部分的に変更されたシステムよりも診断が容易です。

# 111. 最終復旧原則

最も重要な LUMS トラブルシューティングルールは：

> **まず観察。次に変更。そして検証。**

LUMS は複数の独立したセキュリティおよび実行レイヤーを含んでいます。

1 つのレイヤーの問題が自動的に別のレイヤーの変更につながるべきではありません。

したがって、優先されるトラブルシューティングアプローチは：

```text id="c8w5zn"
Observe
   ↓
Classify
   ↓
Isolate
   ↓
Correct
   ↓
Verify
   ↓
Document
```

これにより、トラブルシューティングは管理され、再現可能で、LUMS セキュリティベースラインと互換性のある状態に保たれます。

# 112. ドキュメントのメンテナンス

本ドキュメントは、文書化された運用動作が変更されるたびに更新すべきです。

ドキュメントの変更は以下と一致している必要があります：

```text id="q7m3vx"
Security documentation
Deployment documentation
Agent behavior
Watcher behavior
RBAC model
Package-management behavior
Docker runtime configuration
Test baseline
```

古いトラブルシューティング手順は、廃止されたコマンドやセキュリティを弱める回避策を推奨する場合に危険です。

本番動作が変更された場合、トラブルシューティング手順を完了として扱う前に、関連するドキュメントを更新してください。
