# LUMS ヘルスダッシュボード

## 目的と範囲

認証が必要な `/health` ダッシュボードでは、選択した LUMS およびフリートの状態を運用担当者がすばやく確認できます。

- アプリケーションが判定するデータベースの状態。
- クライアントの合計数、オンライン数、不明数、オフライン数。
- テレメトリがインストールされ、サンプルが存在する有効なクライアントの最近の CPU、メモリ、ネットワークテレメトリ。
- アラート履歴と検出されたテレメトリの中断。
- 設定されたバックアップディレクトリを検査できるか、アプリケーションが認識する最新のバックアップファイル、および監査ログに記録された最後に成功したバックアップ作成。
- 設定されている場合の、オプションの Wazuh および Suricata systemd サービス状態の行。

詳細なクライアント別のホスト／ネットワーク測定値、温度、サービス／コンテナー状態、セキュリティイベント概要は、別の `/monitoring` ページに表示されます。テレメトリユニットはイベント概要のために system journal を読み取り専用で参照します。生のログメッセージ、ユーザー名、送信元アドレスは送信しません。テレメトリサービスアカウントが追加権限なしで実行環境を検査できない場合、コンテナーの詳細は利用できません。これらのページだけでは、ホスト、Docker デーモン、リバースプロキシ、ネットワーク、またはすべての管理対象クライアントが正常であるとは証明できません。バックアップが一覧表示されても、復元できる証明にはなりません。定期的に管理された環境で復元テストを実施してください。

## アクセス制御

`/health` ページを表示するには、サインイン済みで `clients.view` 権限を持つユーザーが必要です。アクセスにはアプリケーションの通常の認証および認可チェックが適用されます。ログインやリバースプロキシの制御を迂回してダッシュボードを公開しないでください。

別の `GET /api/health` エンドポイントは、軽量な稼働応答を返します。応答が成功しても、そのルートが応答できることを示すだけであり、データベース、バックアップ、クライアントの健全性を完全に評価したことにはなりません。

## クライアント状態の解釈

ダッシュボードは最後に報告されたタイムスタンプに基づいてクライアントを分類します。

| 状態 | タイムスタンプの経過時間 |
| --- | --- |
| Online | 120 秒以下 |
| Unknown | 120 秒超～600 秒、タイムスタンプがない／無効、または未来のタイムスタンプ |
| Offline | 600 秒超 |

これらのしきい値が示すのは報告の新しさであり、マシンの電源が入っているか、すべてのサービスが動作しているかではありません。ネットワーク遅延、マシンのサスペンド、エージェントの停止、報告の失敗はいずれも結果に影響します。`unknown` は情報が不足している状態であり、障害の証明ではありません。

## CPU・メモリのテレメトリ

テレメトリはオプションであり、reporting Agent と execution Watcher とは別の機能です。systemd timer が有効で、クライアントがサーバーに接続できる場合、テレメトリサービスは約 5 秒ごとにサンプルを送信します。

ダッシュボードでは 1 時間、24 時間、7 日の履歴期間を選択でき、フリートテレメトリは 5 秒ごとに更新されます。`/monitoring` の詳細なホストデータは最後に報告されたスナップショットです。インターフェースごとの帯域幅は連続するスナップショットから算出されます。履歴クエリは 1～168 時間に制限され、最大 1,000 ポイントにダウンサンプリングされる場合があります。7 日より古いサンプルは新しいテレメトリ送信の処理時に削除されます。すべての送信が停止した場合、保持データの削除が独立して実行されるとは限りません。

監視ページの各 journal クエリは一致するレコード 500 件までです。表示件数 `500+` は、実際の件数がさらに多い可能性を示します。ログイン／ログアウト履歴は 20 件、起動履歴は 10 件までです。ヘルスダッシュボードのレイアウトは固定で、ユーザーごとの既存の CPU／RAM／ディスクしきい値（既定値 90%）が使用されます。しきい値超過とテレメトリの中断は保持中のサンプル履歴から導出されます。サービス状態の遷移と新たに報告された SSH 失敗は、最大 7 日間、タイムスタンプ付きイベントとして記録されます。CSV／JSON エクスポートには選択した期間の全サンプルが含まれます。対話型チャートは最大 1,000 ポイントに制限されます。

Wazuh と Suricata の行はオプトインであり、systemd サービス状態のみを報告します。対応するインストール済みユニットを `LUMS_MONITORED_SERVICES` に含める必要があります。Wazuh または Suricata の API に接続したり、アラートフィードを取り込んだりすることはありません。バックアップ実行時刻は監査ログに由来し、独立した復元検証ではありません。

テレメトリにはクライアント認証が必要です。リモートエージェント接続には HTTPS が必要です。平文 HTTP が受け入れられるのはループバックアドレスのみです。サーバーがプライベート認証局の証明書を使用する場合は CA ファイルを設定してください。設定手順については[テレメトリガイド](テレメトリ.md)と[インストールガイド](インストールとアップグレード.md)を参照してください。原文は[英語のヘルスダッシュボードガイド](../../../LUMS_Health_Dashboard.md)です。

## バックアップストレージの状態

バックアップ欄に表示されるのは、設定済みバックアップディレクトリをアプリケーションが検査できるかどうか、および認識する最新のバックアップファイルです。すべてのバックアップの内容を個別に検証したり、ホスト外への複製を確認したり、データベースを復元できると証明したりするものではありません。

運用では、次の手順を推奨します。

1. 表示されたバックアップ日時が、必要な復旧目標に対して十分に新しいことを確認します。
2. バックアップジョブとアプリケーションログにエラーがないか確認します。
3. バックアップが適切に保護された保存先へコピーされていることを確認します。
4. 別の管理された場所で定期的に復元テストを行います。

トラブルシューティングの近道として、稼働中のデータベースやバックアップファイルを削除または上書きしないでください。

## 状態が正しくないように見える場合の推奨確認事項

1. LUMS コンテナーと最近のログを確認します。
2. ページまたは API に接続できない場合は、リバースプロキシと TLS の設定を確認します。
3. 不明／オフラインと表示されるクライアントについて、reporting Agent と Watcher の timer および最近の journal エントリを確認します。
4. テレメトリが表示されない場合は、`lums-telemetry.timer`、`lums-telemetry.service`、クライアント／サーバーの設定を確認します。
5. バックアップ警告について、設定されたバックアップパス、ファイルシステム権限、空き容量、最近のバックアップログを確認します。
6. 変更を行う前に、確認した状態とタイムスタンプを記録します。

診断コマンドは[トラブルシューティングガイド](トラブルシューティング.md)、定期メンテナンスとバックアップの手順は[管理ガイド](管理とバックアップ.md)を参照してください。原文は[英語のヘルスダッシュボードガイド](../../../LUMS_Health_Dashboard.md)です。
