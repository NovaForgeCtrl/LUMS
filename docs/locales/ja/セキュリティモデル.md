# LUMS セキュリティドキュメント

**LUMS — Linux アップデート管理サーバー**

本文書は、LUMS の現在のセキュリティアーキテクチャ、実装済みのセキュリティ制御、セキュリティ監査結果、運用上の制限、およびセキュリティ関連の設計判断を記述します。

本文書は**現在実装されているシステム状態**を反映しています。計画中または将来の改善は、その旨を明示的に示しています。

---

# セキュリティ原則

LUMS は、Linux アップデート管理に対して多層防御（ディフェンス・イン・デプス）のアプローチを採用しています。

セキュリティモデルは、管理者認証、クライアント認証、認可、制御された更新実行、および監査ログを分離しています。

主要なセキュリティ目標は以下のとおりです：

* 認証済みの管理者アクセス
* ロールベースの認可
* 認証済みのクライアント通信
* 制御された更新実行
* 同時ジョブ実行からの保護
* 復旧可能な更新ジョブ
* 保護されたシークレット
* 制御されたコンテナ実行
* 監査可能なセキュリティ重要操作
* 予測可能な障害処理
* セキュリティ回帰テスト

LUMS は主に、制御されたインフラストラクチャ、ラボ、および内部ネットワーク環境を対象としています。

追加のセキュリティレビューと適切なネットワーク制御なしに、公衆インターネットへ直接公開すべきではありません。

---

# セキュリティアーキテクチャ

LUMS は以下のセキュリティ関連コンポーネントから構成されています：

* Web 管理インターフェース
* REST API
* SQLite データベース
* 管理対象クライアント上の LUMS エージェント
* APT および pacman パッケージ管理バックエンド
* 更新ジョブおよび復旧メカニズム
* Nginx HTTPS リバースプロキシ
* 強化された Docker コンテナ

基本的な管理フローは次のとおりです：

ブラウザ → HTTPS/Nginx → LUMS API → SQLite → LUMS エージェント → パッケージマネージャー → 結果 → SQLite → Web UI

認証と認可は意図的に分離されています。

有効な認証済みセッションは、すべての管理操作へのアクセスを自動的に付与するものではありません。

認可はサーバー側で強制されます。Web インターフェースは現在のロールに利用できない機能を追加的に隠しますが、UI の可視性はセキュリティ境界として扱われることは決してありません。

## 管理者認証

管理者ユーザーは LUMS Web インターフェースを通じて認証します。

パスワードは決して平文で保存されません。LUMS はパスワード保存に Argon2 ベースのパスワードハッシュを使用します。

管理者セッションは以下を使用します：

* 認証済みサーバー側セッション処理
* セッション有効期限
* セッション再生成
* 状態変更ブラウザリクエストに対する CSRF 保護
* ログイン速度制限
* ログアウト時のセッション無効化
* サーバー側ロール検証

認証と認可は別個のセキュリティ制御のままです。

正常に認証されたユーザーであっても、保護された操作には必要な権限を保持していなければなりません。

# ロールベースアクセス制御

LUMS は現在、3 つの Web ユーザーロールをサポートしています：

* `administrator`
* `operator`
* `viewer`

ロールテンプレートは `users.role` に保存され、個別権限はサーバー側の `user_permissions` に保存されます。

サーバーは認証された各アカウントの有効な権限をロードします。
クライアント側の権限情報は表示のみを制御し、サーバー側認可を決して置き換えません。

## Administrator

管理者は完全な管理および運用アクセスを持ちます。

以下を実行できます：

* クライアントの表示
* クライアントの作成
* クライアントの無効化
* クライアントトークンのローテーション
* インストール済みパッケージと利用可能な更新の表示
* 更新ジョブの作成
* サポートされている更新操作の実行
* 更新ジョブ履歴の表示
* パッケージ管理の使用
* システムメンテナンス機能の使用
* ユーザーの管理
* ユーザーロールの管理
* 管理機能へのアクセス

## Operator

オペレーターは運用上の更新管理タスクを実行できます。

以下を実行できます：

* クライアントの表示
* インストール済みパッケージと利用可能な更新の表示
* 更新ジョブの作成
* サポートされている更新操作の実行
* 更新ジョブ履歴の表示
* パッケージ管理の使用
* システムメンテナンス機能の使用

オペレーターは以下を実行できません：

* ユーザーの管理
* ユーザーロールの変更
* クライアントの作成
* クライアントの無効化
* クライアントトークンのローテーション

## Viewer

Viewer は制限された読み取り専用アクセスを持ちます。

以下を実行できます：

* クライアントの表示
* インストール済みソフトウェアの表示

以下の管理領域は Viewer アカウントから隠されます：

* 更新
* 更新ジョブ
* 更新履歴
* パッケージ管理
* システムメンテナンス

Viewer アカウントは状態変更を伴う更新管理操作を実行できません。

サーバーは認証およびユーザーごとの権限チェックを通じて、これらの制限を独立して強制します。

# クライアント認証

管理対象の各 LUMS クライアントは、個別の Bearer トークンを使用します。

認証メカニズムは次のモデルに従います：

`Authorization: Bearer <CLIENT_TOKEN>`

サーバーはクライアントトークンを平文値として保存しません。

代わりに、LUMS はクライアントトークンの SHA-256 16 進ダイジェストを保存します。

認証フローは次のとおりです：

クライアントトークン → SHA-256 → トークンダイジェスト → SQLite

クライアント認証は、認証されたトークンを登録済みクライアントに対して検証し、さらに該当するクライアント状態をチェックします。

セキュリティモデルは、クライアント ID の唯一の証明として送信元 IP アドレスを使用しません。

これにより、LUMS は以下で動作できます：

* プライベートラボネットワーク
* 分離されたインフラストラクチャ
* NAT ベースのネットワーク
* オフライン環境
* クライアントアドレスが変化する可能性のあるネットワーク

クライアントトークンは、認可された管理者によってローテーションできます。

トークンローテーションは、代替トークンを生成し、そのダイジェストのみを保存し、以前のトークンを無効にし、監査ログに管理操作を記録し、代替トークンを一度だけ提示します。

平文のクライアントトークン値は監査レコードに書き込まれません。

# セキュリティ監査 #01

## SQLite 外部キー

アプリケーションデータベース接続に対して SQLite 外部キー強制が有効化されています。

アプリケーションは明示的に以下を有効化します：

`PRAGMA foreign_keys = ON`

これにより、関連するデータベースレコード間の関係に対して参照整合性が強制されます。

監査は以下を検証しました：

* ランタイム外部キー強制
* 外部キー整合性
* クライアントライフサイクル動作
* クライアント無効化動作
* 履歴ジョブ情報の保持
* 監査情報の保持

クライアント状態は保守的に処理されます。

適切な場合、履歴運用情報を破壊する方法でクライアントを削除するのではなく、無効化します。

**ステータス：合格**

# セキュリティ監査 #02

## SQLite ランタイム設定

本番 SQLite データベースはそのランタイム設定についてレビューされました。

検証済みの本番設定は次のとおりです：

* `journal_mode`: `wal`
* `busy_timeout`: `5000`
* `synchronous`: `2`

アプリケーションは明示的に以下を有効化します：

`PRAGMA foreign_keys = ON`

本番データベースは現在 WAL モードを使用しています。

データベース設定は、歴史的な開発設定ではなく、実際に検証された本番状態に基づいて文書化されました。

設定された busy timeout は、別のトランザクションが一時的にデータベースを保持している場合の即時的なデータベース障害を軽減します。

アプリケーションレベルの外部キー設定は、各データベース接続の参照整合性を保証します。

監査には、アクティブな SQLite 設定の本番検証が含まれていました。

**ステータス：合格**

# セキュリティ監査 #03

## 更新タイムアウトとプロセス処理

更新実行は、無期限にブロックするパッケージマネージャープロセスから保護されています。

実行フローは次のとおりです：

プロセス開始
↓
プロセス出力を読み取る
↓
タイムアウトを監視
↓
タイムアウトに達したか？
↓
プロセスを終了
↓
猶予期間
↓
プロセスはまだ実行中か？
↓
必要に応じてプロセスを強制終了
↓
ジョブを完了

実装は制御されたサブプロセス処理を使用しているため、サイレントプロセスが出力を待つ間に無期限にブロックすることはできません。

タイムアウト処理は以下に対してテストされました：

* サイレントプロセス
* 通常のプロセス完了
* タイムアウト条件
* 通常の終了に抵抗するプロセス
* 強制終了フォールバック
* 統合レベルのタイムアウト動作

タイムアウトメカニズムは、パッケージ管理操作が無期限にアクティブ状態のままになることを防ぎます。

エラーとタイムアウト条件は制御されたジョブ結果として返され、ジョブ状態に記録されます。

現在文書化されている LUMS エージェントバージョンは次のとおりです：

`1.7.0`

**ステータス：合格**

# セキュリティ監査 #04

## ログイン速度制限

管理者ログイン試行は速度制限されています。

現在のエスカレーションポリシーは次のとおりです：

* 5 回の失敗試行 → 30 秒
* 6 回の失敗試行 → 60 秒
* 7 回の失敗試行 → 120 秒
* 8 回以上の失敗試行 → 300 秒

速度制限状態は SQLite に永続化されます。

同時ログイン失敗は以下によるトランザクションデータベースロックを使用します：

`BEGIN IMMEDIATE`

これにより、同時認証失敗が競合状態を通じて意図された速度制限状態をバイパスすることを防ぎます。

成功した認証は該当する失敗状態をクリアします。

監査は以下をカバーしました：

* 分離された速度制限動作
* 同時認証失敗
* トランザクションロールバック
* データベースロック処理
* 成功ログイン時のリセット動作
* 速度制限監査イベント
* 本番ログイン動作

したがって、レートリミッターはクライアント側の動作に依存するのではなく、繰り返される認証試行に対するサーバー側制御を提供します。

**ステータス：合格**

# セキュリティ監査 #05

## API 入力検証

LUMS はサーバー側でセキュリティ重要 API 入力を検証します。

クライアント提供の値は、認証された Web インターフェースまたは登録済みクライアントから発信されたという理由だけで信頼されることはありません。

検証は、以下を含む関連 API パラメータに適用されます：

* クライアント識別子
* パッケージ名
* 更新ジョブアクション
* パッケージリスト
* 検索パラメータ
* ユーザー管理パラメータ
* クライアントトークン操作
* ジョブ結果データ

パッケージ名は、パッケージ管理操作に渡される前に検証されます。

更新ジョブ API は明示的にサポートされているアクションのみを受け入れます。

現在サポートされているパッケージ関連アクションは：

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

予期しないアクションは拒否されます。

パッケージリストはジョブ作成前に検証されます。

`UPDATE_PACKAGE` の場合、要求されたパッケージはクライアントの利用可能な更新情報にも存在しなければなりません。

データベースクエリは、信頼できない入力から SQL 文を構築するのではなく、パラメータ化された SQL を使用します。

これにより、ユーザー制御値が SQL 構文として解釈されるのを防ぎます。

監査には、ネガティブ入力テストと SQL インジェクション指向のテストケースが含まれていました。

検証制御は自動テストスイートを通じても検証されました。

**ステータス：合格**

# セキュリティ監査 #06

## セッション無効化

LUMS は認証済み管理者セッションをログアウト後の継続使用から保護します。

セッション処理には以下が含まれます：

* 認証済みサーバー側セッション
* セッション有効期限
* セッション再生成
* ログアウト無効化
* サーバー側認証チェック
* サーバー側ロール検証

ログアウトはアクティブな認証済みセッションを無効化します。

保護された API エンドポイントは認証済みセッションを必要とし、ユーザーが依然として認証されているかを判断するためにクライアント側状態に依存しません。

したがって、保護操作のセッション状態はサーバーによって評価されます。

状態変更ブラウザリクエストはさらに CSRF 保護を必要とします。

監査は以下を検証しました：

* 認証済みアクセスが正常に動作する
* 保護されたエンドポイントが未認証リクエストを拒否する
* ログアウトがアクティブセッションを無効化する
* 以前に認証されたセッションが無効化後に保護機能を使い続けることができない
* ロール情報がサーバー側で評価される

**ステータス：合格**

# セキュリティ監査 #07

## クライアントトークンローテーション

各管理対象 LUMS クライアントは、個別の認証トークンを使用します。

クライアントトークンは平文値として保存されません。

代わりに、LUMS はクライアントトークンの SHA-256 16 進ダイジェストを保存します。

認証モデルは次のとおりです：

`Authorization: Bearer <CLIENT_TOKEN>`

サーバーは提供されたトークンをハッシュ化し、結果のダイジェストを登録済みクライアントトークンダイジェストと比較します。

認可された管理者はクライアントのトークンをローテーションできます。

トークンローテーションは以下の操作を実行します：

1. 代替トークンを生成する。
2. その SHA-256 ダイジェストを計算する。
3. 保存されたクライアントトークンダイジェストを置き換える。
4. 以前のトークンを無効化する。
5. 監査ログに管理操作を記録する。
6. 管理者に代替トークンを提示する。

以前のトークンはローテーション後に認証できません。

平文トークン値は監査ログに書き込まれません。

監査は以下を検証しました：

* 成功したトークン認証
* トークンダイジェスト保存
* トークンローテーション
* 以前のトークンの無効化
* 代替トークンによる認証
* トークンローテーションの認可要件
* 監査ログ
* 未認可ローテーションからの保護

クライアントトークンローテーションは管理者に制限されています。

オペレーターと Viewer はクライアントトークンをローテーションできません。

**ステータス：合格**

# セキュリティ監査 #08

## IP アドレス処理とオフラインネットワーク

LUMS は、クライアントの送信元 IP アドレスをクライアント ID の唯一の証明として使用しません。

クライアント認証は登録済みクライアントトークンに基づいています。

この設計は、管理対象クライアントがネットワークアドレスが変化する環境で動作する可能性があるため意図的なものです。

サポートされる展開シナリオには以下が含まれます：

* プライベートラボネットワーク
* NAT ベースのネットワーク
* 分離されたインフラストラクチャ
* 動的にアドレス指定されるクライアント
* オフライン環境
* 制御された内部ネットワーク

したがって、サーバーは以下を分離します：

**ネットワーク位置**

と：

**クライアント ID**

有効なクライアントトークンは登録済みクライアントを識別します。

クライアントのネットワークアドレスは運用および監査目的で記録される場合がありますが、認証情報として扱われることはありません。

実装はまた、クライアントが固定アドレスから到達可能でなければならないという仮定を回避します。

これは、管理対象システムの論理 ID を変更せずにネットワークトポロジが変化する可能性があるラボ環境およびインフラストラクチャにとって特に重要です。

監査は、固定送信元 IP アドレスに依存せずにクライアント認証を検証しました。

**ステータス：合格**

# セキュリティ監査 #09

## ジョブ復旧とチェックポイント

LUMS 更新ジョブは、中断された実行から安全に復旧するように設計されています。

更新ジョブは SQLite データベースに永続状態を維持します。

個々のパッケージ操作は、全体的なジョブ状態とは別に追跡されます。

これにより、エージェントは中断されたジョブを再開する前に、どのパッケージ操作が既に正常に完了したかを判断できます。

復旧中、正常に完了したパッケージ操作は再度実行されません。

したがって、復旧ロジックは以下の原則に従います：

`永続ジョブ状態 → 完了作業を判断 → 完了項目をスキップ → 残りの作業を続行`

これにより、以下の後の不必要な繰り返しパッケージ操作のリスクが減少します：

* エージェント中断
* プロセス終了
* システム再起動
* 一時的な通信障害
* コンテナ再起動
* その他の実行中断

監査は、中断されたジョブの復旧とチェックポイント動作を検証しました。

復旧は、複数のパッケージ操作を含むジョブと、以前に成功したパッケージアイテムでテストされました。

監査は、完了した作業が保持され、成功した操作を不必要に繰り返すことなく残りの作業を続行できることを確認しました。

**ステータス：合格**

APT 関連の更新操作は、パッケージマネージャー状態と更新結果の信頼性の高い検出についてレビューされました。

`c76f331 security: harden apt update detection`

目的は、LUMS が不完全または曖昧なコマンド出力のみに基づいて、パッケージ管理状態を誤って報告しないようにすることです。

# セキュリティ監査 #17

## ロールベースアクセス制御

LUMS はロールテンプレートと個別に割り当てられた権限を組み合わせています。サポートされているテンプレートは `administrator`、`operator`、`viewer` です。テンプレートを選択するとそのデフォルト権限が選択され、管理者は各アカウントのためにカスタマイズできます。

ロールはアカウントメタデータのままです。保護されたルートは、ロールラベルではなく、アカウントのサーバー保存権限セットに対して認可します。インターフェースは使いやすさのために利用できない機能を隠しますが、サーバーはセキュリティ境界のままです。

---

## RBAC 権限モデル

| 権限              | 付与されるアクセス |
| ----------------- | ------------------ |
| `clients.view`    | クライアントとシステム情報の表示 |
| `software.view`   | インストール済みソフトウェアの表示 |
| `updates.view`    | 利用可能な更新、ジョブ、履歴の表示 |
| `packages.search` | パッケージリポジトリの検索 |
| `jobs.manage`     | パッケージ操作と更新ジョブの作成 |
| `clients.manage`  | クライアントの登録/削除とクライアントトークンのローテーション |
| `users.manage`    | ユーザーの作成とロール、権限の管理 |

デフォルトのロールテンプレートは次のとおりです：

| テンプレート    | デフォルト権限 |
| --------------- | -------------- |
| `administrator` | すべての権限 |
| `operator`      | クライアント/ソフトウェア/更新の可視性、パッケージ検索、ジョブ管理 |
| `viewer`        | クライアントの可視性とインストール済みソフトウェアの可視性 |

クライアント関連の権限には `clients.view` が必要です。`jobs.manage` には `updates.view` も必要です。UI は認証されたアカウントの権限をロードし、ユーザーが使用できないコントロールを省略します。サーバー側チェックは同じ付与を独立して強制します。

---

## 認可の強制

保護された操作はサーバー側認証と権限チェックを使用します。

認可モデルは以下の原則に従います：

`認証 → ユーザー権限をロード → 操作を認可 → 実行`

認証だけでは特権操作にアクセスするのに十分ではありません。

状態変更操作はさらに、該当する場合 CSRF 保護を必要とします。

保護された管理操作の例には以下が含まれます：

* 更新ジョブ作成
* パッケージインストール
* パッケージ削除
* パッケージ更新
* システム更新
* パッケージ管理操作
* クライアント作成
* クライアント無効化
* クライアントトークンローテーション
* ユーザー作成
* ユーザー管理機能

保護されたエンドポイントは、対応する操作に必要な権限を明示的に定義します。

権限が欠けている場合、ユーザーが対応する HTTP リクエストを手動で構築したとしても、サーバーによって拒否されます。

これにより、Web インターフェースで隠されている API エンドポイントを直接呼び出すことによる RBAC モデルのバイパスを防ぎます。

---

## Viewer の制限

Viewer テンプレートは、そのデフォルト権限セットによって意図的に制限されています。

対応する付与を持たないアカウントの場合、クライアントインターフェースは以下を公開しません：

* 更新
* 更新ジョブ
* 更新履歴
* パッケージ管理
* システムメンテナンス

サーバーはさらに、対応する付与を持たないアカウントが保護操作を実行することを防ぎます。

JavaScript インターフェースは `updates.view` なしで更新管理データをロードしません。

これにより、サーバー側認可を実際のセキュリティ制御として維持しながら、運用情報の不必要な露出を減らします。

インストール済みソフトウェアは、読み取り専用の情報機能として Viewer アカウントで利用可能なままです。

---

## 管理者ユーザー管理

ユーザー管理には `users.manage` 権限が必要です。

その権限を持つユーザーは、権限なしでアカウントを作成し、その後、個別の付与を割り当てるか、権限エディターでロールテンプレートを適用できます。ロールテンプレートには、デフォルトの付与を説明する説明があります。

認可されたユーザー管理者は、アカウントごとに内部メモを保存できます。メモは 2,000 文字に制限され、監査ログの詳細には含まれず、アカウント所有者には表示されません。

ユーザー作成には以下が含まれます：

* ユーザー名検証
* ロール検証
* パスワード検証
* Argon2 パスワードハッシュ
* 重複ユーザー検出
* 監査ログ
* CSRF 保護
* サーバー側認可

ユーザー管理エンドポイントは `users.manage` なしではアクセスできません。

サーバーは未知の権限と無効な依存関係の組み合わせを拒否します。少なくとも 1 つのアクティブなアカウントが `users.manage` を保持しなければなりません。最後のユーザー管理者を削除する変更は拒否されます。

パスワードは決して平文で保存されません。

---

## RBAC データベースマイグレーション

ロールテンプレート情報はユーザーデータベースレコードに残ります。個別の付与は、ユーザーアカウントへの外部キーを持つ `user_permissions` テーブルに保存されます。マイグレーション `003-user-permissions` はそのテーブルを作成し、既存のアカウントを現在のロールテンプレートからシードし、移行中にアクセスを保持します。マイグレーション `004-user-admin-notes` はプライベートな `users.admin_note` フィールドを追加します。既存のアカウントは空のメモを受け取ります。マイグレーション `005-backup-permission` は既存の Administrator アカウントに `backups.manage` を付与します。

データベースバックアップ作成には `backups.manage` が必要です。Administrator テンプレートにはデフォルトでこの権限が含まれています。サーバーは SQLite オンラインバックアップをサーバー設定された `LUMS_BACKUP_DIR` にのみ書き込みます。ブラウザからのファイルシステムパスは受け入れません。バックアップファイルは所有者のみの権限で作成され、公開前に整合性チェックされます。

## RBAC セキュリティテスト

RBAC 動作は自動テストでカバーされています。

テストには以下が含まれます：

* Administrator 認可
* Operator 認可
* Viewer 制限
* 保護された API アクセス
* 未認可操作
* クライアント管理制限
* 更新ジョブ制限
* ユーザー管理制限
* クライアントページ可視性
* 権限固有のインターフェース動作

RBAC テストは、ロールテンプレートのデフォルト、カスタム権限、権限依存関係、およびサーバー側認可をカバーします。本番検証には、デフォルトの Administrator、Operator、Viewer テンプレートだけでなく、カスタマイズされた権限を持つアカウントも含めるべきです。

---

## RBAC セキュリティ結果

RBAC 実装は階層化された認可を提供します：

1. 認証がユーザー ID を確立します。
2. サーバーがユーザーの権限をロードします。
3. 保護されたルートが必要な権限を強制します。
4. CSRF 保護が関連するブラウザ状態変更に適用されます。
5. Web インターフェースが利用できない機能を隠します。
6. 自動テストが認可境界を検証します。

したがって、インターフェース自体が認可メカニズムを提供するわけではありません。

サーバーが権威あるセキュリティ境界のままです。

**ステータス：合格**

## コンテナ強化

本番 LUMS コンテナは強化された Docker 設定で実行されます。

本番コンテナは以下を使用します：

* 非 root アプリケーションユーザー
* 読み取り専用ルートファイルシステム
* 削除された Linux ケイパビリティ
* `no-new-privileges`
* 制限された一時ファイルシステム
* 読み取り専用シークレットマウント
* 専用永続アプリケーションデータボリューム
* 再起動ポリシー
* アプリケーションポートのループバック専用ホスト公開

したがって、アプリケーションルートファイルシステムは通常動作中に書き込み可能ではありません。

書き込み可能な場所は、アプリケーションが必要とする場所に明示的に制限されています。

本番コンテナは、有効なランタイム設定を検証するために独立して検査されました。

強化されたランタイムはまた、以下を検証することによってテストされました：

* アプリケーションファイルシステムの書き込みが失敗する
* `/tmp` が必要な場所で利用可能なままである
* `/var/lib/lums` が書き込み可能なままである
* シークレットファイルが読み取り専用のままである
* アプリケーションが動作可能なままである

## ネットワーク露出

LUMS アプリケーションポートは LAN に直接公開されません。

Docker アプリケーションポートはループバックインターフェースにバインドされています：

`127.0.0.1:5050`

外部アクセスは Nginx を通じて提供されます。

本番ホストは、ファイアウォールとリバースプロキシを通じて意図されたネットワークサービスを公開します。

展開は、内部 Docker アプリケーションポートへの直接リモートアクセスを防ぐように検証されました。

ファイアウォールは、着信およびルーティングされたトラフィックに対してデフォルト拒否モデルを使用します。

意図された外部から到達可能なサービスは：

* SSH
* HTTP
* HTTPS

HTTP リクエストは Web サーバーによって HTTPS にリダイレクトされます。

デフォルトの Nginx サイトは、無関係なデフォルトコンテンツが露出しないように削除されました。

## トランスポートセキュリティ

管理 Web アクセスは HTTPS を通じて提供されます。

HTTP は HTTPS にリダイレクトされます。

TLS エンドポイントは、Flask/Gunicorn アプリケーションではなく Nginx によって処理されます。

これにより、トランスポートセキュリティとアプリケーションサービングが分離されたままになります。

したがって、内部 Gunicorn アプリケーションポートはパブリック HTTP エンドポイントを意図していません。

現在の展開は制御された内部インフラストラクチャを対象としています。

公衆インターネットへの直接露出を伴う将来の展開には、追加のセキュリティレビューが必要です。

## シークレットと設定

本番シークレットはアプリケーションソースツリーに保存されません。
