# LUMS 安装指南

## Linux 更新管理服务器

**项目：** LUMS
**口号：** 没有噪音的 Linux 更新管理。
**仓库：** `NovaForgeCtrl/LUMS`

---

## 快速开始：在开始之前理解安装过程

本指南涵盖完整的服务器安装，包括高级维护和验证程序。它**不是**一个可以不经审查就直接运行的单一脚本：服务器名称、TLS 证书、密钥文件、备份目标、网络和数据库在每次安装中都不同。

### 安装哪些内容？

* **LUMS 服务器：** Web 界面和 API，运行在 Docker 容器中。
* **Nginx：** 接受外部 HTTPS 连接并在本地转发到容器。
* **数据卷：** 包含 SQLite 数据库。此数据卷必须在升级中保留，并且在正常的容器替换过程中绝不能删除。
* **密钥文件：** 除其他外，保护应用会话。绝不要把它放入 Git 仓库、Docker 镜像或聊天消息中。
* **LUMS Agent 和 Watcher：** 在受管 Linux 客户端上单独安装。仅一个可用的服务器并不会更新任何客户端。

| 术语 | 含义 |
| --- | --- |
| 终端 / shell | 输入 Linux 命令的文本窗口。 |
| `sudo` | 以管理员权限运行后面的命令。Linux 可能会要求输入密码。 |
| 主机 | 运行 Docker 和 LUMS 服务器的 Linux 计算机。 |
| 容器 | 运行 LUMS Web 应用的隔离进程。 |
| 镜像 | Docker 用来启动容器的预制模板。 |
| 卷 | 当容器被替换时仍然保留的持久化 Docker 存储。 |
| 占位符 | 诸如 `LUMS-SERVER` 之类的文本，必须替换为您的实际值。 |

### 仅运行测试（这不会安装服务器）

这些步骤适用于 Debian 13，用于检出源代码并在本地运行测试。它们**不会**创建可通过网络访问的生产服务器，也不会在另一台计算机上安装 Agent。`sudo` 仅用于安装 Debian 软件包。

```bash
sudo apt update
sudo apt install -y git python3 python3-venv
git clone https://github.com/NovaForgeCtrl/LUMS.git ~/LUMS
cd ~/LUMS
python3 -m venv .venv-test
./.venv-test/bin/python -m pip install -r server/requirements.txt -r requirements-dev.txt
./.venv-test/bin/pytest -q
```

`apt update` 刷新软件包列表；它不会升级所有已安装的软件。`.venv-test` Python 虚拟环境将测试依赖项与系统的其余部分分开。成功的测试运行以退出代码 `0` 结束；测试数量可能会随项目增长而变化。如果创建环境失败，请检查是否已安装 `python3-venv`。如果测试失败，请保存完整错误并阅读[故障排查指南](故障排查.md)；不要删除生产数据。

对于真实安装，请继续阅读编号章节，并先阅读安全和备份说明。如果 LUMS 已在运行，请使用 [`administration.md`](管理与备份.md) 中的升级程序，而不是首次安装程序。

# 1. 概述

LUMS 是一个集中式 Linux 更新管理平台，用于受控的更新分发、客户端上报、软件包管理、更新作业执行、结果验证和可审计管理。

当前架构将管理服务器与受管 Linux 客户端分开。

服务器提供：

* 基于 Web 的管理
* 客户端管理
* 客户端身份验证
* 软件包清单
* 可用更新上报
* 软件包搜索
* 软件包安装和删除
* 更新作业管理
* 作业结果验证
* 更新历史
* 基于角色的访问控制
* 审计日志
* 基于 SQLite 的持久化状态

Linux 客户端提供：

* 系统信息
* 已安装软件包清单
* 可用更新检测
* 软件包操作
* 更新作业执行
* 空闲状态检测
* 作业检查点与恢复
* 重启检测
* 结果上报

当前实现支持：

```text
Debian / Ubuntu
    └── APT / dpkg

Arch Linux
    └── pacman
```

# 2. 架构

生产架构为：

```text
                         LUMS Server
                              │
                              │ HTTPS :443
                              ▼
                       ┌──────────────┐
                       │    Nginx     │
                       │  TLS / Proxy │
                       └──────┬───────┘
                              │
                              │ HTTP
                              ▼
                       127.0.0.1:5050
                              │
                              ▼
                    ┌───────────────────┐
                    │   Docker: lums    │
                    │                   │
                    │   Gunicorn        │
                    │   Flask :5000     │
                    │   SQLite          │
                    └─────────┬─────────┘
                              │
                              ▼
                         lums-data
                              │
                              ▼
                   /var/lib/lums/lums.db


        Linux Client
              │
              │ HTTPS + Bearer Token
              ▼
         LUMS API
              │
              ├── Report
              ├── Package Search
              ├── Job Retrieval
              └── Job Result
```

LUMS 应用**不打算直接暴露给网络**。

应用容器绑定到：

```text
127.0.0.1:5050 → container:5000
```

Nginx 是外部 HTTPS 入口点。

端口 `5000` 不直接发布。

端口 `5050` 必须保持仅限 localhost。

# 4. 安全模型

安装必须保留 LUMS 安全基线。

生产服务器使用：

```text
HTTPS
Bearer-token client authentication
Role-based web authorization
CSRF protection
Audit logging
Read-only container root filesystem
Dropped Linux capabilities
no-new-privileges
Non-root application user
Localhost-only application port
Persistent Docker volume
Read-only secret mount
```

Docker 容器以非特权用户运行：

```text
lums
```

UID：

```text
10001
```

容器不得以特权模式运行。

根文件系统必须保持只读。

应用不得要求对其应用目录的写访问权限。

持久化应用数据通过专用 Docker 卷存储。

# 5. 当前 RBAC 模型

LUMS 目前提供三种 Web 角色：

```text
administrator
operator
viewer
```

## Administrator

管理员可以执行管理操作，包括：

```text
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
Create and disable clients
Rotate client tokens
Manage users
Manage roles
```

---

## Operator

操作员可以执行运维管理：

```text
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
```

操作员无权访问：

```text
User management
Role management
Client creation/disabling
Client-token rotation
```

---

## Viewer

Viewer 具有刻意受限的访问权限。

Viewer 可以访问：

```text
Clients
Installed software
```

以下管理区域在 Viewer 界面中隐藏并在服务器端受保护：

```text
Available updates
Update Jobs
Update History
Package Management
System Maintenance
```

因此隐藏 UI 并不是安全边界。

服务器端授权仍然是强制性的。

# 10. 准备主机配置目录

创建所需的主机侧目录：

```bash
sudo install -d -m 700 /etc/lums
sudo install -d -m 700 /etc/lums/secrets
sudo install -d -m 700 /etc/lums/tls
```

密钥目录包含应用密钥。

TLS 目录包含 TLS 证书和私钥。

保护这些目录可降低意外泄露的风险。

验证：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums \
    /etc/lums/secrets \
    /etc/lums/tls
```

---

# 11. 创建应用密钥

LUMS 应用密钥存储在主机上，而不是直接嵌入 Docker 镜像中。

生产密钥路径为：

```text
/etc/lums/secrets/lums_secret
```

生成随机密钥：

```bash
sudo sh -c 'umask 077 && openssl rand -hex 32 > /etc/lums/secrets/lums_secret'
```

保护生成的文件：

```bash
sudo chmod 600 \
    /etc/lums/secrets/lums_secret
```

在不显示密钥的情况下验证权限：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums/secrets/lums_secret
```

预期：

```text
600
```

密钥绝不应：

```text
Committed to Git
Printed into logs
Included in the Docker image
Placed into screenshots
Published in issues
Included in documentation
```

容器通过只读绑定挂载接收密钥。

---

# 12. 准备 TLS 材料

LUMS 使用 HTTPS 进行外部访问。

推荐的主机侧位置为：

```text
/etc/lums/tls/lums.crt
/etc/lums/tls/lums.key
```

在配置 Nginx 之前，安装相应的证书和私钥。

保护私钥：

```bash
sudo chmod 600 \
    /etc/lums/tls/lums.key
```

证书可由 Nginx 服务读取：

```bash
sudo chmod 644 \
    /etc/lums/tls/lums.crt
```

验证：

```bash
sudo stat -c '%a %U:%G %n' \
    /etc/lums/tls/lums.crt \
    /etc/lums/tls/lums.key
```

私钥绝不应提交到 Git 或包含在 Docker 镜像中。

安装应按受控阶段进行：

```text
Repository
    ↓

    ↓
Application secret
    ↓
TLS material
    ↓
Docker image
    ↓
Persistent volume
    ↓

    ↓
```

# 14. 构建 LUMS Docker 镜像

在构建生产镜像之前，请确保仓库处于预期状态。

进入仓库：

```bash
cd /opt/lums-public
```

```bash
sudo docker image inspect lums:latest
```

Dockerfile 在需要时还使用固定的生产依赖项。

# 15. 审查 Docker 构建

在部署镜像之前，请审查构建输出中的意外错误或警告。

检查生成的镜像：

```bash
sudo docker inspect \
    lums:latest
```

```bash
sudo docker image inspect \
    lums:latest \
    --format '{{.Config.User}}'
```

应用旨在以以下用户运行：

```text
lums
```

应用在正常执行期间不得要求 root 权限。

```bash

```

仓库包含一个 `.dockerignore` 文件，以降低意外将运行时工件包含到镜像中的风险。

# 16. 创建持久化 Docker 卷

创建持久化 LUMS 数据卷：

```bash
sudo docker volume create lums-data
```

验证：

```bash
sudo docker volume inspect lums-data
```

该卷存储持久化应用数据：

```text
lums-data
    ↓
/var/lib/lums
    ↓
/var/lib/lums/lums.db
```

容器文件系统本身不得被视为持久化应用存储。

因此，只要保留 `lums-data` 卷，数据库就能在容器替换后继续存在。

> [!IMPORTANT]
> 在正常应用升级期间，绝不要删除 `lums-data`。

删除该卷会删除存储其中的 SQLite 数据库。

---

# 17. 验证持久化卷

在启动 LUMS 之前，确认该卷存在：

```bash
sudo docker volume inspect \
    lums-data
```

也可以透过 Docker 检查该卷：

```bash
sudo docker volume ls | grep lums-data
```

新创建的卷通常还不包含数据库。

数据库由 LUMS 应用在部署期间初始化。

# 18. 生产容器配置

生产容器同时使用多个安全控制。

预期的运行时基线为：

```text
Non-root user
Read-only root filesystem
All Linux capabilities dropped
no-new-privileges
No privileged mode
Localhost-only application binding
Read-only application-secret mount
Persistent writable data volume
Dedicated /tmp tmpfs
```

应用端口仅发布到 localhost：

```text
127.0.0.1:5050 → container:5000
```

外部 HTTPS 端点由 Nginx 提供。

# 19. 启动加固的 LUMS 容器

在启动新的生产容器之前，请确保没有其他名为 `lums` 的容器正在运行：

```bash
sudo docker ps \
    --filter name=lums
```

如果正在替换现有部署，请保留现有容器，直到新镜像经过验证。

启动加固容器：

```bash
sudo docker run -d \
    --name lums \
    --restart unless-stopped \
    --read-only \
    --cap-drop=ALL \
    --security-opt=no-new-privileges:true \
    --tmpfs /tmp:rw,noexec,nosuid,size=64m \
    --tmpfs /run:rw,noexec,nosuid,size=16m \
    -p 127.0.0.1:5050:5000 \
    -v /etc/lums/secrets/lums_secret:/run/secrets/lums_secret:ro \
    -v lums-data:/var/lib/lums \
    -e LUMS_SECRET_KEY_FILE=/run/secrets/lums_secret \
    lums:latest
```

应用密钥以只读方式挂载。

SQLite 数据库存储在持久化卷中。

根文件系统为只读。

所有 Linux 能力都被丢弃。

`no-new-privileges` 安全选项防止容器内的进程获取额外权限。

# 21. 验证容器安全

```bash
sudo docker inspect lums \
    --format='User={{.Config.User}} ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} Privileged={{.HostConfig.Privileged}} CapDrop={{json .HostConfig.CapDrop}} SecurityOpt={{json .HostConfig.SecurityOpt}}'
```

# 22. 验证应用端口

检查已发布的 Docker 端口：

```bash
sudo docker port lums
```

预期：

```text
5000/tcp -> 127.0.0.1:5050
```

以下内容对生产应用**不可接受**：

```text
0.0.0.0:5050
```

或：

```text
0.0.0.0:5000
```

应用有意只能通过本地反向代理路径访问。

检查监听套接字：

```bash
sudo ss -lntp | grep -E ':5050|:5000'
```

应仅存在 localhost 应用绑定。

# 23. 验证密钥挂载

确认密钥已挂载：

```bash
sudo docker inspect lums \
    --format='{{range .Mounts}}{{println .Source "->" .Destination "RW=" .RW}}{{end}}'
```

应用密钥应类似于：

```text
/etc/lums/secrets/lums_secret -> /run/secrets/lums_secret RW=false
```

确切输出可能包含额外的挂载信息。

重要属性是：

```text
RW=false
```

绝不要打印密钥内容。


预期：


# 30. 验证 SQLite 运行时配置

```text
busy_timeout=5000
synchronous=2
```

# 35. 配置 Nginx

Nginx 提供 LUMS 的外部 HTTPS 入口点。

应用本身仍绑定到：

```text
127.0.0.1:5050
```

预期的请求路径为：

```text
Client
   │
   │ HTTPS
   ▼
Nginx :443
   │
   │ HTTP localhost
   ▼
127.0.0.1:5050
   │
   ▼
LUMS container :5000
```

创建 Nginx 站点配置：

```bash
sudo tee /etc/nginx/sites-available/lums > /dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;

    server_name LUMS-SERVER;

    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    listen [::]:443 ssl;

    server_name LUMS-SERVER;

    ssl_certificate     /etc/lums/tls/lums.crt;
    ssl_certificate_key /etc/lums/tls/lums.key;

    location / {
        proxy_pass http://127.0.0.1:5050;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF
```

替换：

```text
LUMS-SERVER
```

为安装所用的主机名或地址。

不要在生产配置中使用字面占位符。

---

# 65. 客户端令牌

每个 LUMS 客户端都有自己的身份验证令牌。

令牌用作：

```text
Authorization: Bearer <CLIENT-TOKEN>
```

配置后，服务器不需要原始令牌值。

服务器存储令牌的加密表示以进行验证。

这意味着客户端凭据应像密码一样对待。

绝不将真实令牌放入：

```text
Git
documentation
screenshots
issue reports
shell history
public configuration
```

# 66. 配置客户端令牌

根据当前客户端管理工作流程，从 LUMS 管理员界面创建或配置客户端。

生成的客户端令牌必须通过安全通道传输到目标客户端。

仅将其存储在：

```text
/etc/default/lums-agent
```

在客户端上。

不要在多个机器上重复使用一个客户端令牌。

预期关系为：

```text
Client A
    ↓
Token A

Client B
    ↓
Token B

Client C
    ↓
Token C
```

因此，受攻击的令牌应只识别其关联的客户端。

```text
     ↓
Administrator rotates token
     ↓
Old token invalidated
     ↓
New token issued
     ↓
Client configuration updated
```

# 68. TLS 信任

LUMS Agent 通过 HTTPS 与服务器通信。

证书验证必须保持启用。

对于公开受信任的证书，正常操作系统信任存储就足够了。

对于私有实验室 CA，在客户端上安装 CA 证书。

不要通过禁用验证来解决证书问题。

正确的解决方案是让客户端信任预期的证书颁发机构。

# 69. Debian / Ubuntu TLS 信任

在 Debian 系系统上，可以将私有 CA 安装到系统信任存储中。

# 84. 了解空闲感知执行

Watcher 可以在执行更新作业之前使用客户端空闲信息。

预期流程为：

```text
Pending job
    │
    ▼
Watcher
    │
    ▼
Idle detection
    │
    ├── idle state available
    │       │
    │       ▼
    │   idle threshold
    │       │
    │       ▼
    │   execute when allowed
    │
    └── idle state unavailable
            │
            ▼
        use configured
        fallback behavior
```

空闲检测绝不应被解释为身份验证或授权。

它只是一种执行调度机制。

# 85. 验证空闲检测

通过已安装的 Agent/Watcher 实现手动运行空闲检测路径。

检查生成的服务日志：

```bash
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 100 \
    --no-pager
```

如果平台不提供所需的空闲信息，客户端可能报告空闲检测不可用。

这并不自动是失败。

重要的区别是：

```text
idle_supported = available
```

对比：

```text
idle_supported = unavailable
```

不能仅因为未返回空闲信息就假定客户端处于空闲状态。

```text
             ▼
```

```text
Package B → not repeated
Package C → resumed / handled
```

这防止已完成的软件包操作在中断后被不必要地重复。

```bash
    lums-agent-watcher.timer
```

```bash
    -u lums-agent-watcher.service \
```

# 113. SQLite 健康检查

```bash

    python3 - <<'PY'

for name in (
    "journal_mode",
    "busy_timeout",
    "synchronous",
    "foreign_keys",
```

## 可选的 CPU 和内存遥测 Agent

有关遥测测量、安全、数据保留和故障排查的概览，请参阅 [`遥测.md`](遥测.md)。

遥测 Agent 与现有的上报 Agent 和 Watcher 相互独立。它会将 CPU 和内存测量数据发送到经身份验证的 `POST /api/telemetry` 端点。仪表板通过经身份验证的客户端遥测 API 读取这些测量数据。

### 安装文件

安装前请检查以下仓库文件：

- `agent/telemetry.py`
- `agent/lums-telemetry.service`
- `agent/lums-telemetry.timer`
- `scripts/install-telemetry-agent.sh`
- `tests/test_telemetry_agent.py`

按下文配置 `/etc/default/lums-agent` 后，在 Debian 客户端上更新仓库检出内容，并从仓库根目录运行：

```sh
sudo bash scripts/install-telemetry-agent.sh
```

安装程序会在不打印值的情况下验证 `LUMS_BASE` 和 `LUMS_TOKEN` 是否存在。它会安装或更新采集器和 systemd 单元，启用五秒定时器，并立即运行一次采样以验证连接。如果服务失败，会打印近期遥测服务日志。令牌仍保留在现有客户端配置中，不会复制到其他文件。

将遥测脚本安装到 `/usr/local/lib/lums-telemetry/telemetry.py`，由 root 所有且服务账户不可写。将服务和定时器分别安装为 `/etc/systemd/system/lums-telemetry.service` 和 `/etc/systemd/system/lums-telemetry.timer`。

服务使用 `DynamicUser=yes`，以受限权限运行，并加入 `systemd-journal` 组以只读访问系统事件日志。这使仪表板能够提供受限的安全和登录摘要；原始日志消息不会发送到服务器。该服务是由独立定时器调度的一次性服务，不会取代现有的 LUMS Agent 或 Watcher。

普通 LUMS 客户端在线，并不意味着这个独立的遥测定时器已安装或启用。`/monitoring` 页面会说明所选客户端尚未发送样本、仅发送基本指标，还是详细数据已过期。

### 配置与 TLS

在 `/etc/default/lums-agent` 中配置服务器 URL 和每个客户端独立的令牌：

```sh
LUMS_BASE=https://lums.example.invalid
LUMS_TOKEN=REPLACE_WITH_THIS_CLIENTS_TOKEN
LUMS_CA_FILE=/etc/ssl/certs/lums-ca.crt
```

请将示例 URL 和令牌替换为环境中的实际值。保护配置文件，使其仅能由 root 读取，例如设置权限模式 `0600`。切勿将真实令牌提交到源代码管理，也不要在多个客户端之间共享令牌。

可以选择要上报状态的 systemd 服务单元，并使用逗号分隔的允许列表：

```sh
LUMS_MONITORED_SERVICES=lums-agent.service,lums-telemetry.service,ssh.service,wazuh-agent.service,suricata.service
```

如果未设置，Agent 会使用内置的 LUMS、Docker 和 SSH 服务列表。Wazuh 和 Suricata 是可选项：仅添加客户端上已安装的服务单元，然后在 `/health` 仪表板中启用相应状态行。这只会上报 systemd 状态；不会要求或存储 API 凭据，也不会获取安全告警源。

如果需要私有证书颁发机构（CA），请将其证书安装在服务进程可读取的位置，例如 `/etc/ssl/certs/lums-ca.crt`，并相应设置 `LUMS_CA_FILE`。不要禁用证书验证。未设置 `LUMS_CA_FILE` 时，Agent 使用操作系统默认的 CA 信任存储。如果需要私有 CA，请明确将 `LUMS_CA_FILE` 设为一个存在且服务进程可读取的 CA 证书文件。若明确配置的 CA 文件缺失或不可读，Agent 会失败，而不会静默回退到其他信任存储。不要禁用证书验证，也不要通过放宽目录权限来规避证书配置问题。

### 启用前验证

首先运行项目测试并验证单元文件：

```sh
.venv/bin/python -m pytest -q tests/test_telemetry.py tests/test_telemetry_agent.py
systemd-analyze verify agent/lums-telemetry.service agent/lums-telemetry.timer
```

在测试客户端上安装文件和配置、重新加载 systemd，然后手动运行服务，再启用其定时器。确认身份验证成功，并在仪表板中看到传入的样本。只有完成这些检查后，才可在该测试客户端上启用定时器。服务器端版本未经审查和批准前，不要在生产客户端上启用。

Agent 每五秒上报一次。服务器保留测量数据七天；针对每个请求的历史时间窗口，仪表板 API 最多返回 1,000 个等间隔样本，并保留第一个和最新的样本。
