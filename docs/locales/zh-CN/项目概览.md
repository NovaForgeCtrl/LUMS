# LUMS

**没有噪音的 Linux 更新管理。**

## 快速开始

LUMS 集中管理 Linux 更新。服务器显示客户端、已安装软件和可用更新。每个受管 Linux 系统上的 Agent 使用该系统自己的软件包管理器执行已批准的软件包操作。LUMS 不会替代 Debian/Ubuntu 上的 APT，也不会替代 Arch Linux 上的 pacman。

**仅使用现有 LUMS 安装？** 打开管理员提供的地址，并使用您自己的账户登录。如果某项功能缺失，可能是您的账户没有使用该功能的权限。请联系管理员；不要共享账户，也不要把客户端令牌当作网页密码使用。

**安装或运维 LUMS？** 请先阅读[安装指南](install.md)，然后阅读[管理指南](administration.md)。如果出现问题，请使用[故障排查指南](troubleshooting.md)。这些详细技术指南以英文维护；简明的翻译版入门指南位于 [`docs/locales/`](docs/README.md)。

一次测试运行或成功构建的 Docker 镜像**并不等于**生产安装。生产部署还需要 HTTPS、受保护的应用密钥、持久化数据、经过验证的备份以及经过加固的容器。在对照您自己的安装检查占位符和存储路径之前，请不要直接复制生产命令。

### Web 界面语言

Web 界面提供德语、英语（美国和英国）、法语、西班牙语、简体中文、日语、波兰语、瑞典语、挪威博克马尔语和芬兰语。请在登录页面右上角选择语言。如果未选择，LUMS 会尝试使用浏览器语言；登录后，保存在您账户中的语言优先。某些技术性或动态文本在缺少翻译时可能会保留原语言。Markdown 指南与 Web 界面是分开的，不会自动翻译。

LUMS 是一个 Linux 更新管理服务器，旨在为 Linux 客户端提供受控、可审计且安全的软件与更新管理。

LUMS 不依赖不受控制的客户端更新活动，而是为软件清单、更新检测、软件包操作、更新作业、执行监控和结果上报提供集中管理层。

LUMS 面向需要让更新做到**可见、受控、可追踪、可恢复**的环境。

---

## 什么是 LUMS？

LUMS（**Linux Update Management Server**）由一个中央服务器和轻量级 Linux 客户端组成。

服务器提供管理界面、API、身份验证、授权、作业管理、审计日志和持久化状态。

客户端 Agent 执行本地软件包管理器操作，并将结果上报给服务器。

基本架构如下：

```text
                    ┌──────────────────────┐
                    │      Web Browser      │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │     LUMS Server      │
                    │                      │
                    │ Web UI / API         │
                    │ Authentication       │
                    │ RBAC                 │
                    │ Job Management       │
                    │ Audit Logging        │
                    │ SQLite               │
                    └──────────┬───────────┘
                               │
                         HTTPS / API
                               │
              ┌────────────────┴────────────────┐
              │                                 │
              ▼                                 ▼
      ┌─────────────────┐             ┌─────────────────┐
      │   Linux Client  │             │   Linux Client  │
      │                 │             │                 │
      │ LUMS Agent      │             │ LUMS Agent      │
      │ Package Manager │             │ Package Manager │
      │ Watcher         │             │ Watcher         │
      └─────────────────┘             └─────────────────┘
```

## 为什么选择 LUMS？

Linux 系统本身已经提供了出色的软件包管理工具。

LUMS 并不试图替代它们。

相反，LUMS 在这些工具周围提供了一层管理层，使管理员可以集中回答以下问题：

* 存在哪些客户端？
* 安装了哪些软件？
* 有哪些可用更新？
* 应该安装或删除哪些软件包？
* 哪些更新作业正在运行？
* 更新过程中发生了什么？
* 客户端是否成功上报了结果？
* 是否需要进行重启？
* 被中断的作业能否安全恢复？
* 是谁发起了管理操作？

目标不是隐藏底层的 Linux 软件包管理器。

目标是让它的运行变得**可管理、可审计**。

---

## 核心功能

### 客户端管理

LUMS 维护已注册的 Linux 客户端及其身份验证状态。

每个客户端都会获得一个单独的身份验证令牌。

客户端令牌不会以明文凭据的形式存储。服务器存储 SHA-256 摘要，并依据该摘要验证传入的客户端身份验证。

管理员可以：

* 注册客户端
* 禁用客户端
* 轮换客户端令牌
* 查看客户端状态
* 监控客户端上报

---

### 软件清单

客户端将已安装的软件上报给 LUMS 服务器。

服务器存储清单，并通过管理界面公开。

已安装软件视图与软件包管理搜索是刻意分开的。

这样管理员和只读用户可以查看已安装软件，而不会自动暴露软件包管理操作。

---

### 更新清单

客户端会定期判断是否有可用的软件包更新。

服务器存储上报的更新信息，并将其提供给已授权的用户。

更新信息可以作为受控更新作业的基础。

---

### 软件包管理

LUMS 通过客户端 Agent 提供软件包管理操作。

支持的软件包操作包括：

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

软件包管理层抽象了底层软件包管理器。

目前支持的软件包管理器族包括：

* **Debian / Ubuntu：** APT / dpkg
* **Arch Linux：** pacman

LUMS 也提供软件包搜索。

搜索请求会发送到目标客户端，使用本地软件包管理器执行，然后返回服务器进行展示。

---

### 更新作业

更新操作被表示为持久化作业。

一个作业可以包含一个或多个软件包操作，并维护服务器端的执行状态。

一般生命周期如下：

```text
PENDING
   │
   ▼
RUNNING
   │
   ├──────────────► SUCCESS
   │
   └──────────────► FAILED
```

软件包级别的结果会被独立跟踪，因此中断的作业可以恢复，而不必不必要地重复已经成功完成的操作。

---

### 受控执行

LUMS 不会执行由 Web 界面提供的任意 shell 命令。

服务器使用经过验证的操作和软件包名称创建结构化作业。

客户端 Agent 将这些操作映射到相应的本地软件包管理器操作。

这在以下各层之间形成了明确的边界：

```text
Web UI
   ↓
API
   ↓
Validated Job
   ↓
Agent
   ↓
Package Manager
```

---

### 空闲感知执行

LUMS 可以在客户端被认为处于活跃状态时推迟更新执行。

当前空闲阈值为 **300 秒**。

在支持的情况下，Agent 会通过 `loginctl` 使用本地系统的会话/空闲信息。

如果空闲检测不可用，LUMS 不会假装客户端处于空闲状态。

这种区分很重要，因为**未知空闲状态不同于已确认空闲状态**。

---

### 作业恢复

更新作业被设计为可承受中断。

服务器维护持久的作业和软件包项状态。

在恢复过程中，已成功的软件包项不会被不必要地再次执行。

这为多软件包操作提供了一种类似检查点的执行模型。

目标是：

> **恢复作业，而不是盲目地重新启动整个作业。**

---

### 重启检测

某些软件包操作可能需要系统重启。

因此，LUMS 将重启检测视为更新结果处理的一部分，而不是假设软件包管理器成功退出就意味着系统完全可用。

客户端会将检测到的重启需求上报给服务器。

---

### 客户端身份验证

客户端通信使用按客户端划分的令牌进行身份验证。

令牌：

* 单独分配
* 可轮换
* 仅在服务器端以 SHA-256 摘要形式存储
* 在接受客户端上报前进行验证

令牌轮换允许管理员在无需重新创建客户端的情况下使先前签发的客户端凭据失效。

---

### 可审计性

管理和安全相关操作会通过 LUMS 审计日志系统进行记录。

审计记录旨在回答：

```text
谁？
什么？
何时？
针对哪个对象？
结果如何？
```

这包括安全敏感操作，例如身份验证相关操作、客户端管理、用户管理和更新作业创建。

---

## 设计原则

LUMS 遵循一个简单的原则：

> **让 Linux 更新管理可见、受控、可恢复、可审计 —— 同时不隐藏底层的 Linux 工具。**

## 架构

LUMS 将管理、执行和持久化划分为明确定义的组件。

服务器负责编排和策略。

客户端负责本地系统交互。

软件包管理器负责实际安装、删除或更新软件。

这种分离是有意设计的。

```text
Browser
   │
   │ HTTPS
   ▼
┌──────────────────────────────────────────┐
│                LUMS Server                │
│                                          │
│  Web UI                                  │
│  Authentication / Sessions               │
│  RBAC                                    │
│  API                                     │
│  Client Management                       │
│  Package Search                          │
│  Update Job Management                   │
│  Audit Logging                            │
│  SQLite Persistence                       │
└───────────────────┬──────────────────────┘
                    │
                    │ HTTPS / Client API
                    ▼
┌──────────────────────────────────────────┐
│               LUMS Agent                  │
│                                          │
│  Authentication                          │
│  Inventory Reporting                     │
│  Update Detection                        │
│  Package Search                          │
│  Job Execution                           │

│  Reboot Detection                        │
│  Idle Detection                          │
└───────────────────┬──────────────────────┘
                    │
                    ▼
          ┌────────────────────┐
          │ Package Manager    │
          │                    │
          │ APT / dpkg         │
          │ pacman             │
          └────────────────────┘
```

## 服务器组件

LUMS 服务器提供集中管理层。

### Web 应用

Web 应用提供管理界面，用于：

* 客户端管理
* 软件清单
* 更新信息
* 更新作业
* 软件包管理
* 更新历史
* 用户管理
* 系统维护

该界面遵循当前用户的 RBAC 角色。

因此，前端可见性会根据用户权限进行调整，但授权始终在服务器端强制执行。

---

### API

API 将 Web 界面和 Linux 客户端连接到服务器端应用逻辑。

它处理以下操作：

* 客户端注册与管理
* 客户端上报
* 软件包搜索
* 软件包搜索结果
* 更新作业
* 作业结果
* 用户管理
* 审计事件

API 端点会在执行会改变状态的操作之前验证其输入。

---

### 身份验证与会话

管理用户通过 LUMS Web 应用进行身份验证。

会话由服务器控制，并支持显式会话撤销。

身份验证安全包括：

* 使用 Argon2 进行密码哈希
* 会话管理
* 会话撤销
* 登录限速
* CSRF 保护
* 基于角色的授权

客户端身份验证与管理身份验证是分开的。

---

### RBAC

LUMS 将角色模板与按用户划分的权限结合起来。Administrator、Operator 和 Viewer 模板提供起始权限集，可以为每个账户进行自定义。

授权在服务器上使用账户存储的权限强制执行。

前端还会隐藏用户权限不允许的功能。

这意味着隐藏按钮绝不会被视为安全边界。

---

### SQLite 持久化

LUMS 使用 SQLite 存储持久化应用状态。

数据库存储以下信息：

* 用户
* 会话
* 客户端
* 客户端身份验证状态
* 软件清单
* 可用更新
* 更新作业
* 软件包级作业结果
* 软件包搜索请求与结果
* 审计信息

应用程序显式启用 SQLite 外键强制（针对数据库连接）。

当前生产 SQLite 基线为：

```text
journal_mode = wal
busy_timeout = 5000
synchronous = 2
foreign_keys = ON
```

LUMS 在当前生产配置中使用 SQLite WAL 模式。

---

## 容器架构

LUMS 服务器以加固后的 Docker 容器部署。

应用容器被有意视为可丢弃的。

持久化应用状态存储在专用 Docker 卷中：

```text
lums-data
```

生产容器使用只读根文件系统。

可写位置被刻意限制在所需的运行时和持久化存储路径。

生产安全基线包括：

```text
只读根文件系统
丢弃所有 Linux 能力
no-new-privileges
受限 /tmp
受限 /run
只读密钥挂载
专用持久化数据卷
非 root 应用用户
```

应用通过以下地址在内部暴露：

```text
127.0.0.1:5050
```

外部 HTTPS 访问通过反向代理提供。

---

## 持久化与可丢弃组件

LUMS 将持久化状态与可替换的运行时组件分开。

```text
持久化
├── SQLite 数据库
├── 客户端状态
├── 用户状态
├── 作业状态
└── 审计状态

可丢弃
├── Docker 容器
├── 应用进程
└── 生成的运行时状态
```

因此，替换应用容器本质上不会移除 LUMS 数据库。

这种分离对于升级和恢复非常重要。

---

## 客户端架构

Linux 客户端由多个协同工作的组件组成。

### LUMS Agent

Agent 负责与 LUMS 服务器和本地 Linux 系统交互。

当前 Agent 版本：

```text
1.7.0
```

Agent 负责：

* 身份验证
* 清单收集
* 更新检测
* 软件包搜索
* 软件包操作
* 更新作业执行
* 结果上报
* 重启检测
* 空闲状态处理

---

### 软件包管理器层

软件包管理器层围绕原生 Linux 软件包管理器提供受控抽象。

Agent 不要求 LUMS 替换软件包管理器。

相反：

```text
LUMS Action
     │
     ▼
Package Manager Abstraction
     │
     ├── Debian / Ubuntu → APT / dpkg
     │
     └── Arch Linux      → pacman
```

这样可以将特定发行版的软件包处理保留在客户端内部。

---

### 执行 Watcher

Watcher 监控客户端上的更新作业执行。

当前 Watcher 版本：

```text
1.2.1
```

Watcher 与 Agent 和服务器端作业状态协同工作。

其目的是确保预期要执行的作业不会无限期保持未处理状态。

---

## 上报路径

正常客户端上报遵循以下方向：

```text
Linux Client
    │
    │ inventory / update information
    ▼
LUMS API
    │
    ▼
SQLite
    │
    ▼
Web UI
```

例如，客户端执行的一次更新检查会产生信息，该信息被上报到服务器并存储为客户端当前的更新状态。

浏览器不会直接查询客户端的软件包管理器。

---

## 软件包搜索路径

软件包搜索遵循不同的请求/响应流程：

```text
Browser
   │
   │ search request
   ▼
LUMS Server
   │
   │ package-search request
   ▼
Linux Client
   │
   │ APT / pacman search
   ▼
Linux Client
   │
   │ search result
   ▼
LUMS Server
   │
   ▼
Browser
```

因此，服务器不需要为每个客户端维护完整的远程软件包仓库索引。

搜索是使用客户端自身的软件包管理环境执行的。

---

## 更新执行路径

更新作业遵循总体架构：

```text
Browser
   │
   │ create job
   ▼
LUMS API
   │
   │ validate request
   ▼
SQLite
   │
   │ persistent job
   ▼
Linux Client
   │
   │ execute action
   ▼
APT / dpkg / pacman
   │
   │ result
   ▼
Linux Client
   │
   │ validated result
   ▼
LUMS API
   │
   ▼
SQLite
   │
   ▼
Browser
```

这构成了 LUMS 的核心执行链：

> **Browser → API → SQLite → Agent → Package Manager → Result → SQLite → UI**

---

## 原子作业领取

更新作业是服务器端的持久化对象。

在执行之前，Agent 必须获取一个符合执行条件的作业。

作业领取是原子化执行的，因此同一个待处理作业不会被多个执行路径意外领取。

当涉及定时器、重试、恢复或多个客户端侧进程时，这一点尤其重要。

---

## 作业执行

服务器创建结构化作业。

客户端 Agent 解释支持的作业操作，并执行相应的本地操作。

支持的软件包操作是：

```text
INSTALL_PACKAGE
REMOVE_PACKAGE
UPDATE_PACKAGE
UPDATE_SYSTEM
```

在创建软件包作业之前，会验证软件包名称。

Agent 不会将软件包名称视为任意 shell 片段。

---

## 软件包管理抽象

软件包操作被有意实现在软件包管理器抽象之后。

这使高层 LUMS 作业模型独立于特定发行版的命令。

例如：

```text
INSTALL_PACKAGE
       │
       ├── Debian / Ubuntu → APT
       │
       └── Arch Linux      → pacman
```

同样的原则适用于删除和软件包更新。

---

## Debian / Ubuntu

在 Debian 系系统上，LUMS 使用原生 APT/dpkg 工具。

典型职责包括：

* 软件包搜索
* 软件包元数据查询
* 软件包安装
* 软件包删除
* 软件包更新
* 系统更新
* 更新检测

LUMS Agent 不会替代 APT。

它围绕 APT 提供受控编排。

---

## Arch Linux

在 Arch Linux 系统上，LUMS 使用原生 pacman 软件包管理器。

典型职责包括：

* 软件包搜索
* 软件包元数据查询
* 软件包安装
* 软件包删除
* 软件包更新
* 系统更新
* 更新检测

特定发行版的行为保留在软件包管理器层内部。

---

## 软件包搜索

软件包搜索与已安装软件清单是分开的。

这种区别很重要：

```text
Installed Software
        │
        └── What is already installed?

Package Management Search
        │
        └── What package can the client currently find?
```

搜索结果可能包含如下软件包信息：

* 软件包名称
* 版本
* 描述
* 可用时的仓库信息

搜索结果会返回 LUMS 服务器，并在软件包管理界面中显示。

---

## 软件包管理权限

软件包管理是一项特权操作。

当前权限模型是：

```text
Administrator → allowed
Operator      → allowed
Viewer        → not allowed
```

Viewer 仍然可以查看已安装软件。

软件包管理界面对 Viewer 隐藏，相应的服务器端变更端点会独立执行授权。

## 更新结果处理

LUMS 将更新操作的结果视为结构化状态，而不是简单地展示原始命令输出。

相关信息可以包括：

* 成功或失败
* 软件包级结果
* 执行状态
* 错误信息
* 重启需求
* 完成时间戳

这使服务器能够维护有意义的更新历史。

---

## 重启检测

在软件包操作之后，客户端会检查操作是否表明需要重启。

结果会作为作业结果的一部分上报给服务器。

因此，重启需求会与更新操作保持关联，而不会丢失在客户端终端会话中。

## 基于角色的访问控制

LUMS 使用三种管理角色：

```text
Administrator
Operator
Viewer
```

授权在服务器端强制执行。

前端还会根据用户权限调整可见界面，但前端可见性绝不被视为安全边界。

### Administrator

管理员可以访问：

* 查看客户端
* 查看已安装软件
* 查看可用更新
* 创建并执行更新作业
* 查看更新历史
* 使用软件包管理
* 执行系统维护
* 创建和禁用客户端
* 轮换客户端令牌
* 创建和管理用户
* 管理角色和用户访问

### Operator

操作员可以访问：

* 查看客户端
* 查看已安装软件
* 查看可用更新
* 创建并执行更新作业
* 查看更新历史
* 使用软件包管理
* 执行系统维护

操作员无法访问：

* 用户管理
* 角色管理
* 客户端创建或禁用
* 客户端令牌轮换

### Viewer

Viewer 对以下内容具有只读访问：

* 客户端
* 已安装软件

以下功能对 Viewer 不可用：

* 可用更新管理
* 更新作业
* 更新历史
* 软件包管理
* 系统维护
* 其他会改变状态的管理操作

服务器会独立强制执行这些限制。

## 用户管理

LUMS 向拥有 `users.manage` 权限的账户提供用户管理。

拥有该权限的用户可以使用角色模板创建账户，然后单独分配权限或显式应用该模板。新账户初始没有权限；权限编辑器在账户创建后打开。用户管理者还可以保存对账户所有者不可见的私有管理备注。

拥有 `backups.manage` 的管理员可以在服务器配置的目录中创建经过验证的 `.db` 或 `.db.gz` 数据库备份，并在该挂载位置内选择一个安全的子文件夹。关于 Docker 存储设置和恢复，请参阅 [`administration.md`](administration.md) 以及应用内 Markdown 恢复指南。

用户密码使用 Argon2 密码哈希存储，而不是明文或可逆加密。

用户管理操作受到以下保护：

* 身份验证
* 基于权限的授权
* CSRF 保护
* 输入验证
* 重复用户检查
* 审计日志

没有 `users.manage` 权限时，用户管理界面不会暴露。

---

## 会话安全

管理身份验证使用服务器端会话处理。

会话安全包括：

* 已认证会话状态
* 会话撤销
* 对会改变状态的请求进行 CSRF 保护
* 登录限速
* 禁用账户强制
* 角色检查

撤销会话会使相应的已认证状态失效，而不仅仅是隐藏用户界面。

---

## 登录限速

重复的失败登录尝试受到渐进式限速。

当前阈值为：

```text
5 attempts  → 30 seconds
6 attempts  → 60 seconds
7 attempts  → 120 seconds
8+ attempts → 300 seconds
```

相关状态持久化在 SQLite 中。

成功认证会清除适用的失败状态。

这可以防止通过简单的应用重启来绕过登录保护。

---

## 客户端令牌安全

每个已注册客户端都有自己的身份验证令牌。

服务器将令牌存储为 SHA-256 摘要。

正常的服务器端验证不需要原始令牌。

令牌轮换允许管理员使现有凭据失效并签发替代凭据。

这形成了一个清晰的生命周期：

```text
Create
  │
  ▼
Use
  │
  ▼
Rotate
  │
  ▼
Old token invalid
```

---

## API 安全

LUMS 在执行会改变状态的操作之前验证 API 输入。

安全控制包括：

* 身份验证
* 按用户权限授权
* 适用时的 CSRF 保护
* 输入验证
* 软件包名称验证
* 结构化作业操作
* 参数化数据库查询
* 受控错误处理

应用程序不会将用户提供的软件包名称用作不受限制的 shell 命令。

---

## SQL 注入防护

数据库操作使用参数化 SQL 语句。

用户控制的值不会直接拼接到 SQL 查询中。

这适用于以下领域：

* 身份验证
* 客户端管理
* 用户管理
* 软件包搜索
* 更新作业
* 审计数据
* 结果上报

目标是使数据值与 SQL 指令保持分离。

---

## SQLite 安全基线

当前生产 SQLite 配置为：

```text
journal_mode = wal
busy_timeout = 5000
synchronous = 2
foreign_keys = ON
```

应用程序为数据库连接显式启用外键强制。

当前配置使用 WAL 模式。

数据库存储在持久化 Docker 卷中，而不是存储在可丢弃的应用容器文件系统内。

## 作业恢复与检查点

LUMS 将更新作业视为持久化状态机。

一个多软件包作业可能包含多个单独软件包操作。

每个软件包项可以达到自己的结果状态。

如果执行被中断，恢复可以区分：

```text
already successful
        │
        └── do not unnecessarily repeat

not completed
        │
        └── eligible for recovery
```

这降低了中断后盲目重复已完成软件包操作的风险。

---

## 受控更新执行

LUMS 有意限制可以通过更新作业 API 请求的操作。

支持的操作是：

```text
INSTALL_PACKAGE
REMOVE_PACKAGE
UPDATE_PACKAGE
UPDATE_SYSTEM
```

服务器在创建作业之前验证操作和相关软件包信息。

然后 Agent 将结构化操作映射到相应的软件包管理器操作。

这避免了将更新系统变成通用远程命令执行机制。

---

## 软件包操作

软件包操作通过客户端的原生软件包管理器执行。

### 安装

经验证的软件包名称被传递给软件包管理器抽象以进行安装。

### 删除

经验证的软件包名称被传递给软件包管理器抽象以进行删除。

### 软件包更新

当客户端将其上报为可用更新时，可以更新特定软件包。

### 系统更新

系统更新操作将更新过程委托给原生软件包管理器。

所有操作都会向 LUMS 服务器返回结构化结果。

---

## 软件包管理器安全

LUMS 将软件包管理器视为具有特权的本地组件。

因此，Agent 不会尝试自行模拟软件包管理器行为。

相反，它会：

1. 验证所请求的操作
2. 选择合适的软件包管理器实现
3. 执行受控操作
4. 捕获结果
5. 将结果上报给服务器

特定发行版的行为保留在软件包管理器层内部。

---

## 重启处理

某些软件包操作可能需要重启。

LUMS 会将重启需求记录为更新作业结果的一部分。

这允许管理员区分：

```text
Update completed
```

和：

```text
Update completed
Reboot required
```

因此，重启需求是运行状态的一部分，而不是被当作无关通知处理。

## 安全加固

当前部署包含多层加固。

### 容器加固

生产容器使用：

* 非 root 应用执行
* 只读根文件系统
* 丢弃 Linux 能力
* `no-new-privileges`
* 受限临时文件系统
* 只读密钥挂载
* 专用持久化数据卷

### 网络加固

应用容器在主机上绑定到回环地址：

```text
127.0.0.1:5050
```

因此，应用端口不会作为局域网服务直接暴露。

外部访问通过 HTTPS 反向代理处理。

防火墙不会暴露内部应用端口。

### 传输安全

管理访问通过 HTTPS 提供。

反向代理处理外部 TLS 终止。

HTTP 请求会重定向到 HTTPS。

### 密钥与配置

敏感的运行时凭据保留在应用程序源代码树之外。

生产密钥作为只读密钥文件挂载到容器中。

仓库和 Docker 构建上下文规则防止常见的备份、密钥、数据库和证书工件意外进入镜像构建上下文。

### 依赖与构建安全

生产 Python 依赖是固定的。

生产 Python 基础镜像通过摘要固定。

Docker 构建上下文通过 `.dockerignore` 限制。

这些控制提高了构建可重复性，并减少了敏感文件的意外包含。

## 空闲感知执行

空闲感知执行旨在减少对活跃用户的干扰。

当前空闲阈值为：

```text id="g8v0lq"

```


不可用的空闲状态不会被静默解释为空闲。

## 更新作业生命周期

更新作业的完整生命周期可以表示为：

```text id="h4d9kv"
Create
  │
  ▼
Validate
  │
  ▼
Persist
  │
  ▼
Claim
  │
  ▼
Execute
  │
  ├──────────────► SUCCESS
  │
  ├──────────────► FAILED
  │
  └──────────────► RECOVERY
                         │
                         ▼
                      Execute
```

作业在执行之前被持久化。

这意味着即使客户端或应用程序中断，服务器仍保留对预期操作的认识。

## 作业类型

LUMS 目前支持结构化更新操作，包括：

```text id="v7r1f8"
INSTALL_PACKAGE
REMOVE_PACKAGE
UPDATE_PACKAGE
UPDATE_SYSTEM
```

这些操作是有意受限的。

LUMS 是一个更新管理系统，而不是通用远程命令框架。

---

## 软件包级作业状态

包含多个软件包的作业可以跟踪软件包级进度。

例如：

```text id="v9w1sh"
Job #42

package-a → SUCCESS
package-b → SUCCESS
package-c → FAILED
package-d → PENDING
```

因此，恢复可以针对作业中未完成的部分进行操作，而不是盲目重复成功的软件包操作。

---

## 作业恢复

恢复是围绕持久化检查点设计的。

服务器维护作业状态。

客户端上报软件包级结果。

如果执行中断，服务器可以确定哪些工作已经完成，哪些工作仍可恢复。

预期的恢复原则是：

> **从已知状态继续，而不是假设什么都没有发生。**

---

## 结果验证

客户端作业结果在被接受进入持久化服务器状态之前会被验证。

这保护作业状态免受格式错误或不完整结果提交的影响。

验证适用于相关字段，例如：

* 作业身份
* 执行状态
* 软件包结果数据
* 错误信息
* 重启信息

因此，结果处理层充当已认证客户端与持久化服务器状态之间的另一道边界。

---

## 用户管理

用户管理需要 `users.manage` 权限。

已授权用户可以从角色模板创建用户，并自定义分配给每个账户的单独权限。

当前角色是：

```text id="2xqv79"
Administrator
Operator
Viewer
```

用户管理操作会进行身份验证、权限检查、验证、在适用时进行 CSRF 保护，并记录在审计记录中。

---

## 客户端管理

管理员可以管理已注册客户端。

客户端管理功能包括：

* 注册
* 禁用
* 令牌轮换
* 客户端状态查看

每个已注册客户端的身份验证是独立的。

禁用客户端会阻止其继续与服务器进行正常的已认证通信。

---

## 更新历史

LUMS 维护持久化更新作业状态，以便已完成和失败的操作在执行后仍然可见。

已授权用户可以根据其角色查看更新操作历史。

历史记录旨在提供运行上下文，而不仅仅是显示最新的软件包清单。

---

## 可审计性

LUMS 维护两种相关但不同的运行信息形式：

### 应用日志

主要用于：

* 诊断
* 错误
* 运行时行为
* 故障排查

### 审计日志

主要用于：

* 管理操作
* 安全相关事件
* 重要状态更改
* 问责

将这些概念分开可以使故障排查和管理审查更容易。

## 测试策略

LUMS 测试套件覆盖应用程序的多个层次。

### 身份验证

测试覆盖身份验证行为、会话处理和安全控制。

### RBAC

测试验证：

* Administrator 可以执行管理操作
* Operator 获得其允许的管理功能
* Viewer 保持只读

### 软件包管理

测试覆盖软件包搜索行为以及与软件包管理相关的 API 处理。

### 更新作业

测试覆盖：

* 作业创建
* 验证
* 状态转换
* 结果处理
* 恢复行为

### 安全

测试覆盖安全敏感的应用程序行为和回归情况。

### 完整套件

从仓库根目录运行完整测试套件：

```bash
./.venv-test/bin/pytest -q
```

测试数量会随项目发展而变化；请依赖命令结果，而不是本文档中打印的固定数字。

## 安全状态

主要安全审查领域已经实现并审查。

当前安全基线包括：

```text
Authentication
    ├── Argon2 password hashing
    ├── session handling
    ├── session revocation
    └── login rate limiting

Authorization
    ├── Administrator
    ├── Operator
    └── Viewer

Client Security
    ├── per-client tokens
    ├── SHA-256 token digests
    └── token rotation

API Security
    ├── input validation
    ├── CSRF protection
    ├── RBAC enforcement
    └── parameterized SQL

Runtime Security
    ├── non-root container
    ├── read-only root filesystem
    ├── dropped capabilities
    ├── no-new-privileges
    ├── restricted temporary filesystems
    └── protected secret mount

Network Security
    ├── HTTPS
    ├── reverse proxy
    ├── loopback application binding
    └── firewall restrictions
```

安全被视为一项持续的工程责任，而不是一次性检查清单。

## LUMS 不是什么

LUMS 有意不设计为：

* 通用远程 shell
* APT、dpkg 或 pacman 的替代品
* 完整的配置管理平台
* 面向所有操作系统的端点管理套件

* 不受控制的命令执行框架

LUMS 聚焦于更窄的问题：

> **具有持久化状态和可审计性的受控 Linux 软件与更新管理。**

## 变更哲学

变更应该有意识地做出。

一个典型变更应回答：

1. 这解决了什么问题？
2. 哪个组件应该拥有该变更？
3. 该变更是否影响安全？
4. 它是否影响持久化状态？
5. 它是否影响客户端？
6. 是否需要修改文档？
7. 哪些测试证明现有功能仍然有效？

这降低了修复系统某一部分却悄悄破坏另一部分的风险。

## 项目身份

LUMS 建立在一个简单的理念之上：

> **没有噪音的 Linux 更新管理。**

项目并不试图通过假装 Linux 软件包管理很简单来隐藏复杂性。

相反，它让相关状态变得可见：

```text id="q2j5r0"
What is installed?
        ↓
What can be updated?
        ↓
What should change?
        ↓
Who requested it?
        ↓
What actually happened?
        ↓
What state remains?
```

这些信息是受控更新管理的基础。

## 最终架构

在其最高层面上，LUMS 可以理解为五个层次：

```text id="7b4p6n"
┌───────────────────────────────────────────────┐
│                    UI                         │
│       Human interaction and visibility        │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                    API                        │
│    Authentication, authorization, validation  │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                  Persistence                   │
│       Jobs, clients, users, results, audit   │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│                    Agent                      │
│      Local execution and system reporting     │
└───────────────────────┬───────────────────────┘
                        │
┌───────────────────────▼───────────────────────┐
│              Native Linux Tools               │
│              APT / dpkg / pacman             │
└───────────────────────────────────────────────┘
```

每个层次都有特定职责。

UI 提供交互。

API 执行策略。

SQLite 提供持久化状态。

Agent 执行受控的客户端侧操作。

原生软件包管理器执行实际系统更改。

## 最终原则

LUMS 建立在一个核心原则之上：

> **观察系统。控制变更。记录结果。**

该原则适用于软件架构、更新执行、安全模型、恢复机制和文档。

**没有噪音的 Linux 更新管理。**
