# LUMS 安全文档

**LUMS — Linux 更新管理服务器**

本文档描述 LUMS 当前的安全架构、已实施的安全控制、安全审计结果、运行限制以及与安全相关的设计决策。

本文档反映**当前已实施的系统状态**。计划中的或未来的改进会明确标注为这样。

---

# 安全原则

LUMS 对 Linux 更新管理采用纵深防御方法。

安全模型将管理身份验证、客户端身份验证、授权、受控更新执行和审计日志分开。

主要安全目标为：

* 经过身份验证的管理访问
* 基于角色的授权
* 经过身份验证的客户端通信
* 受控的更新执行
* 防止并发作业执行
* 可恢复的更新作业
* 受保护的密钥
* 受控的容器执行
* 可审计的安全敏感操作
* 可预测的故障处理
* 安全回归测试

LUMS 主要面向受控基础设施、实验室和内部网络环境。

在没有额外的安全审查和适当的网络控制的情况下，不应将其直接暴露到公共互联网。

---

# 安全架构

LUMS 由以下与安全相关的组件组成：

* Web 管理界面
* REST API
* SQLite 数据库
* 受管客户端上的 LUMS 代理
* APT 和 pacman 软件包管理后端
* 更新作业和恢复机制
* Nginx HTTPS 反向代理
* 加固的 Docker 容器

基本管理流程为：

浏览器 → HTTPS/Nginx → LUMS API → SQLite → LUMS 代理 → 软件包管理器 → 结果 → SQLite → Web UI

身份验证和授权被有意分开。

有效的已认证会话不会自动授予对每个管理操作的访问权限。

授权在服务器端强制执行。Web 界面还会隐藏当前角色不可用的功能，但 UI 可见性从不会被视为安全边界。

---

## 管理身份验证

管理用户通过 LUMS Web 界面进行身份验证。

密码永远不会以明文形式存储。LUMS 使用基于 Argon2 的密码哈希来存储密码。

管理会话使用：

* 已认证的服务器端会话处理
* 会话过期
* 会话重新生成
* 对会改变状态的浏览器请求进行 CSRF 保护
* 登录限速
* 登出时使会话失效
* 服务器端角色验证

身份验证和授权仍然是独立的安全控制。

成功通过身份验证的用户仍必须拥有受保护操作所需的权限。

---

# 基于角色的访问控制

LUMS 目前支持三种 Web 用户角色：

* `administrator`
* `operator`
* `viewer`

角色模板存储在 `users.role` 中；个人权限存储在服务器端的 `user_permissions` 中。

服务器为每个已认证账户加载有效权限。客户端权限信息仅用于控制显示，绝不替代服务器端授权。

## Administrator

管理员拥有完整的管理和操作访问权限。

他们可以：

* 查看客户端
* 创建客户端
* 禁用客户端
* 轮换客户端令牌
* 查看已安装软件包和可用更新
* 创建更新作业
* 执行支持的更新操作
* 查看更新作业历史
* 使用软件包管理
* 使用系统维护功能
* 管理用户
* 管理用户角色
* 访问管理功能

## Operator

操作员可以执行操作性更新管理任务。

他们可以：

* 查看客户端
* 查看已安装软件包和可用更新
* 创建更新作业
* 执行支持的更新操作
* 查看更新作业历史
* 使用软件包管理
* 使用系统维护功能

操作员不可以：

* 管理用户
* 更改用户角色
* 创建客户端
* 禁用客户端
* 轮换客户端令牌

## Viewer

Viewer 拥有受限的只读访问权限。

他们可以：

* 查看客户端
* 查看已安装软件

以下管理区域对 Viewer 账户隐藏：

* 更新
* 更新作业
* 更新历史
* 软件包管理
* 系统维护

Viewer 账户无法执行会改变状态的更新管理操作。

服务器通过身份验证和按用户权限检查独立执行这些限制。

# 客户端身份验证

每个受管 LUMS 客户端使用一个单独的 Bearer 令牌。

身份验证机制遵循以下模型：

`Authorization: Bearer <CLIENT_TOKEN>`

服务器不会以明文值存储客户端令牌。

相反，LUMS 存储客户端令牌的 SHA-256 十六进制摘要。

身份验证流程为：

客户端令牌 → SHA-256 → 令牌摘要 → SQLite

客户端身份验证根据已注册客户端验证已认证的令牌，并额外检查相关客户端状态。

安全模型不使用源 IP 地址作为客户端身份的唯一证明。

这允许 LUMS 在以下环境中运行：

* 私有实验室网络
* 隔离基础设施
* 基于 NAT 的网络
* 离线环境
* 客户端地址可能变化的网络

客户端令牌可以由授权的管理员轮换。

令牌轮换会生成替代令牌、仅存储其摘要、使之前的令牌失效、在审计日志中记录管理操作，并仅展示一次替代令牌。

明文客户端令牌值不会写入审计记录。

# 安全审计 #01

## SQLite 外键

应用程序数据库连接已启用 SQLite 外键强制。

应用程序显式启用：

`PRAGMA foreign_keys = ON`

这确保对相关数据库记录之间的关系强制执行引用完整性。

审计验证了：

* 运行时外键强制
* 外键完整性
* 客户端生命周期行为
* 客户端禁用行为
* 保留历史作业信息
* 保留审计信息

客户端状态被保守处理。

在适当情况下，客户端被禁用而不是以破坏历史操作信息的方式移除。

**状态：通过**

# 安全审计 #02

## SQLite 运行时配置

对生产 SQLite 数据库的运行时配置进行了审查。

已验证的生产配置为：

* `journal_mode`：`wal`
* `busy_timeout`：`5000`
* `synchronous`：`2`

应用程序显式启用：

`PRAGMA foreign_keys = ON`

生产数据库当前使用 WAL 模式。

数据库配置根据实际验证的生产状态而非历史开发配置进行记录。

配置的 busy timeout 在另一个事务暂时持有数据库时减少了立即的数据库故障。

应用级外键设置确保每个数据库连接的引用完整性。

审计包括对活动 SQLite 配置的生产验证。

**状态：通过**

# 安全审计 #03

## 更新超时和进程处理

更新执行受到保护，防止软件包管理器进程无限阻塞。

执行流程为：

启动进程
↓
读取进程输出
↓
监控超时
↓
是否达到超时？
↓
终止进程
↓
宽限期
↓
进程是否仍在运行？
↓
如有必要杀死进程
↓
完成作业

实现使用受控的子进程处理，使静默进程在等待输出时不会无限阻塞。

超时处理已针对以下内容进行测试：

* 静默进程
* 正常进程完成
* 超时条件
* 抵抗正常终止的进程
* 杀死后备
* 集成级超时行为

超时机制防止软件包管理操作无限期处于活动状态。

错误和超时条件作为受控作业结果返回，并记录在作业状态中。

当前记录在案的 LUMS 代理版本为：

`1.7.0`

**状态：通过**

# 安全审计 #04

## 登录限速

对管理登录尝试进行限速。

当前升级策略为：

* 5 次失败尝试 → 30 秒
* 6 次失败尝试 → 60 秒
* 7 次失败尝试 → 120 秒
* 8 次或更多失败尝试 → 300 秒

限速状态持久化在 SQLite 中。

并发登录失败使用事务性数据库锁定：

`BEGIN IMMEDIATE`

这防止并发身份验证失败通过竞争条件绕过预期的限速状态。

成功的身份验证会清除适用的失败状态。

审计涵盖：

* 隔离的限速行为
* 并发身份验证失败
* 事务回滚
* 数据库锁处理
* 成功登录重置行为
* 限速审计事件
* 生产登录行为

因此，限速器提供了服务器端控制来应对重复的身份验证尝试，而不是依赖客户端行为。

**状态：通过**

# 安全审计 #05

## API 输入验证

LUMS 在服务器端验证安全敏感的 API 输入。

客户端提供的值不会仅因其来源于已认证的 Web 界面或已注册客户端而被信任。

验证应用于相关 API 参数，包括：

* 客户端标识符
* 软件包名称
* 更新作业操作
* 软件包列表
* 搜索参数
* 用户管理参数
* 客户端令牌操作
* 作业结果数据

软件包名称在传递给软件包管理操作之前进行验证。

更新作业 API 只接受显式支持的操作。

当前支持的与软件包相关的操作为：

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

意外操作被拒绝。

软件包列表在作业创建前进行验证。

对于 `UPDATE_PACKAGE`，请求的软件包还必须存在于客户端的可用更新信息中。

数据库查询使用参数化 SQL，而不是从不受信任的输入构造 SQL 语句。

这防止用户控制的值被解释为 SQL 语法。

审计包括负向输入测试和面向 SQL 注入的测试用例。

验证控制还通过自动化测试套件进行了验证。

**状态：通过**

# 安全审计 #06

## 会话撤销

LUMS 保护已认证的管理会话，防止其在登出后继续使用。

会话处理包括：

* 已认证的服务器端会话
* 会话过期
* 会话重新生成
* 登出失效
* 服务器端身份验证检查
* 服务器端角色验证

登出会使活动已认证会话失效。

受保护的 API 端点需要已认证会话，并且不依赖客户端状态来确定用户是否仍处于已认证状态。

因此，对于受保护操作，会话状态由服务器评估。

会改变状态的浏览器请求还需要 CSRF 保护。

审计验证了：

* 已认证访问正常工作
* 受保护端点拒绝未认证请求
* 登出使活动会话失效
* 之前已认证的会话在撤销后无法继续使用受保护功能
* 角色信息在服务器端进行评估

**状态：通过**

# 安全审计 #07

## 客户端令牌轮换

每个受管 LUMS 客户端使用一个单独的身份验证令牌。

客户端令牌不以明文值存储。

相反，LUMS 存储客户端令牌的 SHA-256 十六进制摘要。

身份验证模型为：

`Authorization: Bearer <CLIENT_TOKEN>`

服务器对提供的令牌进行哈希处理，并将结果摘要与已注册的客户端令牌摘要进行比较。

授权的管理员可以轮换客户端的令牌。

令牌轮换执行以下操作：

1. 生成替代令牌。
2. 计算其 SHA-256 摘要。
3. 替换存储的客户端令牌摘要。
4. 使之前的令牌失效。
5. 在审计日志中记录管理操作。
6. 向管理员展示替代令牌。

之前的令牌在轮换后无法进行身份验证。

明文令牌值不会写入审计日志。

审计验证了：

* 成功的令牌身份验证
* 令牌摘要存储
* 令牌轮换
* 之前令牌的失效
* 使用替代令牌进行身份验证
* 令牌轮换的授权要求
* 审计日志记录
* 防止未授权的轮换

客户端令牌轮换仅限于管理员。

操作员和 viewer 无法轮换客户端令牌。

**状态：通过**

# 安全审计 #08

## IP 地址处理和离线网络

LUMS 不使用客户端的源 IP 地址作为客户端身份的唯一证明。

客户端身份验证基于已注册的客户端令牌。

此设计是有意的，因为受管客户端可能在网络地址变化的环境中运行。

支持的部署场景包括：

* 私有实验室网络
* 基于 NAT 的网络
* 隔离基础设施
* 动态寻址的客户端
* 离线环境
* 受控内部网络

因此，服务器将：

**网络位置**

与：

**客户端身份**

分开。

有效的客户端令牌标识已注册客户端。

客户端的网络地址仍可为操作和审计目的而记录，但不会被视为身份验证凭据。

该实现还避免假设客户端必须从固定地址可达。

这对于网络拓扑可能在不改变受管系统逻辑身份的情况下发生变化的实验室环境和基础设施尤为重要。

审计验证了客户端身份验证不依赖固定源 IP 地址。

**状态：通过**

# 安全审计 #09

## 作业恢复和检查点

LUMS 更新作业被设计为在被中断执行后安全恢复。

更新作业在 SQLite 数据库中维护持久状态。

单个软件包操作与整体作业状态分开跟踪。

这允许代理在恢复被中断的作业之前确定哪些软件包操作已成功完成。

在恢复期间，已成功完成的软件包操作不会再次执行。

因此，恢复逻辑遵循以下原则：

`持久作业状态 → 确定已完成工作 → 跳过已完成项 → 继续剩余工作`

这降低了以下情况后不必要的重复软件包操作的风险：

* 代理中断
* 进程终止
* 系统重启
* 临时通信失败
* 容器重启
* 其他执行中断

审计验证了被中断作业的恢复和检查点行为。

恢复已针对包含多个软件包操作的作业和之前已成功的软件包项进行了测试。

审计确认已完成的工作得以保留，剩余工作可继续而无需不必要地重复成功操作。

**状态：通过**

# 安全审计 #10

## APT 健壮性

基于 Debian 的软件包操作通过 LUMS 软件包管理层执行。

APT 相关的更新操作已针对软件包管理器状态和更新结果的可靠检测进行了审查。

实现考虑了软件包管理命令可能成功返回但需要额外解释其输出或结果系统状态的情况。

APT 更新检测已加固，以避免依赖单一简单的命令输出条件。

# 安全审计 #17

## 基于角色的访问控制

LUMS 将角色模板与单独分配的权限结合起来。支持的模板为 `administrator`、`operator` 和 `viewer`；选择模板会选择其默认权限，管理员可以为每个账户进行自定义。

角色仍然是账户元数据。受保护路由针对账户的服务器存储权限集进行授权，而不是角色标签。界面为了可用性隐藏不可用的功能，而服务器仍然是安全边界。

---

## RBAC 权限模型

| 权限              | 授予的访问权限 |
| ----------------- | -------------- |
| `clients.view`    | 查看客户端和系统信息 |
| `software.view`   | 查看已安装软件 |
| `updates.view`    | 查看可用更新、作业和历史 |
| `packages.search` | 搜索软件包仓库 |
| `jobs.manage`     | 创建软件包操作和更新作业 |
| `clients.manage`  | 注册/移除客户端并轮换客户端令牌 |
| `users.manage`    | 创建用户并管理角色和权限 |

默认角色模板为：

| 模板            | 默认权限 |
| --------------- | -------- |
| `administrator` | 所有权限 |
| `operator`      | 客户端/软件/更新可见性、软件包搜索和作业管理 |
| `viewer`        | 客户端可见性和已安装软件可见性 |

客户端相关权限需要 `clients.view`。`jobs.manage` 还需要 `updates.view`。UI 为已认证账户加载权限并省略用户无法使用的控制；服务器端检查独立执行相同的授权。

---

## 授权执行

受保护操作使用服务器端身份验证和权限检查。

授权模型遵循以下原则：

`身份验证 → 加载用户权限 → 授权操作 → 执行`

仅身份验证不足以访问特权操作。

会改变状态的操作在适用时还需要 CSRF 保护。

受保护管理操作的示例包括：

* 更新作业创建
* 软件包安装
* 软件包移除
* 软件包更新
* 系统更新
* 软件包管理操作
* 客户端创建
* 客户端禁用
* 客户端令牌轮换
* 用户创建
* 用户管理功能

受保护端点显式定义相应操作所需的权限。

即使手动构造相应的 HTTP 请求，缺少权限也会被服务器拒绝。

这防止通过直接调用 Web 界面中隐藏的 API 端点绕过 RBAC 模型。

---

## Viewer 限制

Viewer 模板通过其默认权限集有意受限。

对于没有相应授权的账户，客户端界面不会暴露：

* 更新
* 更新作业
* 更新历史
* 软件包管理
* 系统维护

服务器还防止没有相应授权的账户执行受保护操作。

JavaScript 界面在没有 `updates.view` 的情况下不会加载更新管理数据。

这减少了操作信息的不必要暴露，同时保持服务器端授权作为实际安全控制。

已安装软件仍作为只读信息功能对 Viewer 账户可用。

---

## 管理用户管理

用户管理需要 `users.manage` 权限。

拥有该权限的用户可以在没有权限的情况下创建账户，然后在权限编辑器中分配单独授权或应用角色模板。角色模板有描述解释其默认授权。

授权的用户管理者可以保存每个账户的内部备注。备注限于 2,000 个字符，不包括在审计日志详细信息中，且对账户所有者不可见。

用户创建包括：

* 用户名验证
* 角色验证
* 密码验证
* Argon2 密码哈希
* 重复用户检测
* 审计日志记录
* CSRF 保护
* 服务器端授权

没有 `users.manage` 时无法访问用户管理端点。

服务器拒绝未知权限和无效的依赖组合。至少有一个活动账户必须保留 `users.manage`；将移除最后一个用户管理者的更改会被拒绝。

密码永远不会以明文形式存储。

---

## RBAC 数据库迁移

角色模板信息保留在用户数据库记录中。单独授权存储在 `user_permissions` 表中，并带有指向用户账户的外键。迁移 `003-user-permissions` 创建该表并从其当前角色模板播种现有账户，在过渡期间保留其访问权限。迁移 `004-user-admin-notes` 添加私有的 `users.admin_note` 字段；现有账户收到空备注。迁移 `005-backup-permission` 授予现有 Administrator 账户 `backups.manage`。

数据库备份创建需要 `backups.manage`；Administrator 模板默认包含此权限。服务器仅将 SQLite 在线备份写入服务器配置的 `LUMS_BACKUP_DIR`；它不接受来自浏览器的文件系统路径。备份文件以仅所有者权限创建，并在发布前进行完整性检查。

---

## RBAC 安全测试

RBAC 行为由自动化测试覆盖。

测试包括：

* Administrator 授权
* Operator 授权
* Viewer 限制
* 受保护 API 访问
* 未授权操作
* 客户端管理限制
* 更新作业限制
* 用户管理限制
* 客户端页面可见性
* 权限特定界面行为

RBAC 测试涵盖角色模板默认值、自定义权限、权限依赖关系和服务器端授权。生产验证应包括具有自定义权限的账户以及默认的 Administrator、Operator 和 Viewer 模板。

---

## RBAC 安全结果

RBAC 实现提供分层授权：

1. 身份验证确定用户身份。
2. 服务器加载用户的权限。
3. 受保护路由执行所需权限。
4. CSRF 保护适用于相关的浏览器状态更改。
5. Web 界面隐藏不可用的功能。
6. 自动化测试验证授权边界。

因此，界面本身不提供授权机制。

服务器仍然是权威的安全边界。

**状态：通过**

---

## 容器加固

生产 LUMS 容器使用加固的 Docker 配置运行。

生产容器使用：

* 非 root 应用用户
* 只读根文件系统
* 丢弃的 Linux 能力
* `no-new-privileges`
* 受限临时文件系统
* 只读密钥挂载
* 专用持久化应用数据卷
* 重启策略
* 仅回环的主机应用端口发布

因此，应用根文件系统在正常运行期间不可写。

可写位置被明确限制在应用所需的位置。

生产容器已独立检查以验证有效的运行时配置。

加固的运行时还通过验证以下内容进行了测试：

* 应用文件系统写入失败
* `/tmp` 在需要时保持可用
* `/var/lib/lums` 保持可写
* 密钥文件保持只读
* 应用保持可运行

---

## 网络暴露

LUMS 应用端口不直接暴露到 LAN。

Docker 应用端口绑定到回环接口：

`127.0.0.1:5050`

外部访问通过 Nginx 提供。

生产主机通过防火墙和反向代理暴露预期的网络服务。

部署已验证可防止对内部 Docker 应用端口的直接远程访问。

防火墙对入站和路由流量使用默认拒绝模型。

预期可从外部访问的服务为：

* SSH
* HTTP
* HTTPS

HTTP 请求被 Web 服务器重定向到 HTTPS。

默认 Nginx 站点已移除，以免暴露无关的默认内容。

---

## 传输安全

管理 Web 访问通过 HTTPS 提供。

HTTP 被重定向到 HTTPS。

TLS 端点由 Nginx 而非 Flask/Gunicorn 应用直接处理。

这保持了传输安全和应用服务的分离。

因此，内部 Gunicorn 应用端口不是公共 HTTP 端点。

当前部署面向受控内部基础设施。

未来直接暴露到公共互联网的部署将需要额外的安全审查。

---

## 密钥和配置

生产密钥不存储在应用源代码树中。

LUMS 密钥通过受保护的密钥文件提供。

生产容器通过以下方式接收密钥：

`/run/secrets/lums_secret`

密钥文件以只读方式挂载。

应用通过配置的密钥文件机制读取密钥。

仓库和 Docker 构建上下文处理已审查以防止意外包含：

* 数据库文件
* 备份文件
* 密钥文件
* 私钥
* 证书

## 依赖和构建安全

生产 Docker 镜像使用固定的 Python 基础镜像摘要。

生产运行时依赖显式固定版本。

当前生产依赖集包括：

* Flask `3.1.3`
* argon2-cffi `25.1.0`
* Gunicorn `23.0.0`

Docker 构建上下文通过 `.dockerignore` 限制。

重复的生产构建在审计期间进行了比较。

相关的依赖和软件包元数据在重复构建之间保持一致，除了预期的生成 Python 字节码差异。

这为生产镜像提供可重复的基线，同时保持构建上下文受限。

## 文件系统和运行时权限

生产应用以专用 `lums` 用户而非 root 运行。

持久化应用数据存储在专用 LUMS 数据卷中。

应用根文件系统是只读的。

运行时写访问被限制在明确要求的位置。

生产运行时已验证会拒绝未经授权的对应用文件系统的写入。

这减少了应用容器内意外或恶意文件修改的影响。
