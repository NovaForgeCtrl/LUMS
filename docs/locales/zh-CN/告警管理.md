# LUMS 告警管理：当前实现

本文说明 LUMS 当前包含的告警管理代码。它是代码参考，不是功能路线图，也不表示界面上可见的每个控件都能正常工作。实现主要位于 `server/alerts.py` 和 `server/alerts_routes.py`。

## 已实现的功能

LUMS 使用 SQLite 持久化告警规则、告警记录和告警状态历史。Flask 蓝图使用应用的数据库连接工厂，为每个请求创建一个 `AlertManager`。管理器会在每次请求时从数据库加载规则和未解决的告警。

当前 API 支持：

- 列出、创建、更新和删除告警规则；
- 为现有的已启用规则手动触发告警；
- 查看活动告警和分页告警历史；
- 确认、解决活动告警，或手动升级活动告警。

告警严重级别为 `critical`、`warning` 和 `info`。存储的告警状态为 `triggered`、`acknowledged`、`resolved` 和 `escalated`。确认、解决和升级操作会写入 `alert_history`。已解决的告警会从管理器的活动告警集合中移除，但仍保留在数据库中。

## 重要限制

规则模型会存储条件、阈值、严重级别、升级路径、分组标记和去重标记。当前服务器**不会**根据遥测数据或其他测量值评估条件。规则不会自动触发：经过身份验证的调用方必须调用 `POST /alerts/trigger`。分组和去重配置只会被存储，当前不会应用。

手动触发告警时，管理器可以尝试通过规则升级路径中指定的提供程序发送告警。但是，Web 应用创建每个管理器时都会传入空的提供程序映射，而且集成端点无法配置提供程序，因此由应用触发的告警目前不会发送通知。

`AlertManager` 定义了电子邮件、Slack、PagerDuty 和通用 Webhook 提供程序类，但应用不会通过这些类配置提供程序。集成 API 会明确报告集成不可用，并对配置、测试和删除请求返回 `501 Not Implemented`。因此不应期待有通知送达。`POST /alerts/clear-all` 同样返回 `501`，以防通过该端点删除告警历史。

`/alerts/` 页面是一个基础的服务器渲染概览。规则、历史记录和集成选项卡控件以及告警操作按钮并非完整的交互式管理界面。应以文档所述的 API 行为为准，不要假设界面上可见的按钮能够执行操作。当前实现不提供实时推送或 WebSocket 更新。

## 路由和访问控制

所有路由都要求已通过身份验证的 Web 会话。

| 方法 | 路由 | 权限 | 当前行为 |
| --- | --- | --- | --- |
| `GET` | `/alerts/` | `alerts.view` | 渲染基础告警概览 |
| `GET` | `/alerts/rules` | `alerts.view` | 列出已存储规则 |
| `POST` | `/alerts/rules` | `alerts.manage` | 创建经过验证的规则 |
| `PUT` | `/alerts/rules/<rule_id>` | `alerts.manage` | 更新已存储规则 |
| `DELETE` | `/alerts/rules/<rule_id>` | `alerts.manage` | 在数据库约束允许时删除规则 |
| `GET` | `/alerts/current` | `alerts.view` | 返回活动告警 |
| `GET` | `/alerts/history` | `alerts.view` | 返回告警历史 |
| `POST` | `/alerts/trigger` | `alerts.manage` | 为已启用规则手动创建告警 |
| `POST` | `/alerts/<alert_id>/acknowledge` | `alerts.manage` | 记录确认操作 |
| `POST` | `/alerts/<alert_id>/resolve` | `alerts.manage` | 解决活动告警 |
| `POST` | `/alerts/<alert_id>/escalate` | `alerts.manage` | 手动增加告警升级计数 |
| `POST` | `/alerts/clear-all` | `alerts.manage` | 已禁用；返回 `501` |
| `GET` | `/alerts/integrations` | `alerts.view` | 返回空列表和 `available: false` |
| `POST` / `DELETE` | `/alerts/integrations/...` | `alerts.manage` | 已禁用；返回 `501` |

修改数据的路由除了要求相应权限外，还需要 CSRF 保护。权限检查在服务器端执行。`alerts.manage` 依赖 `alerts.view`；角色授权由安全迁移和权限配置维护。

## 持久化数据表

`AlertManager` 创建时会初始化以下数据表：

- `alert_rules`：规则定义及其配置值；
- `alerts`：告警记录和当前生命周期状态；
- `alert_history`：确认、解决和升级历史；
- `notification_integrations`：预留的集成配置架构；
- `alert_notifications_log`：预留的通知发送日志架构。

后两张表并不表示集成功能已经可用。HTTP 集成端点会继续保持禁用状态，直至实现安全的持久化配置和通知发送行为。

## 验证

`tests/test_alerts.py` 覆盖告警路由、权限执行、负载验证、持久化和生命周期行为。部署时应针对实际部署的代码版本重新运行相关测试。测试套件通过并不意味着已禁用的集成路由或尚未评估的规则变成可用功能。
