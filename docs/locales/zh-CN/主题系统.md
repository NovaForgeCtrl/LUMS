# LUMS — 可选主题系统

> **一个 LUMS · 多种界面 · 同一后端**

LUMS 提供可选的客户端主题系统，使用户界面能够改变视觉外观，同时不改变底层 LUMS 功能。

主题仅属于呈现层。它们不会替换、修改或绕过 LUMS 后端、身份验证、授权、更新执行、软件包管理、客户端管理、作业处理或安全控制。

主题系统旨在让 LUMS 适应不同的视觉偏好，同时保持应用本身的一致性。

## 实现状态与事实来源

当前浏览器端实现位于 `server/static/theme.js`。它支持
`standard`、`LUMSStadium`、`golf`、`nerd`、`geek` 和 `admin`；会将选择
保存到浏览器 `localStorage` 中的 `lums-theme` 键；如果已保存的标识符缺失或
无效，则回退到 `standard` 主题。`nerd` 主题会启动矩阵效果，`geek` 主题会
启动网络效果。主题选择是浏览器偏好，而非账户设置或服务器端授权状态。

本参考文档也包含设计要求和概念示例。文中使用“应该”“必须”或“未来”等
措辞的内容，描述的是架构指导，并不能证明某项视觉功能或无障碍行为已经实现。
在将某个概念视为已发布能力之前，请先在源代码中核实当前行为。

## 1. 概述

可选主题系统允许 LUMS Web 界面提供多种视觉环境，同时继续使用相同的应用后端。

主题可以改变：

* 颜色
* 字体排版
* 背景
* 装饰元素
* 视觉强调
* 导航外观
* 动画
* 可选视觉效果
* 页面特定的呈现方式

主题不得改变：

* 用户权限
* 可用 API 端点
* 身份验证行为
* 授权决定
* CSRF 保护
* 客户端身份验证
* 更新执行
* 软件包管理权限
* 作业状态处理
* 审计日志
* 数据库行为
* 安全边界

原则很简单：

> **主题改变 LUMS 的外观，而不是 LUMS 可以执行的操作。**

---

## 2. 设计原则

主题系统遵循若干原则。

### 2.1 可选

主题是可选的前端功能。

即使没有选择任何其他主题，LUMS 仍应完全可用。

标准 LUMS 外观是默认呈现方式。

---

### 2.2 客户端侧

主题选择属于前端。

更改主题不得要求修改服务器端应用状态。

因此，用户选择的主题属于呈现偏好，而不是账户权限或后端配置。

---

### 2.3 后端独立

所有主题使用同一个 LUMS 后端。

以下内容不受所选主题影响：

```text
身份验证
授权
RBAC
客户端管理
软件清单
更新检测
软件包管理
更新作业
作业恢复
审计日志
数据库操作
```

后端仍是所有涉及安全和运维的决策的权威来源。

---

### 2.4 主题不承担安全功能

主题绝不能被用作安全机制。

例如，在界面中隐藏某项操作并不会授予或撤销权限。

如果用户无权执行某项操作，无论当前启用哪个主题，服务器都必须拒绝该请求。

这样可确保前端呈现不会成为授权边界。

---

### 2.5 平稳回退

主题系统应始终提供有效的回退方案。

如果出现以下情况：

* 尚未选择主题；
* 本地保存的主题已不可用；
* 主题标识符无效；
* 主题资源无法加载；

LUMS 应回退到标准呈现方式，而不是让界面无法使用。

---

## 3. 概念架构

可以将主题系统视为现有 LUMS 应用外围独立的呈现层。

```text
┌──────────────────────────────────────┐
│              LUMS 界面               │
│                                      │
│  ┌────────────────────────────────┐  │
│  │            主题呈现             │  │
│  │                                │  │

│  │ 极客 / 技术实验室 / 管理后台 …  │  │
│  └────────────────────────────────┘  │
│                  │                   │
│                  ▼                   │
│            通用前端逻辑              │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│              LUMS API                │
│                                      │
```

关键边界位于**呈现层**与**应用逻辑**之间。

主题属于该边界之上。

## 4. 主题生命周期

从概念上说，选择主题的流程如下：

```text
用户选择主题
        │
        ▼
前端保存选择
        │
        ▼
初始化主题
        │
        ▼
将主题应用到界面
        │
        ▼
LUMS 继续使用
同一后端和权限
```

选择主题本身不会创建新的 LUMS 环境。

系统仍然只有一个 LUMS 应用、一个后端和一套安全模型。

## 5. 主题标识符

主题应使用稳定的内部标识符，而不是依赖其显示名称。

例如：

```text
standard
LUMSStadium
golf
nerd
geek
admin
```

标识符属于实现细节。

可以独立更改可见的主题名称，而不必更改后端或应用架构。

移除或重命名主题标识符时，主题系统应为本地仍保存着旧标识符的用户提供回退方案。

## 6. 职责分离

主题系统的职责刻意保持狭窄。

### 主题层

负责：

* 视觉呈现
* 主题选择
* 主题专属样式
* 可选视觉效果
* 主题专属的前端装饰
* 与无障碍相关的呈现行为

### 通用前端

负责：

* 显示应用数据
* 调用 LUMS API
* 呈现作业和软件信息
* 处理用户交互
* 控制呈现层面的可见性

### 后端

负责：

* 身份验证
* 授权
* RBAC
* CSRF 保护
* 客户端身份验证
* 创建作业
* 执行作业
* 软件包管理
* 数据库操作
* 审计日志
* 安全决策

这种分离是设计的根本原则。

---

## 7. 安全边界

在授权方面，主题系统**不是可信代码**。

即使主题修改或隐藏了界面元素，后端仍有责任验证所请求的操作。

概念上：

```text
前端可见性
        ≠
后端权限
```

例如：

```text
Viewer
  │
  ├── 主题可以不显示软件包管理控件
  │
  └── 后端仍会拒绝未经授权的软件包操作
```

同一原则也适用于管理功能、更新作业、客户端管理以及所有其他特权操作。

---

## 8. 运维原则

主题系统应与 LUMS 的运维架构相互独立，不产生可见影响。

更改主题不得要求：

* 重建数据库
* 更改客户端配置
* 更改客户端令牌
* 重启更新代理
* 更改更新作业
* 修改 RBAC
* 更改网络配置
* 更改软件包管理行为

主题是呈现偏好，而不是运维配置。

## 第 2 部分 — 主题结构与选择

## 11. 主题结构

可选主题系统将主题选择与实际视觉呈现分开。

从概念上说，主题由三个层次组成：

```text
主题标识符
       │
       ▼
主题选择
       │
       ▼
主题呈现
```

标识符用于确定选择的是哪个主题。

选择机制决定当前应启用哪个主题。

呈现层将对应的视觉配置应用于 LUMS 界面。

这种分离使得可以添加或移除主题，而不改变 LUMS 应用的基础架构。

---

## 12. 主题选择

主题由前端选择。

所选主题被视为本地呈现偏好，而不是服务器端账户属性。

概念上：

```text
用户
 │
 ▼
主题选择器
 │
 ▼
所选主题标识符
 │
 ▼
前端主题初始化
 │
 ▼
当前主题
```

后端不需要知道当前选择了哪种视觉主题。

这也意味着更改主题不会影响其他用户。

两个用户可以访问同一个 LUMS 实例，同时使用完全不同的视觉主题。

---

## 13. 本地主题偏好

浏览器可以在本地保存所选主题。

本地持久化的目的是方便用户：

```text
浏览器
   │
   ├── 主题偏好
   │
   └── LUMS 应用
```

因此，应将已保存的主题选择视为不可信的客户端状态。

绝不能由服务器将其解释为：

* 角色
* 权限
* 身份验证状态
* 安全设置
* 管理员偏好

浏览器可以选择外观，但不能控制授权。

---

## 14. 主题初始化

加载 LUMS 界面时，前端会确定应启用哪个主题。

概念流程如下：

```text
页面加载
   │
   ▼
读取已保存主题
   │
   ▼
主题是否有效？
   │
   ├── 是 ──────► 应用主题
   │
   └── 否 ──────► 使用标准主题
```

如果不存在偏好设置，应使用标准 LUMS 呈现方式。

如果已保存的标识符不再受支持，也应采用相同的回退行为。

这样可防止过期的本地偏好设置破坏界面。

---

## 15. 默认主题

标准 LUMS 主题是基准呈现方式。

它提供可选主题所依据的参考外观。

因此，标准主题应保持：

* 可用
* 易读
* 无障碍
* 视觉完整
* 不依赖可选的装饰性资源

可选主题不得成为 LUMS 正常运行的前提。

---

## 16. 应用主题

前端可以通过共享的应用状态或根级主题属性表示当前主题。

概念示例：

```html
<html data-theme="theme-id">
```

随着前端演进，具体实现可能会有所不同。

重要的架构要求是：前端样式系统能够一致地识别当前主题。

这样就可以将主题专属样式与通用应用结构分开。

---

## 17. 主题专属样式

主题样式应主要通过 CSS 实现，而不是复制应用标记结构。

概念上：

```text
通用 HTML
     │
     ├── 标准样式
     ├── 体育场样式
     ├── 高尔夫样式
     ├── 极客样式
     ├── 技术实验室样式
     └── 管理后台样式
```

这样可以让相同的应用组件在所有主题中保持可用。

例如，无论当前启用哪个主题，客户端表格仍然是客户端表格。

只有它的呈现方式会改变。

---

## 18. 共享应用组件

主题不应为 LUMS 页面创建彼此独立的版本。

应遵循以下原则：

```text
一个组件
       │
       ├── 主题 A
       ├── 主题 B
       ├── 主题 C
       └── 主题 D
```

而不是：

```text
主题 A → 独立页面
主题 B → 独立页面
主题 C → 独立页面
```

复制页面会显著增加维护难度，并可能导致不同主题的行为不一致。

因此，主题应装饰通用界面，而不是取代应用本身。

---

## 19. 主题资源

适当情况下，主题可以使用额外的前端资源。

可能的资源包括：

* 背景图片
* 装饰图形
* 图标
* 动画
* 视觉叠加效果
* 主题专属插图

资源仍属于前端呈现层。

其中不得包含：

* 凭据
* 客户端令牌
* 密钥
* 数据库文件
* 身份验证材料
* 私有运维数据

主题资源应视为公开的前端资源。

---

## 20. 可选视觉效果

某些主题可能提供额外的视觉效果。

例如：

* 动态背景
* 装饰性网络效果
* 环境动态效果
* 主题化界面元素
* 动态视觉装饰

这类效果必须保持可选。

它们绝不能成为 LUMS 功能运行的必要条件。

---

## 21. 减少动态效果

视觉效果应尊重偏好减少动态效果的用户。

如果使用动画或持续变化的元素，主题系统应提供适当的减少动态效果行为。

概念上：

```text
正常动态效果
     │
     ├── 启用动画
     └── 启用视觉效果

减少动态效果
     │
     ├── 减少或禁用动画
     └── 保持基本界面功能可用
```

无障碍优先于装饰性动画。

即使禁用了视觉效果，主题仍应可用。

---

## 22. 主题独立性

更改主题不得触发运维副作用。

例如：

```text
更改主题
     │
     ├── 不重启客户端
     ├── 不重启代理
     ├── 不取消作业
     ├── 不迁移数据库
     ├── 不轮换令牌
     └── 不更改权限
```

因此，主题系统刻意与 LUMS 的运维生命周期隔离。

---

## 23. 主题故障处理

主题应以安全的方式失败。

如果主题专属资源或呈现组件无法加载，通用 LUMS 界面仍应可用。

首选的恢复路径是：

```text
主题错误
    │
    ▼
回退到标准呈现方式
    │
    ▼
LUMS 仍可使用
```

视觉问题不得演变成应用可用性问题。

---

## 24. 添加新主题

新主题应遵循应用行为与呈现相分离的现有设计。

概念步骤如下：

```text
1. 定义主题标识符
2. 定义视觉设计
3. 添加主题样式
4. 添加可选资源
5. 将主题加入选择机制
6. 测试常规页面
7. 测试不同 RBAC 角色
8. 测试减少动态效果时的行为
9. 测试回退行为
10. 确认后端行为未改变
```

只有在现有 LUMS 功能保持不变时，新主题才算完成。

---

## 25. 移除主题

移除主题时也应妥善处理。

如果用户本地仍保存着已移除的主题，前端应检测到该标识符已不可用，并回退到标准主题。

因此，移除视觉主题不得导致用户的 LUMS 界面无法使用。

---

## 26. 主题命名

主题名称应明确区分：

* 内部标识符
* 显示名称
* 视觉概念

例如：

```text
内部标识符：  standard
显示名称：    Standard LUMS
```

这种区分使可见文字可以演进，而不必无谓地更改内部实现。

# LUMS — 可选主题系统

## 第 3 部分 — 主题概念

## 29. 标准 LUMS

标准 LUMS 主题是应用的参考呈现方式。

它旨在提供简洁、实用的界面，而不要求采用特定的视觉概念。

标准主题应优先考虑：

* 易读性
* 清晰的信息层次
* 可预测的导航
* 无障碍
* 尽量减少视觉干扰
* 组件呈现的一致性

它是主题系统的回退呈现方式。

因此，即使所有可选视觉主题都不可用，标准 LUMS 主题仍应保持可用。

---

## 30. LUMS 体育场

**LUMS 体育场**是对 LUMS 界面更具表现力的视觉诠释。

这一概念将系统管理与体育场风格的视觉身份相结合。

可能的设计元素包括：

* 记分牌风格的信息面板
* 更醒目的视觉状态指示
* 事件导向的呈现
* 主题化背景
* 突出运维状态的视觉表现
* 体育场装饰元素

该主题在功能上与标准 LUMS 完全相同。

成功的更新仍然是成功的更新。

失败的作业仍然是失败的作业。

变化的只有呈现方式。

---

## 31. 高尔夫俱乐部

**高尔夫俱乐部**主题刻意采用对比鲜明的视觉身份。

界面不采用传统服务器或基础设施风格，而是运用更平静的休闲概念。

视觉方向可以强调：

* 简洁的表面
* 克制的装饰
* 高尔夫风格的元素
* 球场式的视觉隐喻
* 平和的状态呈现
* 轻量的主题点缀

这一概念说明，即使 LUMS 的视觉上不像传统管理控制台，仍然可以保持功能完整。

后端和应用行为不变。

---

## 32. 极客模式

**极客模式**面向更具技术感和趣味性的呈现方式。

这一概念可以通过以下元素突出 LUMS 的技术属性：

* 终端风格的样式
* 技术术语
* 面向系统的视觉元素
* 开发者风格的呈现
* 诊断式美学
* 刻意采用的技术装饰

主题仍必须保持清晰的信息层次。

趣味化界面不应让运维信息更难理解。

---

## 33. 技术实验室

**技术实验室**代表一种更具实验性的技术环境。

视觉概念可以结合：

* 实验室美学
* 技术实验
* 基础设施可视化
* 系统图表
* 科学或工程风格元素
* 实验性视觉效果

该主题旨在让界面具有基础设施实验室的感觉，同时保留下层完全相同的 LUMS 功能。

视觉实验必须与运维应用隔离。

---

## 34. 企业管理后台

**企业管理后台**主题代表更为稳重的管理界面。

其视觉方向可以强调：

* 结构化信息
* 紧凑布局
* 管理仪表板
* 清晰的状态指示
* 高密度运维信息
* 减少装饰元素

此主题尤其适合偏好传统管理控制台外观的用户。

它不会提供额外的管理员权限。

名称描述的是视觉概念，而不是授权级别。

---

## 35. 主题比较

可以将这些主题视为同一应用的不同视觉诠释：

| 主题 | 视觉方向 | 主要特征 |
| --- | --- | --- |
| 标准 LUMS | 简洁 / 实用 | 参考界面 |
| LUMS 体育场 | 体育场 / 事件 | 富有表现力 |
| 高尔夫俱乐部 | 休闲 / 平和 | 轻松 |
| 极客模式 | 技术 / 趣味 | 面向开发者 |
| 技术实验室 | 实验 / 技术 | 实验室风格 |
| 企业管理后台 | 结构化 / 管理 | 稳重 |

此表仅描述呈现概念。

它**不**描述以下方面的差异：

* 权限
* 功能
* API 访问
* 客户端访问
* 作业执行
* 软件包管理
* 安全性

---

## 36. 同一界面，不同呈现

核心设计目标之一是：同一个应用组件在不同主题下都应保持可识别。

例如：

```text id="5dhlf7"
客户端列表
   │
   ├── 标准呈现
   ├── 体育场呈现
   ├── 高尔夫呈现
   ├── 极客呈现
   ├── 技术实验室呈现
   └── 企业管理呈现
```

底层客户端数据保持完全相同。

变化的只有呈现方式。

以下内容也遵循相同原则：

* 软件清单
* 可用更新
* 更新作业
* 作业历史
* 用户信息
* 系统状态
* 软件包管理界面

---

## 37. 运维状态

主题可以用视觉方式突出不同的运维状态。

例如：

```text id="5wyy17"
待处理
运行中
成功
失败
```

主题可以为这些状态使用不同的视觉表现，但语义必须保持一致。

主题不得重新定义应用状态。

例如：

```text id="j4i9qd"
成功 ≠“看起来是绿色”

成功 = 实际的 LUMS 作业状态
```

视觉表现只是对后端状态的渲染。

---

## 38. 错误呈现

主题也可以改变错误的视觉呈现方式。

但是，错误信息必须保持易于理解。

主题不得：

* 隐藏重要错误信息
* 用装饰性文字替代技术信息
* 让警告与正常状态无法区分
* 压制运维故障信息

视觉样式可以改善呈现，但不得移除理解问题所需的诊断信息。

---

## 39. 状态一致性

相同状态在所有主题中都应具有一致的语义。

例如：

| 状态 | 含义 |
| --- | --- |
| 待处理 | 等待执行 |
| 运行中 | 正在处理 |
| 成功 | 已成功完成 |
| 失败 | 执行失败 |

主题可以使用不同的颜色、图标、字体或布局来呈现这些状态。

底层含义必须保持不变。

---

## 40. 主题专属装饰

装饰元素应始终处于运维信息的次要位置。

例如：

* 背景
* 图案
* 插图
* 环境效果
* 主题图标
* 视觉装饰

应保持以下优先顺序：

```text id="3m08d7"
运维信息
        │
        ▼
应用可用性
        │
        ▼
无障碍
        │
        ▼
视觉装饰
```

装饰绝不能优先于运行 LUMS 所需的信息。

---

## 41. 视觉密度

不同主题可以采用不同的视觉密度。

例如：

* 企业管理后台可以优先展示高密度信息。
* 标准 LUMS 可以优先保持阅读均衡。
* 高尔夫俱乐部可以使用更多留白。
* 极客模式可以采用紧凑的技术元素。
* 体育场主题可以突出大型状态区域。
* 技术实验室可以提供更多视觉上下文。

这些差异仍属于呈现选择。

它们不会改变底层数据的数量或权威性。

---

## 42. 不同主题下的无障碍

每种主题都必须保留基本的可用性。

这包括：

* 易读的文字
* 足够的视觉区分度
* 可用的控件
* 易于理解的状态指示
* 键盘可访问性
* 可用的焦点状态
* 兼容减少动态效果偏好

颜色不得成为传达重要状态的唯一方式。

例如，不应只能通过特定颜色识别失败作业。

---

## 43. 主题专属动画

如果动画有助于体现视觉概念，主题可以包含动画。

例如：

* 轻微过渡效果
* 动态背景
* 网络效果
* 状态过渡
* 环境装饰

动画应处于应用的次要位置。

动画不得：

* 阻止交互
* 遮挡控件
* 持续干扰运维数据
* 妨碍无障碍
* 影响后端操作

---

## 44. 动态网络

某些 LUMS 主题可能使用动态的网络风格视觉层。

这一概念将 LUMS 表现为一个动态的基础设施环境：

```text id="7w1v8b"
客户端 ────┐
           │
客户端 ────┼──── LUMS
           │
客户端 ────┘
```

除非明确连接到实际应用数据，否则这种可视化仅为装饰。

因此，除非应用明确提供相关信息，否则绝不能将视觉网络图视为权威的网络拓扑。

区分二者非常重要：

> **视觉表示并不会自动成为运维遥测数据。**

---

## 45. 装饰数据与真实数据

主题专属视觉效果必须与真实 LUMS 数据明显区分。

例如：

```text id="z6i5j0"
装饰节点
    ≠
真实客户端

动态连接线
    ≠
真实网络连接

视觉状态效果
    ≠
后端作业状态
```

这样可以避免用户将审美可视化与实际系统信息混淆。

---

## 46. 主题身份

每种主题都应有可识别的身份，但不得变成独立产品。

目标是：

```text id="qv1fbe"
不同的视觉身份
          +
相同的 LUMS 功能
          =
可选的 LUMS 主题
```

这样既能让主题系统有趣而灵活，又能保持应用的技术完整性。

---

## 47. 主题设计规则

所有主题最重要的设计规则是：

> **主题可以富有表现力、与众不同、技术化、趣味化或稳重，但必须始终保持为 LUMS。**

无论选择哪种视觉呈现，应用都必须始终能被识别为同一个系统。

# LUMS — 可选主题系统

## 第 4 部分 — 前端实现与无障碍

## 48. 前端主题层

可选主题系统完全属于 LUMS 前端。

其职责仅限于呈现和用户偏好处理。

概念上：

```text
┌─────────────────────────────────┐
│            LUMS 前端            │
│                                 │
│          通用应用逻辑           │
│              │                  │
│              ▼                  │
│           主题呈现              │
│              │                  │
│              ▼                  │
│           浏览器渲染            │
└─────────────────────────────────┘
```

主题层不会取代通用前端逻辑。

相反，它会在通用前端逻辑之外提供一个额外的呈现层。

---

## 49. 主题初始化

主题初始化应作为常规前端启动过程的一部分。

概念流程如下：

```text
前端启动
      │
      ▼
主题系统初始化
      │
      ▼
评估已保存的偏好
      │
      ▼
检查主题是否可用
      │
      ├── 有效 → 所选主题
      │
      └── 无效 → 标准主题
      │
      ▼
渲染 LUMS 界面
```

初始化应保持轻量，且不得依赖后端是否可用。

即使后续 API 请求失败，用户仍应能够加载视觉呈现。

---

## 50. 主题状态

当前主题属于前端状态。

因此，应将它与应用状态区别对待。

### 主题状态

例如：

```text
当前视觉主题
减少动态效果偏好
视觉呈现偏好
```

### 应用状态

例如：

```text
已登录用户
用户角色
客户端状态
软件包状态
更新状态
作业状态
审计状态
```

主题状态绝不能覆盖或冒充应用状态。

---

## 51. 根级主题属性

根级属性适合用于表示当前主题。

例如：

```html
<html data-theme="standard">
```

或者：

```html
<html data-theme="nerd">
```

随后，CSS 可以使用当前主题作为选择器。

具体实现可能会演进，但架构目标保持不变：

> **一种应用结构，多种呈现定义。**

---

## 52. CSS 组织方式

主题专属样式应与 LUMS 通用样式清晰区分。

概念上：

```text
通用样式
│
├── 布局
├── 表单
├── 表格
├── 导航
├── 状态元素
└── 共享组件

主题样式
│
├── 标准
├── 体育场
├── 高尔夫
├── 极客
├── 技术实验室
└── 管理后台
```

通用样式应定义功能结构。

主题样式应定义视觉身份。

这样可以减少重复，并使今后的主题维护更容易。

---

## 53. CSS 变量

主题系统可以使用 CSS 自定义属性，将语义值与视觉表现分离。

例如：

```css
:root {
    --lums-background: ...;
    --lums-surface: ...;
    --lums-text: ...;
    --lums-accent: ...;
}
```

主题随后可以提供自己的取值：

```css
[data-theme="example"] {
    --lums-background: ...;
    --lums-surface: ...;
    --lums-text: ...;
    --lums-accent: ...;
}
```

重要原则是：在可行的情况下，组件应使用语义变量，而不是硬编码主题专属值。

---

## 54. 共享组件

主题系统应为共享组件设置样式，而不是复制这些组件。

常见组件包括：

* 导航
* 按钮
* 表单
* 表格
* 状态指示
* 卡片
* 对话框
* 软件包管理元素
* 更新作业元素
* 客户端信息
* 系统信息

无论启用哪个主题，同一个组件的功能都应保持完全一致。

---

## 55. 主题资源

可选主题可以使用专属资源。

可能的资源类别包括：

```text
图片
图标
背景
装饰图形
字体
动画资源
视觉效果
```

主题资源应保持为前端资源。

其中不得包含敏感的应用信息。

尤其是，主题资源绝不能包含：

* 密码
* 密钥
* 客户端令牌
* 数据库内容
* 私有证书
* 身份验证材料

---

## 56. 加载资源

仅在需要时才应加载主题资源。

不能仅仅因为某个主题存在，就不必要地增加每个 LUMS 页面所需的资源。

在可行的情况下，应采用：

```text
所选主题
      │
      ▼
所需资源
      │
      ▼
浏览器
```

而不是：

```text
所有主题
      │
      ▼
同时加载所有资源
```

随着主题和视觉效果不断增加，这一点会越来越重要。

---

## 57. 主题性能

视觉定制不得显著降低 LUMS 的可用性。

应特别注意：

* 大型背景图片
* 持续动画元素
* Canvas 效果
* 反复更新 DOM
* 开销较大的视觉滤镜
* 不必要的网络请求

客户端列表、软件清单和更新作业视图等运维页面应保持响应灵敏。

---

## 58. 装饰性 JavaScript

主题可以使用 JavaScript 实现视觉效果。

例如：

* 动态背景
* 网络可视化
* 动态装饰
* 主题专属交互

此类 JavaScript 应与运维应用逻辑隔离。

装饰脚本绝不能负责：

* 授权
* 创建作业
* 安装软件包
* 删除软件包
* 执行更新
* 客户端身份验证
* 审计日志

必须明确区分：

```text
主题 JavaScript
      ≠
LUMS 运维 JavaScript
```

---

## 59. 网络可视化

如果主题使用网络风格的可视化，应将其视为呈现组件。

例如：

```text
Canvas / 视觉层
        │
        ▼
装饰性网络
        │
        ▼
主题呈现
```

除非明确连接到权威的 LUMS 数据，否则该可视化不应暗示自己代表实际网络状态。

这样可防止装饰图形被误认为监控或遥测数据。

---

## 60. 减少动态效果

使用动画的主题应支持减少动态效果偏好。

概念上，首选行为如下：

```text
prefers-reduced-motion: reduce
            │
            ▼
减少或禁用装饰性动态效果
```

基本功能必须保持不变。

减少动态效果只影响呈现。

---

## 61. 焦点和键盘导航

主题样式必须保留键盘可用性。

重要的交互元素应保留清晰可见的焦点状态。

如果主题移除了焦点轮廓，则必须提供同样清晰的替代方式。

例如：

```text
键盘焦点
      │
      ▼
清晰可见的控件状态
```

这适用于：

* 导航
* 按钮
* 链接
* 表单字段
* 选择器
* 对话框
* 软件包管理控件

---

## 62. 不依赖颜色传达信息

重要信息不得只依赖颜色传达。

例如：

```text
失败
```

即使主题颜色不可用，也应能通过文字、图标、结构或其他无障碍提示理解其含义。

由于不同主题可能使用完全不同的配色，这一点尤其重要。

---

## 63. 对比度

每种主题都应确保以下内容之间具有足够的对比度：

* 文字与背景
* 控件与背景
* 状态指示与周围元素
* 焦点元素与周围内容

有趣的配色不能替代易读的信息。

如果主题配色与无障碍要求冲突，应优先保证可读性。

---

## 64. 主题选择界面

主题选择器本身属于 LUMS 通用界面的一部分。

无论当前启用哪个主题，都应让用户能够理解它。

概念上：

```text
主题选择器
      │
      ├── 标准 LUMS
      ├── LUMS 体育场
      ├── 高尔夫俱乐部
      ├── 极客模式
      ├── 技术实验室
      └── 企业管理后台
```

选择其他主题应更新呈现方式，而不改变当前 LUMS 会话或运维状态。

---

## 65. 与会话无关

更改主题不得使用户退出登录。

也不得：

* 使会话失效
* 更改角色
* 轮换客户端令牌
* 修改服务器端身份验证状态

主题偏好与身份验证相互独立。

```text
更改主题
     │
     └── 会话保持不变
```

---

## 66. 与 RBAC 无关

主题必须独立于 RBAC。

例如：

```text
Administrator
     │
     └── 可见管理员获准使用的功能

Operator
     │
     └── 可见操作员获准使用的功能

Viewer
     │
     └── 可见查看者获准使用的功能
```

所选主题不会改变这些权限。

使用“企业管理后台”主题的 Viewer 不会变成管理员。

使用“极客模式”的 Administrator 不会失去管理权限。

任何情况下，后端仍是权威来源。

---

## 67. 故障隔离

可选视觉功能发生故障时，不应破坏 LUMS 的核心运行。

例如，如果装饰动画发生故障：

```text
动画故障
      │
      ▼
主题仍可使用
      │
      ▼
LUMS 仍可运行
```

在可能的情况下，视觉功能应独立于应用功能发生故障。

这对动态背景或网络可视化等可选效果尤其重要。

---

## 68. 浏览器兼容性

主题系统应使用 LUMS 部署环境所针对浏览器支持的功能。

如果某项视觉功能不可用，界面应平稳降级，而不是变得无法使用。

标准呈现方式应始终作为基准回退方案。

---

## 69. 实现原则

实现可以概括为：

```text
通用 HTML
     +
通用 LUMS JavaScript
     +
主题选择
     +
主题专属 CSS / 资源
     =
可选视觉层
```

以下内容必须保持在主题层之外：

```text
身份验证
授权
数据库
作业
软件包管理
客户端身份验证
审计日志
安全决策
```

这种分离让主题系统可以充分展现个性，同时避免它与 LUMS 核心行为耦合。

# LUMS — 可选主题系统

## 第 5 部分 — 安全、测试与开发

## 70. 安全边界

主题系统属于前端，因此运行在不可信的客户端环境中。

浏览器控制呈现层。

浏览器**不**控制 LUMS 授权。

安全边界如下：

```text id="h8e2ks"
浏览器
   │
   │ 不可信的呈现
   ▼
LUMS API
   │
   │ 权威验证
   ▼
LUMS 后端
```

因此，所有与安全有关的决策都必须留在服务器端。

---

## 71. 主题选择不是授权

绝不能将所选主题解释为授权信号。

例如：

```text id="8u3r8v"
data-theme="admin"
```

并不表示当前用户是管理员。

主题标识符中的 `admin` 纯粹是描述性文字。

用户的实际角色必须始终由经过身份验证的应用会话和服务器端授权逻辑决定。

---

## 72. 前端可见性不等于安全性

主题或前端脚本可以隐藏界面元素。

这对呈现有帮助。

但这不足以实现访问控制。

例如：

```text id="7m8c6w"
隐藏按钮
      ≠
阻止未经授权的操作
```

对应的 API 端点必须独立验证用户权限。

这适用于所有 LUMS 特权功能。

---

## 73. 主题资源是公开的

对于任何能够访问 LUMS Web 界面的人而言，前端资源都应视为可公开访问。

因此，主题文件绝不能包含密钥信息。

绝不要在主题资源中放入以下内容：

```text id="1zjz7n"
密码
API 密钥
客户端令牌
私钥
数据库文件
会话密钥
身份验证凭据
```

如果信息必须保密，就不应放在主题资源中。

---

## 74. 主题中不得包含后端密钥

主题 JavaScript 不得包含服务器凭据或特权 API 材料。

必要时，主题应通过现有前端应用层进行通信。

主题不得引入另一套身份验证机制。

适用的原则是：

> **主题使用呈现数据，而不创建安全凭据。**

---

## 75. 跨站请求伪造

主题功能不得绕过现有 CSRF 保护。

如果主题提供的界面元素会触发需要受保护请求的操作，则该请求必须遵循 LUMS 通用界面相同的安全要求。

主题代码属于视觉代码，并不因此获得豁免。

---

## 76. API 使用

主题应避免自行实现运维 API 逻辑。

如果主题需要应用数据，应使用既有的 LUMS 前端／应用机制。

这样可以避免出现多套独立实现，包括：

* 身份验证
* API 请求
* 错误处理
* 授权假设
* 作业处理

通用应用逻辑仍是权威的前端集成层。

---

## 77. 主题隔离

移除主题时，不应同时移除 LUMS 核心功能。

概念上：

```text id="3m1o8q"
移除可选主题
        │
        ▼
标准 LUMS 仍可用
        │
        ▼
应用仍可运行
```

这才使主题真正成为可选功能。

---

## 78. 安全测试

安全测试应着重证明主题变更不会改变 LUMS 安全模型。

相关检查包括：

* Viewer 仍然是 Viewer
* Operator 仍然是 Operator
* Administrator 仍然是 Administrator
* 受保护的 API 端点仍受到保护
* CSRF 保护仍然有效
* 客户端身份验证保持不变
* 更新作业权限保持不变
* 软件包管理权限保持不变
* 审计日志保持不变

主题本身绝不能作为某项操作安全性的证据。

---

## 79. 主题功能测试

每种主题都应针对通用应用进行测试。

至少测试：

```text id="9w6h1m"
登录
客户端列表
客户端详情
已安装软件
可用更新
更新作业
作业历史
软件包管理
用户管理
系统维护
注销
```

具体可用功能取决于经过身份验证的用户角色。

测试目的是确保主题渲染不会破坏应用的正常功能。

---

## 80. RBAC 主题测试

主题测试应涵盖所有相关角色。

基本矩阵如下：

| 角色 | 主题测试 |
| --- | --- |
| Administrator | 必须 |
| Operator | 必须 |
| Viewer | 必须 |

对每种角色，都要验证更改主题不会改变其获准使用的功能。

例如：

```text id="3n5p2m"
Viewer + 极客模式
        =
Viewer 权限

Viewer + 企业管理后台
        =
Viewer 权限
```

视觉主题不得改变结果。

---

## 81. 主题切换测试

应反复测试主题切换。

示例顺序：

```text id="gk2j7m"
标准
   ↓
体育场
   ↓
高尔夫
   ↓
极客
   ↓
技术实验室
   ↓
管理后台
   ↓
标准
```

在整个切换过程中，应用都应保持可用。

应特别注意：

* 布局变化
* 表格
* 导航
* 对话框
* 表单
* 状态指示
* 长文本
* 响应式行为

---

## 82. 持久化测试

如果主题偏好会在本地持久化，应进行以下测试：

1. 选择一个主题。
2. 重新加载页面。
3. 确认主题仍处于选中状态。
4. 关闭浏览器。
5. 再次打开 LUMS。
6. 确认偏好设置仍能正确处理。
7. 删除或使已保存的主题无效。
8. 确认回退到标准主题。

绝不能将已保存的值视为应用安全状态。

---

## 83. 无效主题测试

无效的主题标识符不得破坏界面。

例如：

```text id="4j5cqn"
unknown-theme
```

应触发安全回退，而不是让页面无法使用。

预期行为：

```text id="5x9h2f"
无效主题
     │
     ▼
标准主题
     │
     ▼
LUMS 仍可使用
```

---

## 84. 资源故障测试

也应测试可选资源发生故障时的行为。

例如：

* 图片缺失
* 动画不可用
* 资源路径无效
* 不支持某项视觉功能
* 可选装饰中的 JavaScript 错误

在可能的情况下，通用应用应继续保持可用。

---

## 85. 减少动态效果测试

对于包含动画的主题，应分别在普通和减少动态效果环境中测试。

```text id="l1h4nb"
正常动态效果
     │
     └── 可使用主题效果

减少动态效果
     │
     └── 减少或禁用效果
```

在这两种情况下，重要的应用控件都必须完全可用。

---

## 86. 响应式测试

应在不同视口大小下测试主题。

至少包括：

* 桌面
* 平板大小的视口
* 窄屏／手机大小的视口

视觉身份不得以牺牲控件可用性或应用数据可读性为代价。

应特别关注：

* 导航
* 表格
* 操作按钮
* 软件包管理控件
* 作业状态信息
* 对话框
* 主题选择器

---

## 87. 性能测试

应评估视觉效果对浏览器性能的影响。

相关观察项包括：

* 页面加载时间
* 渲染响应速度
* CPU 使用率
* 内存使用量
* 动画流畅度
* 重复的 DOM 更新
* 网络请求

主题应是呈现增强，而不能成为性能瓶颈。

---

## 88. 开发工作流

在可能的情况下，新主题应独立于后端变更进行开发。

推荐工作流：

```text id="1i8qz6"
设计
   ↓
前端实现
   ↓
集成主题选择器
   ↓
无障碍审查
   ↓
功能测试
   ↓
RBAC 测试
   ↓
回退测试
   ↓
性能审查
   ↓
文档记录
```

只有存在真实应用需求时才应引入后端变更。

视觉主题通常不应要求修改后端。

---

## 89. 开发规则

开发主题时：

1. 重用现有 LUMS 组件。
2. 避免复制页面。
3. 隔离主题专属样式。
4. 将装饰性 JavaScript 与运维逻辑分开。
5. 不引入身份验证逻辑。
6. 不引入授权逻辑。
7. 不暴露密钥。
8. 保持无障碍。
9. 保持减少动态效果的行为。
10. 测试所有相关角色。
11. 测试标准主题回退。
12. 记录新资源和行为。

---

## 90. 变更验证

在认为主题变更完成之前，应同时验证呈现和功能。

实用的验证顺序如下：

```text id="i1v9yb"
更改主题
      │
      ▼
视觉检查
      │
      ▼
页面功能
      │
      ▼
角色行为
      │
      ▼
API 行为
      │
      ▼
浏览器控制台
      │
      ▼
回归测试
```

仅仅因为主题看起来正确，并不代表主题已经完成。

还必须确保 LUMS 行为保持不变。

---

## 91. 回归原则

主题开发应遵循与其他 LUMS 变更相同的一般原则：

> **变更 → 测试 → 验证 → 记录**

视觉变更仍可能造成功能回归。

例如：

* 按钮被隐藏
* 文字无法阅读
* 布局损坏
* 控件无法访问
* JavaScript 冲突
* 资源缺失
* 选择器错误
* 移动端布局失败

因此，测试是主题开发的一部分，而不是可有可无的最后一步。

---

## 92. 故障排查：主题未加载

如果所选主题没有显示：

1. 重新加载页面。
2. 检查标准主题是否能够加载。
3. 检查浏览器控制台。
4. 检查所选主题标识符是否有效。
5. 检查所需主题资源是否可用。
6. 检查是否发生 JavaScript 错误。
7. 必要时清除本地主题偏好。
8. 重新加载并验证标准主题回退。

不要通过修改后端安全配置来解决前端主题问题。

---

## 93. 故障排查：主题破坏布局

如果主题导致布局问题：

1. 切换到标准 LUMS 主题。
2. 确认通用界面正常工作。
3. 找出受影响的组件。
4. 检查主题专属 CSS。
5. 检查响应式行为。
6. 检查浏览器控制台错误。
7. 修正主题专属样式。
8. 重新测试其他主题。

标准主题提供了重要的诊断对照。

---

## 94. 故障排查：主题导致 JavaScript 错误

如果主题专属 JavaScript 导致错误：

1. 切换到标准主题。
2. 确认 LUMS 正常功能可用。
3. 找出发生故障的主题脚本。
4. 判断错误属于装饰性问题还是应用问题。
5. 修复主题专属故障。
6. 验证 LUMS 通用 JavaScript 未受影响。
7. 重新测试主题切换。

不得仅为弥补装饰主题错误而修改运维 JavaScript。

---

## 95. 故障排查：主题偏好无效

如果本地仍保存着旧主题或无效主题：

```text id="b9n8wq"
已保存的偏好无效
        │
        ▼
回退到标准主题
        │
        ▼
选择有效主题
```

首选解决方案是安全回退，而不是手动干预后端。

---

## 96. 主题文档

每个新主题都应记录：

* 内部标识符
* 显示名称
* 视觉概念
* 所需资源
* 可选视觉效果
* 无障碍注意事项
* 减少动态效果时的行为
* 已知限制

实现专属文档应描述实际的当前代码，而不是对主题可能如何工作的假设。

---

## 97. 当前主题集合

当前文档记录的主题概念如下：

```text id="r0w4u5"
standard       → 标准 LUMS
LUMSStadium    → LUMS 体育场
golf           → 高尔夫俱乐部
nerd           → 极客模式

```

主题集合可以扩展。

只要保持呈现与应用行为相分离，就可以添加其他主题，而不改变底层 LUMS 架构。

## 98. 开发原则

可选主题系统应保持为受控的前端扩展。

它旨在让 LUMS 更具表现力和适应性，同时不增加运维复杂性。

因此，首选架构如下：

```text id="l2e8o9"
通用 LUMS
     │
     ├── 通用功能
     ├── 通用安全机制
     ├── 通用后端
     └── 通用应用状态
              │
              ▼
          可选主题层
              │
       ┌──────┼──────┐
       ▼      ▼      ▼
    主题 A  主题 B  主题 C
```

通用应用始终是基础。

主题始终是可选扩展。

# LUMS — 可选主题系统

## 第 6 部分 — 维护、扩展与最终状态

## 99. 主题维护

在可能的情况下，主题维护应与 LUMS 核心维护分开。

视觉主题更新通常只应涉及前端资源。

常见变更包括：

* CSS 调整
* 视觉资源
* 主题专属 JavaScript
* 无障碍改进
* 响应式布局修正
* 动画调整
* 主题命名或呈现方式变更

主题更新不应要求更改：

* 客户端配置
* 客户端令牌
* 数据库架构
* 更新作业
* 软件包管理逻辑
* 身份验证
* RBAC
* 服务器端安全控制

如果主题变更意外地要求进行此类修改，应先审查其依赖关系，再继续操作。

---

## 100. 主题更新

主题更新应遵循 LUMS 的常规开发流程：

```text id="2p7z9r"
修改
   ↓
测试
   ↓
验证
   ↓
记录
```

对于较大的变更：

```text id="p7l5me"
设计
   ↓
实现
   ↓
功能测试
   ↓
无障碍测试
   ↓
RBAC 回归测试
   ↓
性能审查
   ↓
文档记录
```

不能仅因视觉效果正确，就认为主题已经完成。

---

## 101. 添加新主题

可以在不更改 LUMS 后端的情况下引入新主题。

推荐流程：

### 步骤 1 — 定义概念

描述：

* 视觉身份
* 目标风格
* 字体排版
* 颜色
* 装饰元素
* 可选动画

### 步骤 2 — 定义标识符

选择稳定的内部标识符。

### 步骤 3 — 实现呈现

添加所需样式和资源。

### 步骤 4 — 集成选择功能

通过通用主题选择器提供该主题。

### 步骤 5 — 测试

验证：

* 常规页面
* 交互控件
* 响应式布局
* 无障碍
* 减少动态效果
* 所有相关 RBAC 角色
* 回退行为

### 步骤 6 — 记录

记录主题及其相关实现细节。

---

## 102. 移除主题

移除主题时，应考虑到仍在本地选择了该主题的用户，并将其视为兼容性变更。

因此，前端应安全地处理已过时的标识符。

首选行为：

```text id="x4e7p1"
旧主题标识符
       │
       ▼
主题已不可用
       │
       ▼
标准 LUMS
```

移除主题时，绝不应仅为了删除浏览器端偏好而要求进行数据库迁移。

---

## 103. 重命名主题

显示名称通常可以独立于内部标识符更改。

例如：

```text id="8q4n1k"
内部标识符
        │
        └── 保持稳定

显示名称
        │
        └── 可以更改
```

如果内部标识符本身发生变化，则可能需要迁移或兼容映射，以处理现有的本地偏好设置。

在可行的情况下，首选做法是保持标识符稳定。

---

## 104. 主题兼容性

主题应与 LUMS 通用界面的变更保持兼容。

引入新的共享组件时，应检查现有主题是否存在：

* 样式缺失
* 间距损坏
* 文字不可读
* 颜色错误
* 响应式行为缺失
* 焦点状态错误
* 控件不可访问

新增后端功能并不自动意味着必须新增主题功能。

通用应用仍是事实来源。

---

## 105. LUMS 新功能

LUMS 新增功能时，通常应在通用功能正常工作后再评估主题支持。

推荐顺序：

```text id="z4b7jx"
LUMS 新功能
       │
       ▼
通用实现
       │
       ▼
功能测试
       │
       ▼
主题兼容性
       │
       ▼
主题专属完善
```

这样可防止视觉定制成为核心功能开发的依赖。

---

## 106. 主题 API 稳定性

除非确有需求，否则主题系统应避免创建单独的 API 层。

主题最好使用 LUMS 已采用的相同前端应用状态和 API 机制。

这样可以减少：

* 重复的请求逻辑
* 重复的错误处理
* 不一致的授权假设
* 额外维护工作
* 不必要的攻击面

因此，主题系统刻意保持轻量。

---

## 107. 主题安全审查

添加或大幅修改主题时，请审查以下内容：

```text id="3eq4w6"
[ ] 资源中没有凭据
[ ] 资源中没有客户端令牌
[ ] 没有私钥
[ ] 没有绕过身份验证
[ ] 没有授权逻辑
[ ] 没有绕过 CSRF
[ ] 没有直接执行安全决策
[ ] 没有意外的 API 端点
[ ] 前端资源中没有敏感信息
[ ] 装饰脚本保持隔离
```

即使变更看起来纯粹是视觉方面，也应执行此审查。

前端代码仍然是可执行代码。

---

## 108. 主题无障碍审查

对每种主题都要验证：

```text id="1y9xw6"
[ ] 文字仍然易读
[ ] 对比度足够
[ ] 焦点状态清晰可见
[ ] 键盘导航正常
[ ] 控件仍然可用
[ ] 状态提示不只依赖颜色
```

## 110. 运维独立性

可选主题系统刻意与 LUMS 运维生命周期相互独立。

更改主题不得要求：

```text id="b2i1k4"
重启 Agent
重启 Watcher
重启数据库
重新注册客户端
轮换令牌
取消作业
更改软件包管理器
更改网络
```

这样，呈现层便可独立于基础设施层演进。

---

## 111. 部署独立性

主题资源属于 LUMS 应用前端。

一般部署流程仍记录在主要安装和管理文档中。

本文有意不重复以下内容：

* Docker 部署流程
* 容器加固命令
* Nginx 配置
* 数据库备份流程
* 服务器恢复流程
* 客户端安装流程

这些主题应由相应的运维文档负责。

这种分离可避免部署架构变化时主题文档随之过时。

---

## 112. 源代码与运行时的分离

应将主题系统视为应用源代码的一部分。

两者之间存在如下区别：

```text id="b6q7jv"
源代码
   │
   ├── 主题定义
   ├── CSS
   ├── JavaScript
   └── 资源

运行时
   │
   ├── 已构建的 LUMS 镜像
   └── 正在运行的 LUMS 应用
```

源代码中的主题变更并不意味着正在运行的部署已自动获得该变更。

仍应由常规 LUMS 构建和部署流程负责交付更新后的前端资源。

## 113. 版本管理

主题无需引入单独的 LUMS 后端版本。

主题可以作为前端／应用版本的一部分演进。

如果主题变更引入了兼容性问题，应明确记录这些问题。

例如：

```text id="5y1p8f"
主题变更
     │
     ├── 仅影响视觉
     │
     └── 影响兼容性
```

第二类变更需要额外的回归测试。

## 119. 最终原则

可选主题系统旨在让 LUMS 更具个性、更富表现力且更易适应，同时不损害技术架构。

根本规则仍然是：

> **一个 LUMS · 多种界面 · 同一后端**

主题可以改变 LUMS 的氛围。

绝不能改变 LUMS 实际获准执行的操作。
