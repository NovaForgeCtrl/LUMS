# LUMS 故障排查

本指南提供针对 LUMS 服务器、Linux 代理、执行监视器、更新作业、身份验证、软件包管理、数据库和 Docker 部署的故障排查程序。

故障排查过程应始终从**观察先于修改**开始。

目标是识别预期行为停止的第一个组件，同时不必要地更改配置、数据库状态、凭据或安全控制。

---

## 快速开始：安全地进行故障排查

如果您是 Linux 新手，错误并不自动意味着数据已经丢失。不要同时更改多个内容。从下面的检查开始，并记录**问题何时发生**以及紧接在此之前**发生了什么操作**。

### LUMS 服务器上的首次检查

```bash
sudo docker ps -a --filter name=lums
sudo docker logs --tail 100 lums
sudo systemctl status nginx --no-pager
sudo nginx -t
```

`docker ps -a` 还会显示已停止的容器。`docker logs` 读取最近的应用消息。`systemctl status` 显示 Nginx 是否正在运行；`nginx -t` 在不更改配置的情况下检查其配置。如果 `nginx -t` 失败，在纠正原因之前**不要**重新加载 Nginx。

### 受管客户端上的首次检查

```bash
sudo systemctl status lums-agent.service --no-pager
sudo journalctl -u lums-agent.service -n 100 --no-pager
sudo systemctl status lums-agent-watcher.service --no-pager
sudo journalctl -u lums-agent-watcher.service -n 100 --no-pager
```

代理和监视器是独立的服务：成功的代理上报并不能证明监视器可以运行更新作业。对于 `oneshot` 服务，成功运行后 `inactive` 可能是正常的；同时检查结果和日志消息。

### 在分享命令输出之前

检查日志和配置中的密码、客户端令牌、会话或 API 密钥、私钥和个人信息。绝不要分享密钥文件的内容或完整的环境变量值。如果您需要帮助，请在移除敏感信息后仅分享相关的错误消息。

**不要一开始就**删除数据库或 Docker 卷、以特权模式运行容器、禁用安全选项、移除软件包管理器锁文件或轮换令牌。这些操作可能损坏数据、抹除证据或使问题更严重。如果某项检查失败，保存其输出并继续下面的相关章节。

---

# 1. 故障排查理念

LUMS 由多个独立组件组成。

成功的客户端上报并不自动意味着更新执行正在工作。

主要运行路径为：

```text
Linux Client
    │
    ├── LUMS Agent
    │
    └── Execution Watcher
            │
            ▼
          HTTPS
            │
            ▼
        Nginx
            │
            ▼
        LUMS API
            │
            ▼
         SQLite
```

更新执行增加了软件包管理层：

```text
Browser
   │
   ▼
LUMS API
   │
   ▼
SQLite
   │
   ▼
Update Job
   │
   ▼
Execution Watcher
   │
   ▼
LUMS Agent
   │
   ▼
APT / pacman
   │
   ▼
Result
   │
   ▼
LUMS API
   │
   ▼
SQLite
```

故障排查时，请识别**第一个失败的组件**。

例如：

```text
Agent report fails
    ↓
Check agent service
    ↓
Check network
    ↓
Check TLS
    ↓
Check client token
    ↓
Check LUMS API
```

不要立即：

* 修改数据库
* 删除 Docker 卷
* 重新安装代理
* 轮换凭据
* 移除软件包管理器锁文件
* 禁用安全控制
* 使容器成为特权容器

这些操作可能破坏有用的诊断信息或造成其他问题。

# 2. 诊断基线

在调查具体问题之前，先确定主要组件的当前状态。

LUMS 生产部署使用：

```text
Application port: 127.0.0.1:5050
External access: HTTPS through Nginx
Database: /var/lib/lums/lums.db
Docker volume: lums-data
Agent: 1.7.0
Watcher: 1.2.1
```

生产容器已加固，具备：

```text
Read-only root filesystem
No Linux capabilities
no-new-privileges
Non-root application user
Protected secret mount
Dedicated persistent data volume
```

应用端口有意仅绑定到本地主机。

预期的网络路径为：

```text
Client / Browser
       │
       ▼
     HTTPS
       │
       ▼
    Nginx :443
       │
       ▼
127.0.0.1:5050
       │
       ▼
 Docker container
       │
       ▼
    LUMS :5000
```

# 3. 首次诊断检查

## 3.1 检查 LUMS 容器

在 LUMS 服务器上：

```bash
sudo docker ps
```

`lums` 容器应正在运行。

要获得完整的容器概览：

```bash
sudo docker ps -a \
    --filter name=lums
```

在调查已停止的容器之前不要移除它们。

在调查部署问题时，较早的回退容器可能包含有用信息。

---

## 3.2 检查最近的应用日志

查看最近的 LUMS 日志：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

实时输出：

```bash
sudo docker logs \
    -f \
    lums
```

在调查特定请求或作业时，尽可能在复现问题之前开始检查日志。

这样可以更容易地将客户端操作与相应的服务器端事件关联起来。

---

## 3.3 检查 Nginx

检查反向代理：

```bash
sudo systemctl status nginx \
    --no-pager
```

验证配置：

```bash
sudo nginx -t
```

成功的配置测试应报告：

```text
syntax is ok
test is successful
```

如果 Nginx 未运行，即使 Docker 容器本身健康，通过 HTTPS 访问 LUMS 通常也会失败。

---

## 3.4 检查代理

在受管 Linux 客户端上：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

查看最近的代理输出：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

对于 `Type=oneshot` 服务，成功执行后处于非活动状态可能是正常的。

重要信息是执行结果。

成功的执行应以以下内容结束：

```text
status=0/SUCCESS
```

---

## 3.5 检查执行监视器

监视器是与上报代理分开的组件。

独立检查：

```bash
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

查看最近的输出：

```bash
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 100 \
    --no-pager
```

因此，成功的代理上报**不**证明执行监视器正在正常运行。

---

## 3.6 检查 LUMS 定时器

检查所有相关定时器：

```bash
sudo systemctl list-timers \
    --all | grep lums
```

预期的定时器包括代理和监视器调度机制。

如果某个定时器缺失或处于非活动状态，在更改任何内容之前先检查相应的单元。

---

# 4. LUMS 容器未运行

如果 `lums` 容器未运行，不要立即重新创建它。

首先检查其状态：

```bash
sudo docker ps -a \
    --filter name=lums
```

然后检查容器：

```bash
sudo docker inspect lums
```

检查最近的日志：

```bash
sudo docker logs \
    --tail 200 \
    lums
```

检查退出状态：

```bash
sudo docker inspect \
    --format '{{.State.Status}} {{.State.ExitCode}}' \
    lums
```

结果可以帮助区分：

```text
Normal shutdown
Application failure
Configuration failure
Container runtime failure
Health/startup problem
```

如果容器意外退出，在替换它之前先保留日志和容器状态。

---

# 5. 容器启动但 LUMS 不可达

LUMS 应用不应通过网络直接通过 Docker 应用端口访问。

生产应用绑定到：

```text
127.0.0.1:5050
```

验证端口绑定：

```bash
sudo docker port lums
```

同时检查主机监听：

```bash
sudo ss -lntp | grep -E ':443|:5050'
```

预期架构为：

```text
HTTPS :443
    │
    ▼
  Nginx
    │
    ▼
127.0.0.1:5050
    │
    ▼
Docker
    │
    ▼
LUMS :5000
```

如果容器正在运行但 HTTPS 失败，请分别调查各层：

1. Docker 容器
2. 本地应用端口
3. Nginx 配置
4. TLS
5. 防火墙/网络路径

不要将端口 `5050` 作为故障排查捷径公开暴露。

---

# 6. Nginx 返回错误

检查服务：

```bash
sudo systemctl status nginx \
    --no-pager
```

验证配置：

```bash
sudo nginx -t
```

查看最近的 Nginx 消息：

```bash
sudo journalctl \
    -u nginx \
    -n 100 \
    --no-pager
```

然后验证 LUMS 容器确实正在运行：

```bash
sudo docker ps
```

反向代理错误并不自动意味着 LUMS 应用本身已损坏。

可能的故障位置包括：

```text
Browser
   ↓
TLS
   ↓
Nginx
   ↓
127.0.0.1:5050
   ↓
Docker
   ↓
LUMS
```

分别测试各层，而不是同时更改多个组件。

---

# 7. HTTPS / TLS 问题

首先测试 HTTPS 端点：

```bash
curl -I https://LUMS-SERVER/
```

如果证书验证失败，请确定问题是：

```text
Certificate
Certificate chain
Hostname
Trust store
Nginx configuration
Client CA configuration
```

验证 Nginx：

```bash
sudo nginx -t
```

如果证书或 TLS 配置是有意更改的，请重新加载 Nginx：

```bash
sudo systemctl reload nginx
```

然后再次测试：

```bash
curl -I https://LUMS-SERVER/
```

使用私有证书颁发机构的客户端必须信任相应的 CA 证书。

不要将禁用 TLS 证书验证作为永久变通方案。

绕过证书验证的成功连通性测试并不能证明生产 TLS 配置正确。

---

# 8. 代理服务失败

检查服务：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

阅读最近的日志：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

只有在检查之前的结果后才再次启动服务：

```bash
sudo systemctl start \
    lums-agent.service
```

然后检查：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

以及：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

查找：

```text
Configuration errors
Missing environment values
TLS errors
Authentication failures
API errors
Python exceptions
Package-manager errors
```

不要仅仅因为一次执行失败就重新安装代理。

---

# 9. 代理报告缺少 `LUMS_TOKEN`

代理通常通过其 systemd 服务环境接收生产配置。

如果从 shell 手动启动代理，systemd 的 `EnvironmentFile` 不会自动加载到该 shell 中。

因此：

```bash
sudo /opt/lums-agent/agent.py --version
```

可能与以下命令的行为不同：

```bash
sudo systemctl start \
    lums-agent.service
```

当令牌仅通过 systemd 配置提供时。

调查身份验证问题时，请先测试实际服务：

```bash
sudo systemctl start \
    lums-agent.service
```

然后检查：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

不要不必要地将生产令牌复制到 shell 命令中。

绝不要将生产令牌打印到诊断日志中。

---

# 10. 代理无法访问服务器

从网络连通性开始：

```bash
ping LUMS-SERVER
```

然后测试 HTTPS：

```bash
curl -I https://LUMS-SERVER/
```

如果 HTTPS 工作但代理仍然失败，请调查：

```text
Client configuration
Client token
TLS trust
API response
Client identity
Agent version
```

检查代理：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

同时检查服务器：

```bash
sudo docker logs \
    --tail 200 \
    lums
```

这有助于确定请求是否到达 LUMS。

如果客户端看到连接失败而服务器没有显示相应请求，请在更改应用配置之前调查网络或 TLS 路径。

如果基本的服务器、Docker、Nginx、TLS 和代理层正在工作，请继续：

# 12. 客户端身份验证

LUMS 使用客户端特定身份验证进行代理通信。

客户端注册后，会收到用于与 LUMS 服务器进行身份验证通信的凭据。

调查身份验证失败时不应暴露客户端令牌。

---

## 12.1 客户端未被 LUMS 接受

如果代理报告身份验证失败，首先检查代理日志：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

然后检查 LUMS 容器日志：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

查找：

```text
401 Unauthorized
403 Forbidden
Invalid client token
Unknown client
Authentication failure
```

`401` 响应通常表示身份验证问题。

`403` 响应可能表示身份验证成功但请求的操作不被允许。

不要立即轮换令牌。

首先确定问题是：

```text
Wrong token
Wrong client ID
Disabled client
Incorrect server URL
TLS problem
Malformed request
Server-side authentication failure
```

---

## 12.2 客户端存在但身份验证失败

验证客户端仍然存在于 LUMS 管理界面中。

不要仅仅因为代理请求失败就修改客户端记录。

如果客户端存在，请将配置的客户端身份与代理使用的身份进行比较。

生产令牌本身绝不应打印到诊断输出中。

使用配置元数据和服务状态进行故障排查，而不是暴露凭据。

---

# 13. 客户端令牌轮换

客户端令牌轮换使前一个令牌失效并替换为新凭据。

如果令牌被有意轮换，受影响的代理必须在能够再次进行身份验证之前收到新令牌。

预期顺序为：

```text
Administrator
    │
    ▼
Rotate client token
    │
    ▼
Old token becomes invalid
    │
    ▼
New token assigned to client
    │
    ▼
Agent configuration updated
    │
    ▼
Agent reports again
```

如果代理继续使用旧令牌，身份验证将失败。

---

## 13.1 令牌轮换后

检查代理服务：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

然后通过 systemd 运行代理：

```bash
sudo systemctl start \
    lums-agent.service
```

检查结果：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

如果身份验证仍然失败，请检查服务器日志：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

不要重复轮换令牌。

重复轮换会使确定客户端上当前部署的是哪个凭据更加困难。

---

# 14. 客户端已禁用

已禁用的客户端不应被视为活动受管客户端。

如果属于已禁用客户端的代理尝试通信，请检查服务器端身份验证结果。

检查：

```text
Client identity
Client enabled state
Authentication result
Agent configuration
```

不要仅仅为了使错误消失就重新启用客户端。

首先确定客户端被禁用的原因。

---

# 15. 更新检测

更新检测由多个独立步骤组成。

代理必须：

1. 执行软件包管理器查询
2. 解析结果
3. 将结果发送给 LUMS
4. LUMS 必须验证结果
5. LUMS 必须持久化结果
6. UI 必须显示当前状态

任何步骤的失败都可能导致更新信息显示不正确。

基本流程为：

```text
APT / pacman
     │
     ▼
Agent
     │
     ▼
HTTPS
     │
     ▼
LUMS API
     │
     ▼
SQLite
     │
     ▼
Web UI
```

---

## 15.1 未显示更新

首先确定客户端是否实际成功上报。

检查：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 100 \
    --no-pager
```

然后检查服务器：

```bash
sudo docker logs \
    --tail 100 \
    lums
```

如果代理成功完成但未显示更新，请在更改软件包管理器之前调查 API 和数据库状态。

---

## 15.2 Debian / Ubuntu 更新检测

Debian 软件包管理器使用 APT。

调查 APT 相关问题时，首先验证 APT 本身是否正常运行：

```bash
sudo apt update
```

故障排查期间不要自动运行软件包升级。

此测试的目的是确定仓库元数据是否可以成功刷新。

如果 APT 报告仓库、DNS、TLS、签名或锁错误，请在调查 LUMS 之前解决底层 APT 问题。

---

## 15.3 Arch Linux 更新检测

Arch Linux 使用 `pacman`。

检查仓库元数据：

```bash
sudo pacman -Sy
```

仅在诊断确实需要刷新仓库元数据时使用。

不要将不必要的系统升级与诊断测试结合起来。

对于软件包相关错误，请在更改配置之前检查确切的 `pacman` 输出。

---

# 16. LUMS 和客户端之间的可用更新不同

更新信息可能在两次观察之间发生变化。

例如：

```text
Client reports updates
        ↓
Repository metadata changes
        ↓
Package is upgraded manually
        ↓
LUMS displays older information
```

因此，始终考虑最后一次成功客户端上报的时间戳。

差异并不自动表示数据库问题。

检查：

```text
Last Agent execution
Last successful report
Package-manager state
Repository metadata
Displayed update state
```

---

# 17. 软件包管理

LUMS 软件包管理与客户端页面上显示的已安装软件包过滤器是分开的。

软件包管理工作流程为：

```text
User
 │
 ▼
Package Search
 │
 ▼
LUMS API
 │
 ▼
Agent
 │
 ▼
APT / pacman
 │
 ▼
Search Result
 │
 ▼
LUMS API
 │
 ▼
Web UI
```

安装、删除或更新软件包使用正常的 LUMS 作业机制。

预期的执行路径为：

```text
Package Action
     │
     ▼
Update Job
     │
     ▼
Execution Watcher
     │
     ▼
Agent
     │
     ▼
APT / pacman
```

---

## 17.1 软件包搜索未返回结果

首先验证代理是否正常运行：

```bash
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

然后检查代理日志：

```bash
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

对于基于 Debian 的客户端，验证 APT 元数据。

对于基于 Arch 的客户端，验证 pacman 仓库元数据。

不要假设空搜索结果意味着 LUMS 数据库为空。

搜索是通过客户端软件包管理器执行的。

---

## 17.2 软件包搜索工作但安装失败

成功的搜索仅证明软件包管理器可以找到该软件包。

它并不证明安装将成功。

可能的原因包括：

```text
Dependency conflicts
Repository changes
Package no longer available
Insufficient privileges
Package-manager lock
Disk-space problems
Network problems
Package-manager errors
```

检查相应的更新作业。

代理日志应包含软件包管理器结果。

---

# 18. 软件包安装作业

软件包安装使用正常的更新作业基础设施。

相关操作为：

```text
INSTALL_PACKAGE
```

对安装进行故障排查时：

1. 检查 LUMS 中的作业状态。
2. 检查代理执行。
3. 检查软件包管理器输出。
4. 检查报告给 LUMS 的最终结果。

不要手动修改 SQLite 中的作业状态。

预期生命周期为：

```text
PENDING
   ↓
RUNNING
   ↓
SUCCESS
```

或：

```text
PENDING
   ↓
RUNNING
   ↓
FAILED
```

失败的软件包安装应通过正常的作业和审计机制保持可追踪。

---

# 19. 软件包删除作业

软件包删除遵循相同的作业生命周期。

操作为：

```text
REMOVE_PACKAGE
```

当删除失败时，检查：

```text
Update job
Agent journal
Package-manager output
Final job result
```

不要手动移除数据库记录来隐藏失败的软件包操作。

失败的作业是有用的诊断信息。

---

# 20. 软件包更新作业

特定软件包更新使用：

```text
UPDATE_PACKAGE
```

在创建作业之前，LUMS 必须知道该软件包有可用更新。

如果 UI 未提供预期的软件包更新：

1. 刷新更新信息
2. 验证软件包管理器状态
3. 验证可用更新结果
4. 如果状态不一致，检查服务器日志

不要手动将更新记录插入 SQLite。

---

# 21. 系统更新作业

完整的系统更新使用：

```text
UPDATE_SYSTEM
```

这与以下操作不同：

```text
UPDATE_PACKAGE
```

系统更新可能影响多个软件包，并且根据操作系统和生成的软件包状态可能需要重启。

对系统更新进行故障排查时，请确定失败发生在：

```text
Update preparation
Package-manager execution
Result collection
Reboot detection
Post-reboot reporting
```

---

# 22. 软件包管理器锁

当另一个软件包管理进程已在运行时，软件包管理器可能拒绝操作。

典型示例包括：

```text
APT is already running
dpkg is locked
pacman is locked
```

首先识别持有锁的进程。

不要盲目删除锁文件。

锁文件可能表明另一个软件包管理进程正在合法活动。

在软件包操作正在运行时移除它可能损坏软件包管理状态。

正确的故障排查顺序为：

```text
Lock error
   ↓
Identify active process
   ↓
Determine whether it is legitimate
   ↓
Wait or resolve the process safely
   ↓
Retry operation
```

---

# 23. 软件包管理器故障 vs. LUMS 故障

始终区分软件包管理器故障和 LUMS 故障。

例如：

```text
APT fails
    ↓
Agent reports APT failure
    ↓
LUMS stores FAILED result
```

在这种情况下，即使作业失败，LUMS 也可能正常运行。

相反：

```text
APT succeeds
    ↓
Agent cannot report result
    ↓
LUMS never receives SUCCESS
```

此时软件包操作可能已成功，而 LUMS 上报路径失败。

因此，软件包管理器结果和 LUMS 作业结果必须分开调查。

---

# 24. 有用的诊断分离

当软件包作业失败时，首先分类失败：

```text
A. Package-manager failure
B. Agent execution failure
C. Agent reporting failure
D. Server/API failure
E. Database persistence failure
F. UI display problem
```

这种分类可防止修改不相关的组件。

软件包管理器错误不应自动导致 Docker 重建。

UI 显示问题不应自动导致删除数据库。

身份验证失败不应自动导致重新安装代理。

---

# 25. 下一个故障排查领域

如果客户端身份验证、更新检测和软件包管理正常工作，下一个诊断领域是执行生命周期本身：

```text
Update Job
    ↓
Watcher
    ↓
Agent
    ↓
Execution
    ↓
Result
    ↓
Checkpoint / Recovery
    ↓
Final Job State
```

下一节涵盖**执行监视器、空闲检测、作业状态、恢复和重启处理**。

# 26. 更新作业执行

LUMS 更新作业通过代理和执行监视器异步执行。

正常的执行路径为：

```text
User
 │
 ▼
LUMS API
 │
 ▼
SQLite
 │
 ▼
Pending Job
 │
 ▼
Execution Watcher
 │
 ▼
Agent
 │
 ▼
Package Manager
 │
 ▼
Result
 │
 ▼
LUMS API
 │
 ▼
SQLite
```

UI 中可见的作业不一定已在执行。

始终先确定当前作业状态。

---

## 26.1 作业卡在 `PENDING`

如果作业保持在 `PENDING`，请在调查代理之前检查执行监视器。

检查监视器：

```bash id="wq5h3v"
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

查看最近的监视器输出：

```bash id="8y0v7e"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

然后检查代理：

```bash id="j8x4qm"
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

挂起的作业通常表示执行阶段尚未开始。

可能的原因包括：

```text
Watcher is not running
Watcher timer is not running
Client is offline
Client is not idle
Client has not reported recently
Job is not eligible for execution yet
```

不要手动更改 SQLite 中的作业状态。

---

# 27. 作业卡在 `RUNNING`

`RUNNING` 作业表示执行已开始。

首先确定代理是否实际在执行该作业。

检查：

```bash id="s2z5ek"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

然后检查监视器：

```bash id="x4f6cb"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

运行中的作业可能需要一些时间，取决于：

```text
Package count
Repository speed
Network latency
Package-manager operations
System load
Reboot requirements
```

不要仅因为 UI 尚未更新就终止活动的软件包操作。

首先确定底层进程是否仍然活动。

---

# 28. 作业为 `FAILED`

失败的作业不一定表示 LUMS 服务器故障。

确定哪一层产生了失败。

检查：

```text id="5t9b83"
Job state
Agent execution result
Package-manager result
Server logs
Agent logs
```

主要类别为：

```text
Package-manager failure
Agent execution failure
Agent reporting failure
Server/API failure
Authentication failure
Recovery failure
```

应尽可能保留原始错误。

不要用手动创建的成功记录替换失败的作业。

---

# 29. 作业为 `SUCCESS` 但软件包未更改

成功的 LUMS 作业意味着根据代理结果所请求的操作已完成。

如果预期的软件包状态与作业结果不匹配，请直接验证客户端。

对于基于 Debian 的系统：

```bash id="gqdbm7"
dpkg-query -W \
    -f='${Package} ${Version}\n' \
    PACKAGE_NAME
```

对于 Arch Linux：

```bash id="2x9f7v"
pacman -Q \
    PACKAGE_NAME
```

将 `PACKAGE_NAME` 替换为正在调查的软件包。

然后将本地软件包状态与 LUMS 结果进行比较。

可能的解释包括：

```text
Package was changed after the job
Package name refers to a virtual/provided package
Package-manager output was interpreted differently than expected
The job result was generated before another local change
```

在识别出差异之前不要修改 LUMS 数据库。

---

# 30. 执行监视器

执行监视器负责发现符合执行条件的作业。

监视器必须被视为独立组件。

检查其服务：

```bash id="w5m0c8"
sudo systemctl status \
    lums-agent-watcher.service \
    --no-pager
```

检查其定时器：

```bash id="3v1x7r"
sudo systemctl list-timers \
    --all | grep lums
```

检查其日志：

```bash id="d5m0xk"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

如果代理工作但作业从未启动，监视器应是首先调查的组件之一。

---

# 31. 监视器运行但不执行作业

监视器执行并不自动意味着作业将被启动。

作业必须满足执行条件。

检查：

```text id="m7p2zq"
Client exists
Client is enabled
Client is reachable
Client has recent status
Client is eligible
Job is pending
Job is not already completed
Execution conditions are satisfied
```

如果客户端不符合条件，监视器可能正确地将作业留在挂起状态。

这不一定是错误。

---

# 32. 空闲检测

LUMS 在决定是否应执行作业时可以使用客户端空闲信息。

目的是避免在客户端正在被积极使用时启动维护操作。

因此，空闲决策应被视为调度条件，而不是执行失败。

客户端可能成功上报但仍被视为非空闲。

故障排查顺序为：

```text
Agent reports
     ↓
Idle information available?
     ↓
Idle state acceptable?
     ↓
Job eligible?
     ↓
Watcher executes
```

---

## 32.1 客户端上报但不被视为空闲

检查代理日志：

```bash id="5r2q1k"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

查找所报告的空闲信息。

然后检查监视器：

```bash id="2a6v8m"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

重要的区别是：

```text
Agent communication successful
```

对比：

```text
Client eligible for maintenance execution
```

这些是独立的状态。

---

# 33. 空闲检测不可用

某些系统可能不提供所有空闲状态信息。

不可用的空闲机制不应自动被解释为代理损坏。

首先确定所报告的能力。

相关概念为：

```text
Idle supported
Idle source
Idle state
Idle duration
```

如果平台无法提供预期的空闲信息，请调查代理的平台特定实现，而不是修改服务器数据库。

---

# 34. 更新作业恢复

LUMS 使用检查点和恢复来防止中断的更新作业被视为已完成。

作业可能因以下原因中断：

```text
Agent restart
Client reboot
Network interruption
Package-manager interruption
Server restart
Watcher restart
System failure
```

恢复必须区分已完成的工作和仍需执行的工作。

原则为：

```text
Completed work remains completed.
未完成的工作仍可恢复。
```

---

# 35. 中断的作业

如果作业被中断，首先检查其状态。

然后检查代理：

```bash id="3u8d4k"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

检查监视器：

```bash id="w4x1b9"
sudo journalctl \
    -u lums-agent-watcher.service \
    -n 200 \
    --no-pager
```

不要手动将作业标记为成功。

恢复机制应确定哪些软件包项已经完成。

---

# 36. 恢复重复软件包操作

当触发恢复时，已成功的软件包项不应被不必要地再次执行。

恢复模型基于项级状态。

概念上：

```text
Job
 ├── Package A → SUCCESS
 ├── Package B → SUCCESS
 ├── Package C → FAILED
 └── Package D → PENDING
```

恢复应保留成功的项并继续剩余工作。

如果此行为似乎不正确，请在更改数据库之前检查作业和软件包项历史。

---

# 37. 客户端在更新期间重启

重启可能中断代理进程。

预期的恢复路径为：

```text
Update starts
    ↓
Package operation
    ↓
Client reboot
    ↓
Agent starts again
    ↓
State is reported
    ↓
LUMS evaluates recovery
```

因此，重启并不自动意味着作业永久失败。

客户端返回后检查代理服务：

```bash id="jjh3u8"
sudo systemctl status \
    lums-agent.service \
    --no-pager
```

然后检查最近的执行：

```bash id="h7y5gk"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

---

# 38. 重启检测

重启检测用于确定是否作为更新操作的一部分发生了系统重启。

这在更新更改了需要重启或重新启动的软件包时尤其相关。

对于 Arch Linux，重启检测不得与软件包管理器退出状态混淆。

软件包操作可能成功而系统仍需要重启。

对重启处理进行故障排查时，比较：

```text
Package operation result
Reboot requirement
Actual reboot state
Post-reboot Agent report
Final LUMS job state
```

---

# 39. 作业结果未上报

如果软件包操作似乎已完成但 LUMS 未显示最终结果，请调查上报路径。

检查代理：

```bash id="t0r8kf"
sudo journalctl \
    -u lums-agent.service \
    -n 200 \
    --no-pager
```

然后检查服务器：

```bash id="h5n1xv"
sudo docker logs \
    --tail 200 \
    lums
```

如果代理报告错误而软件包操作本身成功，请将问题分类为上报失败而非软件包管理失败。

---

# 40. 作业执行期间服务器重启

服务器重启不得自动被视为更新操作失败的证据。

在服务器再次可用后必须评估作业状态。

检查：

```text id="j4t7yw"
Container state
Database availability
Job state
Client state
Agent report
Watcher state
```

恢复机制负责确定中断的工作是否可以安全继续。

服务器重启后不要手动重写作业状态。

---

# 41. 数据库可用但作业状态看起来错误

如果 SQLite 可访问但作业状态似乎不一致，请在修改数据库之前检查应用和审计日志。

有用的信息包括：

```text
Job ID
Client ID
Job action
Job creation time
Current state
Package-item states
Agent result
Recovery events
Audit events
```

数据库是应用数据存储，而不是手动修复界面。

直接修改可能绕过验证、授权、审计和恢复逻辑。

---

# 42. 手动更改作业状态

手动 SQL 更改更新作业状态不应作为常规故障排查使用。

避免如下操作：

```sql id="8hbyqv"
UPDATE update_jobs ...
```

或：

```sql id="n1h7yr"
DELETE FROM update_jobs ...
```

除非受控数据库恢复程序明确要求。

如果确实需要数据库级修复，请先保留备份并记录确切的更改，然后再应用。

正常的运维问题应通过应用和代理机制解决。

---

# 43. 监视器和代理诊断矩阵

使用以下矩阵识别最可能的层：

| 症状                                             | 首先检查的组件             |
| ------------------------------------------------ | -------------------------- |
| 客户端无法进行身份验证                           | 代理 + LUMS API            |
| 客户端成功上报但作业保持挂起                     | 执行监视器                 |
| 作业变为运行中但未完成                           | 代理 + 软件包管理器        |
| 软件包操作失败                                   | 软件包管理器               |
| 软件包操作成功但结果缺失                         | 代理上报                   |
| 客户端在更新期间重启                             | 代理 + 恢复                |
| 重启后作业仍然不一致                             | 恢复 + 数据库状态          |
| 作业从未被发现                                   | 监视器 + 定时器            |
| 客户端不符合条件                                 | 空闲/客户端状态            |
| UI 显示过时状态                                  | API + 最新客户端上报       |

此矩阵是起点，不是检查实际日志和作业状态的替代品。

---

# 44. 下一个故障排查领域

验证作业执行后，下一个领域为：

```text
SQLite and database state
RBAC and user management
Authentication sessions
Application and audit logging
Container security
Tests and CI
```

这些领域应与软件包执行分开调查。

# 45. SQLite 和数据库故障排查

LUMS 使用 SQLite 作为其应用数据库。

生产数据库存储在持久化 Docker 卷内：

```text id="9c6w3e"
/var/lib/lums/lums.db
```

数据库由应用管理，通常不应手动修改。

调查数据库相关问题时，首先确定问题是：

```text id="4k4z1m"
Database availability
Database locking
Application configuration
Data consistency
Migration state
Application logic
```

---

# 46. 数据库不可用

如果 LUMS 报告数据库错误，首先检查容器是否正在运行：

```bash id="0l5q6h"
sudo docker ps
```

然后检查应用日志：

```bash id="6j5p8m"
sudo docker logs \
    --tail 200 \
    lums
```

不要立即删除 Docker 卷。

持久化卷包含生产应用数据。

删除它可能永久移除：

```text id="4bq9rj"
Users
Clients
Client configuration
Update jobs
Audit data
Application state
```

---

# 47. SQLite 数据库锁定

SQLite 锁定问题应通过应用日志进行调查。

检查：

```bash id="l8f6vk"
sudo docker logs \
    --tail 200 \
    lums
```

生产应用使用：

```text id="2d3m8x"
journal_mode = wal
busy_timeout = 5000
synchronous = 2
```

应用还在其数据库连接上启用了 SQLite 外键强制。

数据库锁并不自动意味着数据库已损坏。

可能的原因包括：

```text id="9w4qcz"
Concurrent writes
Long-running transaction
Application process still using the database
Unexpected process termination
Filesystem problem
```

不要手动删除 SQLite 日志文件。

---

# 48. SQLite 外键

LUMS 在应用层显式启用 SQLite 外键强制。

这意味着在建立应用连接时，SQLite 会验证数据库记录之间的关系。

如果发生与外键相关的错误，请首先检查应用日志。

不要禁用来键强制以使操作成功。

外键失败可能表明应用逻辑或数据完整性问题。

---

# 49. SQLite 数据库完整性

如果怀疑数据库损坏，首先停止进行不必要的更改。

保留当前状态并检查应用日志。

可以对数据库副本执行受控的完整性检查。

除非有文档化的恢复程序要求，否则不要直接对生产数据库执行破坏性修复操作。

一般原则为：

```text id="t4d1km"
Preserve
   ↓
Inspect
   ↓
Verify
   ↓
Recover
   ↓
Validate
```

绝不从以下开始：

```text id="z1f6rw"
Delete database
Recreate database
Recreate Docker volume
```

---

# 50. 数据库迁移

LUMS 使用应用迁移引入数据库架构更改。

当发生迁移问题时，检查容器日志：

```bash id="x4h9vf"
sudo docker logs \
    --tail 200 \
    lums
```

查找：

```text id="m2x7kc"
Migration failure
SQL error
Duplicate column
Missing table
Constraint error
Migration already applied
```

不要手动编辑迁移记录，除非迁移系统特别需要受控恢复程序。

已应用的迁移通常不应再次手动执行。

---

# 51. 数据库卷

LUMS 数据库存储在持久化 Docker 卷中：

```text id="p6m3jw"
lums-data
```

检查该卷：

```bash id="v4c7yq"
sudo docker volume inspect \
    lums-data
```

该卷必须在正常容器重建期间保持持久。

应用容器本身是可丢弃的。

应用数据则不是。

因此：

```text id="z9f4ws"
Container
    ≠
Persistent database
```

重建容器不得与重建数据卷混淆。

---

# 52. 数据库磁盘空间

SQLite 需要可用的文件系统空间才能正常运行。

检查主机文件系统：

```bash id="j6k1pt"
df -h
```

同时检查 inode 可用性：

```bash id="q2c5ra"
df -i
```

磁盘空间不足可能产生最初看起来像应用问题的数据库错误。

如果数据库突然变为只读或写入开始失败，请在修改 SQLite 配置之前验证文件系统容量。

---

# 53. RBAC 故障排查

LUMS 使用基于角色的访问控制。

当前角色为：

```text id="k8w5j2"
Administrator
Operator
Viewer
```

权限有意不同。

---

## 53.1 Administrator

管理员可以：

```text id="n4x7pa"
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
Create and disable clients
Rotate client tokens
Manage users
Manage roles
```

仅限管理员的操作包括用户管理和角色管理。

---

## 53.2 Operator

操作员可以：

```text id="b7c2mz"
View clients
View installed software
View available updates
Create and execute update jobs
View update history
Use package management
Use system maintenance
```

操作员不可以：

```text id="q8v3kd"
Manage users
Manage roles
Create or disable clients
Rotate client tokens
```

---

## 53.3 Viewer

Viewer 具有有意受限的访问权限。

Viewer 可以：

```text id="y5m2rx"
View clients
View installed software
```

以下功能在 Viewer 界面中隐藏并在服务器端阻止：

```text id="e8c4nw"
Available Updates
Update Jobs
Update History
Package Management
System Maintenance
```

这是有意的安全控制。

如果 Viewer 可以访问其中一项功能，请将问题视为 RBAC 问题而非单纯的 UI 问题。

---

# 54. Viewer 看到过多内容

如果 Viewer 看到不应可用的功能，请检查两层：

```text id="x5j3mq"
Browser UI
    +
Server-side authorization
```

在 JavaScript 或 HTML 中隐藏元素不是足够的安全性。

API 还必须拒绝未经授权的操作。

调查时：

1. 确定已认证用户的角色。
2. 识别受影响的端点。
3. 检查服务器响应。
4. 如有必要，检查应用日志。
5. 验证相关的 RBAC 测试。

不要仅通过隐藏 UI 元素来解决授权问题。

---

# 55. Viewer 无法看到预期数据

Viewer 仍应能够访问当前 RBAC 模型明确允许的信息。

如果允许的客户端信息缺失：

```text id="3h6q8f"
Verify login
   ↓
Verify role
   ↓
Verify client visibility
   ↓
Inspect API response
   ↓
Inspect browser console if necessary
```

不要仅仅因为页面目前看起来不完整就授予额外权限。

首先确定缺失的信息是否被有意限制。

---

# 56. Operator 无法执行操作

如果 Operator 收到 `403 Forbidden`，首先确定所请求的操作是否仅限管理员。

操作员访问不包括：

```text id="n5y7cu"
User management
Role administration
Client creation/deactivation
Client token rotation
```

如果该操作应对操作员允许，请检查端点的授权装饰器和相应的 RBAC 测试。

不要作为诊断捷径临时将用户提升为 Administrator。

---

# 57. Administrator 无法执行操作

Administrator 应能访问当前支持的所有管理操作。

如果 Administrator 收到授权错误：

```text id="q7d2nv"
Verify authenticated session
        ↓
Verify current role
        ↓
Verify endpoint authorization
        ↓
Inspect CSRF requirements
        ↓
Inspect application logs
```

对于会更改状态的操作，仅有有效会话可能不足够。

在需要时还必须满足 CSRF 保护。

---

# 58. 用户管理

用户管理仅限于管理员。

用户管理工作流程为：

```text id="x4j6pw"
Administrator
    │
    ▼
User Management
    │
    ├── Create user
    ├── Assign role
    └── Enable / disable user
```

当无法创建用户时，检查：

```text id="b3q9fz"
Current role
Username validation
Role validation
Duplicate username
Password validation
CSRF protection
Application logs
```

不要在 SQLite 中直接创建用户。

直接数据库插入绕过密码哈希、验证、授权和审计日志。

---

# 59. 用户创建失败

如果用户创建失败，请检查浏览器响应和服务器日志。

API 应验证：

```text id="7x3m5n"
Username
Role
Password requirements
Duplicate account
Authenticated administrator
CSRF token
```

如果请求被拒绝，请确定触发了哪条验证规则。

不要仅为了使一个账户创建请求成功而削弱验证。

---

# 60. 密码问题

LUMS 使用密码哈希机制存储用户密码，而不是明文密码。

如果用户无法登录：

```text id="9w3r5b"
Verify username
   ↓
Verify account enabled state
   ↓
Verify password
   ↓
Check login rate limiting
   ↓
Inspect authentication logs
```

绝不存储或记录明文密码。

不要将密码复制到诊断命令或日志文件中。

---

# 61. 已禁用用户账户

已禁用的账户不应被视为活动登录账户。

如果已禁用用户仍能进行身份验证，请调查：

```text id="z6t2hx"
Current account state
Authentication lookup
Session state
Session revocation
Browser session
Server-side authorization
```

不要简单地删除账户。

保留账户对审计历史可能很重要。

---

# 62. 会话问题

LUMS 使用服务器端会话处理。

当用户似乎拥有过时或意外的访问权限时，请先注销并建立新会话。

如果问题仍然存在，请调查：

```text id="q1y7vm"
Account state
Role
Session state
Session revocation
Cookie configuration
CSRF protection
```

不要为了绕过登录问题而禁用会话安全控制。

---

# 63. 会话撤销

会话撤销在以下情况相关：

```text id="4n8z7p"
A password changes
A user is disabled
A role changes
A session must be invalidated
A security event requires forced logout
```

如果用户在账户更改后似乎仍保留访问权限，请确定现有会话是否已正确失效。

只有在确认账户状态后才使用新的浏览器会话进行测试。

不要假设仅删除浏览器 cookie 就能证明服务器端会话撤销有效。

---

# 64. 登录限速

LUMS 对重复的失败身份验证尝试应用登录限速。

当前行为使用递增的锁定间隔：

```text id="p7k4xz"
5 attempts  → 30 seconds
6 attempts  → 60 seconds
7 attempts  → 120 seconds
8+ attempts → 300 seconds
```

失败状态持久化在 SQLite 中。

如果登录尝试意外被阻止，请在更改数据库之前检查身份验证状态。

限速响应并不自动是身份验证失败。

它可能表明账户已达到配置的失败尝试阈值。

---

# 65. 登录成功但 API 返回 `403`

成功的登录证明身份验证，而非授权。

`403 Forbidden` 响应可能表明：

```text id="m9c2vx"
Insufficient role
Missing CSRF protection
Disallowed operation
Disabled functionality
```

在更改任何内容之前先识别确切的端点。

正确的故障排查问题是：

```text id="0q4g1k"
"Is this user authenticated?"
```

然后是：

```text id="x8v5md"
"Is this authenticated user authorized for this operation?"
```

这些是独立的安全检查。

---

# 66. CSRF 错误

会更改状态的浏览器请求受跨站请求伪造保护。

如果会更改状态的请求意外失败：

```text id="6z4qpn"
Verify authenticated session
        ↓
Verify CSRF token
        ↓
Verify request method
        ↓
Verify endpoint
        ↓
Inspect server response
```

不要作为故障排查变通方案禁用 CSRF 保护。

CSRF 检查失败是安全控制按预期工作。

---

# 67. 浏览器 UI 和 API 不一致

如果 UI 显示某个操作可用但 API 拒绝它：

```text id="v8n3ty"
Browser UI
   ↓
Displayed role/state
   ↓
API request
   ↓
Server-side authorization
```

服务器端结果是权威的。

UI 在以下情况后可能包含过时状态：

```text id="4g7m2x"
Role changes
Session changes
Client changes
Page remains open for a long time
```

重新加载页面并建立新会话，然后再假设服务器端授权不正确。

---

# 68. RBAC 诊断矩阵

| 症状                             | 首先检查的组件                        |
| -------------------------------- | ------------------------------------- |
| Viewer 看到管理 UI               | 客户端页面角色处理                    |
| Viewer API 请求成功              | 服务器端 RBAC                         |
| Operator 收到 `403`              | 端点权限模型                          |
| Administrator 收到 `403`         | 会话 / CSRF / 端点授权               |
| 用户无法被创建                   | 管理员角色 + 验证                     |
| 已禁用用户仍能登录               | 账户状态 + 会话处理                   |
| 登录暂时被阻止                   | 限速                                  |
| 会更改状态的请求被拒绝           | CSRF / 会话                           |
| UI 和 API 不一致                 | 浏览器状态 + 服务器授权               |

服务器端授权结果始终比界面元素是否可见更重要。

---

# 69. 下一个故障排查领域

接下来的诊断领域为：

```text id="8r5w2q"
Application and audit logging
Container security
Filesystem permissions
Docker runtime configuration
Tests and CI
Diagnostic snapshots
Final recovery checklist
```

这些领域应在不削弱安全基线的情况下进行调查。

# 70. 应用日志

LUMS 使用应用日志提供诊断信息，而不暴露敏感凭据。

调查应用问题时，从最近的日志开始：

```bash id="f6m2qa"
sudo docker logs \
    --tail 200 \
    lums
```

持续监控：

```bash id="x3v8kp"
sudo docker logs \
    -f \
    lums
```

尽可能在监控日志的同时复现问题。

这样可以更容易关联：

```text id="p8k4zw"
User action
    ↓
HTTP request
    ↓
Application event
    ↓
Database operation
    ↓
Agent interaction
```

---

# 71. 应用日志包含错误

首先识别产生消息的组件。

典型来源包括：

```text id="w4c8rn"
Flask application
Gunicorn
Database layer
Authentication
Authorization
Package management
Job execution
Client reporting
```

不要假设最后一条日志消息是根本原因。

在事件序列中查找第一个相关错误。

尽可能关联：

```text id="n6q2vy"
Timestamp
Client
Request
Job ID
Error
Result
```

---

# 72. 审计日志

LUMS 在审计日志中记录与安全相关的应用操作。

审计日志在调查以下内容时有用：

```text id="j8r4px"
User changes
Authentication events
Administrative actions
Client management
Token operations
Update-job creation
Security-relevant state changes
```

审计事件应被视为应用事件的证据，而不是系统日志的替代。

应用日志用于技术执行细节，审计日志用于与安全相关的应用操作。

---

# 73. 审计事件缺失

如果预期的审计事件缺失：

1. 识别确切的操。
2. 识别 API 端点。
3. 验证操作确实到达了服务器。
4. 检查应用日志。
5. 确定操作是否在应创建审计事件之前被拒绝。

不要仅为了使审计追踪看起来完整而手动插入审计记录。

审计记录应对应真实的应用事件。

---

# 74. 审计日志和应用日志不同

两个日志系统具有不同的用途。

例如：

```text id="7q2m5k"
Application log
→ technical execution information

Audit log
→ security-relevant application event
```

因此，软件包管理器错误可能出现在应用或代理日志中，而不代表单独的管理审计事件。

相反，即使用户管理操作本身在技术上很简单，也应产生可审计的应用事件。

---

# 75. 日志中的敏感信息

绝不要有意将以下内容放入诊断输出：

```text id="3m7v9x"
Client tokens
Application secret keys
Passwords
Session secrets
Private keys
TLS private material
```

如果诊断命令会暴露其中一个值，请使用已脱敏或仅元数据的检查代替。

在分享日志进行故障排查时，在复制到工单、文档、GitHub 问题或聊天之前先检查是否有密钥。

---

# 76. Docker 容器安全

生产 LUMS 容器是有意加固的。

预期的安全属性包括：

```text id="z4w6pt"
Non-root application user
Read-only root filesystem
All Linux capabilities dropped
no-new-privileges enabled
No privileged mode
Dedicated writable data volume
Read-only secret mount
Restricted temporary filesystems
```

如果其中一项属性意外更改，请将其视为配置漂移。

除非已明确评估安全影响，否则不要削弱容器来解决应用问题。

---

# 77. 验证容器运行时安全

检查容器：

```bash id="b8x5jq"
sudo docker inspect lums
```

针对性的运行时检查：

```bash id="r3n7cw"
sudo docker inspect \
    --format='ReadonlyRootfs={{.HostConfig.ReadonlyRootfs}} Privileged={{.HostConfig.Privileged}} CapDrop={{json .HostConfig.CapDrop}} SecurityOpt={{json .HostConfig.SecurityOpt}}' \
    lums
```

预期值包括：

```text id="k5m2zr"
ReadonlyRootfs=true
Privileged=false
CapDrop=[ALL]
SecurityOpt=[no-new-privileges:true]
```

确切格式可能因 Docker 版本而异。

重要的是安全属性本身。

---

# 78. 容器以 root 运行

LUMS 应用应以其专用非特权应用用户运行。

如果容器意外以 root 运行，首先检查镜像和运行时配置：

```bash id="p6x4nz"
sudo docker inspect \
    --format='{{.Config.User}}' \
    lums
```

然后检查 Dockerfile。

不要通过将生产容器切换为 root 来解决应用权限问题。

如果目录需要写访问权限，请识别确切路径并确定它应该是持久化应用数据还是临时数据。

---

# 79. 只读根文件系统

生产容器使用只读根文件系统。

这保护应用镜像免受不必要的运行时修改。

如果应用报告：

```text id="y5k8mc"
Read-only filesystem
Permission denied
Cannot create file
Cannot write temporary data
```

首先确定应用尝试写入**哪里**。

预期的可写位置被有意限制。

持久化应用数据属于：

```text id="q9m3xr"
/var/lib/lums
```

临时运行时数据可以使用配置的临时文件系统。

不要仅因为某个应用路径意外可写就禁用 `--read-only`。

---

# 80. `/tmp` 不可写

如果应用需要临时存储，请验证临时文件系统：

```bash id="a7w4vn"
sudo docker inspect \
    --format='{{json .HostConfig.Tmpfs}}' \
    lums
```

生产容器提供受限的 `/tmp`。

临时文件系统仅用于临时数据。

持久化数据不得存储在那里。

---

# 81. 密钥挂载问题

LUMS 应用密钥通过受保护的文件挂载提供。

密钥不应直接嵌入镜像。

如果 LUMS 报告密钥缺失，请首先检查运行时配置：

```bash id="j4p7zx"
sudo docker inspect \
    lums
```

检查密钥挂载是否存在且为只读。

不要打印密钥的内容。

一个有用的诊断是在不显示内容的情况下验证文件存在且具有预期权限。

---

# 82. 密钥文件缺失

如果主机上不存在密钥文件，且未设置 `LUMS_SECRET_KEY` 回退值，应用会在启动时立即失败，并抛出 `RuntimeError: LUMS secret is not configured. Provide LUMS_SECRET_KEY_FILE or LUMS_SECRET_KEY.`（`server/app.py`）。这是启动失败，而不仅仅是身份验证问题。有关文件与环境变量回退的详情，请参见第 114 节。

首先确认预期的密钥路径是否存在。

不要随机重新创建密钥。

根据应用如何使用密钥，替换密钥可能使现有会话或其他加密状态失效。

因此，任何有意更换密钥的操作都必须作为受控的安全操作处理。

---

# 83. 持久化卷不可写

如果 LUMS 无法写入应用数据，请检查卷：

```bash id="y6c2mt"
sudo docker volume inspect \
    lums-data
```

然后检查容器挂载：

```bash id="e5w8rq"
sudo docker inspect \
    --format='{{json .Mounts}}' \
    lums
```

应用数据库必须位于持久化可写卷上。

不要作为变通方案使整个容器文件系统可写。

正确的解决方案是识别需要持久化的特定路径。

---

# 84. Docker 容器启动但应用失败

如果容器启动后立即退出：

```bash id="t7x3mp"
sudo docker ps -a \
    --filter name=lums
```

然后检查：

```bash id="n4q6vz"
sudo docker logs \
    --tail 200 \
    lums
```

常见原因包括：

```text id="w3j8kc"
Application startup error
Missing secret
Database initialization error
Migration failure
Invalid environment configuration
Permission problem
Dependency problem
```

不要立即重建镜像。

确定问题是在镜像、运行时配置、持久化数据还是外部配置中。

---

# 85. Docker 镜像 vs. 容器配置

一个可用的镜像仍可能因错误的运行时配置而失败。

始终区分：

```text id="s7q2mj"
Docker image
    +
Container runtime configuration
    +
Persistent volume
    +
Secret/configuration
```

例如：

```text id="m5v9rz"
Image is valid
      +
Wrong volume
      =
Application failure
```

或：

```text id="r6c3pk"
Image is valid
      +
Missing secret
      =
Application startup failure
```

不要重建一个在其他方面有效的镜像来修复运行时配置问题。

---

# 86. Docker 构建问题

如果无法构建新镜像，请首先检查 Dockerfile。

检查基础镜像和依赖定义。

生产 Dockerfile 使用固定的 Python 基础镜像摘要。

这提供了可重复性并防止构建静默移动到不相关的基础镜像修订。

如果构建突然改变行为，请比较：

```text id="e3y7pn"
Dockerfile
Base-image digest
Requirements
Application source
Build context
```

---

# 87. `.dockerignore` 问题

Docker 构建上下文不应包含不必要的本地文件或敏感材料。

仓库使用 `.dockerignore` 排除如下文件：

```text id="k2x8vw"
Local backups
Temporary files
Editor artifacts
Backup copies
Other unnecessary runtime material
```

如果构建意外包含不应存在的文件，请检查：

```bash id="q5m8cz"
cat .dockerignore
```

不要通过将敏感文件复制到镜像来解决构建上下文问题。

---

# 88. 文件系统权限问题

如果 LUMS 报告权限错误，请首先识别确切路径。

有用信息：

```bash id="p4r7yn"
sudo docker inspect \
    lums
```

以及：

```bash id="n8v2km"
sudo docker logs \
    --tail 200 \
    lums
```

重要的区别是：

```text id="x6c9pw"
Application data
Temporary data
Application source
Secret material
Host configuration
```

每者具有不同的预期权限。

不要作为故障排查捷径递归更改整个文件系统的所有权或权限。

---

# 89. 生产配置漂移

当运行环境不再匹配预期的安全基线时，就会发生配置漂移。

示例包括：

```text id="r5j8tx"
Container runs as root
Port 5050 exposed externally
Read-only filesystem disabled
Capabilities restored
Privileged mode enabled
Secret mounted read-write
Unexpected container running
```

如果检测到漂移：

1. 记录当前状态。
2. 确定何时更改。
3. 识别负责的配置。
4. 有意识地纠正配置。
5. 重新运行相关的安全验证。

不要一次做出多项不相关的更改。

---

# 90. 意外网络暴露

应用端口应保持本地：

```text id="n7w4cp"
127.0.0.1:5050
```

检查监听：

```bash id="y2m6vk"
sudo ss -lntp
```

如果 `5050` 暴露在非回环地址上，请立即调查 Docker 端口映射。

不要仅因为 Nginx 似乎难以诊断就暴露应用端口。

预期架构为：

```text id="h3x8qm"
Network
   ↓
Nginx :443
   ↓
```

# 104. 常见故障排查错误

避免以下捷径：

## 不要删除数据库

```text id="h7k2px"

Deleting lums-data
```

可能破坏持久化应用状态。

## 不要禁用安全控制

不要永久禁用：

```text id="j5r9cw"

CSRF protection
TLS validation
Container hardening
Read-only filesystem
no-new-privileges
Capability restrictions
```

移除安全控制的变通方案不是已完成的修复。

---

## 不要以特权模式运行容器

避免作为故障排查解决方案使用：

```text id="b3x7mz"

```

如果应用需要额外访问权限，请确定确切需要什么访问权限。

不要将：

```text id="v8n4qr"

```

更改为：

```text id="p2m6wy"

```

仅仅为了绕过 Nginx。

---

## 不要手动修改作业状态

避免直接更改：

```text id="r7c5xn"

update_job_packages
```

来隐藏运维问题。

使用应用、代理、监视器和恢复机制。

---

## 不要盲目删除软件包管理器锁

锁可能表明活动的软件包管理器进程。

首先识别该进程。

---

## 不要重复轮换凭据

重复令牌或密钥轮换可能造成额外的身份验证问题。

首先确定当前配置的是哪个凭据以及服务器期望哪个凭据。

### 一次只更改一项

# 114. 启动配置陷阱

**症状：** 容器立即退出，或服务器使用的数据库、备份目录与 Docker 卷所暗示的位置不同。

**代码事实（`server/app.py`）：**

- 未配置密钥时，应用会抛出 `RuntimeError: LUMS secret is not configured. Provide LUMS_SECRET_KEY_FILE or LUMS_SECRET_KEY.`。
- 如果 `LUMS_SECRET_KEY_FILE` 指定的文件不存在，代码会回退到 `LUMS_SECRET_KEY`。此回退仅处理文件缺失；文件因权限问题无法读取时，可能会抛出文件系统错误。
- `LUMS_DB_PATH` 和 `LUMS_BACKUP_DIR` 会覆盖默认路径 `/var/lib/lums/lums.db` 和 `/var/backups/lums`。过期的覆盖值会使 LUMS 静默地指向挂载卷之外的其他位置。

**核实（只读）：**

```text
docker compose logs lums | grep "LUMS secret"
docker inspect lums --format '{{range .Config.Env}}{{println .}}{{end}}'
ls -l <secret file>   # permissions only; never print the contents
```

**修复：** 更正密钥路径或权限，或删除过期的 `LUMS_DB_PATH` / `LUMS_BACKUP_DIR` 覆盖值。不要随意生成替代密钥（参见第 82 节）。

# 115. Agent 因导入时检查而无法启动

**症状：** `lums-agent` 在读取令牌之前就失败，例如报错 `RuntimeError: No supported package manager found. Supported package managers: apt, pacman`，或出现关于 CA 文件的 SSL 错误。

**原因：** 导入模块时，`agent/agent.py` 会检测软件包管理器并创建 TLS 上下文。没有 `apt` 或 `pacman` 的主机（或 `LUMS_CA_FILE` 缺失、不可读）会因此在启动时失败。Windows 等测试环境也会遇到同样情况。

**核实：**

```text
systemctl status lums-agent --no-pager
journalctl -u lums-agent -n 50 --no-pager
```

**修复：** 使用受支持的发行版，确认服务运行时的 `PATH` 中包含软件包管理器，并确认服务用户能够读取 `LUMS_CA_FILE`。

# 116. Agent 使用了错误的服务器地址（端口 5000 与 5050）

**症状：** 尽管服务器运行正常，Agent 仍报告连接被拒绝。

**原因：** Agent 内置默认值为 `LUMS_BASE=http://127.0.0.1:5000`，而文档所述容器发布端口为 `127.0.0.1:5050`。本指南中的 `5050` 示例描述的是服务器发布端口，并非 Agent 的默认值。

**核实：**

```text
systemctl show lums-agent --property=Environment
ss -lntp | grep -E ':5000|:5050'
```

**修复：** 将 `LUMS_BASE` 明确设置为客户端实际可访问的端点（通常是部署的 HTTPS URL）。不要为规避此问题而将端口 `5050` 暴露到公网。

# 117. Watcher 以状态 1 退出

**症状：** `lums-watcher` 以失败状态结束，并记录以下消息之一：`CLIENT LOOKUP FAILED`、`RUNNING JOB LOOKUP FAILED`、`JOB LOOKUP FAILED`、`IDLE CHECK FAILED`、`JOB CLAIM FAILED`、`UPDATE EXECUTION FAILED`。

**原因：** Watcher 是一次性单元。它会捕获所有错误、记录日志并以状态 1 退出，不会在进程内重试；下次定时器触发时会重新启动。它只会恢复状态严格等于 `running` 的作业。否则它会查找待处理作业；`NO UPDATE JOB // SYSTEM CLEAN` 是正常结果。

**核实：**

```text
journalctl -u lums-watcher -n 100 --no-pager
systemctl status lums-watcher lums-watcher.timer
```

**修复：** 解决对应故障（API 可达性、令牌、空闲状态检查或软件包管理器锁），然后等待定时器再次运行。通过界面或 API 检查作业状态；切勿手动编辑 SQLite 中的作业状态。

# 118. Host Updater 持续记录心跳失败

**症状：** `lums-host-updater` 仍在运行，但反复记录 `Heartbeat failed (ValueError)` 或 `Heartbeat failed (HTTPError)`。

**原因：** Host updater 会在循环中有意捕获错误并重试。常见根因（`host_updater/agent.py`）包括：

- `Host-updater token is missing or too short` — 令牌文件不存在或长度不足 32 个字符。
- `Only a loopback LUMS endpoint is permitted` — URL 必须使用 `http` 或 `https`，主机必须严格为 `127.0.0.1`，必须指定端口，且不得包含凭据、查询参数或片段（例如 `http://127.0.0.1:5050`）。
- HTTP `401`，错误标识 `host_updater_authentication_required` — bearer 令牌无效。
- HTTP `503`，错误标识 `host_updater_not_configured` — 服务器未配置 host-updater 令牌。
- 当心跳响应未明确报告 `update_execution_enabled: false` 时，服务会记录 `Unexpected update-execution state; stopping` 并以状态 1 退出。请检查服务器与 host updater 版本是否匹配。

**核实（不要打印令牌）：**

```text
journalctl -u lums-host-updater -n 100 --no-pager
systemctl show lums-host-updater --property=Environment
stat /etc/lums-host-updater/token
```

**修复：** 修复令牌文件的所有者和权限，校正回环地址，然后仅重启服务一次。

# 119. 告警集成请求返回 501

**症状：** 配置、测试或移除电子邮件、Slack、PagerDuty 或 webhook 集成时，返回 `501` 和 `Notification integrations are disabled pending secure persistent configuration`。

**原因：** 这是有意设计的行为（`server/alerts_routes.py`）。集成当前不可用，`POST /alerts/clear-all` 也会返回 `501`，并且规则不会自动评估。不要重试，也不要输入服务提供商密钥。

**相关说明：** 这些路由需要 `alerts.manage` 权限和 CSRF 保护。CSRF 令牌缺失或错误时，会先返回 `403` 和 `csrf_validation_failed`，不会到达 `501`。不要禁用 CSRF。参见 `docs/LUMS_REALTIME_ALERTING_IMPLEMENTATION.md`。

# 120. 登录失败：CSRF、速率限制与锁定

**症状：** 多次失败后，即使密码正确也遭拒，或出现审计记录 `login.rate_limit`。

**原因：** 登录尝试按用户名和来源进行限速，状态保存在 SQLite 的 `login_rate_limits`（含 `locked_until`）中，因此重启后仍然保留。`/login` 路由不受 CSRF 检查约束，所以登录失败并非由缺少 CSRF 令牌导致；请检查凭据、Cookie 和速率限制。

**核实（只读）：**

```text
sqlite3 /var/lib/lums/lums.db "select rate_limit_key, locked_until from login_rate_limits;"
```

**修复：** 等待锁定到期，并解决造成登录失败的原因。不要手动删除记录，也不要反复尝试登录来测试。

# 121. SQLite 忙碌或迁移操作了错误的数据库

**症状：** 并发时写入失败，或迁移看似成功，但运行中的服务器仍缺少表或功能。

**原因：** 应用连接使用 `PRAGMA busy_timeout = 5000`，因此写入最多等待五秒。数据库采用 WAL 模式（`server/init_db.py`），所以 `-wal` 和 `-shm` 文件是正常的。迁移脚本自行读取 `LUMS_DB_PATH`，因此可能会修改与服务器不同的数据库文件。

**核实：**

```text
sqlite3 /var/lib/lums/lums.db "pragma busy_timeout; pragma journal_mode;"
docker inspect lums --format '{{range .Config.Env}}{{println .}}{{end}}'
```

**修复：** 找出并停止造成冲突的进程，保留 WAL 和 SHM 文件，并确保迁移环境与服务器配置一致。切勿删除 `-wal` 或 `-shm` 文件。

# 122. 恢复操作拒绝执行（存在 WAL/SHM 文件）

**症状：** 恢复操作停止，并显示 `Restore verweigert: SQLite-WAL/SHM-Datei vorhanden.`（代码中的消息为德语）。

**原因：** 为避免新旧数据混合，`server/database_backup.py` 在目标数据库存在旁路文件时会安全地拒绝操作。

**核实：** `find /var/lib/lums -maxdepth 1 -type f -name 'lums.db*'`

**修复：** 停止或暂停应用，并使用文档规定的恢复流程。切勿手动删除旁路文件。

# 123. 快照和发布验证错误

**症状及原因（`scripts/volume_snapshot.py`、`scripts/release_verification.py`）：**

| 消息 | 含义 |
| --- | --- |
| `Could not create or publish the snapshot.` | 目标已存在或不可写；快照不会覆盖现有内容。 |
| `Source tree changed during snapshot creation.` | 复制期间源文件发生变化；暂停写入后重试。 |
| `Invalid snapshot filename.` / `Invalid restore target.` | 检测到不安全的路径或文件名并予以拒绝。 |
| `Duplicate restore target: ...` | 归档包含重复条目；请使用受支持工具生成的归档。 |
| 发布验证在校验和数据上失败 | 校验和元数据上限为 4096 字节；请获取官方校验和文件，不要绕过验证。 |

非 root 用户执行恢复时，不会应用归档中任意指定的所有权。请以预期服务账户按文档执行恢复，而不要将容器改为 root 运行。可以使用 `tar -tf` 列出归档成员，但不要解压。

# 124. 故障排查指南结束

LUMS 故障排查应以证据为依据并重视安全。

如有疑问：

```text id="r9x4kw"
Preserve the state.
Inspect the evidence.
Identify the failing layer.
Make the smallest safe change.
Verify the result.
Document what happened.
```

不要为了快速变通而牺牲安全或数据完整性。
