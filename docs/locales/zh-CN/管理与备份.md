# LUMS — 管理指南

> **没有噪音的 Linux 更新管理。**

本指南描述服务器和客户端安装完成后 LUMS 的日常管理与运维。

重点介绍通过 LUMS Web 界面执行的管理任务，以及在 LUMS 服务器和受管客户端上进行的受控运维任务。

安装程序单独记录在 `install.md` 中。

故障排查程序单独记录在 `troubleshooting.md` 中。

安全架构和审计信息单独记录在 `security.md` 中。

---

## 快速开始：日常管理

本指南面向负责现有 LUMS 安装的人员。详细技术章节以英文维护。请先了解以下术语：

* **用户账户：** 决定某人在 LUMS Web 界面中可以做什么。不要共享账户；为每个人分配其自己的账户。
* **客户端：** 一台受管的 Linux 计算机。其客户端令牌是机密，与 Web 账户密码不同。
* **更新作业：** 由 Agent 在目标计算机上使用 APT 或 pacman 检索并执行的请求操作。开始前请检查目标和软件包。
* **备份：** 数据库的独立、经过验证的副本。同一 Docker 卷中的副本无法防止该卷丢失。
* **升级：** 替换容器版本，而不是数据库。正常升级不得删除或重建 `lums-data`。

### 进行变更前的安全检查清单

1. 检查是否有更新作业正在运行以及是否需要维护窗口。
2. 确认存在近期可用的数据库备份。
3. 记录正在运行的镜像、容器设置和数据路径。
4. 在停止活动容器之前构建并测试新镜像。
5. 使用相同的数据、密钥和备份挂载以及相同的安全选项替换容器。
6. 检查启动后的容器状态、日志、HTTPS 登录和数据。
7. 保留旧容器作为回滚选项，直到新版本经过验证。

**不要运行** `docker volume rm lums-data`、`docker system prune --volumes` 或作为正常升级一部分的其他删除命令。它们可能永久删除数据。如果您不确定哪个容器或路径处于活动状态，请先停止并检查当前设置；不要未经检查就复制示例命令。

## 1. 管理概览

LUMS 提供对 Linux 软件清单、可用更新、软件包操作、更新作业、受管客户端、用户和运维历史的集中管理。

管理界面提供三种角色模板：

* **Administrator**
* **Operator**
* **Viewer**

创建账户时，所选角色会填充推荐的一组权限。管理员可以按用户调整这些权限；已保存的权限而非角色标签决定访问权限。

LUMS 还将服务器端管理操作与客户端软件包执行分开。

正常运行流程为：

```text
Administrator / Operator
        │
        ▼
   LUMS Web UI
        │
        ▼
     LUMS API
        │
        ▼
      SQLite
        │
        ▼
   Managed Client
        │
        ▼
 APT / pacman / system
        │
        ▼
      Result
        │
        ▼
     LUMS API
        │
        ▼
      SQLite
        │
        ▼
    Web Interface
```

LUMS 服务器不会直接在受管客户端上执行软件包管理命令。

软件包操作由安装在受管系统上的 LUMS Agent 执行。

---

## 2. 管理职责

LUMS 管理可分为几个领域。

### 用户管理

管理员管理：

* LUMS 用户
* 用户角色
* 账户状态
* 管理访问权限

用户管理需要 `users.manage` 权限。

Administrator 模板默认包含此权限。

Operator 和 Viewer 默认不获得此权限。

---

### 客户端管理

管理员管理：

* 已注册客户端
* 客户端状态
* 客户端身份验证
* 客户端令牌
* 令牌轮换
* 客户端启用与禁用

客户端管理需要 `clients.manage` 权限，因为客户端身份验证决定了哪些系统可以向 LUMS 上报。

---

### 更新管理

Administrator 和 Operator 模板授予以下权限：

* 查看可用更新
* 创建更新作业
* 执行软件包操作
* 审查更新历史
* 管理单个软件包
* 执行系统更新

Viewer 模板为只读，无法执行更新操作。

---

### 软件包管理

LUMS 通过客户端的原生软件包管理器支持软件包管理操作。

当前支持的软件包管理后端包括：

* 用于 Debian 系系统的 **APT/dpkg**
* 用于 Arch Linux 的 **pacman**

LUMS 不会替代操作系统的软件包管理器。

相反，LUMS 提供一个集中界面来请求和跟踪软件包操作。

---

### 运维管理

管理员和操作员可能需要监控：

* 正在运行的更新作业
* 失败的作业
* 已完成的作业
* 客户端上报
* 重启需求
* 软件包管理器错误
* 审计活动

针对这些情况的详细故障排查程序记录在 `troubleshooting.md` 中。

---

## 3. 管理角色

LUMS 目前提供三种角色。

| 角色          | 用途                                     |
| ------------- | ---------------------------------------- |
| Administrator | 完整管理控制                             |
| Operator      | 日常运维管理                             |
| Viewer        | 只读的客户端和软件可见性                 |

每个角色都是一个权限模板。账户单独保存的权限在服务器端强制执行。

因此隐藏界面元素本身不被视为安全控制。

未经授权的 API 操作也必须被服务器拒绝。

---

## 4. Administrator

Administrator 模板默认提供 LUMS 应用的全部权限集。

管理员可以：

* 查看受管客户端
* 查看已安装软件
* 查看可用更新
* 创建并执行更新作业
* 审查更新历史
* 执行软件包管理操作
* 执行系统维护
* 创建客户端
* 禁用客户端
* 轮换客户端令牌
* 创建和管理 LUMS 用户
* 分配角色模板和单独权限

完整 Administrator 模板权限应仅授予需要它们的用户。

当 Operator 或 Viewer 账户足够时，不应用管理账户进行日常只读监控。

---

## 5. Operator

Operator 模板用于日常更新和系统管理。

操作员可以：

* 查看受管客户端
* 查看已安装软件
* 查看可用更新
* 创建并执行更新作业
* 审查更新历史
* 执行软件包管理操作
* 执行系统维护

Operator 模板不授予：

* 创建或管理 LUMS 用户
* 分配用户角色
* 创建或禁用客户端
* 轮换客户端令牌

这种默认分离允许日常更新操作，而不授予账户和客户端管理权限。单独授权可以由拥有 `users.manage` 权限的用户更改。

---

## 6. Viewer

Viewer 模板提供只读可见性。

Viewer 可以：

* 查看受管客户端
* 查看已安装软件

Viewer 模板不授予以下管理功能：

* 可用更新管理
* 更新作业创建
* 更新作业执行
* 更新历史
* 软件包管理
* 系统维护
* 用户管理
* 客户端管理
* 令牌轮换

相应的变更型 API 操作也在服务器端受到保护。

因此，Viewer 访问适用于需要可见性但不需要运维控制的用户。

---

## 7. 角色选择指南

使用提供所需功能的最小角色。

### Administrator

当用户必须管理以下内容时使用：

* 用户
* 角色
* 客户端
* 客户端身份验证
* 令牌
* 更新
* 软件包
* 系统操作

### Operator

当用户需要执行日常运维工作时使用，例如：

* 检查更新
* 安装软件包
* 删除软件包
* 更新软件包
* 执行更新作业
* 审查作业历史

### Viewer

当用户仅需要以下可见性时使用：

* 客户端
* 已安装软件

## 8. 管理安全原则

LUMS 管理遵循最小权限原则。

管理访问应限制在用户任务所需的功能范围内。

特别是：

* 不要使用 Administrator 账户进行日常查看
* 不要在管理员之间共享账户
* 不要共享客户端令牌
* 不要将凭据放入文档
* 不要在截图或日志中暴露客户端令牌
* 除非有文档化的恢复程序明确要求，否则不要通过直接修改数据库绕过 LUMS Web 界面

当管理操作失败时，在更改持久化状态之前先调查原因。

使用以下原则：

> **先观察。后变更。再验证。**

## 9. 管理工作流程

正常的管理工作流程应遵循以下顺序：

```text
1. Authenticate
      │
      ▼
2. Verify role
      │
      ▼
3. Select client / operation
      │
      ▼
4. Review current state
      │
      ▼
5. Perform required operation
      │
      ▼
6. Monitor job
      │
      ▼
7. Verify result
      │
      ▼
8. Review history / audit information
```

管理操作在执行后应始终进行验证。

成功的 API 请求本身并不能证明所请求的软件包或系统操作已成功完成。

受管客户端上报的最终状态才是相关的运维结果。

## 11. 用户管理

用户管理可供拥有 `users.manage` 权限的用户使用。

管理员可以通过专用用户管理界面创建和管理 LUMS 应用账户。

用户账户与受管客户端身份验证是分开的。

LUMS 用户使用应用账户对 Web 应用进行身份验证。

受管客户端使用客户端令牌对 LUMS API 进行身份验证。

这些身份验证机制不得混淆。

```text
LUMS User
    │
    │ username + password
    ▼
Web Interface
    │
    ▼
LUMS Application

Managed Client
    │
    │ client token
    ▼
LUMS API
```

## 12. 创建用户

拥有 `users.manage` 的用户可以创建新的 LUMS 用户。

创建用户时，管理员指定：

* 用户名
* 密码
* 角色标签，角色模板可供后续权限分配使用

可用的角色模板包括：

* `administrator`
* `operator`
* `viewer`

服务器在创建账户之前验证提供的值。

新账户初始没有权限。创建后，管理员可以分配单个复选框或应用角色模板之一。应用模板会预选其默认权限，之后可进行自定义。可用权限包括：

| 权限              | 授予的访问权限                                      |
| ----------------- | --------------------------------------------------- |
| `clients.view`    | 查看客户端列表和系统信息                            |
| `software.view`   | 查看已安装软件                                      |
| `updates.view`    | 查看更新、作业和更新历史                            |
| `packages.search` | 搜索软件包仓库                                      |
| `jobs.manage`     | 创建软件包操作和更新作业                            |
| `clients.manage`  | 注册/移除客户端并轮换客户端令牌                    |
| `users.manage`    | 创建用户并管理角色、权限和内部备注                  |
| `backups.manage`  | 创建和检查数据库备份                                |

客户端相关权限需要 `clients.view`；`jobs.manage` 还需要 `updates.view`。LUMS 阻止移除最后一个拥有 `users.manage` 的活动账户，因此管理员不会意外锁定自己。

密码不会以明文形式存储。

LUMS 对应用凭据使用基于 Argon2 的密码哈希。

创建后验证：

* 用户名出现在用户列表中
* 角色模板和单独权限正确
* 账户已启用
* 用户可以成功通过身份验证

不要通过文档、工单、截图或其他不安全渠道传输密码。

## 数据库备份界面

拥有 `backups.manage` 权限的用户可以从**数据库备份**创建 SQLite 备份。管理员账户通过迁移 `005-backup-permission` 获得此权限；新账户通过应用 Administrator 模板获得该权限，也可以显式授予。

该界面支持原生 `.db` 和压缩 `.db.gz` 文件。它使用 SQLite 的在线备份 API，验证已完成的数据库，并以仅所有者权限存储文件。UI 列出最新的十个文件。备份不会被 LUMS 加密、自动删除、调度、下载或恢复；拥有 `backups.manage` 的管理员可以在确认后从列表中删除单个备份。请相应地保护目标位置。

基础目标目录由服务器端 `LUMS_BACKUP_DIR` 设置固定。界面允许在此基础目录下选择相对子目录并在需要时创建；绝对路径、父目录遍历和符号链接的子目录会被拒绝。主机路径必须由服务器管理员挂载到 Docker 中。对于 Docker 部署，请创建一个由容器 UID/GID `10001` 可写的单独主机目录：

```bash
sudo install -d -o 10001 -g 10001 -m 0700 /var/backups/lums
```

将以下选项添加到 LUMS 容器配置：

```bash
-v /var/backups/lums:/var/backups/lums \
-e LUMS_BACKUP_DIR=/var/backups/lums \
```

使用单独的磁盘或远程存储以防止主机故障。例如，先在 Debian 主机上挂载 NAS，然后将该挂载路径用作 Docker 绑定挂载的左侧。备份 UI 显示容器侧的基础目录；所选的相对路径位于其下方。备份目标必须在容器内可用且可写；否则界面会报告备份存储不可用。

有关恢复步骤，请参阅 [`server/static/backup-restore.md`](server/static/backup-restore.md)。

## 13. 用户角色

根据所需的最低权限选择角色模板，然后审查每个账户的单独权限。

| 角色模板      | 用户管理 | 客户端管理 | 更新 | 软件包管理 | 只读访问 |
| ------------- | -------: | ---------: | ---: | ---------: | -------: |
| Administrator |       是 |         是 |   是 |         是 |       是 |
| Operator      |       否 |         否 |   是 |         是 |       是 |
| Viewer        |       否 |         否 |   否 |         否 |       是 |

这些是默认值，不是固定边界。管理员可以自定义每个用户的权限集。角色强制执行在服务器上通过生成的按用户权限进行。

Web 界面反映所分配的角色，但服务器仍然是权威的安全边界。

---

## 14. 禁用用户账户

当账户不再被允许访问 LUMS 时，请禁用该账户，而不是共享或重新利用凭据。

示例包括：

* 管理员离开项目
* 操作员不再需要访问权限
* 临时移除管理访问权限
* 对已泄露账户的安全响应

禁用账户后，验证身份验证被拒绝。

在账户安全调查期间也应考虑现有已认证会话。

除非有文档化的恢复程序明确要求数据库级干预，否则不要手动修改 `users` 表。

---

## 15. 密码管理

密码是应用凭据，必须作为敏感信息处理。

管理员应确保：

* 密码不被共享
* 密码不存储在 Git 中
* 密码不放入文档
* 密码不包含在截图中
* 密码不被不必要地写入 shell 历史记录
* 用户通过适当的安全渠道接收其凭据

LUMS 存储密码哈希而不是明文密码。

如果怀疑密码已泄露，请通过适当的账户管理程序进行替换，而不是尝试恢复原始密码。

---

## 16. 会话

LUMS 使用已认证的应用会话进行 Web 访问。

会话处理是应用安全边界的一部分。

如果相关账户不应再拥有访问权限，管理员应将意外的已认证会话视为安全事件。

相关情况包括：

* 已禁用的账户仍显示为活动
* 意外的管理访问
* 疑似凭据泄露
* 意外的浏览器会话
* 安全调查

有关详细的会话和身份验证故障排查，请参阅 `troubleshooting.md`。

---

## 17. 登录限速

LUMS 对重复的失败登录尝试应用限速。

当前渐进规则为：

| 失败尝试次数 |     锁定 |
| -----------: | -------: |
|            5 | 30 秒    |
|            6 | 60 秒    |
|            7 | 120 秒   |
|           8+ | 300 秒   |

限速状态持久化在 SQLite 中。

成功登录会清除适用的失败尝试状态。

应调查重复的身份验证失败，而不是绕过限速器。

可能的原因包括：

* 凭据不正确
* 保存的凭据已过期
* 使用不正确凭据的自动化客户端
* 重复的手动登录尝试
* 可能的凭据攻击

## 18. 客户端管理

受管客户端是运行 LUMS Agent 的 Linux 系统。

客户端向 LUMS 提供如下信息：

* 客户端身份
* 已安装软件
* 可用更新
* 软件包管理结果
* 更新作业结果
* 重启状态
* 运行状态

LUMS 服务器存储客户端状态并通过 Web 界面公开。

客户端在本地执行实际的软件包管理操作。

---

## 19. 客户端身份验证

每个受管客户端使用客户端令牌向 LUMS 进行身份验证。

该令牌充当受管客户端的凭据。

像对待密码一样谨慎对待客户端令牌。

绝不：

* 将令牌提交到 Git
* 将令牌放入公开文档
* 在截图中包含令牌
* 将令牌粘贴到问题跟踪器中
* 在诊断输出中暴露令牌
* 将一个客户端的令牌与另一个客户端共享

令牌只应安装在为其签发的客户端上。

---

## 20. 客户端注册

新客户端必须首先向 LUMS 注册。

注册过程建立服务器端客户端身份和身份验证凭据。

注册后：

1. 安装 LUMS Agent
2. 配置客户端令牌
3. 配置 LUMS 服务器端点
4. 建立 TLS 信任
5. 执行初始 Agent 运行
6. 验证客户端成功上报
7. 确认客户端出现在 LUMS 界面中

客户端不应仅仅因为 Agent 服务成功启动就被视为可运行。

服务器必须接收并接受有效的客户端上报。

---

## 21. 客户端状态

应使用客户端视图来区分不同的运行状态。

示例包括：

* 客户端已注册但未上报
* 客户端正常上报
* 客户端上报过时信息
* 客户端已禁用
* 客户端身份验证失败
* 客户端侧软件包管理器失败

当客户端停止上报时，首先确定问题是否为：

1. 网络连通性
2. TLS 信任
3. 客户端身份验证
4. Agent 执行
5. 服务器可用性
6. 服务器端处理

在确定实际失败的层之前，避免更改客户端凭据。

---

## 22. 客户端令牌轮换

需要时可以轮换客户端令牌。

典型原因包括：

* 疑似令牌暴露
* 凭据轮换策略
* 管理维护
* 替换客户端配置
* 安全事件响应

令牌轮换会更改客户端接受的凭据。

轮换后：

1. 获取新的客户端令牌
2. 更新客户端配置
3. 运行 Agent
4. 验证身份验证成功
5. 验证生成的客户端上报
6. 确认正常上报恢复

在新身份验证路径验证之前，不要移除旧客户端配置。

---

## 23. 禁用客户端

当客户端不再应参与 LUMS 操作时，可以将其禁用。

示例包括：

* 系统退役
* 临时维护
* 客户端替换
* 疑似凭据泄露

在禁用客户端之前，检查是否有与其关联的活动更新作业。

禁用后：

* 验证客户端不再被视为可运行
* 审查相关更新作业历史
* 保留调查所需的审计信息

不要仅因为客户端暂时离线就删除持久化客户端数据。

---

## 24. 客户端管理检查清单

添加或更改客户端时，验证完整链路：

```text
[ ] Client exists in LUMS
[ ] Client is enabled
[ ] Client token is valid
[ ] TLS trust is valid
[ ] LUMS Agent is installed
[ ] Agent configuration is valid
[ ] Initial report succeeds
[ ] Client appears in the Web UI
[ ] Installed software is reported
[ ] Available updates are reported
[ ] Update jobs can be tracked
[ ] Results are returned correctly
```

只有当完整的上报和身份验证链正常工作时，客户端才可运行。

---

## 25. 管理原则

用户管理和客户端管理应保持分离。

LUMS 应用账户决定**一个人被允许做什么**。

客户端令牌决定**哪个受管系统被允许与 LUMS 通信**。

```text
Application User
      │
      └── Role / Permissions

Managed Client
      │
      └── Client Token / Identity
```

不要将一种机制用作另一种机制的替代。

## 26. 软件清单

LUMS 维护受管客户端上报的软件信息。

软件清单允许管理员和操作员确定客户端上安装了哪些软件包。

清单由 LUMS Agent 收集并上报给服务器。

服务器然后通过客户端界面公开上报的信息。

清单应被视为客户端所上报状态的快照。

它不会替代原生软件包管理器。

---

## 27. 已安装软件

**已安装软件**部分显示所选客户端上报的软件包。

管理员和操作员可以使用本地软件包过滤器缩小显示的清单。

已安装软件过滤器是本地界面功能。

它与软件包管理搜索分开。

这一区别很重要：

```text
Installed Software
    │
    └── Filter already reported package inventory

Package Management
    │
    └── Search the client's package repositories
```

因此，已安装的软件包如果不再存在于配置的仓库中，可能不会出现在软件包管理搜索中。

---

## 28. 可用更新

LUMS 还收集有关可用更新的软件包信息。

可用更新信息在受管客户端上使用其原生软件包管理系统生成。

上报的信息可用于识别需要关注的软件包。

创建更新作业之前，请审查：

* 客户端身份
* 软件包名称
* 当前安装版本
* 可用版本
* 软件包状态
* 客户端当前是否可访问

不要假设所有可用更新都应立即安装。

执行前应考虑运维要求、维护窗口、应用依赖关系和客户端状态。

---

## 29. 软件包管理

LUMS 为受支持的 Linux 客户端提供集中式软件包管理操作。

当前软件包管理操作包括：

* `INSTALL_PACKAGE`
* `REMOVE_PACKAGE`
* `UPDATE_PACKAGE`
* `UPDATE_SYSTEM`

操作通过 LUMS 请求，但由 LUMS Agent 在本地执行。

Agent 将实际软件包操作委托给原生软件包管理器。

```text
LUMS Web UI
      │
      ▼
LUMS API
      │
      ▼
Update Job
      │
      ▼
LUMS Agent
      │
      ├── APT / dpkg
      │
      └── pacman
```

因此，LUMS 保持独立于操作系统的软件包数据库和软件包管理实现。

---

## 30. 软件包搜索

**软件包管理**界面提供与已安装软件过滤器分开的软件包搜索。

搜索从受管客户端请求软件包信息。

在 Debian 系系统上，Agent 使用 APT 软件包管理工具。

在 Arch Linux 上，Agent 使用 `pacman`。

搜索结果可能包含：

* 软件包名称
* 软件包版本
* 软件包描述
* 可用时的仓库信息

软件包搜索不会安装任何内容。

因此，搜索是只读操作。

---

## 31. 安装软件包

管理员和操作员可以创建软件包安装作业。

正常工作流程为：

1. 选择受管客户端
2. 打开**软件包管理**
3. 搜索所需软件包
4. 审查结果
5. 选择安装操作
6. 创建作业
7. 监控执行
8. 验证结果
9. 刷新或重新检查已安装软件

软件包由 Agent 使用原生软件包管理器安装。

成功创建作业并不意味着安装已完成。

必须检查最终作业结果。

---

## 32. 删除软件包

软件包删除遵循相同的受控作业工作流程。

删除软件包之前，验证：

* 正确的客户端
* 正确的软件包
* 预期的操作
* 是否有其他软件依赖该软件包

执行后，验证生成的作业状态和客户端上报的软件状态。

LUMS 不会绕过软件包管理器的依赖关系处理。

原生软件包管理器仍负责解决该操作。

---

## 33. 更新软件包

当有可用更新时，可以更新特定软件包。

工作流程为：

```text
Available Update
      │
      ▼
Review Package
      │
      ▼
Create UPDATE_PACKAGE Job
      │
      ▼
Agent Execution
      │
      ▼
Result Validation
```

LUMS 在创建相应更新作业之前验证软件包信息。

如果软件包不再列为可更新，则该作业请求不应被视为有效的更新操作。

这可以防止盲目执行过时的更新信息。

---

## 34. 更新系统

`UPDATE_SYSTEM` 使用客户端的原生软件包管理机制执行更广泛的系统更新。

此操作影响多个软件包，因此应被视为维护操作。

开始系统更新之前，验证：

* 客户端可用性
* 维护窗口
* 当前运行的作业
* 软件包管理器状态
* 相关时的可用磁盘空间
* 是否需要重启

更新后，验证：

* 作业结果
* 客户端上报
* 已安装软件
* 可用更新
* 重启状态

---

## 35. 更新作业

所有变更型软件包和更新操作都表示为 LUMS 更新作业。

这提供了通用的执行和跟踪模型。

典型作业生命周期：

```text
PENDING
   │
   ▼
RUNNING
   │
   ├──────────────► FAILED
   │
   ▼
SUCCESS
```

当客户端不可用或执行中断时，作业也可能需要额外处理。

作业历史应被用作权威的运行记录，而不是仅仅依赖当前客户端视图。

---

## 36. 作业创建

创建更新作业之前，请仔细验证预期操作。

检查：

* 客户端
* 操作
* 软件包
* 适用时的目标版本
* 当前软件包状态
* 维护要求

支持的操作包括：

| 操作              | 用途                         |
| ----------------- | ---------------------------- |
| `INSTALL_PACKAGE` | 安装软件包                   |
| `REMOVE_PACKAGE`  | 删除软件包                   |
| `UPDATE_PACKAGE`  | 更新特定软件包               |
| `UPDATE_SYSTEM`   | 执行系统范围的更新           |

更新作业创建仅限于 **Administrator** 和 **Operator** 角色。

Viewer 无法创建更新作业。

---

## 37. 作业执行

创建后，作业由 LUMS Agent 处理。

Agent 接收作业并在本地执行所请求的操作。

服务器跟踪生成的状态。

Agent 不会将成功的 HTTP 请求视为软件包操作成功的证明。

相反，实际的软件包管理器结果会返回给 LUMS。

这一区别很重要：

```text
API request accepted
        ≠
Package operation successful
```

因此，必须始终检查最终执行结果。

---

## 38. 作业结果

已完成的作业应包含明确的结果。

相关结果包括：

* 成功执行
* 失败执行
* 软件包管理器错误
* 执行中断
* 与恢复相关的状态
* 适用时与重启相关的状态

管理员和操作员在作业失败时应检查结果，而不是立即重复相同的操作。

在不理解原始失败原因的情况下重复执行可能使诊断更加困难。

---

## 39. 作业历史

更新历史提供先前更新活动的运维记录。

使用它来回答如下问题：

* 此软件包是否已更新？
* 哪个客户端执行了该操作？
* 作业何时创建？
* 执行何时开始？
* 执行何时完成？
* 操作是否成功？
* 软件包管理器是否报告错误？

历史作业信息在调查重复失败或中断的维护操作时尤其重要。

---

## 40. 失败的作业

当作业失败时：

1. 记录客户端和作业 ID
2. 检查作业结果
3. 确定失败发生在服务器还是客户端
4. 检查相关的 Agent 日志
5. 检查原生软件包管理器状态
6. 修正底层问题
7. 只有在理解原因后才重试

常见原因包括：

* 仓库不可用
* 软件包管理器锁
* 网络问题
* 无效的软件包请求
* 依赖关系冲突
* 磁盘空间不足
* 软件包操作中断
* 客户端身份验证或通信问题

详细诊断程序记录在 `troubleshooting.md` 中。

---

## 41. 软件包管理器锁

APT 和 pacman 可以阻止并发软件包操作。

如果软件包管理操作因软件包管理器已在使用而失败：

* 识别活动的软件包管理进程
* 确定正在运行的操作
* 适当时等待合法操作完成
* 之后重试 LUMS 操作

在软件包管理器运行时**不要**盲目删除软件包管理器锁文件。

删除锁文件并不能解决底层的并发操作，并且可能损坏软件包管理状态。

---

## 42. 空闲感知执行

LUMS 可以在确定更新作业是否应执行时使用客户端空闲信息。

此机制旨在避免中断受管系统的活动交互使用。

空闲检测由客户端上的 Agent 执行。

如果空闲信息不可用，Agent 必须报告该情况，而不是虚构空闲状态。

管理员应区分：

* 客户端处于空闲
* 客户端处于活动
* 空闲检测不可用
* 客户端不可达

这些状态具有不同的运维含义。

---

## 43. 更新执行监控

维护期间监控：

* 作业状态
* 客户端连通性
* Agent 活动
* 软件包管理器结果
* 重启需求

不要假设作业无限期保持 `RUNNING` 状态意味着软件包管理器仍在工作。

如果执行似乎卡住，请在创建另一个作业之前调查客户端和 Agent 状态。

---

## 44. 重启需求

某些软件包和系统更新可能需要重启。

LUMS 跟踪受管客户端上报的重启相关状态。

系统更新后：

1. 检查上报的重启状态
2. 确定是否需要重启
3. 在适当的维护窗口执行重启
4. 允许 Agent 再次上报
5. 验证客户端恢复正常运行

重启需求不应自动被解释为更新失败。

---

## 45. 运维更新检查清单

对于日常软件包维护：

```text
[ ] Correct client selected
[ ] Client is reachable
[ ] Current software state reviewed
[ ] Available updates reviewed
[ ] Correct package/action selected
[ ] Maintenance requirements checked
[ ] Update job created
[ ] Job execution monitored
[ ] Job result verified
[ ] Installed software verified
[ ] Available updates rechecked
[ ] Reboot state checked
[ ] Job history reviewed if required
```

只有在生成的客户端状态经过验证后，操作才算完成。

---

## 46. 软件包管理原则

LUMS 提供集中式编排和可见性。

受管操作系统仍负责实际的软件包管理。

因此：

> **LUMS 请求并跟踪操作。原生软件包管理器执行操作。**

这种分离允许 LUMS 管理不同的 Linux 系统，同时保留每个操作系统的软件包管理语义。

## 47. 作业恢复

LUMS 旨在处理中断的更新作业，而不必盲目重复已成功完成的操作。

更新执行使用检查点信息来跟踪进度。

这在以下情况下尤为重要：

* Agent 中断
* 客户端重启
* 服务器重启
* 网络通信暂时不可用
* 软件包操作在结果上报之前已完成

恢复机制使用记录的作业状态来确定仍需执行的工作。

---

## 48. 软件包级检查点

包含多个软件包操作的作业会单独处理。

成功的软件包操作在 Agent 进入下一操作之前被记录。

概念上：

```text
Job
 │
 ├── Package A → SUCCESS
 │
 ├── Package B → SUCCESS
 │
 ├── Package C → interrupted
 │
 └── Package D → PENDING
```

恢复后，已完成的软件包操作不应被不必要地再次执行。

剩余工作可以从记录的状态继续。

这降低了中断后重复软件包操作的风险。

---

## 49. 中断的作业

当更新作业被中断时，不要立即创建替代作业。

首先确定：

1. 哪个作业被中断
2. 哪个软件包操作处于活动状态
3. 哪些软件包操作已成功
4. 软件包管理器是否完成了该操作
5. Agent 是否自动恢复了作业
6. 客户端是否需要重启

在手动干预之前应检查现有作业历史和 Agent 日志。

---

## 50. Agent 恢复

Agent 负责在中断后继续可恢复的工作。

恢复应尽可能保留成功的软件包结果。

如果某个软件包操作已记录为成功，恢复不得盲目再次执行同一操作。

如果恢复无法安全确定操作状态，则应将此情况视为运维问题并进行调查。

不要仅仅为了让作业看起来已完成就手动更改数据库中的作业状态。

---

## 51. 作业期间的服务器重启

LUMS 服务器重启不一定意味着客户端侧软件包操作被中断。

服务器和客户端具有单独的执行状态。

服务器重启后：

1. 验证 LUMS 容器正在运行
2. 验证数据库可用性
3. 验证客户端可以与 LUMS 通信
4. 检查受影响的更新作业
5. 检查 Agent 上报
6. 验证最终软件包状态

客户端侧执行结果仍然是软件包操作的重要事实来源。

---

## 52. 作业期间的客户端重启

客户端重启可能会中断 Agent 执行，或因更新本身需要重启而出现。

这些情况必须加以区分。

### 预期重启

更新已完成，系统需要重启。

### 意外中断

系统在操作完成或结果上报之前重新启动。

客户端返回后：

1. 允许 Agent 正常启动
2. 验证与 LUMS 的通信
3. 检查受影响的作业
4. 验证软件包状态
5. 检查重启状态
6. 在适用时允许恢复继续进行

---

## 53. 重启检测

LUMS 可以跟踪受管客户端上报的重启需求。

重启检测不同于检测机器当前是否可达。

这些是独立状态：

```text
Client reachable
        │
        ├── reboot not required
        │
        └── reboot required

Client unreachable
        │
        └── current state cannot be confirmed
```

因此，管理员应避免将不可达客户端视为需要重启的证明。

---

## 54. 重启后验证

在需要重启之后：

1. 等待操作系统可用
2. 验证 Agent 服务或定时器
3. 验证客户端身份验证
4. 验证客户端上报
5. 检查受影响的更新作业
6. 验证已安装软件包版本
7. 验证可用更新
8. 检查是否需要再次重启

只有在客户端再次成功上报之后，重启才应被视为运维完成。

---

## 55. 更新作业监控

管理员和操作员应在计划维护期间监控作业。

重要的状态包括：

| 状态      | 含义                                     |
| --------- | ---------------------------------------- |
| `PENDING` | 作业存在但执行尚未开始                   |
| `RUNNING` | 作业执行正在进行中                       |
| `SUCCESS` | 执行已成功完成                           |
| `FAILED`  | 执行以错误完成                           |

作业状态应始终结合其结果信息进行解释。

例如，`FAILED` 作业应使用其记录的结果进行调查，而不是简单地重试。

---

## 56. 执行 Watcher

LUMS Agent 包含专用的执行 watcher。

watcher 负责监控客户端上的更新作业执行。

其目的是独立于上报工作流程支持可靠的执行处理。

当前 watcher 版本为：

**Watcher 1.2.1**

Agent 版本为：

**Agent 1.7.0**

客户端升级后应验证这些版本。

---

## 57. Watcher 监控

管理员可以通过受管客户端上的 systemd 检查 watcher。

有用的检查包括：

```bash
systemctl status lums-agent-watcher.service --no-pager
```

以及：

```bash
journalctl -u lums-agent-watcher.service --no-pager -n 100
```

定时器可以使用以下命令检查：

```bash
systemctl status lums-agent-watcher.timer --no-pager
```

一次性服务的实际活动/非活动状态应结合其定时器和日志进行解释。

对于一次性服务，`inactive (dead)` 状态并不自动是错误。

---

## 58. 上报和执行定时器

LUMS 将常规客户端上报与执行监控分开。

上报定时器负责计划的 Agent 执行。

watcher 定时器负责计划的 watcher 执行。

在诊断客户端侧调度问题时检查两者：

```bash
systemctl list-timers --all | grep lums-agent
```

预期单元包括：

```text
lums-agent.timer
lums-agent-watcher.timer
```

如果定时器未运行，请检查：

```bash
systemctl status lums-agent.timer --no-pager
systemctl status lums-agent-watcher.timer --no-pager
```

然后检查相应的日志条目。

## 59. 审计日志

LUMS 在审计日志中记录重要的管理和安全相关应用操作。

审计信息可以帮助建立：

* 发生了什么操作
* 哪个用户发起了操作
* 哪个客户端受到影响
* 操作何时发生
* 操作是否被接受
* 执行了哪个管理操作

审计信息应被视为运维证据。

不应随意删除或修改。

---

## 60. 管理审计事件

相关的管理活动包括如下操作：

* 用户创建
* 角色分配
* 客户端管理
* 令牌轮换
* 更新作业创建
* 软件包管理操作
* 与身份验证相关的安全事件

确切的事件数据取决于操作。

管理员在调查意外活动时应将审计信息与作业历史一起使用。

---

## 61. 审计日志处理

审计日志应谨慎处理。

不要：

* 修改历史审计条目以隐藏操作
* 在导出的日志中暴露敏感凭据
* 发布包含客户端令牌的日志
* 发布密码或身份验证材料
* 将敏感的日志输出复制到公共问题跟踪器

如果必须共享日志以进行故障排查，请先脱敏凭据和其他敏感信息。

## 62. 应用日志

应用日志描述 LUMS 服务器的内部运行。

有用的来源包括：

```bash
sudo docker logs --tail 100 lums
```

对于实时监控：

```bash
sudo docker logs -f lums
```

调查问题时，尽可能缩小时间窗口。

当较小的相关部分足够时，不要自动转储整个生产日志。

## 63. Agent 日志

客户端侧 Agent 活动可以通过 systemd 检查：

```bash
journalctl -u lums-agent.service --no-pager -n 100
```

watcher 活动：

```bash
journalctl -u lums-agent-watcher.service --no-pager -n 100
```

对于特定的时间窗口，可以使用 systemd 日志过滤。

示例：

```bash
journalctl -u lums-agent.service \
    --since "30 minutes ago" \
    --no-pager
```

在可能的情况下，日志应与受影响的作业 ID 相关联。

## 64. 日志关联

在调查更新问题时，跨系统关联信息：

```text id="jv3j7c"
  │

LUMS API / Application Log
```

## 66. 恢复原则

当发生更新问题时，最安全的管理方法是：

```text
Observe
   │
   ▼
Identify affected job/client
   │
   ▼
Inspect state and logs
   │
   ▼
Determine actual failure point
   │
   ▼
Correct underlying problem
   │
   ▼
Allow recovery or retry
   │
   ▼
Verify final state
   │
   ▼
Document significant incidents
```

除非理解了实际失败状态，否则避免破坏性恢复操作。

特别是，不要仅仅为了恢复看起来整洁的界面就手动删除作业、数据库记录、软件包管理器锁或持久化客户端数据。

> **首先保留证据。其次修复状态。第三验证结果。**

## 67. 数据库管理

LUMS 使用 SQLite 作为其应用数据库。

生产数据库存储在持久化 Docker 卷内：

```text
/var/lib/lums/lums.db
```

只要 Docker 卷得以保留，数据库在容器替换期间持久存在。

数据库包含如下应用状态：

* 用户
* 受管客户端
* 更新作业
* 软件包信息
* 审计信息
* 身份验证相关状态
* 迁移状态

管理员应将数据库视为关键应用数据。

---

## 68. SQLite 运行时配置

当前生产 SQLite 基线为：

| 设置          | 值                    |
| ------------- | --------------------- |
| `journal_mode` | `wal`                 |
| `busy_timeout` | `5000`                |
| `synchronous`  | `2`                   |
| `foreign_keys` | 由应用启用            |

应用为数据库连接显式启用 SQLite 外键强制。

管理员不应随意更改这些设置。

数据库运行时配置的更改应在引入生产之前进行测试。

---

## 69. 数据库完整性

当有数据库损坏或意外应用行为的迹象时，应检查数据库完整性。

典型的 SQLite 完整性检查为：

```bash id="f0g8sl"
sudo docker exec lums \
    sqlite3 /var/lib/lums/lums.db \
    "PRAGMA integrity_check;"
```

健康的数据库应返回：

```text
ok
```

如果完整性检查报告错误，请不要盲目地继续修改应用状态。

保留受影响的数据库并调查原因。

---

## 70. 数据库迁移

LUMS 使用应用迁移引入数据库变更。

应允许迁移通过应用的正常启动和迁移机制运行。

管理员不应仅为了绕过错误而手动修改迁移状态。

应用更新后，验证：

1. 容器成功启动
2. 迁移完成
3. 应用可访问
4. 现有用户仍然可用
5. 现有客户端仍然可用
6. 现有作业历史仍然可用

---

## 71. 持久化 Docker 卷

包含 LUMS 应用数据的 Docker 卷是关键持久化资源。

生产卷为：

```text
lums-data
```

使用以下命令检查：

```bash id="f3z2kd"
sudo docker volume inspect lums-data
```

在替换 LUMS 容器时，该卷必须保持挂载。

移除容器**不会**自动移除该卷。

然而，除非存在单独的备份，否则移除卷会永久删除持久化应用数据。

---

## 72. 容器管理

LUMS 应用运行在加固的 Docker 容器内。

生产安全基线包括：

* 非 root 应用用户
* 只读根文件系统
* 丢弃 Linux 能力
* `no-new-privileges`
* 受限临时文件系统
* 只读密钥挂载
* 专用持久化数据卷
* 仅限 localhost 的应用端口

不应仅仅因为故障排查变得更方便就以较弱的安全设置启动容器。

---

## 73. 容器状态

使用以下命令检查当前容器状态：

```bash id="4n6p2v"
sudo docker ps --filter name=lums
```

使用以下命令检查完整的运行时配置：

```bash id="k1q4z8"
sudo docker inspect lums
```

重要属性包括：

* 运行状态
* 重启策略
* 用户
* 只读根文件系统
* 能力
* 安全选项
* 端口绑定
* 卷挂载

---

## 74. 容器安全验证

加固的运行时应继续提供预期的属性。

例如：

```bash id="0u7x3n"
sudo docker inspect lums \
    --format '{{.Config.User}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.Privileged}}'
```

预期基线等同于：

```text
lums true false
```

能力应保持被丢弃：

```bash id="k5n8ae"
sudo docker inspect lums \
    --format '{{json .HostConfig.CapDrop}}'
```

预期：

```text
["ALL"]
```

安全选项应包括：

```text
no-new-privileges:true
```

## 75. 应用端口

LUMS 应用通过回环接口在主机上监听。

预期映射为：

```text
127.0.0.1:5050 → container:5000
```

使用以下命令验证：

```bash id="b6v2w0"
sudo docker port lums
```

应用端口不应直接暴露给局域网。

外部访问通过 Nginx 的 HTTPS 提供。

---

## 76. Nginx 和 HTTPS

Nginx 提供 LUMS 的外部 HTTPS 入口点。

正常的请求路径为：

```text
Client Browser
      │
      ▼
HTTPS :443
      │
      ▼
Nginx
      │
      ▼
127.0.0.1:5050
      │
      ▼
LUMS Container
```

Docker 应用端口应保持绑定到 localhost。

因此，管理员应避免通过防火墙或 Docker 配置直接暴露端口 `5050`。

---

## 77. HTTPS 验证

在更改 Nginx 后，始终在重新加载之前验证配置：

```bash id="7f1h9m"
sudo nginx -t
```

如果配置有效：

```bash id="4g5s2w"
sudo systemctl reload nginx
```

然后验证 HTTPS：

```bash id="2w8v6c"
curl -I https://LUMS-SERVER/
```

将 `LUMS-SERVER` 替换为服务器 TLS 证书所覆盖的主机名。不要使用 `-k` 进行常规验证；它会跳过证书验证。

成功的 HTTPS 响应确认 Nginx 可以访问 LUMS 应用。

还应使用管理员通常使用的主机名或地址测试证书验证。

不要使用 `-k` 永久禁用证书验证。

---

## 78. HTTP 重定向

HTTP 端点应将客户端重定向到 HTTPS。

验证：

```bash id="w5q0rx"
curl -I http://127.0.0.1/
```

预期行为是向 HTTPS 端点的 HTTP 重定向。

管理访问应使用 HTTPS。

---

## 79. TLS 证书维护

TLS 证书和私钥位于 Docker 镜像外部。

典型位置为：

```text
/etc/lums/tls/lums.crt
/etc/lums/tls/lums.key
```

私钥必须保持受保护。

替换证书之前：

1. 验证新证书
2. 验证匹配的私钥
3. 验证文件权限
4. 验证 Nginx 配置
5. 重新加载 Nginx
6. 验证 HTTPS
7. 验证应用登录

绝不要将私有 TLS 密钥放入 Git 仓库或 Docker 镜像中。

## 80. 密钥管理

应用密钥存储在容器镜像之外。

生产密钥以只读方式挂载到容器：

```text
/etc/lums/secrets/lums_secret
        │
        ▼
/run/secrets/lums_secret
```

应用通过以下方式接收密钥：

```text
LUMS_SECRET_KEY_FILE
```

管理员绝不应：

* 提交密钥
* 打印密钥
* 在文档中包含密钥
* 在截图中暴露它
* 将其放入镜像层

如果怀疑密钥已暴露，请将其视为已泄露，并遵循适当的密钥轮换程序。

## 81. 备份策略

在重要的管理变更之前应备份 LUMS 数据。

至少考虑保护：

* SQLite 应用数据
* 应用配置
* TLS 材料
* 应用密钥
* 客户端配置信息
* 相关运维文档

备份应存储在生产容器及其持久化 Docker 卷之外。

仅存在于同一主机或 Docker 卷内的备份无法充分防止该主机或卷丢失。

## 82. 数据库备份

SQLite 数据库应使用 SQLite 感知的方法进行备份，而不是简单地复制正在积极修改的数据库文件而不考虑其状态。

执行备份之前：

1. 确定生产数据库
2. 确保备份目标可用
3. 使用适当的 SQLite 安全方法创建备份
4. 验证备份存在
5. 记录其创建时间

不要假设成功的文件复制自动意味着存在有效的可恢复数据库备份。

在测试之前，备份不被视为可靠。

定期验证备份可以被：

* 读取
* 作为 SQLite 数据打开
* 检查完整性
* 恢复到隔离的测试环境

例如，可以使用以下命令检查提取的测试副本：

```bash id="p3v7cx"
sqlite3 /path/to/test-copy.db \
    "PRAGMA integrity_check;"
```

预期结果：

```text
ok
```

生产备份绝不应通过覆盖活动生产数据库来测试。

## 88. 服务器管理原则

LUMS 将应用状态与可丢弃的应用容器分开。

```text
Disposable
└── LUMS Container

Persistent
├── SQLite Database
└── lums-data Volume

External
├── TLS Material
└── Application Secret
```

这种分离允许替换应用容器而不会有意破坏持久化应用数据。

> **在必要时替换应用。除非明确打算删除数据，否则保留数据。**

## 93. 受控容器替换

容器替换应有意识地进行。

替换生产容器之前：

```text id="m3z8qk"
[ ] Tests passed
[ ] New image exists
[ ] Database backup available
[ ] Active jobs reviewed
[ ] Current image recorded
[ ] Persistent volume confirmed
[ ] Secret available
[ ] TLS configuration available
[ ] Rollback image identified
```

在运行示例之前，请将其与实际运行的容器进行比较。以下值只是一个示例，而不是对每次安装都安全的命令。特别是，`:` 左侧的 Docker 绑定挂载源路径必须与您的主机匹配，旧容器的名称可能不同。

显示镜像、挂载、已发布端口、重启策略和加固设置，而不打印环境变量值：

```bash
sudo docker inspect lums --format 'Image={{.Config.Image}}
Mounts={{json .Mounts}}
Ports={{json .HostConfig.PortBindings}}
Restart={{json .HostConfig.RestartPolicy}}
Readonly={{.HostConfig.ReadonlyRootfs}}
CapDrop={{json .HostConfig.CapDrop}}
SecurityOpt={{json .HostConfig.SecurityOpt}}
Tmpfs={{json .HostConfig.Tmpfs}}'
```

将输出保存在私人位置，并使用它来检查新容器是否保持相同的数据库卷、密钥文件、备份目录、仅本地端口绑定和安全选项。不要将密钥内容或环境变量值粘贴到笔记或消息中。

只有在考虑这些条件后才停止现有容器。

生产容器应保留加固的运行时配置。

示例：

```bash id="n8q2kf"
sudo docker stop lums
sudo docker rename lums lums-before-upgrade
```

然后使用已建立的加固配置启动新镜像：

```bash id="c7w4md"
sudo docker run -d \
    --name lums \
    --restart unless-stopped \
    --read-only \
    --cap-drop=ALL \
    --security-opt=no-new-privileges:true \
    --tmpfs /tmp:rw,noexec,nosuid,size=64m \
    --tmpfs /run:rw,noexec,nosuid,size=16m \
    -p 127.0.0.1:5050:5000 \
    -v /etc/lums/secrets/lums_secret:/run/secrets/lums_secret:ro \
    -v lums-data:/var/lib/lums \
    -v /var/backups/lums:/var/backups/lums \
    -e LUMS_SECRET_KEY_FILE=/run/secrets/lums_secret \
    -e LUMS_BACKUP_DIR=/var/backups/lums \
    lums:new
```

在新部署经过验证之前，不要移除 `lums-before-upgrade`。

## 94. 升级后验证

替换容器后立即验证：

```bash id="b4m7tz"
sudo docker ps --filter name=lums
```

然后检查日志：

```bash id="v5n2ra"
sudo docker logs --tail 100 lums
```

验证 HTTPS：

```bash id="w9x1kf"
curl -I https://LUMS-SERVER/
```

将 `LUMS-SERVER` 替换为服务器 TLS 证书所覆盖的主机名。不要使用 `-k` 进行常规验证；它会跳过证书验证。

然后通过正常管理界面验证应用。

检查现有用户、客户端和近期历史仍然存在。审查日志是否有启动或迁移错误。单独运行的容器并不能证明应用或其数据库健康。

### 如果新容器不工作则回滚

保留旧容器，直到新版本通过验证。如果新容器无法使用并且您已确认旧容器名为 `lums-before-upgrade`，请停止并移除**仅新容器**，然后重命名并启动旧的：

```bash
sudo docker stop lums
sudo docker rm lums
sudo docker rename lums-before-upgrade lums
sudo docker start lums
```

不带 `-v` 的 `docker rm lums` 移除容器，而不是 `lums-data` 卷。绝不要向此回滚命令添加 `-v`。如果容器名称不同，或者您不确定哪个容器是旧的哪个是新的，请不要运行这些命令；先检查当前状态或向管理员寻求帮助。回滚后，检查日志并验证 Web 界面和数据可用。

## 95. 升级后的持久化数据

容器替换不得移除持久化 Docker 卷。

验证：

```bash id="j4p8sx"

    --format '{{json .Mounts}}'
```

确认：

```text id="m7z3kc"
/var/lib/lums
```

由预期的持久化卷支持。

然后验证：

* 角色保持正确
* 客户端保持注册
* 作业历史保持可用
* 审计信息保持可用
* 迁移成功完成

## 96. 升级后的安全基线

部署新镜像后，再次验证加固的运行时。

检查：

```bash id="q6c3xv"
sudo docker inspect lums \
    --format '{{.Config.User}} {{.HostConfig.ReadonlyRootfs}} {{.HostConfig.Privileged}}'
```

预期基线：

```text id="s0r8jm"

```

同时验证：

```text id="g4m2vx"

SecurityOpt = no-new-privileges:true
```

以及：

```text id="c3p9rw"
127.0.0.1:5050 → container:5000
```

仍然是应用的暴露方式。

成功的应用升级不得静默削弱安全基线。

## 99. 回滚

当新镜像导致意外生产问题时，应能够回滚。

保留：

* 先前工作的镜像
* 持久化数据
* 数据库备份
* 先前配置
* 先前 TLS 材料
* 相关日志

如果新容器不可用：

1. 停止新容器
2. 在可行时为调查保留它
3. 停止进一步的管理变更
4. 恢复先前已知良好的镜像
5. 重用现有持久化卷
6. 启动加固运行时
7. 验证应用
8. 验证客户端
9. 验证作业状态
10. 单独调查失败的镜像

不要作为正常回滚的一部分删除持久化卷。

## 101. 应急管理

应急管理应尽可能保留证据和持久化状态。

示例包括：

* 反复的应用崩溃
* 数据库完整性错误
* 广泛的客户端身份验证失败
* 意外的软件包作业行为
* 疑似凭据暴露
* 损坏的升级
* 影响所有用户的 TLS 故障

首选顺序为：

```text id="f8k3wz"
Preserve
   ↓
Observe
   ↓
Isolate
   ↓
Recover
   ↓
Verify
   ↓
Document
```

不要仅仅因为日志、数据库、容器或客户端记录似乎是问题的一部分就删除它们。

## 102. 管理变更原则

每个重要的生产变更都应具有三个清晰定义的状态：

### 变更前

当前生产状态已知且可恢复。

### 变更期间

使用文档化的程序执行变更。

### 变更后

将生成的状态与预期基线进行验证。

这使管理工作可复现并减少意外配置漂移。

---

## 103. 受控卸载

卸载是破坏性管理操作。

仅当有意移除 LUMS 部署时才应执行。

移除 LUMS 之前：

```text id="u5r2nc"
[ ] All managed clients identified
[ ] Active update jobs reviewed
[ ] Required job history exported or preserved
[ ] Required audit information preserved
[ ] Database backup created
[ ] Backup verified
[ ] TLS material preserved if required
[ ] Application secret preserved if required
[ ] Documentation preserved
[ ] Reinstallation requirements documented
```

在确认不再需要之前，不要移除持久化数据。

---

## 104. 移除容器

在部署退役后移除应用容器：

```bash id="n2x7kc"
sudo docker stop lums
sudo docker rm lums
```

Docker 卷被有意**不**通过这些命令移除。

这允许应用数据可供后续检查或恢复使用。

---

## 105. 移除持久化数据

移除 LUMS Docker 卷是单独的破坏性操作。

只有在确认数据库和所有存储的应用状态不再需要后才执行此操作。

示例：

```bash id="r8w3mz"
sudo docker volume rm lums-data
```

这会永久删除存储在该卷中的持久化应用数据。

不要在正常升级或回滚期间执行此命令。

---

## 106. 移除客户端组件

当受管客户端从 LUMS 中永久移除时，根据客户端操作系统程序卸载或禁用其 Agent 组件。

客户端在退役后不应再向 LUMS 服务器上报。

如果需要历史记录，请在移除客户端之前保留相关的作业和审计信息。

## 109. 管理完成

LUMS 管理应始终优先考虑受控、可观察和可逆的变更。

管理生命周期为：

```text id="w6f1pa"
Plan
  ↓
Observe
  ↓
Change
  ↓
Verify
  ↓
Document
  ↓
Maintain
```

最重要的运维原则为：

> **使用所需的最小权限。**

> **保留持久化数据。**

> **在没有理解当前状态的情况下不要更改状态。**

> **验证每个重要操作的结果。**

> **保持经过测试的恢复路径。**

有关安装程序，请参阅 `install.md`。

有关安全架构和审计结果，请参阅 `security.md`。

有关诊断和恢复程序，请参阅 `troubleshooting.md`。

## 110. 最终管理原则

LUMS 旨在使 Linux 更新管理可预测且可观察。

因此，管理工作不应基于假设或盲目重复。

当有变更时：

**先观察。后变更。再验证。**

当出现问题：

**保留证据。确定失败层。谨慎恢复。**

当一切正常：

**记录结果并保持已知良好的基线。**
